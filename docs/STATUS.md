## 1. 되는 것

### 1.1 인게임 오버레이 (완료, 안정)

`xinput1_4.dll` 프록시로 주입하고 D3D12 스왑체인에 ImGui 를 얹는다.
한글이 정상 표시되고(맑은 고딕), Insert 로 켜고 F10 으로 비활성화한다.
비활성화 뒤 다시 켜는 것도 된다.

성능은 실측 63 FPS 유지, 예외 0회, 해체·재초기화 14회 반복 통과.

**주입 경로:** `dinput8.dll` 은 이 게임의 임포트 테이블(92개 DLL)에
없다. `xinput1_4.dll` 이 있고 ordinal 2·3 을 쓴다. 그래서 그것을
프록시한다.

**D3D12 훅에서 반드시 지킬 것 두 가지.** 둘 다 실측으로 배웠다.

1. 커맨드 큐를 `ExecuteCommandLists` 에서 추측하면 안 된다. 실행마다
   다른 큐가 잡혔다(0x8e2ba10 / 0x120a26d0 / 0x52e67800 / 0x8bd0e30).
   NVIDIA Streamline 문서도 이를 금지한다. `CreateSwapChain`(vtbl 10)과
   `CreateSwapChainForHwnd`(vtbl 15)를 후킹해 (큐, 스왑체인) 쌍을
   확정적으로 얻는다.
2. 펜스 동기화 없이는 안 된다. 프레임 컨텍스트마다 fence_value 를 두고,
   `allocator->Reset()` 전에 대기하고 `ExecuteCommandLists` 뒤에
   `Signal` 한다. 리소스 해제 전에는 전부 대기한다. 이걸 빠뜨리면
   런타임이 "drop the call and remove the device" 한다.

이 두 가지를 빠뜨려 0xC0000005 로 죽었고, 원인을 찾는 데 시간이 걸렸다.
당시 변경 두 개를 한 빌드에 묶어 이등분이 불가능했던 것이 화근이었다.

### 1.1.1 입력 격리 · 커서 가드 (완료 2026-09-11~12)

오버레이가 열려 있는 동안 게임에 입력이 새지 않는다(`src/input/`).

- **입력 격리(filter):** raw input 은 장치로 가른다 - 마우스는 늘, 키보드는 글자 입력칸에
  포커스가 있을 때만 게임에 안 준다(오버레이를 켠 채 걷는 것은 된다). `GetAsyncKeyState`
  도 같은 규칙으로 0 을 돌려준다 - 안 그러면 검색창에 타자를 치는 동안 캐릭터가 움직인다.
- **커서 가드(cursor):** 열려 있는 동안 게임의 `SetCursorPos`·`ClipCursor` 를 막는다
  (프레임당 500회 예산, 넘으면 통과시키고 한 번 경고). `ShowCursor` 는 후킹하지 않는다 -
  게임의 `while (ShowCursor(TRUE) < 0);` 가 끝나지 않아 멎는다. 열 때 가두기를 풀고 카운터를
  0 으로, 닫을 때는 **기억한 값에 그 사이 게임이 바꾼 만큼을 얹어**(상대 복원) 되돌리고
  가두기는 **게임의 마지막 요청**을 프레임 번호로 판정해 이번·직전 프레임 것만 다시 건다
  (`cursor_clip_restore`). 열기 전 상태를 되돌리면 그 사이 인벤을 연 경우 마우스룩 중앙
  가두기가 되살아나 인벤에서 커서가 굳는다(사용자 보고 2026-09-12, 해결). 창 안의 포인터는
  ImGui 소프트 커서라(`MouseDrawCursor`, wndproc 이 OS 커서를 끈다) OS 카운터로는 안 보인다.
- **숨김 동안 입력 차단(2026-09-16):** 오버레이가 꺼져 있으면 입력 메시지를 ImGui 백엔드에
  **안 넘긴다**(`backend_should_see`). 넘기면 이벤트 큐에 쌓이기만 하고 - 비우는 것은
  `NewFrame` 뿐인데 숨김 상태에서는 안 돈다 - 켤 때 그 밀린 것이 **재생돼** 켜기 전의
  손놀림과 클릭이 되풀이됐다(굳음·떨림·의도치 않은 동작이 **동시에**, 전투에서 최악).
  창 크기·포커스·DPI 는 늘 넘긴다. 전문: `TROUBLESHOOTING.md` 2.14.
- **좌표는 백엔드가 넣은 프레임에는 안 넣는다(2026-09-16):** 한 프레임에 좌표 원천이 둘이면
  최종값을 큐 도착 순서가 정한다. 실측으로 두 값이 자주 어긋나(최대 180px) 겹쳐 넣지 않는다.
  백엔드가 조용한 프레임에는 그대로 넣는다 - 실측 113·122 프레임이 그 경우였다.
- **마우스 채우기(mouse):** 백엔드(imgui_impl_win32)는 WM_MOUSEMOVE 를 한 번이라도 받아
  추적 중이면 GetCursorPos 대체 경로를 끄는데, 게임 마우스룩은 커서가 창 안에서 움직여도
  창에 WM_MOUSEMOVE 를 안 준다 - 그 상태로 열면 소프트 커서가 그 자리에 굳는다(사용자 보고
  2026-09-12, 진단 로그로 확정, 해결). 렌더 스레드가 프레임마다(백엔드 NewFrame 뒤)
  포그라운드면 `GetCursorPos` 를 ImGui 좌표로 직접 넣고, 창 메시지가 끊긴 것이 실측되면
  펌프 스레드가 WM_INPUT 에서 모아 둔 버튼·휠을 넣는다(`decode_raw_mouse`). 끊김의 증거는
  둘 - 300ms 이상 이어서 움직이는데 창 메시지 없음(`legacy_gate_step`), 또는 raw 버튼·휠이
  50ms 넘게 창 메시지로 답을 못 받음(`raw_answered`, 움직임 없이 누른 첫 클릭을 잃지 않게).
  창 메시지가 살아 있으면 답 받은 raw 는 버린다(휠 중복 방지). 합성으로 내린 버튼의 raw 뗌은
  살아 있어도 넣어 짝을 맞추고 닫을 때 남은 것은 떼어 주며, 다른 창이 앞에 있으면 판정도
  입력도 쉰다(리뷰 M-1~M-3·R-1). 게임이 마우스룩에서 왜 창 메시지를 안 주는지(펌프 필터인지
  NOLEGACY 재등록인지)는 닫을 때의 `raw 등록 flags` 로 다음 실행에서 가린다.
- **진단:** 열고 닫을 때 로그에 한 줄씩(`커서 가드 열기: 카운터 -1 → 0`, `커서 가드 닫기:
  카운터 … 가두기 다시 걺/풂 … 막음 SetCursorPos N ClipCursor M …`), 닫을 때 `마우스 진단:
  창 메시지 이동 N 버튼 N 휠 N, raw 마우스 N …, 판정 끊김/끊김 판정 없음 …, raw 등록 flags`
  한 줄, 끊김이 처음 판정되면 `마우스: 창 마우스 메시지가 끊겼다(이유; 기준 …)` 한 줄. 훅은
  끄기만 하고 트램폴린·원본 포인터는 프로세스가 사는 동안 남긴다(디투어에 멈춰 있던 스레드가
  깨어나도 안전).

### 1.2 RTTI 객체 탐색 (완료, 신뢰 가능)

MSVC x64 RTTI 를 따라 클래스 이름에서 살아있는 인스턴스까지 내려간다.
사람이 값을 바꿔 줄 필요가 없는 결정론적 탐색이라, 모드가 실행될 때마다
스스로 객체를 찾는다.

게임에는 RTTI 클래스 **14,901개**, 그중 `pa` 네임스페이스가 **5,025개**
있다. (초기에 468개로 잘못 셌다. 정규식이 네임스페이스·템플릿이 붙은
이름을 제외해 Havok 것만 남았던 것이다.)

**힙 스캔은 vtable 마다 한 번이다.** `instances_of_class` 는 그 클래스의 vtable 수만큼
힙 전체를 읽는다(카메라 탐색의 네 클래스가 vtable 7개라 월드 안에서 122초, 실측
2026-09-12). 여러 클래스를 한 번에 찾을 때는 `find_objects_of(이름들, 상한)` 으로
힙을 한 번만 훑는다 - 카메라 탐색이 그렇게 바뀌었고(같은 카메라 집합, probe `camera`
로 확인), 분석 통과는 `prefetch_instances(이름들, 클래스별 상한)` 로 단계들의 클래스를
통과 시작에 한 번 모아 둔다(단계들은 캐시 스냅숏에서, 통과 끝에 비움; 상한에 닿은
클래스는 그 단계가 다시 걷는다). 가짜 RTTI 이미지 위의 시험 9개가 그 계약(합집합
동일·전체 상한·주소 오름차순·스냅숏·클래스별 상한과 폴백)을 지킨다. 스캔은 영역 하나를 통째로 읽다 실패하면 그 영역을 건너뛰어 매번
완전하지 않다(장비 캐시가 그래서 검증 유지, §1.12).

카메라 객체 지도를 이것만으로 특정했다:

| 클래스 | 역할 |
|---|---|
| `pa::CameraManager` | 카메라 보유 |
| `pa::FreeCamCamera` | 개발자 프리카메라. **할당돼 있으나 비활성** |
| `pa::PhotoCamera` | 포토 카메라 |
| `pa::PlayerCameraComponent` | 플레이어 카메라 컴포넌트 |
| `pa::PlayerCameraComponentScript` | 스크립트 계층 |

**후보를 고를 때 가장 작은 주소를 쓰면 안 된다.** vtable 값을 우연히
담은 메모리가 가짜 후보로 잡히고, 그게 진짜보다 낮은 주소면 그것을
집는다. 실측에서 11회 연속 어긋났다. 카메라는 `+0x48` 에 자기 이름을
들고 있으므로(SSO, `+0x18` 에 인라인) 그것으로 검증한다.

### 1.3 함수 후킹 (완료, 실증)

MinHook 으로 게임 함수를 후킹했다. 대상은 바이트 패턴으로 찾는다 —
RVA 를 박으면 게임이 갱신될 때마다 깨진다.

카메라 좌표 갱신 함수 `0x140A58540` 에 걸어 **108,000회 호출 동안
안정**했다. Denuvo 무결성 검사에 걸리지 않았다.

**패턴 찾기 절차:** 저장 명령 22바이트로 위치를 잡고(실행 섹션 전체에서
한 곳만 일치하는 것을 확인), 거기서 `CC CC CC` 패딩까지 거슬러 함수
시작을 구한 뒤 프롤로그(`48 8B C4`)로 검증한다.

**인자 규약은 디스어셈블로 확인한다.** 이 함수는 RDX/R8/R9 를 읽기
전에 전부 덮어쓰고 XMM1 만 읽으므로 `void __fastcall f(컴포넌트*, float)`
가 정확하다. 추측하지 않았다.

`MH_CreateHook` 이 코드 9(트램폴린 메모리 할당 실패)로 3회 실패한 뒤
4회째에 성공한 적이 있다. 재시도 로직이 필요하다.

### 1.4 외부 분석 도구 `cdtb_probe` (완료)

게임에 붙어 메모리를 읽는 명령줄 도구. **인게임 UI 가 아니라 명령줄인
이유는 이 작업의 조작자가 사람이 아니라 에이전트이기 때문이다.**
반복 실행할 수 있어야 값을 찾는 일을 자율적으로 한다.

| 명령 | 용도 |
|---|---|
| `info` `regions` | 프로세스·메모리 요약 |
| `types` `vtable` `instances` `objects` `whatis` | RTTI 탐색 |
| `dump` `floats` | 메모리 덤프 |
| `diff` | 시간차로 변하는 float 슬롯 |
| `setf` | float 쓰기 |
| `camera` | 모드와 **같은 탐색 코드**를 돌린다 (배포 전 검증용) |
| `findvec3` / `findvec3d` | 좌표와 일치하는 float3 / double3 |
| `findmat` | 좌표 근처의 정규직교 4x4 |
| `findquat` | 시점을 돌리는 동안 변하는 단위 쿼터니언 |
| `hold` / `holdmany` | 값을 눌러 써서 화면 반응을 본다 |
| `dumpimage` | 실행 중 프로세스의 이미지를 PE 로 뜬다 |
| `loc` | 현지화 표를 읽어 이름을 푼다 (1.6) |
| `items` | 아이템 표를 키+이름으로 나열·검색 (1.7). 모드와 **같은 목록 함수**를 돌린다 |

`camera` 가 모드와 같은 코드를 돌리는 것이 중요하다. 배포하기 전에
탐색 결과를 확인할 수 있다.

### 1.5 하드웨어 브레이크포인트 (구현 완료, 이 게임에는 부적합)

디버그 레지스터 4개(DR0~DR3)를 동시에 걸어 "누가 이 주소에 쓰는가"를
찾는다. 자체 테스트 8종 통과.

**이 게임에서는 쓸 수 없다.** 보호 코드가 250ms 마다 121개 스레드 중
약 47개의 디버그 레지스터를 지운다(한 창에서 2,274회 다시 걸었다).
어떤 값은 잡히고 어떤 값은 영원히 히트 0으로 보여 결과를 신뢰할 수
없다. 자동 분석 경로에서는 뺐고 클래스와 테스트는 남겼다 — 보호가
없는 대상에는 여전히 유효하다.

**자체 테스트가 링크 배치에 민감하다 (미해결).** 2026-09-01, 무관한
소스 파일을 테스트 대상에 더했더니 `watchpoint_shutdown_is_idempotent`
가 `0xC0000005` 로 죽었다 — 4회 연속 재현. 그 파일을 빼면 통과하고,
전체 재링크로 배치가 바뀌자 다시 통과했다(6회 연속). 즉 코드 논리가
아니라 `g_target` 이 어디 놓이느냐에 달려 있다.

`on_exception` 의 주석이 이 실패 모양을 이미 적어 두었다 — 처리되지
않은 단일 스텝 예외로 프로세스가 죽는 경우. `shutdown()` 이 핸들러를
떼는 것과 낙오 스레드의 예외가 겹치는 창이 의심된다. **지금은 나타나지
않을 뿐 고쳐진 것이 아니다.** 워치포인트를 다시 쓸 일이 생기면 여기서
시작할 것.

### 1.6 현지화 조회 (완료, 실측)

게임의 현지화 표를 **읽기만으로** 걸어 이름을 푼다. 게임의 조회 함수는
부르지 않는다 — 그 함수는 잠금을 잡고 못 찾은 키의 항목을 표에 끼워
넣는다.

```
$ cdtb_probe loc item 2200
  필드 0x70  키 9448928051312 :  [카테고리 7] '편전'
  필드 0x71  ...              :  '일반 화살보다 짧고 날렵한 형태로 ...'
```

키는 `(엔티티키 << 32) | 필드번호` 이고 0x70 이 이름, 0x71 이 설명이다.
문자열 풀은 11.9 MB 한 덩어리이고 이름은 `풀기준 + 오프셋` 이다.

전역 주소는 박지 않는다. `LocalizationStringBase::str()` 본문 28바이트가
이미지 전체에서 한 곳만 일치하고, 그 disp32 가 곧 전역이다.

자세한 것은 `specs/2026-09-01-localization-lookup.md`.

### 1.7 아이템 표 (완료, 실측)

`pa::ItemInfoManager` 를 RTTI 로 찾아 레코드 포인터 배열을 걷는다.
**6,810개 중 6,738개(98.9%)의 이름이 풀린다.**

```
$ cdtb_probe items find 비약
  1000028   프레야의 하급 비약
  1000030   아프로니아의 하급 비약
  1000034   멜리아라의 하급 비약
```

이름 키는 조립하지 않는다. 레코드 `+0x28` 이 게임 자신의 64비트
현지화 키를 들고 있다.

후보를 그대로 믿지 않는다 — 색인 표의 첫 키와 첫 레코드의 키가 같은지
보고, 개수가 터무니없으면(0 이거나 2^20 초과) 거부한다.

**argv 는 시스템 ANSI 코드페이지로 온다**(이 기계 ACP 949). 게임
문자열은 UTF-8 이라 그대로 비교하면 한글이 절대 맞지 않는다. probe 의
검색은 비교 전에 UTF-8 로 옮긴다. 오버레이는 ImGui 입력도 UTF-8 이라
변환이 필요 없다.

### 1.8 인게임 아이템 목록 (완료, 화면 확인)

오버레이에 "아이템 목록" 패널. 검색창 + 목록, 줄을 누르면 키가 **지급 칸과
클립보드로** 간다(지급은 6). 머리글을 누르면 정렬한다.

화면에서 확인했다. 한글 정상, **70.0 FPS**, 경고·오류 0건.

```
[12:01:18.992] INFO  아이템 표: 6810개, 이름 풀린 것 6738개
```

프레임마다 게임 메모리를 읽지 않는다. 배경 분석 루프가 만들어 둔
목록을 걸러 보여주기만 하고, 6,810줄 중 보이는 줄만 그린다
(`ImGuiListClipper`).

**배경 루프에 얹었다.** 그 루프가 이미 350MB 이미지를 읽고 힙을
훑고 있어, 두 번 할 이유가 없다.

**모드는 자기 프로세스를 읽는다.** 잘못된 포인터 하나가 게임을
죽이는데, 읽기는 전부 `mem::Reader` 를 거치고 `LocalReader::read` 는
`safe_read_bytes`(SEH) 라 크래시 대신 false 다.

자세한 것은 `specs/2026-09-01-item-table.md`.

### 1.9 탈것·캐릭터 카탈로그 뷰어 (완료, 화면 확인 2026-09-04)

`VehicleInfoManager`·`CharacterInfoManager` 를 아이템과 같은
`StaticInfoManager2` 컨테이너로 읽어 오버레이 "탈것·용병·캐릭터" 창에
낸다. 화면 확인했다 - 탈것 34개(Dragon·Wolf·Wyvern…), 캐릭터
7251개(Kliff=1·Damian=4…)가 키·**내부 이름**과 함께 뜬다. FPS 62.5,
예외 0.

레코드 구조가 아이템과 다르다: 키가 u16(record +0x00), 내부 이름은
`_stringKey`(+0x08)가 가리키는 엔진 문자열 객체(+0x00 char*, +0x08
길이)의 **내부 이름**이다(한글 표시명 아님 - 현지화 경로가 달라
Tier 1b).

**한글 표시명은 레코드 `+0x00` 의 u32 전체**를 현지화 엔티티 키로 써서
푼다(2026-09-09 정정). 예전에는 이 자리를 u16 으로 잘라 쓰고 빗나가면
내부 이름 끝자리 숫자로 다시 찾았는데, 그 폴백이 엉뚱한 이름을 붙였다
(새끼 와이번 -> "클리프"). 진짜 키는 `_characterName`(+0x18) 객체의
`+0x14` 가 들고 있고 그 값이 레코드 `+0x00` 과 같다.

**용병(MercenaryInfo) 표도 읽는다**(2026-09-09~10). 이 표만 `+0x00` 이
포인터라 키로 못 쓰고 **행 번호가 키 노릇**을 한다. 매니저 검증(색인 첫
키 == 첫 레코드 키)도 통과 못 해 느슨한 판정을 쓴다(개수가 작고 첫
레코드 `+0x08` 문자열이 읽히면 통과). 21행에서 `_mercenaryType`(+0x20:
1 본대 · 2 탈것 · 3 마차 · 4 펫 · 5 가축 · 6~12 사람 용병)과
`_isPlayable`(+0x22)까지 낸다. 캐릭터 표 `+0xBE`(`_mercenaryInfo`)가
이 행 번호를 가리키고, 그 값이 있어야 동반자다.

자세한 것은 `specs/2026-09-04-vehicle-pet-review.md`. probe 검증:
`probe roster`.

### 1.10 동반자 종 교체 (완료, 전 과정 화면 확인 2026-09-10)

**원하는 탈것·특수 탑승물·반려동물을 얻는 문제는 풀렸다.** 부적 6종도,
포획도, 금지된 소환 치트(2988)도 필요 없다. **이미 가진 동반자 하나의
종만 바꿔 쓴다** — 명부 레코드 `+0x20`(캐릭터 표 행 번호) 제자리 쓰기.
UI·소환·탑승·저장까지 전부 따라온다.

야생에서 근처 획득(2338)한 개체도 된다. 반려동물(타입행 9) ->
특수 탑승물(타입행 5) 교차 교체도 된다. 검증: 혹멧돼지->사자,
까마귀->`Riding_Wolf_1001`, 앵무새->`Riding_Wyvern_1000`,
까마귀->`Animal_Tiger_Wild_1`(호랑이). 전부 소환·탑승·리로드 생존.

**소환 널 가드가 함께 있어야 한다**(`src/game/spawnguard.cpp`).
종을 제자리에서 바꾸면 게임의 종류별 색인(`0x208FC30`)이 안 따라와
`0x2AD51F8` 의 레코드 조회가 널을 내는데 **호출자에 검사가 없다**.
게임 자신이 같은 조회를 쓰는 다른 두 자리(`0x2ABD8F0`·`0x2AD5322`)
에서는 널이면 전역 빈 레코드(`0x6BB3F70`)로 대신한다 — 그 처리를
빠진 자리 하나에 넣은 것뿐이고, 조회 함수 자체는 안 건드린다.
(이 문단의 주소는 2760 기준. 2850 값은 `src/game/spawnguard.cpp` 와
`specs/2026-09-11-game-update-2850.md`.)

쓰기는 반드시 오버레이 `[바꾸기]` 나 `probe setspecies` 로 한다.
명부 주소는 휘발성이라 생 `poke` 는 게임을 팅긴다.

전체 기록은 `specs/2026-09-10-companion-species-swap-session.md`.

### 1.10.1 명부 컴포넌트를 스캔 없이 찾기 (해결 2026-09-12)

실마리 2 가 맞았다. 런타임 명부는 `[[세션 + 0x68] + 0x110]` 에 살고, 세션은
세션 표(`pick_drive_session` 이 쓰는 것)에서 온다. `game::clan_object(reader, 0, &c)` 가
세션 전부를 같은 사슬로 훑어 읽기 두 번에 잡고, 레코드 머리 검사 + RTTI 클래스 이름이
서버 클래스(`MercenaryClanActorComponent`)인지까지 본다(클라 쪽 컴포넌트도 머리가 같다 -
클라를 잡으면 종 바꾸기·소환 판정이 서버에 안 닿는다). 실측 2026-09-12 07:56: 세션이
잡힌 직후 `동반자 명부: 세션 사슬로 잡았다` - **10.7초 스캔이 사라졌다.**

RTTI 인스턴스 스캔은 폴백으로만 남는다: 월드 안(세션이 잡힌 뒤)인데 사슬이 비었을 때
30초에 한 번, 분석 루프의 상시 바퀴에서. 캐시가 상하면(동반자를 얻어 컴포넌트가 새로
만들어짐) 배경 워커가 자기 리더(`LocalReader`)로 다시 찾고, `g_rtti` 는 워커가 먼저
찾은 경우에도 채운다(비면 종 바꾸기·획득 뒤처리·캐시 복구가 전부 막힌다). 내 동반자
탭의 `다시 찾기` 버튼은 값싼 길을 먼저 시도하고 없으면 배경 재탐색을 부탁한다.

남은 것: 세션 표의 첫 사슬이 클라 쪽이면 값싼 길이 통과하지 못해 30초 스캔으로
떨어진다 - 세션 전부를 돌며 서버 클래스인 것을 고르면 완결(리뷰 O2, 후속 후보).
사고 기록: 첫 수정(대기 루프)은 상시 루프를 굶겨 인벤·장비·치트까지 멈추게 할 뻔했다 -
리뷰가 잡아 배포 전에 세션 사슬 우선 + 상시 루프 재시도로 바꿨다(`.superpowers/sdd/
2026-09-11-uiux-p3/clan-discovery-review*.md`).

### 1.11 크래시·멈춤 진단 (완료 2026-09-09)

`bin64/CDToybox.crash.txt` 에 죽은 자리를 **모듈 RVA** 로 남긴다.
예외 코드·RIP·접근 주소·레지스터·스택의 복귀 주소 후보. 예외 없이
멈추는 교착은 감시 스레드가 잡아 **모든 스레드의 스택**을 뜬다.

**CRT 를 한 줄도 쓰지 않는다**(`CreateFileW`/`WriteFile` 뿐). 힙이
깨진 채 죽을 때 `std::format`·`ofstream` 은 힙 락에서 멈춰, 게임이
죽는 대신 굳어 강제 종료해야 한다. 스레드를 세운 채로 파일을 쓰지도
않는다 — 다 뜬 뒤 되살리고 그다음에 쓴다.

예외는 처리하지 않고 흘려보내므로 게임의 원래 동작은 그대로다.
`CDToybox.log` 는 실행마다 `.prev`·`.prev2` 로 밀어 죽은 판의 기록을
남긴다. **게임이 팅기면 이 파일부터 본다.**

### 1.12 장비 소켓·담금질·연마·염색 에디터 (완료, 화면 확인; 담금질·연마·캐릭터 선택 2026-09-12 추가, 같은 날 사용자 확인)

오버레이 "장비 소켓·연마" 창. **착용 중인 장비**를 인벤토리 컨테이너
핸들도 NPC 도 없이 고친다.

**담금질과 연마는 다른 필드다.** 착용 항목 `+0x0A` 는 인벤토리 레코드와 같은 자리인
**담금질**(툴팁 게이지 10칸, 상한 `max_temper`)이고, **장비 연마**는 `+0x58`(툴팁 "장비
연마 N/100", 상한 `max_sharpness`)이다. 이식 원본(Trinity)이 `+0x0A` 를 "refinement" 라
불러 창이 오래 "연마" 로 표시했다 - 실측 2026-09-12: 창에서 10 을 쓴 장비가 전부 `+0x0A`
= 10 이고 `+0x58` 은 한 개만 50 이었다. 지금은 두 칸을 따로 보이고 따로 쓴다(상한은
아이템 표에서, 0 이면 "-"; 일괄 버튼 "전부 담금질 최대"·"전부 연마 최대").

**캐릭터 선택.** 클리프·웅카·데미안은 번갈아 조종하는데 아래의 "정신력 풀 + 착용 조각
최다" 규칙은 늘 클리프를 골라, 웅카로 플레이해도 클리프 장비만 보였다(사용자 보고
2026-09-12). 장비 컴포넌트마다 캐릭터 행을 `actor_character_row(comp+0x08)` 로 푼다
(실측: 조각 21/16/11 → 행 0 클리프 / 5 웅카 / 3 데미안). 정신력 풀은 동행에도 있어(7조각짜리
동반자 행 5654 실측) 후보는 플레이어블(주인공 행 0 또는 Mercenary_Main)만 남긴다. 창의
콤보로 고른 캐릭터의 테이블을 쓰고, 월드에 없으면 자동으로 돌아간다(선택을 바꾼 직후
발견이 소화할 때까지는 "갱신 중"). 후보 목록은 창이 열려 있는 동안 20초마다·"다시 읽기"
때 다시 훑는다. 힙 스캔은 매번 완전하지 않아(영역 읽기 실패 시 통째로 건너뜀, 실측 26/29개)
한 번 찾은 테이블은 같은 자리에서 다시 검증되면 캐시에 남긴다 - 그래야 후보가 사라졌다
나타났다 하지 않고 both-realms 쓰기가 양쪽을 찾는다. 후보·표시 캐릭터가 바뀌면 `장비 캐릭터
후보 N개: …` 한 줄을 남기고, probe `equipchars [행]` 이 같은 계산을 밖에서 보여 준다.
사용자 확인 2026-09-12: 웅카 선택 → 웅카 장비 표시, 담금질·연마 재장착 뒤 툴팁 반영. 선택은 `cdtoybox_ui.ini` 의 `equip_character_row`(-1 = 자동)에 남는다.
플레이어 치트(1.13)의 표시용 앵커와 낙사 root 계산도 이 선택을 따른다. 조종 중인
캐릭터를 **자동으로** 따라가는 것은 세션 전역 사슬이 2850 에서 끊겨 아직 없다(§1.15) -
그동안 주인공 판정은 `roster.h kProtagonistRow`(행 0) 폴백이다.

플레이어를 찾는 길은 힙 스캔이다. `EquipSlotActorComponent` 를 RTTI 로
전부 찾고(서버·클라 합쳐 128개 넘게 나온다 - 상한 512), 컴포넌트마다
착용 배열을 유도하되 **서로 다른 슬롯 태그 수**로 점수를 매긴다(진짜
착용은 슬롯마다 하나; 조각 수 최다는 보관 배열에 밀려 불안정했다).
그중 플레이어는 정신력 풀 + 착용 조각 최다로 고르고, 동률이면 앞서 고른
것을 유지한다(매 주기 목록이 튀지 않게). 헤더에 적혀 있던 `cplayer` 포인터
경로(MGRCHAIN AOB)는 한 번도 안 타서 2026-09-10 에 지웠다.

되는 것: 칸마다 보석 박기·비우기, **잠긴 칸 열기**, 담금질·연마 값 바꾸기,
`전부 담금질 최대` · `전부 연마 최대` · `전부 소켓 5칸` 일괄, zone 별 염색(ColorEdit).

**쓰기는 both-realms 다.** 착용 장비는 클라·서버 두 사본이 있어 한쪽만
쓰면 되돌아간다. 쓴 뒤 read-back 으로 확인하고, **화면에 반영되려면
재장착(RE-EQUIP)** 해야 한다. 인벤토리 레코드에는 이 문제가 없다(6 참고).

읽기는 분석 스레드가 캐시한다(`equip_snapshot`) - 프레임마다 읽지
않는다. 출처는 XeTrinityz/Trinity (MIT) 를 다시 이식한 것이고 근거는
`specs/2026-09-05-equip-editor-port.md`.

### 1.13 플레이어 치트 · 낙사 방지 (치트 게임 검증 2026-09-05)

오버레이 "플레이어 치트" 창. 무적(Godmode) · 무한 스태미나 · 무한
정신력. 스탯 게이지 배열을 잡아 현재값을 최대값으로 눌러 둔다(freeze).

체인은 `char(장비 comp+0x08) +0x68 액터 +0x20 marker +0x18 root +0x58`
이 게이지 배열이고, 항목 k 는 `배열 + k*0x90` 에 `+0x00 타입 ·
+0x08 현재 · +0x18 최대` 다. 게이트는 `entry[0].type == 0`(Health).

**힙 스캔을 하지 않는다.** 장비 에디터(1.12)가 이미 고른 플레이어
컴포넌트에서 값싸게 유도하고, 한 번 잡으면 고정한다(스티키). 체인이
한 번 어긋나도 흔들리지 않는다. 단 장비 창의 캐릭터 선택이 바뀌면 앵커(표시용 주
배열·낙사 root 계산)는 그 캐릭터로 옮겨간다(2026-09-12) - freeze 자체는 원래 플레이어형
전원(동행 포함)의 클라·서버 게이지 배열에 걸린다.

**플레이어 식별의 핵심은 정신력 풀이다.** 게이지 배열이 Health 게이트를
통과하고 정신력(타입 21/23, max>0)을 가지면 플레이어다 - 적·NPC 는
정신력 풀이 없다. 이 판정이 장비 목록이 주변 NPC 로 흔들리던 것까지
같이 고쳤다.

**위험 타입은 핀하지 않는다** - 17/18(발열·자연발화), 48(탈것 화염).

**낙사는 무적으로 안 막힌다 - 별개 기능이다**(`nofall.{h,cpp}`,
`nofall_cave.{h,cpp}`). **2026-09-12 재설계**: 빌드 2.01.00 이 옛 사이트(낙하
누적값 쓰기)를 지웠다 - 옛 AOB 도 그 결합부도 2850 이미지 전량에서 0곳이고
돌아오지 않는다(참고 모드도 같은 결론). 그래서 누적기가 아니라 **데미지/
스테이터스 디스패처의 진입점**(RVA 0x01719850, 이미지에서 유일 1곳, 호출자
39곳)을 훅한다. 진입 인자를 그대로 읽어 판정한다:

```
델타(r9) < 0  &&  statusId(dx) == 0(Health)  &&  rcx == 내 root
        &&  sourceCtx([rsp+0x28]) == 내 char        ->  r9 = 0
```

**"출처가 나 자신" 이 낙하의 표식이다(2026-09-13 게임 검증).** 이 게임은 낙하·환경
피해의 `sourceCtx` 에 **때린 쪽이 아니라 맞은 쪽 자신의 캐릭터 객체**를 적는다.
적의 타격은 그 적의 char 가 들어오므로 둘이 자연히 갈린다.

> **CT v5.0 의 `sourceCtx+0x68`(가해자 슬롯) 판별은 이 빌드에서 쓰면 안 된다.**
> `+0x68` 은 가해자가 아니라 **char -> actor 링크**라 낙하에서도 늘 채워져 있다
> (실측: 그 객체의 vtable 이 0 이라 액터도 아니다). 그 판별로는 낙하가 100%
> 통과한다 - 취소함 0 / 통과시킴만 오르는 모습으로 나타난다.

내 root = `[[[char+0x68]+0x20]+0x18]` - 게이지 체인과 같은 자리다.
**관찰 학습이 사라져 첫 낙하부터 막는다.** 캐릭터 교체·지역 이동으로 root 가
바뀌므로 캐시하지 않고 **렌더 틱(~16ms)에서 매번 다시 계산**한다 - 분석 통과
한 바퀴는 수십 초라 낡은 root 가 남는 창이 너무 길다(낡은 root 를 물려받은
다른 개체의 피해까지 지울 수 있다). 하나도 못 구하면 0 을 써서 보호를 끈다.

**root 는 두 칸이다(both-realms).** 같은 캐릭터가 클라·서버 두 realm 으로 존재하고
디스패처가 `rcx` 로 넘기는 것은 **서버 root** 인데, `player_char()` 는 장비 창의
캐릭터 선택을 따라가므로 어느 realm 이 잡힐지 보장되지 않는다. 한 칸만 봤을 때
**훅이 설치되고 root 도 채워졌는데 카운터가 끝까지 0** 인 실행이 나왔다
(2026-09-12 실측). `player_roots()` 가 캐릭터 행으로 짝지어 두 realm 을 모두 모으고,
케이브가 `cmp rcx,[rax]` / `cmp rcx,[rax+8]` 로 둘 다 맞춘다 - 옛 한 칸 비교
(`mov rax,[rax]` + `test` + `cmp`)보다 **2바이트 짧다**(126 → 124바이트).

**전 과정이 라이브에서 확정됐다.** 케이브가 기록까지 하므로(아래 vars 배치) 밖에서
`probe dump <vars> 104` 로 그대로 읽을 수 있다. 2026-09-12~13 실측:

| 잰 것 | 값 |
| --- | --- |
| 피해 이벤트(r9 < 0) | 120건 - **이 함수가 피해 경로가 맞다**(플레이어 6, 나머지는 주변 몹) |
| 플레이어의 Health 피해 | `rcx` = 서버 root, **`dx` = 0**, 델타 **-337,500** |
| 같은 시각 생명 변화 | 1,500,000 → 1,165,500 (**-334,500**) → 델타와 일치 |
| 플레이어의 다른 수치 | `dx` 13(델타 -5e8/-9e8), `dx` 23(-5,000) - 생명이 아니다 |
| 낙하 피해의 출처 | `sourceCtx` = **내 char**(`equip diag` 의 row 0 char 와 일치), vtable = `pa::ServerChildOnlyInGameActor` |
| `[sourceCtx+0x68]` | 내 actor(vtable 0) - **가해자가 아니다** |
| **최종 검증(2026-09-13)** | 규칙 "출처가 나 자신" 으로 2회 낙하 → **취소함 2 / 통과시킴 0**, 취소된 델타 -498,000 / -535,500, 생명 **1,500,000/1,500,000 그대로**(사용자 확인 "안 깎임") |
| 주변 몹 | `dx` 33/54/55 - `rcx` 가 우리 root 와 다르다 |

즉 **`statusId 0` = Health 가 맞다.** 다만 이 id 공간은 게이지 엔트리의 `type`
(0 생명 / 22 스태미나 / 21·23 정신력)과 **같은 공간이 아니다** - 디스패처는
`cmp bx, [rcx+0xa0]` 로 TLS/전역 디스크립터의 id 와 비교한다(상수 0 이 아니다).
**판별 규칙은 화면에서 바꿀 수 있다**(`vars[kNofallRule]`, 패널 콤보). 후보를
게임을 껐다 켜지 않고 갈아 보려고 둔 장치이고, 그 덕에 하루 안에 판별식을 찾았다:
0 출처가 나 자신(기본·검증됨) / 1 가해자 없음(CT 원안, **이 빌드에선 안 먹음**) /
2 출처 없음 / 3 무조건(시험용, 사실상 생명 무적). 규칙 3 으로 낙하가 막힌 것이
"r9 를 0 으로 만드는 방식 자체는 통한다" 는 증명이었고, 그 뒤 판별식만 좁히면 됐다.

**막는 것은 "낙하" 가 아니라 "가해자가 없는 Health 피해" 다.** 낙하가 대표적인
경우일 뿐, 출처 없는 환경 피해(익사·지형·지속 피해)도 함께 취소된다. 화면 문구도
그렇게 적는다 - "낙하만 막는다" 고 적으면 사용자가 모르는 사이 부분 갓모드가 된다.

가해자 판정(`sourceCtx+0x68`)은 **정적으로 못 박는다** - 틀리면 조용한
갓모드다. 그래서 케이브가 **취소함/통과시킴** 두 숫자를 `lock inc` 로 세고
패널이 그것을 띄운다(여러 게임 스레드가 들어오므로 lock 이 없으면 증가가 유실된다).
검증은 「무적」을 끈 채로:

- ① 낮은 데서 떨어지면 **취소함**이 올라야 한다.
- ② 적에게 맞으면 **통과시킴**이 올라야 한다. 오르면 가해자 판정이 살아 있다는
  뜻이고, 그때 취소함이 같이 올라도 상관없다(출혈·독이 함께 취소된 것이다).
  통과시킴이 안 오르고 취소함만 오르면 조용한 갓모드이니 **즉시 끈다**.
- ③ 둘 다 안 오르면 훅이 안 물린 것이다(판정 불가) - 켠 채로 두지 않는다.

**케이브에서 게임 메모리를 만지는 명령은 `mov rax,[rax+0x68]` 하나뿐이고, 그
주소에 VEH 폴트 가드를 건다.** 앞의 두 검사(`>= 0x10000`, canonical)는 매핑을
보장하지 못해 센티널·해제 직후 포인터에서 액세스 위반이 날 수 있는데, 훅이 켜진
동안 플레이어의 모든 Health 피해가 이 경로를 지나므로 그대로 두면 랜덤 크래시다.
가드는 **그 한 명령의 주소와 정확히 같을 때만** 끼어들어 `done` 으로 떨군다
(= 판정 불가는 피해를 그대로 통과시킨다. 안전한 쪽). 낀 횟수는 패널에
"판정 불가 N회" 로 낸다 - 0 이 정상이다.

**사이트 패치는 8바이트 원자 쓰기다**(`_InterlockedExchange64`, 뒤 3바이트 보존).
`memcpy` 로 5바이트를 쓰면 dword+byte 두 번으로 나가는데, 호출자 39곳이 붐비는
디스패처라 그 틈에 다른 스레드가 진입하면 `E9` + 옛 바이트로 뛰어 즉사한다.
사이트가 8바이트 정렬이 아니면 설치를 거부한다(2850 은 `site % 16 == 0`).
설치 자체는 specguard 와 같은 CAS(`0 안 함 / 1 설치 중 / 2 끝`)로 한 스레드만
들어간다 - 지금 호출자는 분석 루프 하나뿐이지만 "백업 호출" 한 줄이면 이중 패치다.

케이브 조립은 `nofall_cave.cpp` 의 순수 함수라 시험한다(**18개**, 관찰 케이브 포함) - 골든 바이트열
적용 124·관찰 136바이트 전체 비교, 모든 rel8 변위가 앞으로만 뛰고 done 을 안 넘는지,
길이 상한 가드(시험만 작은 상한을 넘겨 **실제로 태운다**)와 그때 오프셋이 0 으로
비워지는지, `xor r9d` 단 한 번, 카운터 둘 다 `lock`, 그리고 **계약 시험** - 본문을
명령 단위로 **선형 해독**해 허용 목록에 없는 인코딩이 나오면 실패시킨다. 바이트
훑기가 아니라 전진 해독인 이유는, 목적지만 틀린 오타(`mov rcx,[rsp+0x38]`)나 REX
없는 32비트 쓰기(`xor ecx,ecx`)가 바이트 필터를 통째로 빠져나가기 때문이다
(실측: 옛 필터에 걸리는 명령은 126바이트에서 **단 1개**였다). probe `nofall` 이 설치 없이 AOB 유일성과
조립 결과(적용 124·관찰 136바이트)를 찍는다 - 다음 게임 갱신 때 가장 먼저 돌릴 명령이다.
**설치는 분석 스레드 머리**(RTTI 색인 직후, 다른 코드 훅과 같은 자리)에서 한다.
RTTI 이미지와 모듈 베이스만 있으면 되고 월드·카메라·아이템 표를 기다릴 이유가
없다 - 예전에는 세 번째 루프에 있어 **월드 진입 뒤 1~2분**이 지나야 걸렸다
(실측 2026-09-12: 08:24 실행 → 08:25:59 설치). 세 번째 루프의 호출은 재시도로
남겨 둔다( 가 한 번 실패해도 다시 볼 기회가 있게 - 이중 설치는 CAS 가 막는다).

**사이트 AOB 가 이 빌드에서 유일하게 맞지 않으면 설치를 거부하고**
패널에 "이 게임 빌드 미지원" 으로 낸다(무효, 안전). AOB 해석 실패·정렬 불일치도
같은 갈래로 보내고 WARN 한 줄을 남긴다(조용한 무한 재시도 금지).

**언인스톨은 없다.** 케이브·vars 는 `VirtualAlloc` 이라 DLL 수명과 무관하고 케이브가
DLL 코드를 부르지 않으므로 언로드돼도 안전하게 돈다(xinput 프록시라 실질적으로
언로드되지도 않는다). 끄기는 owner=0 한 번으로 완전하다. 다만 **DLL 이 언로드되면
owner 를 갱신할 주체가 사라져 마지막 root 가 영구히 남는다** - 그 주소가 재사용되면
엉뚱한 개체가 면역이 된다. 나중에 언인스톨을 넣는다면 순서는 owner=0 -> 원본
5바이트 복원(원자 쓰기) -> 케이브·vars 는 **해제하지 않고 누수**시키는 것이다
(다른 스레드가 케이브 안에 있을 수 있다). `g_orig` 를 들고 있는 것이 그 준비다.
출처: CT v5.0 "No Fall Damage"(mul0095/Trinity, MIT) 이식.

### 1.16 가방·보관함 용량 (재부착 2026-09-13, 게임 적용 확인 / 저장 생존은 미확정)

인벤토리 컴포넌트의 컨테이너 객체를 직접 고친다. `+0x00` 레코드 배열 · `+0x08` 물리 칸
수(1460, 18개 전부) · `+0x10` 종류 · `+0x12` 사용 중 · `+0x14` 용량(화면) · `+0x16` 확장
합계 · `+0x18` 확장 갈래 A · `+0x1A` 확장 갈래 B. 실측 18개 전부 `+0x16 = +0x18 + +0x1A` 다.
가방(종류 1) 240/190/190/0, 보관함(종류 7) 440/200/0/200 - **가방은 A 에, 보관함은 B 에**
정당한 확장을 단다. 기본 슬롯은 반드시 `+0x14 - +0x16` 으로 유도한다(한 칸만 보면 틀린다 -
2026-09-05 사고의 원인 절반).

**상한 700(화면) / 732(엔진), 종류를 가리지 않는다.** 참고 모드 둘이 독립적으로 732 초과는
엔진이 깨진다고 적고, 그 상태로 저장하면 로드에서 죽는다고 한다. **보관함만의 상한은 상류
문서에도 실행 파일에도 없다**(2026-09-13 조사) - ASI 의 "모든 보관함 확장" 버튼도 "732 초과
거부" 라고 적힌 그 입력칸 값을 쓰고, 확장 초과 오류 코드는 `eErrNoTryOverExpandInventorySlot`
하나뿐이다. 그래서 상한은 종류 넷 다 700 이되, 표(`BagKindRule`)로 빼 두어 근거가 생기면
숫자만 고치면 된다.

732 의 기전은 이번에도 못 짚었다. **"물리 칸 1460 의 절반" 가설은 기각됐다** - 레코드 stride 가
0xC8(200바이트)이고 1460 은 바이트가 아니라 칸 수다(CT 소스가 같은 덤프를 적는다).
ASI CHANGELOG 를 보면 999 로 내놨다가 깨진 뒤 좁혀 내려온 **실험값**으로 읽힌다.
실패 비용이 세이브 손상이라 그 위는 시험하지 않는다.

종류별 **데이터 천장**(`InventoryInfo._maxSlotCount`)은 상한과 별개다(보관함 440).
그건 "우리 값이 재계산에 지워질 수 있는 선" 이고, 자동 재적용이 맡는다.

**리로드가 인벤토리를 통째로 새로 만든다.** 세이브를 불러오면 옛 컴포넌트의 컨테이너 배열이
`0xFFFF`·개수 `0` 인 쓰레기가 된다(실측). 그래서 메모리에 쓴 용량은 저장에 남든 안 남든
화면에서 사라진다. 둘로 대응한다.

- `inventory_check_alive` 가 realm 별로 컴포넌트 생존을 보고(컨테이너 배열이 읽히는가 -
  **"아이템이 들어 있는가" 로 보면 안 된다**, 다 비운 플레이어와 구분이 안 된다) 10초 넘게
  못 읽으면 버리고 다시 찾는다.
- 사용자가 이번 실행에 누른 설정을 기억했다가 인벤토리가 **새 세대**로 잡히면 한 번 더 건다
  (`bag_auto_*`). 주소가 아니라 세대 카운터로 판단한다 - 힙이 같은 자리를 돌려주면 주소
  비교는 조용히 실패한다. 상류 ASI 도 `KeepMaxed ; Re-apply it every tick, so it survives
  the game recalculating` 로 같은 일을 한다.

**확장 칸은 종류마다 다르다**(2026-09-13 조사가 첫 가설을 뒤집었다). CT v5.0 2605~2618행이
`container+0x1A` 를 보관함 세이브의 `_varyExpandSlotCount` 로 적고, `+0x14` 는
`_defaultSlotCount + container[0x1A]` 로 **다시 계산되는 캐시**라고 한다. 그런데 그 블록은
머리에서 `DURABLE STORAGE EXPANSION, and it is a different thing from Max Bag Space` 라고
못박는다 - 즉 그 관계는 **보관함 것**이고 가방의 확장은 별개 경로다. 실측과 맞는다: 보관함의
정당한 200 은 `+0x1A` 에, 가방의 190 은 `+0x18` 에 있다.

그래서 `+0x1A` 에 넣은 60 이 사라진 것이 설명된다 - **가방에게는 남의 칸**이었고 가방 쪽
재계산이 덮었다. 한 칸을 모든 종류에 강요하면 반드시 절반이 남의 칸을 쓴다. 지금은 칸을
종류별로 고른다(가방 A · 보관함류 B). A·B 강제는 시험용으로만 남겼다.

**보관함이 저장에 남는지는 아직 미확정이다.** 이제 그 시험이 값어치가 있다 - `+0x1A` 는
상류가 세이브 필드로 적은 바로 그 칸이다. 가리려면 적용·저장한 뒤 **게임을 완전히 껐다
켜고**, "로드 후 자동 다시 적용" 을 **끈 채로** 본다. 게임 안 불러오기로는 자동 재적용이
다시 걸어 놓아 반대 답이 나온다.

**되돌리기가 유일한 방어선이다.** 기록의 열쇠는 `(realm, 종류)`(주소가 아니다). 규칙 셋:
① 바꾸지 않았어도 주소는 갱신한다 - "이미 그 값이다" 는 우리 값이 저장에서 살아 돌아온
경우의 판정이라, 그때 주소를 안 고치면 **기능이 성공했을 때만** 되돌리기가 잠긴다.
② 손대기 전 값이 우리가 써 놓은 값과 다르면 그것이 새 원본이다(재기준) - 없으면 자동
재적용이 기준값을 매번 덮어써서, 적용 → 확장권 구매 → 리로드 → 되돌리기 순서에 사용자가
돈 주고 산 칸을 지운다. ③ 되돌리기 직전에 `cap/sum` 대조 · 기본 슬롯 대조 · `used > 원래
용량` 이면 거부.

`bag_expand` 는 분석 스레드(자동 재적용)와 렌더 스레드(버튼) 양쪽에서 불리므로 쓰기 전체를
뮤텍스로 직렬화한다. 안 하면 되돌리기의 네 쓰기 사이에 자동 재적용이 끼어들어 `cap < sum` 인,
`plan_bag_expand` 가 **영원히** 거부하는 상태가 만들어지고 그 값이 세이브로 간다.

순수 부분(`plan_bag_expand` · `bag_kind_selected` · `bag_backup_upsert` ·
`bag_restore_blocked` · `bag_restore_already_original` · `should_auto_reapply`)은 전부
시험으로 덮었다. 리뷰 3회에서 치명 5 · 중대 9 · 경미 16 이 나왔고 전부 반영했다 - 전문
`.superpowers/sdd/2026-09-13-bag-capacity/` 와 `.superpowers/sdd/2026-09-13-bag-reload/`.

### 1.17 스킬 포인트 = 어비스 결속 (2026-09-13, 저장 생존 미확정)

**이 빌드의 스킬 트리는 "스킬 포인트" 로 안 돈다.** 엔진에
`CharacterStatusSaveData::_remainSkillPoint`(+0x48 i16)와 `SkillPointSaveData` 가 실재하지만
출시 빌드에서 소비자가 0곳인 잔재다. 화면이 쓰는 것은 **어비스 결속**이고, 아이템도 아니다
(아이템 표 6813개에 "결속" 0건 - 지급으로는 못 늘린다).

`Client/ServerKnowledgeActorComponent +0xC8` -> 구조체. 사용자가 결속 하나를 쓰는 순간의
전후 비교로 확정했다.

| 오프셋 | 폭 | 뜻 |
|---|---|---|
| +0x00 | u16 | **보유** (기술 창 우상단 카운터 넷 중 넷째) |
| +0x02 / +0x08 / +0x0E | u16 | 총합(누적 획득). 셋이 같은 값이었다 |
| +0x0C | u16 | 별개 카운터 - 배울 때 같이 1 줄었다. 정체 미상, **안 건드린다** |

두 realm 의 이 16바이트가 바이트까지 같았다. **좌하단 "사용 어비스 결속" 은 저장된 값이
아니다** - 화면이 `총합 - 보유` 로 계산해 그린다(보유 1->0 인데 저장된 151 셋은 그대로였고
화면은 150->151). 그래서 보유만 올리면 "사용" 이 줄어 쓰지도 않은 것을 되돌려받은 것처럼
보인다 - 총합도 같이 올리는 선택지를 둔 이유다.

한 번에 100, 천장 9999. **상류 근거가 없는 숫자다** - 참고 모드 둘 다 스킬 포인트 기능이
없어 빌려 올 값이 없고, u16 이라 65535 가 구조적 한계일 뿐이다. 가방의 732 처럼 "엔진이
깨지는 선" 을 아는 것이 아니다.

컴포넌트 생존은 가방과 같은 모양으로 본다(경과 시간 10초 · 탐색 조절 · 포기 카운터 ·
되돌리기 혈통 검사 · 쓸 때마다 포인터 재읽기).

### 1.18 강화 조건 관문 우회 (2026-09-13) — **게임 코드에 직접 쓴다**

지금까지의 치트는 전부 데이터를 고쳤다. 이것만 `.text` 를 고친다. 관문 본체는
`KnowledgeActorComponent::CheckLearnOrLevelUp`(RVA 0x0208B070, 약 4.3KB)이고 그 안에 관문이
여덟 단계 있다. 둘을 푼다.

| 관문 | 자리 | 원본 -> 패치 |
|---|---|---|
| 습득 경로("특정 조건을 통해 배울 수 있습니다") | RVA **0x0E0AB860** (`CanLearnByFromType` 진입점) | `48 89 5C` -> `B0 01 C3` (`mov al,1 ; ret`) |
| 결속 비용 | RVA **0x0208B639** | `0F 9D 44 24 40`(`setge byte [rsp+0x40]`) -> `C6 44 24 40 01`(`mov byte [rsp+0x40],1`) |

`CanLearnByFromType` 는 썽크 0x0208AF80(`E9 DB 08 02 0C`)을 거친다 - 0x0208AF80+5+0x0C0208DB
= 0x0E0AB860. 호출자 셋(0x0208B41F · 0x026BA087 · 0x0E0A8503)이 전부 호출 직후 `test al,al`
만 보므로 `al` 만 세우면 되고, 덮는 3바이트는 프롤로그 **첫 명령 안**이라 RSP 도 비휘발성
레지스터도 아직 그대로다(`ret` 한 번이 정확히 복귀한다).

**쓰기는 정렬된 8바이트 한 번의 `_InterlockedExchange64`.** 짧은 바이트를 memcpy 로 쓰면
dword+byte 두 번으로 나가고, 그 틈에 다른 스레드가 **반쯤 바뀐 명령**을 실행한다.
0x0208B639 는 정렬이 안 맞아 창이 0x0208B638 이고 off 1 이다.

**확인은 창 8바이트 전체로 한다 — 쓰기 폭으로 확인하면 안 된다.** 이것이 검토가 잡은 치명
하나다. `48 89 5C` 는 MSVC x64 가 가장 흔히 내는 프롤로그 머리라 이 실행 파일의 실행
섹션에 **136,428곳**(8정렬 자리만 95,665곳) 있다. 게임이 갱신되면 그 RVA 는 다른 함수의
몸통이 되고(이 저장소는 갱신마다 영역별로 다르게 밀리는 것을 실측해 뒀다 - §1.15),
3바이트 비교는 **약 3분의 1 확률로 통과해** 남의 함수를 `mov al,1; ret` 로 만든다.
창 8바이트로 비교하면 44곳, 관문1 은 **유일**하다.

**결속 비용 관문은 "결속이 안 줄어든다" 를 뜻하지 않는다.** 판정 함수는 총비용을 출력
인자로 그대로 내보내고(0x0208B623 `add word [rcx], dx`), 실제 차감은 이 함수 밖(서버 요청
처리기 쪽)에 있는데 아직 그 자리를 못 찾았다. 보유보다 비싼 노드를 찍으면 u16 보유 칸이
음수로 돌 수 있다 - **미확인 위험**이라 화면이 그렇게 적는다. 결속 자체를 늘리는 길
(§1.17)을 먼저 쓰는 쪽이 안전하다.

**선행 지식(`[깨달음] 필요`)은 안 푼다.** 0x0208B669~ 의 루프가 판정만 하는 것이 아니라
화면에 뿌릴 목록도 만든다. 잘못 건드리면 툴팁이 깨지므로 따로 조사한다.

되돌리기는 `on_frame` 의 **해체 요청 블록**에서만 돈다. `teardown()` 에 두면 안 된다 -
그 함수는 `on_resize` 에서도 돌아서 알트탭 한 번에 관문이 조용히 풀린다. 되돌릴 때는
지금 값이 우리가 쓴 것인지 본다(남이 같은 창에 트램펄린을 달았으면 안 되돌린다).

읽기·쓰기를 `GateIo` 로 밖에서 받아 상태 기계 전체를 가짜 메모리 위에서 시험한다.
검토 1회에서 치명 1 · 중대 6 · 경미 8 이 나왔고 전부 반영했다 - 전문
`.superpowers/sdd/2026-09-13-skill-gate/`(`review.md` · `review-response.md`).

### 1.19 지식(스킬 트리 노드) 표 — 선행 조건 풀기 (2026-09-13 · **저장 생존 확인 2026-09-15**)

화면의 `[깨달음] 필요` 와 `[원소: …] 중 하나` 는 **둘 다 선행 지식**이다. 별개 시스템이
아니다. 문자열 키가 `UI_Skill_RequiredKnowledgeNotLearned` /
`UI_Skill_RequiredAnyKnowledgeNotLearned` **한 쌍**이고, 둘을 고르는 코드
(RVA 0x00E84A4D~0x00E84A7E)가 **같은 목록·같은 개수 변수**를 쓰고 메시지만 갈아 끼운다 —
목록 원소가 2개 이상이고 `_learnRequirementType == 1` 이면 "중 하나" 쪽이다.

`ElementalMaterialKey` 계열은 **무관하다.** 그쪽 필드가 `_totalFuelAmount` ·
`_increasePerSecond` · `Freeze` · `BurnPhase1` · `Wetness` 라 **불 번짐·젖음·결빙 같은
월드 재질 시뮬레이션**이지 스킬 조건이 아니다.

**판정은 한 줄이다** (`CheckLearnOrLevelUp` 안, RVA 0x0208BC20 `cmp dword [r10+rcx*8], eax`,
바이트 `41 39 04 CA` 확인):

```
배운지식표[선행지식번호].레벨 >= 필요레벨
```

그 루프(0x0208BB7D~0x0208BCD9)는 **쓰기가 하나도 없다.** 툴팁의 "부족한 것" 목록은
**다른 루프**(아이템·재화, 0x0208B669~0x0208BA21, 오류 `eErrNoItemIsLack`/`eErrNoMoneyIsLack`)
가 만든다. 2026-09-13 조사 초반에 이 둘의 라벨을 뒤바꿔 적었다가 바로잡았다.

**매니저를 찾는 법** — 조회 함수 RVA 0x003C1C70 이 그대로 보여 준다:

```
rbx = *(전역 RVA 0x06C2E2D8)          ; KnowledgeInfoManager
if (번호 >= [rbx+0x08]) 실패          ; 전체 지식 개수
info = *(u64*)( [rbx+0x58] + 번호*8 ) ; KnowledgeInfo* 포인터 배열
```

힙 스캔이 필요 없다. **고정 RVA 라 갱신에 밀리므로**(§1.15) 매니저 개수와 컴포넌트 표
개수가 **같은지 대조하고 다르면 멈춘다** — `Initialize`(RVA 0x0E09C4F0)가 매니저의 개수로
표를 잡으므로 두 값은 반드시 같다.

**배운 지식 표** (`KnowledgeActorComponent`):

| | |
|---|---|
| `+0x18` / `+0x20` / `+0x24` | 데이터 · 개수 · 용량 |
| 레코드 | **24바이트** (실측: 4796번 `…C1A0`, 4859번 `…C788`, 차이 0x5E8 = 63 × 24) |
| `+0x00` i32 | **레벨** (0 = 미습득) |
| `+0x08` ptr | 지연 생성 객체 — **안 건드린다** |
| `+0x10` u8 | 습득 플래그 (게임도 1 을 쓴다) |

전체 지식 수만큼 **미리 잡힌 밀집 배열**이라 끼워 넣을 것이 없다. 레벨 한 칸만 쓰면 된다 —
게임이 지식을 지급할 때 하는 쓰기와 같다(RVA 0x02AA620C / 0x02AA6224).

**실측 결과(사용자 확인 2026-09-13):**

| | 결과 |
|---|---|
| 스킬 획득 조건의 `[깨달음] 필요` | **사라진다** |
| 리로드(같은 세션) 후 레벨 | 남았다 |
| 게임 안 원형 휠의 어두운 칸 | **안 켜진다** |

**저장을 넘는다 — 게임에서 저장하면**(실측 2026-09-15). 위에 적어 둔 그 순서로
사용자가 그대로 재 주셨다:

| 순서 | 결과 |
|---|---|
| 적용 → **저장 안 하고** 종료 → 재시작 | 사라진다 |
| 적용 → **저장하고** 종료 → 다시 로드 | **남아 있다** |

쓴 값은 살아 있는 컴포넌트 표에 들어가고 게임이 저장할 때 그 표를 그대로 내려
적는다. 그러니 저장을 안 하고 끄면 안 남는 것이 당연하다.

**09-14 에 "저장을 못 넘는다" 고 단정한 것은 틀렸다 — 철회한다.** 그때 건 것들
(5089: 1→0, 4712: 3→1)은 **저장을 안 하고 껐던 것**이다. 한 번의 음성 결과로
"안 남는다" 를 적었고, 정작 이 문단이 스스로 제안한 실험(쓰기 → 직접 저장 → 완전
종료 → 재시작)을 하루 넘게 안 돌렸다. TROUBLESHOOTING [3.8](TROUBLESHOOTING.md#38-리로드만-보고-저장-생존-이라-적었다) 참조.

**자동 재적용은 그대로 둔다** — 저장을 잊고 끄는 일이 있기 때문이다. 목록은 이제
ini(`knowledge_keep = 번호:레벨,…`)에 남아 **다음 실행에도 이어진다.**

**휠이 안 켜지는 것은 그와 별개로 배제 근거가 된다.** 전체 로드 경로가 세이브에서 다시 만들었는데도 안 켜졌으니,
휠을 켜는 상태는 **지식 레벨에서 파생되는 것이 아니라 따로 저장되는 별개 상태**다.
`KnowledgeSaveData` 가 레벨 말고도 `SkillLearnElementSaveData{KnowledgeKey,
SkillPointOwnerType}` · `FollowLearnElementSaveData` · `KnowledgeLearnDelayElementSaveData`
를 들고 있고, 퀵슬롯 쪽에 `UseItemReserveSlotElementSaveData{ReserveSlotKey, ItemKey,
SkillKey, …}` 가 따로 있다. **어느 것인지는 조사 중이다.**

**기능 관문을 찾았다(2026-09-14).** `ServerKnowledgeActorComponent` 에만 있는 해시맵이다:

| | |
|---|---|
| `+0xE8` / `+0xEC` / `+0xF4` | 버킷 수 · 보조 · **원소 수** |
| `+0xF8` / `+0x100` | 버킷 배열 · 값 배열 |
| 키 / 값 | 지식 id / **{ u32 SkillKey, i32 레벨 }** |

사슬: 진짜 습득이 **`0x02AA55D0`** 으로 이 맵에 넣고(`KnowledgeInfo._learnApplySkillInfo`
`+0x104` 에서 SkillKey 를 꺼낸다) → `ServerSkillActorComponent` vtable 슬롯 19
(RVA 0x02B26DE0)가 그 맵을 훑어 스킬 컴포넌트에 등록한다. **그때 휠이 켜진다.**
레벨 표는 이 맵을 안 건드리므로, 화면은 "배운 것처럼" 보이고 기능은 안 된다.
클라 컴포넌트의 같은 자리는 전부 0 이다(실측) - **서버 전용 필드**다.

해시맵이라 손으로 못 쓴다. 게임 함수를 부르는 수밖에 없고, 인자는 게임 자신의
호출부(RVA 0x02AA6450 / 0x02AA64F8)와 대조해 확인했다 -
`(rcx = 서버 comp, dx = u16 지식키, r8d = i32 레벨, r9b = 1)`.
**다만 렌더 스레드에서 부르면 죽는다**(TLS, TROUBLESHOOTING 1.8/1.13) - 소환 치트가
쓰는 게임 스레드 자리에 걸어 두고 집어 가게 한다. 2026-09-14 기준 **아직 성공을
확인하지 못했다.**

레코드 `+0x08` 은 객체가 아니라 **습득 시각**이다(`0x0201E3F0` 은 할당자가 아니라
`{일,시,분,초,ms}` -> 밀리초 변환 함수다). 0 이면 "이 지식 없음" 으로 보는 소비자가
있어(0x028348EA) 정상 습득한 지식의 값을 복사해 채운다.

정적 표의 사슬도 확정돼 있다:
`KnowledgeInfo._learnApplySkillInfo(+0x104)` -> `SkillInfo._reserveSlotInfoList(+0xE8)`.
조건식 함수 이름표에 `CheckKnowledge` · `SkillTreeNodeLearnable` · `CheckReserveSlot` 이 있다.

**컴포넌트는 플레이어 액터 사슬로 잡는다** - `*(u64*)( *(u64*)(액터+0x68) + 0x150 )`.
RTTI 탐색은 vtable 값이 들어 있는 **표까지 객체로 잡아**(2026-09-14: 후보 둘이 16바이트
간격) 화면에 쓰레기 숫자를 그렸다. 사슬이 주는 것은 **클라** 쪽이므로
(`player_char()` 가 클라 액터다) realm 은 `rtti.class_of_object` 로 판정한다.
서버 쪽은 여전히 RTTI 가 잡되 레벨 표 구조 검사를 통과해야 받는다.

**지역화는 실행 파일에 없다.** 플레이어용 한국어가 **한 글자도** 없다(UTF-8/UTF-16/CP949
전부 0회). 지식 이름과 키는 `.paz`(192개·약 175GB·매직 `PAR `)에서 런타임에 올라오므로
**게임이 켜져 있을 때 메모리에서 읽는 수밖에 없다.**

전문: `.superpowers/sdd/2026-09-13-knowledge-unlock/`.

### 1.20 원소 휠 = 예약 슬롯 (**2026-09-15 해결 · 게임에서 확인됨**)

**휠에 어떤 칸이 있는지는 예약 슬롯이 정하고, 그 칸의 잠금은 조건이 정한다.**
지식 레벨을 써도(스킬 트리에는 활성으로 뜬다) 스킬 등록 함수를 불러도 칸이 안 켜졌던
것은 **번호를 잘못 골랐기 때문**이다 — 아래 "조건 넷의 정체" 에서 풀렸다. 그때 쓴
캐릭터 접두사 붙은 원소 지식 여섯은 `_learnApplySkillInfo` 가 0xFFFF 라 **붙는 스킬
자체가 없고**, 휠도 그것들을 보지 않는다.

```
ReserveSlotInfoManager = *(u64*)(이미지 + 0x06C2E300)
  +0x08 개수(28) · +0x58 `ReserveSlotInfo*` 배열(키로 색인)
  +0xA0.. 잘 알려진 키 여덟 - **+0xAA 가 ElementalSelectSlot**
ConditionInfoManager   = *(u64*)(이미지 + 0x06C2F260)   같은 배치(개수 10785)

slotComp = *(u64*)( *(u64*)(액터+0x68) + 0x38 )   EquipSlotActorComponent
  +0x58 배열 / +0x60 개수, 엔트리 **0x110** { u16 ReserveSlotKey @+0, 레코드 @+8 }
```

조회 함수(`0x003C1C70` 지식 / `0x0039A830` 조건)가 쓰는 전역을 그대로 읽으면 되므로
**게임 함수를 부를 필요가 없다.**

**실측(2026-09-14):**

| | |
|---|---|
| `ElementalSelectSlot` | 키 **19**, `_key` 1000012, `usingType` 5, `blocked` 0 |
| 후보 목록(`+0x68`/`+0x70`) | **5개**. 원소는 4바이트 `{u16 SpecialName, u16 ConditionInfoKey}` |
| `[0]` SpecialName 30894 | **조건 없음(0xFFFF)** → 화면의 초록 잎사귀, 항상 켜짐 |
| `[1~4]` 30895~30898 | 조건키 **9198·9199·9200·9201** → 어두운 넷 |
| 런타임 슬롯[19] | **엔트리는 있는데 비어 있다**(전부 0xFFFF) |
| 대조군 탈것 슬롯[24] | `+0xD8 = 5` 로 채워져 있다 |

**화면과 정확히 맞는다** - 조건 없는 하나만 켜져 있고 조건 걸린 넷이 어둡다.
**막는 것은 그 조건 넷이다.**

**깨달음은 예약 슬롯이 아니다.** 28개를 전부 훑었는데 **후보 목록이 있는 슬롯은
원소(19) 하나뿐**이고 나머지 27개는 0개다. 화면의 무기/도구 휠에 있던 어두운 칸은
이 구조가 아니다(장착물로 채워지는 쪽으로 보인다).

**한때 읽었다고 적은 조각은 틀렸다(2026-09-15 정정).** `ConditionInfo` 는
**0x40바이트**인데 0x60 을 떠서, `c_Cloak_V_0` · `Dem` · `76867` · `19270889044443` 은
전부 **이웃 객체의 내용**이었다. 거기서 끌어낸 "c_Cloak = 냉기" 와 "조건이 캐릭터와
묶여 있다" 는 **둘 다 철회한다.**

실제 배치(로더 RVA 0x0145EAF0 · 0x021FC600 을 읽어 확정):

| 오프셋 | 필드 |
|---|---|
| `+0x00` | `_key` u32 |
| `+0x08` | `_stringKey` 문자열 객체 포인터 ← **여기에 조건식 원문이 들어 있었다** |
| `+0x10` | `_isBlocked` u8 |
| `+0x18` | `_gameCondition` **GameCondition\* 실체 포인터** |
| `+0x28` | `_originalString` — 네 조건 모두 **공유 빈 문자열 싱글턴**(RVA 0x0692E4C0) |
| `+0x30` | `_parserType` u8 |

문자열 객체는 `+0x00 char*(UTF-8) · +0x08 u32 길이 · +0x10 i32 refcount`.
`_gameCondition` 의 `+0x08` u16 은 **466개짜리 조건 함수 이름표**(RVA 0x0584FA10)의
색인이다 — 원문이 없었다면 이쪽으로 풀 작정이었는데, 쓸 필요가 없었다.

**원소 넷은 각각 자기 조건키를 들고 있으므로 하나씩 켤 수 있다**(확정).

**게임 쪽 사실(사용자가 공략 영상으로 확인, 2026-09-15)** — 게임 안에서의 정규 경로다:

- 원소는 **넷**이다: **벼락 · 냉기 · 화염 · 바람**. 후보 5개 중 조건 걸린 넷과 수가 맞는다
  (조건 없는 하나는 "원소 미선택" 쪽이다).
- **정규 습득 경로는 "어비스 던전의 관문 클리어"** 다.
- 활성화는 **물약 퀵슬롯에서 고르는 것**이고, 그것이 곧 이 `ElementalSelectSlot` 이다.
- **"어비스 기어" 는 별개다.** 장갑에 끼워 원소 스킬에 추가 타격을 붙이는 장비이고
  원소당 2개씩 있다. **원소를 여는 열쇠가 아니다** — 한때 그렇게 추측했다가 틀렸다.

다만 **잠금을 푸는 조건 자체는 관문과 무관하다.** 아래에서 평문으로 나왔다.

#### 조건 넷의 정체 (**해결**, 실측 2026-09-15)

`_stringKey` 가 잠금 툴팁 키가 아니라 **조건식 원문**을 들고 있었다:

| 조건키 | `_stringKey` | SpecialName | 원소 |
|---|---|---|---|
| 9198 | `CheckEquipSlotName(Bracelet) && CheckKnowledge(Knowledge_MpFire)` | 30895 | 화염 |
| 9199 | `… CheckKnowledge(Knowledge_MpIce)` | 30896 | 냉기 |
| 9200 | `… CheckKnowledge(Knowledge_MpLightning)` | 30897 | 벼락 |
| 9201 | `… CheckKnowledge(Knowledge_MpWind)` | 30898 | 바람 |

**조건은 둘뿐이다 — 팔찌(Bracelet) 장착 + 그 지식.** 관문 클리어도, 진행도 변수도,
어비스 기어도 아니다. 앞서 "조건 넷은 어비스 관문 클리어 여부를 본다(유력)" 고 적었던
것은 **틀렸다 — 철회한다.** 진행변수 가설도 실측으로 기각됐다: `GamePlayVariable`
표는 **62개뿐**이고 어비스 관련 항목이 **하나도 없다**(전부 풍차·등대·주거).

**그리고 조건이 보는 것은 접두사 없는 이름이다.** 여러 번 헛돈 원인이 바로 이것이다:

| 내부 이름 | 번호 | 정체 |
|---|---|---|
| `Knowledge_MpFire` · `MpIce` · `MpLightning` · `MpWind` | **4883 · 4884 · 4885 · 4886** | **휠이 보는 넷** |
| `Knowledge_Kliff_Mp*` | 4706~4709 | 클리프 스킬트리 노드 |
| `Knowledge_Damian_Mp*` | 4793~4796 | 데미안 스킬트리 노드 |
| `Knowledge_Oongka_Mp*` | 4879~4882 | 웅카 스킬트리 노드 |

그동안 눌러 온 4795·4796·4879~4882 는 전부 **캐릭터 접두사가 붙은 다른 것**이었다.
이름이 비슷해 같은 것으로 보고, 스킬 트리에는 활성으로 뜨는데 휠은 안 켜지는 상황을
반복했다. **휠이 보는 넷은 한 번도 써 본 적이 없었다.** 지식 쪽을 판 방향 자체는
맞았고, **번호를 잘못 골랐던 것**이다.

`KnowledgeInfo +0x08` 이 **내부 이름 문자열**이라는 것도 이때 확인됐다
(`Knowledge_Hp` · `Knowledge_Fatal` …). 그래서 코드는 번호를 박지 않고 **이름으로
매번 찾는다** — 게임이 갱신되면 번호가 밀리기 때문이다.

**화면**: 플레이어 치트 > **원소** 절이 넷을 이름으로 찾아 가진 것·없는 것을 보이고,
없는 것만 **[얻기]** 를 그린다. 쓰기는 §1.19 의 `know_learn` 그대로이므로 **저장을 못
넘기는 것도 그대로**이고, 자동 재적용 목록에 함께 기억시킨다.
**팔찌는 화면이 안 건드린다 — 직접 끼셔야 한다.**
같은 화면의 **[휠 진단]** 이 위 자리를 한 번에 찍는다(읽기 전용).

#### 게임에서 확인됨 (2026-09-15 12:51)

팔찌를 낀 채로 넷을 썼더니 **휠 다섯 칸이 전부 켜졌다** - 화염·냉기·벼락·바람에
초록 잎사귀까지. 고르기도 되고 "원소 : 화염" 으로 선택이 걸린다.

```
12:51:56  지식 4883 번을 레벨 1 로 - realm 2개
12:51:57  지식 4884 …   12:51:58  4885 …   12:51:59  4886 …
```

칸을 어둡게 그리는 최종 판정 코드는 실행 파일에 없지만(`.paz` UI 스크립트 층),
**조건이 충족되면 그 층이 알아서 켠다**는 것이 이것으로 확인됐다. 우리 쪽에서 UI 를
건드릴 일은 없다.

**한 번 헛디뎠던 자리**: 절을 `CollapsingHeader` 로 접어 둬서 사용자가 못 보고,
예전처럼 선행 조건 표의 `원소 : …` 줄(= 접두사 붙은 가짜 넷)을 눌렀다. 화면은
`DefaultOpen` 으로 펴고, 옆 표가 헷갈리게 한다는 경고를 같은 자리에 적었다.
찾은 번호 넷도 이제 로그에 남긴다 - 그때는 어느 번호를 썼는지 알 길이 없어 로그를
전부 뒤져야 했다.

**저장도 넘는다** — §1.19 대로, 얻은 뒤 게임에서 저장하면 그대로 남는다(2026-09-15
확인). 저장을 잊었을 때는 `knowledge_keep` 이 다음 실행에 다시 걸어 준다.

### 1.21 스토리 탈것 휠 소환 (**2026-09-16 · A.T.A.G. · 드래곤 둘 다 해결**)

A.T.A.G.(종행 6818)를 6시 휠에서 **네이티브로 소환·탑승**시킨다. 파트 16종도
연구 없이 지급·장착된다. **드래곤(종행 7008)도 7시 칸에서 소환되고, 타고 날 수
있다**(2026-09-16 게임 확인 - 소환 19:29, 탑승·비행 그 뒤).

#### 드래곤을 막던 것은 둘이었다

**(1) 호출 모션이 없었다 — 지식 한 칸.** 호출 모션은 **스킬**이고 그 스킬은
**지식**이 준다(`KnowledgeInfo._learnApplySkillInfo` +0x104):

| 지식 | 행 | 붙는 스킬 |
|---|---|---|
| `Knowledge_CallVehicle` (말 — 대조군) | 5024 | `Skill_CallVehicle` "탈승물 호출" |
| **`Knowledge_CallDragon`** | **5025** | `Skill_CallDragon` "용을 호출한다" |

드래곤 쪽만 레벨 0 이었다. `know_learn` 으로 레벨 1 을 쓰자:

```
18:04:27.613  동반자 캡처 [부르기/프레임] ID 2895               <- 처음 나갔다
18:04:27.616  소환게이트(0x2ACA250): 키=0x2 오류코드=0
```

**레벨 표 쓰기로 충분하다.** §1.19 의 "레벨 표로는 기능이 안 붙는다" 는
**스킬트리 지식에 대해서만** 참이다 — 말 호출 지식도 서버 스킬 맵에 없는데 잘
불린다(19개 전수 확인).

**(2) 휠에 올라가 있던 레코드가 빈 껍데기였다.** 명부에 `Riding_Dragon_1` 이
**둘** 있다(앞 문서의 "realm 마다 한 벌" 은 틀렸다 — `clan client` 에 둘 다 나오는
서로 다른 동반자다):

| 칸 | 1000483 | **1000724** |
|---|---|---|
| `+0xA0` 생명 | 1 | **2500** |
| `+0x158`/`+0x15C` 성장치 | 1 / 1 | **30 / 30** |
| `+0x148` 휠 칸 | `0x0000` (등록돼 있었다) | `0xFFFF` |

`+0x148` 을 서로 바꾸자 재시작 뒤 스탯 2500 이 뜨고 소환된다. 그래서
`wheel_fill` 이 이제 **종마다 제일 멀쩡한 레코드 하나만** 올리고 나머지는
내린다(`wheel_fill_better`).

**배제한 것(전부 실측):** 정적 `characterinfo` 스탯 배선(`recdiff` 차이 0건) ·
`_grownLevel`(+0x498) · `_statusGroupInfo`(+0x5B8) · 장비 파트(말·A.T.A.G. 도
장비가 체력에 영향 없다) · `MercenarySaveData` 반사 속성(스탯 속성 자체가 없다) ·
`+0xA0` 직접 쓰기(**게임이 곧바로 되돌린다**).

### 1.21.1 마을 소환 제한 · 강제 하차 (**2026-09-17 해제 · 게임 확인**)

마을에서 못 부르는 것도, 타고 들어가면 내려지는 것도 **같은 조건**
`IsInTown()` 이다(`gamedata/failmessageinfo` 평문). 그 함수가 무엇을 읽는지
실행 파일에서 전부 떴다:

```
IsInTown(액터) = (지금 겹쳐 들어와 있는 구역 중 하나라도 RegionInfo._isTown != 0)
              || (dword [[액터+0x68]+0xB0]+0x358 != 0)
```

앞 갈래(RVA 0x1764580)가 본체다. 액터의 구역 상태(`[[액터+0x68]+0x1A0]+0x38`)에
지금 겹친 구역 목록이 있고, 항목 앞 u16 은 `_key` 가 아니라 **표의 행 번호**다
(조회 함수 0x49BB80 이 배열 첨자로 그대로 쓴다).

**그래서 `RegionInfo._isTown`(+0x75)을 0 으로 두면 조건이 그 자리에서 거짓이
된다.** 표 1007행 중 마을이 **172행**, `_limitVehicleRun` 이 **15행**이다.
게임에서 소환·탑승 둘 다 확인했다(2026-09-17). **모드 토글로도 재확인했다**
— 데메니스 시내에서 A.T.A.G. 가 불렸다(2026-09-18, 사용자 실측).

화면은 "드래곤 · A.T.A.G." 창의 **마을 (소환 · 강제 하차)** 절, 코드는
`src/game/towngate.{h,cpp}` 다. 정적 표라 **세이브에 안 남고** 실행마다 다시
걸어야 한다. 끄면 원래 값을 되돌린다(자국은 레코드 포인터가 아니라 **행
번호**로 들고 있어 표가 다시 잡혀도 남의 메모리에 안 쓴다).

> ⚠️ **범위가 넓다.** `IsInTown()` 은 현상금·상점·NPC 일과도 같이 쓴다. 상시가
> 아니라 사용자가 켜고 끄는 토글이다.
>
> 아직 **안 풀린 것**: 지도의 붉은 구역(`IsVehicleAllowedInEnteredRegion`).
> 그 재료가 `RegionInfo._forbiddenMercenaryKeyList` 라는 가정은 깨졌다 — 그
> 목록은 `Region_Abyss` 한 행에만 있다. 전문:
> `specs/2026-09-16-vehicle-place-and-dismount.md` §5-1-1.
>
> (2026-09-18 반쯤 정정: 그 목록을 **읽는 곳은 있다** — 호출 시점 오류
> "호출할 수 없는 지역입니다" 가 그것이다. §1.21.2)

### 1.21.2 호출 위치 거부 — 실내 · 지붕 · 지역 · 위치 (**2026-09-18**)

`failmessageinfo` 조건층(§1.21.1 의 `IsInTown()`)과 **다른 층**이다. 그쪽은
부르기 전에 조건식을 보고, 이쪽은 **호출 처리기가 지금 서 있는 자리**를 보고
`eErrNo*` 를 돌려준다.

#### 오류 이름 뒤에 한국어 설명이 붙어 있다 (이 층을 푼 열쇠)

등록 루프(RVA 0x2150380~)가 오류마다 `{값 전역 슬롯, 설명, 이름}` 을 넘긴다.
그래서 이름 문자열 **바로 뒤가 화면 문구**이고, 값 슬롯을 `xref_data.py` 로
역참조하면 **그 오류를 내는 코드가 한 곳**으로 좁혀진다.

| 화면 문구 | 오류 | 값 슬롯 | 내는 곳 | 분기 |
|---|---|---|---|---|
| 실내에서는 호출할 수 없습니다 | `...MercenaryIndoor` | `+0x6BBCBC0` | RVA `0x9635FE` | `0x9635FC` je |
| 지붕 위에서는 호출할 수 없습니다 | `...MercenaryOnRoof` | `+0x6BBCBC4` | RVA `0x96365B` | `0x963659` je |
| 호출할 수 없는 지역입니다 | `...MercenaryRegion` | `+0x6BBCBC8` | RVA `0x9626BB` | `0x9626B9` je |
| **호출할 수 없는 위치입니다** | `...InvalidPosition` | `+0x6BBCBA4` | RVA `0x9624E6` | `0x9624E4` **jne** |

넷 다 조건 점프 한 바이트를 `jmp`(0xEB)로 바꾸면 오류 대입을 건너뛴다. 전부
정렬된 8바이트 창 안이라 `skillgate` 의 원자 교환을 그대로 쓴다. 코드는
`src/game/callgate.{h,cpp}`, 화면은 "드래곤 · A.T.A.G." 창의
**소환 (호출 장소)** 절이다.

#### **성벽 위는 "지붕" 이 아니라 "위치" 다**

관문 셋을 켜고 성벽 위에서 불렀는데 여전히 막혔다. 화면 문구가
"지붕 위에서는…" 이 아니라 **"호출할 수 없는 위치입니다"** 였다 — 게임이 그
자리를 지붕이 아니라 유효하지 않은 위치로 분류한다. 넷째 관문은 그래서 생겼다.

위치 관문만 `jne`(0x75)다(통과 쪽이 아래로 붙었다). 창이 실내 관문과 모양까지
닮아서(`… 84 C0 7x 0x 8B 05`) 헷갈릴 자리라, 앞 두 바이트가 다르다는 것을
시험이 못박는다.

판정 함수 셋은 **표 값이 아니라 월드 질의**다 — 지붕은
`call 0x7479E0(월드, 위치, 반경)`, 위치는 `call 0x9CD730`. 데이터로는 못 끈다.
지역만 예외로 `[[액터+0x68]+0x1A0]+0x38`(겹쳐 있는 구역 목록)을 들고
RVA `0x16E4380` 을 부르고, 그 함수가 `_forbiddenMercenaryKeyList` 를 읽는다.

#### **게임 확인 (2026-09-18, exe 1.0.0.2944)**

사용자 실측으로 **소환 위치 관련이 전부 됐다.** 관문 넷이 2944 자리에 그대로
걸린 것이 로그로 남았다:

```
14:44:31  마을 판정: 187칸을 풀었다 (_isTown·_limitVehicleRun -> 0)
14:44:39  호출 위치 관문 '실내에서도 호출'     켬: 0x1409DE7DC
14:44:39  호출 위치 관문 '지붕 위에서도 호출'   켬: 0x1409DE839
14:44:40  호출 위치 관문 '금지 구역에서도 호출' 켬: 0x1409DD899
14:44:40  호출 위치 관문 '막힌 위치에서도 호출' 켬: 0x1409DD6C4
```

**187칸은 2850 때와 같은 수**(마을 172 + 달리기 제한 15)다 — 구역 표 전역
재도출(`0x6D69AD0`)도 맞았다는 뜻이다. 성벽 위에서 막히던 것은

> ⚠️ 상시가 아니라 **토글**이다. 정말 못 서는 자리에서 부르면 탈것이 지형에
> 박히거나 곧 사라질 수 있다(지금까지는 그런 보고가 없다).
>
> 같은 오류를 내는 자리가 하나 더 있다(RVA `0x2B2AD05`). 좌표가 (0,0,0)인지
> 보는 위생 검사라 **안 건드린다.**

전문: `specs/2026-09-16-vehicle-place-and-dismount.md` §5-1-2.

**벽은 서버가 아니라 동반자 카테고리 한 칸이었다** — `CharacterInfo.
_mercenaryInfo`(+0xBE). 메인 휠 칸(1000006)은 1(말)·5(특수 탑승물)만 받는데
A.T.A.G. 가 3 이었다. `_vehicleInfo`(+0x6E)는 *무엇이 나오는가* 를 정하므로
건드리지 않는다.

### 1.21.3 탈것 체력 · 스태미나 (**2026-09-19, 게임 확인**)

창: 드래곤 · A.T.A.G. → **체력 · 스태미나**.

**액터에서 곧장 닿는 게이지 배열은 거울이다.** 처음 판에서는 그 배열에만
썼고, 사용자가 "드래곤·A.T.A.G. 는 바꾸면 바로 복구된다" 고 신고했다. 추적
전문은 `TROUBLESHOOTING.md` [3.3.1]. 요점만:

| 층 | 클래스 | 역할 |
|---|---|---|
| `ClientChildOnlyInGameActor` → `ClientStatusActorComponent` | 클라 | **거울.** 회복 틱마다 덮인다 |
| `ServerChildOnlyInGameActor` → `ServerStatusActorComponent` | 서버 | **권위.** 게임이 읽는 값 |

두 realm 을 잇는 열쇠는 **액터 `+0x60` 의 핸들**이다(양쪽이 같은 값). 클라
사슬 어디에도 서버 쪽 포인터가 없어 RTTI 로 `ServerStatusActorComponent` 를
훑어 `{핸들 → 컴포넌트}` 를 만든다.

```
컴포넌트 +0x08 -> 액터   · 액터 +0x60 -> 핸들(재확인용)
컴포넌트 +0x18 -> root   · root +0x58 -> 권위 게이지 배열
항목 k = 배열 + k*0x90 : +0x00 타입 · +0x08 현재 · +0x18 최대 · +0x58 기준최대
```

최대는 **두 칸**(`+0x18` 유도 · `+0x58` 기준)이라 함께 쓴다. 힙 전수 탐색은
**부탁할 때만** 돌고(분석 스레드), 쓸 때마다 컴포넌트에서 주소를 다시 얻으며
핸들을 재확인한다 — 탈것을 돌려보내면 객체가 재사용되기 때문이다.

확인용 프로브 명령: `cdtb_probe mountauth` (거울/권위를 나란히 낸다),
`cdtb_probe mountauth <핸들> <체력현재> <체력최대> <기력현재> <기력최대>`.
(프로브는 **밖에서** 붙으므로 쓰기를 `Remote` 로 한다 - 모드의
`safe_write_bytes` 는 같은 프로세스 안에서만 먹는다.)

#### 게임 확인 (2026-09-18)

```
탈것 권위 사본: ServerStatusActorComponent 후보 352개 중 351개를 짝지었다
  B0100003 A.T.A.G.  거울 1,692,000/2,500,000  권위 0x5F60BFC9000 1,692,000/2,500,000
```

권위에 체력 2,500,000 · 최대 3,000,000(기준 포함) · 기력 최대 500,000 을 쓰고
20초(8틱) 지켜본 결과:

| | 결과 |
|---|---|
| 체력 현재 | 2,500,400 → 2,503,200 — **우리가 쓴 값에서부터** 회복한다 |
| 체력 최대 · 기준 | 3,000,000 유지 |
| 기력 최대 · 기준 | 500,000 유지 |
| 거울 | 다음 틱에 따라왔다(체력 2,554,800 / **3,000,000**) |

**전과 무엇이 다른가** — 거울에만 썼을 때는 다음 틱에 현재치가 "우리 값" 이
아니라 "**엔진 자기 값 + 회복량**" 으로 올라갔다. 이제는 우리 값에서 올라간다.
그것이 "권위에 닿았다" 의 증거다.

기력은 안 타는 동안 틱이 안 돌아 거울로 안 내려온다. 그래서 코드는 **양쪽에
다 쓴다**(프로브로 6칸 쓰기 → 거울·권위 둘 다 500,000/500,000 확인).

### 1.22 오버레이 UI 상태 기억 (2026-09-16, 게임에서 확인)

창의 **열림/닫힘**과 창 안 **헤더의 펼침**이 다음 실행에 그대로 돌아온다.

ImGui 는 창의 위치·크기·접힘만 저장한다. 나머지 둘은 저장하지 않는다 -
헤더 상태는 창의 메모리 저장소에만 있어 게임을 끄면 사라졌다. ImGui 설정
핸들러로 우리 구역을 같은 파일(`cdtoybox_ui.ini`)에, 같은 저장 시점에
태운다.

```
[CDToyboxUI][State]
H=main.module=1        헤더: 고정 키 = 펼침
W=아이템 목록=1         창: 제목 = 열림
```

- **모르는 키는 헤더가 접힘**이다. 그래서 새 헤더가 펼친 채 튀어나오지 않고
  `DefaultOpen` 플래그를 따로 둘 이유가 없다(원소·즐겨찾기에서 뗐다).
- **최초 실행에는 본창만 열린다.** 다섯이 한꺼번에 뜨면 화면을 가리고,
  어차피 한 번 고르면 기억된다.
- 키는 라벨이 아니라 **고정 문자열**이다 - 라벨에는 개수가 붙어 있어
  (`즐겨찾기 (3)`) 그것을 키로 쓰면 개수가 바뀔 때 상태가 날아간다.
  보관함 세트만 이름이 키다(`stash.set.<이름>`).
- `init_show_flags` 는 ImGui 가 ini 를 읽기 전이면 **씨를 안 뿌리고 물러난다.**
  그 전에 뿌리면 지난 실행 상태를 기본값으로 덮는데, 증상이 "가끔 창 배치가
  초기화된다" 라 원인을 찾기 어렵다.

**`primary`(옛 `default_open`)는 시작 표시가 아니다.** 그 필드는 배치
묶음이고 `layout_tests` 가 "같은 묶음끼리 안 겹친다" 를 검사한다. 열 창을
전부 안 겹치게 놓을 자리는 1920 폭에 없어 묶음이 둘이다. 시작 표시는
`init_show_flags` 가 정한다.

검증(2026-09-16, PostMessage 화면 확인 3회): 최초 실행에 본창만·헤더 전부
접힘 / 헤더 하나와 창 하나를 켜니 ini 에 `H=` · `W=` 가 생김 / 재시작하니
그대로 복원. 순수 로직은 단위 시험 603개.

### 1.23 장비의 캐릭터 전용 구분 (2026-09-17, 게임에서 확인)

아이템 목록과 인벤토리에 **전용** 열이 붙는다. 공용 · 클리프 · 데미안 ·
웅카 넷으로 갈리고, 필터 Combo 와 머리글 정렬이 같이 돈다. 두 창이 같은
`filter_bar` 를 쓰므로 Combo 하나가 둘 다 건다.

**구분은 `ItemInfo._stringKey`(+0x08) 의 내부 이름 접두사에서만 나온다.**
표시명은 현지화되므로 거기엔 없다 - 표시명에 캐릭터가 든 장비는 3157개 중
2개뿐이다.

```
_stringKey(+0x08) -> { char* +0x00, u32 길이 +0x08 }
   "Demian_PlateArmor_Helm_IV"      황금 광휘 판금 투구
   "Oongka_PlateArmor_Helm_II"      용맹한 발걸음 판금 투구
   "Kliff_PlateArmor_Helm"          카이로스 판금 투구
   "Marni_Devotee_PlateArmor_Helm"  공용 (접두사가 캐릭터가 아니다)
```

전수 분류(exe 2850, 내부 이름을 못 읽은 것 0개):

| 구분 | 개수 | 접두사 |
|---|---|---|
| 공용 | 3072 | 그 외 전부 |
| 데미안 | 60 | `Demian_` 47 + `Damian_` 13 |
| 웅카 | 16 | `Oongka_` |
| 클리프 | 9 | `Kliff_` |

**철자가 함정이다.** 클리프는 `Cliff` 가 아니라 **`Kliff`**, 웅카는 `Unka`
가 아니라 **`Oongka`**, 데미안은 `Demian` 과 `Damian` 이 **둘 다** 쓰인다
(캐릭터 표는 `Damian`, 장비는 주로 `Demian`). 접두사는 밑줄까지 맞춘다 -
표에 `Demeniss`(23개) 가 있다.

열 색인이 정렬과의 계약이라 양쪽이 맞물려 있다. 아이템 목록은 전용이 4 ·
이름이 5(`item_sort_from_specs`), 인벤토리는 전용이 2 · 그 아래가 한 칸씩
밀린다(`apply_sort`). 시험이 이 계약을 못박고 있다.

**캐릭터 축은 아이템 스칼라 칸에도 `EquipTypeInfo` 에도 없다** - 장비
3157개의 레코드 1280바이트를 전수 조사해 배제했다. 그 과정과 두 번 헛짚은
필드는 `TROUBLESHOOTING.md` 4.30 에 있다.

### 1.24 범죄수치(수배) — **읽기 확인 (2026-09-19, 2944)** · 쓰기는 realm 두 벌 (2026-09-20)

#### 값은 **두 벌**이다 (2026-09-20 실측 — 여기가 핵심)

이 게임은 싱글인데 안이 MMO 프레임워크라 클라와 서버가 한 프로세스에 산다

키의 레코드가 값이 다르다.**

```

        +0x28 = 1000131   +0x30 = 0x2710 = 10000   (100.00)
클라  ClientSelfWantedActorComponent  0x476E3B7B6E0 -> 0x477E87F4300
        +0x28 = 1000131   +0x30 = 0x0BB8 =  3000   ( 30.00)
```

같은 `WantedRegionData` 클래스이고 `+0x1B`·`+0x1E`·`+0x2E` 도 갈린다(서버 쪽만
채워진 칸이 있다). 살아 있는 수는 **서버 2 · 클라 2 · 커먼 1** 인데, 그중 낮은
주소(`0x806CA040` 등)는 객체가 아니라 **등록표 행**이다(아래).

그동안 우리는 **클라 한 벌만** 썼다. `setspecies` 가 이미 클라+서버로 쓰는데
수배만 안 그랬다. 지금은 `bounty_write_region` 이 살아 있는 realm 에 전부 쓰고
쓴 realm 수를 낸다. 화면도 realm 별 칸으로 보이고, 어긋나면 붉게 뜬다.

#### 진짜 컴포넌트와 등록표 행 (2026-09-20)

예전 탐색 기준은 "`+0x30` 이 `WantedRegionData` 를 가리킨다" 였다. 그건 **범죄
기록이 있을 때만** 참이라, 죄가 없으면 컴포넌트를 영영 못 찾았다 — 2026-09-20
09:57~09:58 에 3회 연속 실패하고 그만둔 것이 그것이다(회당 ~50초).

가르는 것은 `+0x08` 이다.

```
클라 진짜  +0x08 -> ClientChildOnlyInGameActor
서버 진짜  +0x08 -> ServerChildOnlyInGameActor
등록표 행  +0x08 =  0x565 / 0x37E2      ← 포인터가 아니라 클래스 번호

```

지역 레코드의 vtable 도 이제 힙을 안 훑고 얻는다 — `find_types` +
`vtables_for`. realm 셋은 `find_objects_of` 로 **힙 한 통과**에 잡는다.

#### 게임의 자기 동작 (2026-09-20)

스크립트 동작 이름표(RVA `0x5984708`)에 `SetWanted` 와 `ClearWanted` 가 나란히
있다. `StageChart_Function_SetWanted` 의 필드는 `_wantedRegion` ·
`_wantedCrimeType` · `_wantedPrice` · `_wantedFaction` 이다. 메시지
2837(`TrocTrClearWantedReq`) · 2983(`TrocTrChangeWantedStateReq`) 은 배선돼
있으나 **아직 한 번도 안 보냈다**(로그에 요청 줄이 없다).

**`+0x30` 은 포인터가 아니라 벡터다**(2026-09-19 정정 — 아래 §"구역은 여럿이다").

```
ClientSelfWantedActorComponent
  +0x30 {데이터 ptr, +0x38 크기 u32, +0x3C 용량 u32}   WantedRegionData 벡터
    원소 0x40바이트 : +0x28 u32 구역 키 · +0x30 u64 벌금
```

`+0x30` 은 **2자리 고정소수**다 — `10000` 이 화면의 `100.00`. 액수가 0 이 되면
화면 라벨이 "현상 수배" 에서 "벌금" 으로 바뀐다. **상태는 이 레코드에 없다** —
두 상태를 바이트로 견주면 `+0x30` 말고는 한 바이트도 안 다르다.

#### 게임 확인 (2026-09-19 17:23, exe 1.0.0.2944)

메모리와 화면을 같은 순간에 맞춰 봤다.

```
로그    수배 컴포넌트: 0x262E371C200 (지역 0x26387991EC0 .?AVWantedRegionData@pa@@)
메모리  0x26387991EF0 (+0x30)  10 27 00 00 00 00 00 00   = 0x2710 = 10000
화면    우상단 전단 "현상 수배 · 체포 · 가축 상해 · 100.00"  (데메니스 시)
```

`10000 = 100.00` 이 그대로 맞고, `+0x00` 도 모듈+0x1558DF18 로 성한 vtable 이다.
**2850 실측이던 `+0x30` 사슬이 2944 에서도 유효하다**(2944 스펙 §10 이 "정적으로
확인 불가" 로 남겨 둔 항목 - 이것으로 닫힌다).

#### 구역은 여럿이다 (2026-09-19) — **다만 이것은 수배가 안 풀리는 원인이 아니었다**

> ### ⛔ 정정 — "그래서 수배가 안 풀렸다" 는 틀렸다
>
> 아래 발견(구역이 둘인데 첫 칸만 봤다)은 **진짜 결함이 맞고 고친 것도 맞다.**
> 그런데 그것을 곧바로 *"그래서 수배가 안 풀렸다"* 로 적었다. **틀렸다.**
>
> 고친 뒤 실측: 구역이 **하나뿐**이고 그 하나가 **0 인데도** 사용자 화면에서
> 수배가 안 풀린다(2026-09-19, `벌금: 구역 1000138 10000 -> 0` 뒤).
>
> 즉 **벌금 금액과 수배 상태는 별개**다 — `wanted.h` 가 원래 적어 둔
> *"상태는 이 레코드에 없다"* 가 맞다. 구역 벡터는 **그 위에 겹쳐 있던 두
> 번째 결함**이었을 뿐이다. 증상 하나에 원인 하나를 서둘러 붙였다
> (`TROUBLESHOOTING.md` 4.29 와 같은 갈래).

사용자 보고: **벌금을 0 으로 내려도 수배 상태가 안 풀린다.** 지도 표식도, 게임
메뉴의 수배 화면도, 상점·NPC 게이팅도 그대로였다.

그 추적에서 **우리가 구조를 잘못 읽고 있던 것**이 드러났다. `+0x30` 은 단일 포인터가 아니라
`{데이터, 크기, 용량}` **벡터**이고, 그때 크기가 **2** 였다.

| | `+0x28` 구역 키 | `+0x30` raw | 화면 |
|---|---|---|---|
| `[0]` | 1000138 | `0` | 데메니스 왕국 · 벌금 0 |
| `[1]` | 1000131 | `0x1FA4` = **8100** | **에르난드 공국 · 현상 수배 81.00** |

즉 데메니스를 0 으로 만드는 동안 **에르난드의 81.00 은 한 번도 안 건드려졌다.**
사용자 스크린샷의 `에르난드 공국 / 현상 수배 / 81.00` 과 바이트까지 맞았다.

**게임 창은 지금 있는 구역 하나만** 보여 주고 우리 창은 **벡터의 첫 칸만**
보였다. 둘이 어긋나 "고쳤는데 안 고쳐진" 것처럼 보였다.

영토는 다섯이다 — 에르난드 공국 · 페일론 연합국 · 데메니스 왕국 · 델레시아
공화국 · 붉은사막(사용자 확인). 그래서 기록도 **다섯까지** 난다.

**고쳤다** — 화면이 구역을 **전부** 내고(키 · 벌금 · 줄마다 `[0 으로]`),
`[전부 0 으로]` 를 뒀다. 쓰기는 **쓸 때마다 벡터를 다시 읽어** 자리를 다시
찾는다 — 구역이 하나 늘면 재할당돼 옛 주소가 죽기 때문이다(실측:
`0x26387991EC0` → `0x262F33FAC00`). 경위는 `TROUBLESHOOTING.md` 4.35.

#### 구역 이름 — 붙였다가 **걷어냈다** (2026-09-19)

이름의 필드 번호를 모르는 채 *"`0x00..0x80` 을 훑어 **처음 비지 않은 문자열**을
쓴다"* 로 지었다. `0x60` 이 걸렸고, 화면이 데메니스 왕국을 **"구매하기({price})"**
라고 불렀다.

```
구역 이름 필드를 찾았다: 0x60 (구역 1000138 -> 구매하기({price}))
```

§4.8 의 *"폴백은 틀린 답을 자신 있게 내놓는다"* 를 그대로 재현했다 — 그 교훈을
커밋 메시지에 **인용해 놓고** 같은 짓을 했다. 걷어냈고, 화면은 다시 키로 간다.

**그 대신 라이브로 재서 사실을 얻었다**(`probe loc find "에르난드 공국" 40`):

```
cat 9  엔티티 61 · 81 · 202 · 6101   필드 0x92   "에르난드 공국"
cat 9  엔티티 6101                   필드 0x93   "에르난드 공국의 심장부…"
```

- 구역 이름은 **카테고리 9 · 필드 0x92** 다.
- 그런데 엔티티가 **61 · 81 · 202 · 6101** 같은 작은 수다. 수배 레코드의
  `+0x28`(1000131 · 1000138)은 **현지화 엔티티 키가 아니다** — 가정 둘이 다
  틀렸다.

**남은 길**: 수배 키 → `RegionInfoManager` 의 행 → `_displayRegionName`(+0x18,
`fields.py` 로 떴다) → 그 객체가 든 진짜 엔티티 → `0x92` 로 해석.
`towngate.h` 가 이미 그 표의 매니저와 `_stringKey`(+0x08)를 쓴다.

#### 아직 안 된 것 — **수배 "상태" 를 못 찾았다**

이것이 지금 이 기능의 가장 큰 구멍이다. **벌금 금액은 읽고 쓸 수 있지만, 수배
상태는 못 끈다.**

- `WantedRegionData` 는 100.00/현상수배 때와 0/벌금 때가 **`+0x30` 말고 한
  바이트도 안 다르다**(두 판의 덤프를 견줬다). 상태는 이 레코드에 없다.
- 구역이 **하나뿐이고 그것이 0 인데도** 지도 표식·메뉴·NPC 게이팅이 남는다
  (2026-09-19 사용자 실측).

**재는 방법은 A/B 다 — 바이트를 눈으로 훑지 않는다.** `+0x30`(벌금)을 찾은 것이
바로 그 방법이었다("두 상태를 바이트로 견주면 `+0x30` 말고는 한 바이트도 안
다르다"). 같은 것을 상태에 쓴다. 2026-09-19 에 A/B 없이 바이트를 읽다가 **원인을
두 번 틀리게 적었다**(위 정정 둘).

```powershell
.\scripts\wanted-snap.ps1 on     # 수배가 켜진 판에서
.\scripts\wanted-snap.ps1 off    # 게임 안에서 수배를 푼 뒤
.\scripts\wanted-snap.ps1 -Diff  # 다른 줄만 낸다
```

컴포넌트 주소는 로그에서 읽고, **뜨기 전에 `whatis` 로 아직 그 객체인지
확인한다** - 주소는 죽는다(§1.4). 실제로 첫 판에 죽은 주소를 떴다가 그 가드가
잡았다(그 자리엔 `ClientSyncSceneObjectBVHNodeMetaData` 가 들어앉아 있었다).

**다음에 볼 곳 — `WantedState` 는 실재하고, `AllyGroup`(세력)이 얽혀 있다.**

실행 파일에서 `eErrNo` 이름을 훑어 다섯을 얻었다(2026-09-19). 이 어휘가
지금까지 없던 단서다.

| 이름 | 읽히는 것 |
|---|---|
| `eErrNoPrevWantedStateCannotChange` | **상태를 바꾸려다 거부**될 때. `TrocTrChangeWantedStateReq` 의 거부로 유력하다 |
| `eErrNoUnsaveableWantedState` | 상태에 **저장 가능/불가** 구분이 있다 |
| `eErrNoNotExistAllyGroupWantedCrimeType` | **세력(AllyGroup)별 범죄 종류**가 있다 — 구역이 아니라 세력 축일 수 있다 |
| `eErrNoIsCrimeException` | 범죄 예외 판정 |
| `eErrNoDontUseContentsWantedLevel` | **WantedLevel** 이라는 별도 축 |

즉 **벌금(금액) · WantedState · WantedLevel · 세력별 범죄종류**가 각각 다른
것으로 보인다. 우리가 읽고 쓰는 것은 그중 **금액 하나뿐**이다.

#### NPC·상점 차단 관문을 찾았다 (2026-09-19) — **아직 안 걸었다**

§1.21.2 의 방법 그대로 내려갔다. 등록 루프가 `lea rcx=값슬롯 / lea r8=설명 /
lea rdx=이름` 으로 넘기므로, 이름을 가리키는 `lea` 자리를 디스어셈블하면 셋이
한 화면에 나온다.

```
eErrNoDontUseContentsWantedLevel
  등록   RVA 0x02209500   설명 0x0592E670 "범죄 상태에서는 할 수 없습니다."
  값슬롯 RVA 0x06CF7E6C
  내는 곳 RVA 0x021F2CC6  ← **딱 한 곳**
```

관문 모양은 `callgate`(§1.21.2)와 같다.

```
0x021F2CB9  call  0x21F2ED0          ; 판정 함수
0x021F2CBE  test  al, al
0x021F2CC0  jne   0x21F2D85          ; 통과 (al != 0)
0x021F2CC6  mov   eax, [0x06CF7E6C]  ; "범죄 상태에서는 할 수 없습니다."
0x021F2CCC  mov   [r14], eax         ; 오류 대입
```

**닻은 분기 창이 아니라 그 앞 창이다.** §1.5 대로 8바이트 창의 일치 수를 세어
확인했다.

| 자리 | 창 8바이트 | 실행 섹션 일치 |
|---|---|---|
| 분기 `0x021F2CC0` | `0F 85 BF 00 00 00 8B 05` | **4곳** — 유일하지 않다 |
| 그 앞 `0x021F2CB8` | `CD E8 12 02 00 00 84 C0` | **1곳 · 유일** |

분기만 보고 걸면 갱신 뒤 남의 함수를 덮을 수 있다. 앞 창으로 자리를 확정한 뒤
분기를 고치는 것이 맞다. `jne`(`0F 85`)는 near 분기라 `90 E9`(nop + jmp rel32)로
바꾸면 길이가 그대로고 변위도 그대로다.

> **아직 안 걸었다.** 이것은 `.text` 쓰기라 §1.5·§1.18 의 규율(원자 8바이트 ·
> 창 전체 확인 · 되돌리기는 `on_frame` 해체 블록)을 다 갖춰야 한다.

#### 상태 변경 처리기도 자리가 났다

```
eErrNoPrevWantedStateCannotChange
  값슬롯 RVA 0x06CDD908
  내는 곳 RVA 0x025D8386 · 0x025D83FB   (같은 함수)
  함수   RVA 0x025D8110 ~ 0x025D8460 (848바이트)
```

**함수를 읽었다 (2026-09-19). 거부 조건이 한 줄이다.**

```
0x025D837F  cmp   byte [r14 + 0x18], 2     ; 상태 바이트가 2인가
0x025D8384  jne   0x25D83AC                ; 아니면 계속 진행
0x025D8386  mov   eax, [0x06CDD908]        ; eErrNoPrevWantedStateCannotChange
0x025D838C  mov   [rsi], eax
```

**수배 상태는 바이트이고 값 `2` 면 변경이 거부된다.** 앞머리에 관문이 하나 더 있다 -
`cmp byte [rax+0x50], 7` 을 통과 못 하면 `0x06CDDFB8`(세력별 범죄 종류 없음)을 낸다.
즉 **세력별 범죄 종류(< 7) -> 이전 상태(!= 2)** 순으로 본다.

인자 배치도 드러났다 - `r14` = 대상 객체(vtable 있음 · `+0x18` 상태 u8 ·
`+0x28` u16), `r12b` = 요청한 새 상태(3번째 인자), `r15` = 액터.

남은 것은 **`r14` 가 무엇인가** 다. vtable 을 쓰고(`+0x148`·`+0x180`·`+0x188`)
`+0x28` 이 u16 이라 `WantedRegionData` 는 아닌 것으로 보인다 - 우리 덤프에서
그 레코드의 `+0x18` 바이트는 늘 `0xFF` 였다(2 가 아니다). 라이브로 이 함수를
훅해 `r14` 의 클래스를 찍으면 한 번에 갈린다.

> **정정 (2026-09-20) — `r14` 는 수배 컴포넌트다. 그런데 "2 = 수배" 는 틀렸다.**
>
> `r14` 는 `WantedActorComponent` 다. 살아 있는 클라 컴포넌트
> `0x476E3B7B6E0` 의 vtable(`0x14558E458`)에 그 함수와 같은 구역의 메서드
> (`0x1425D6830` · `0x1425D6AB0` · `0x1425D6BE0`)가 들어 있고, `probe whatis`
> 가 `.?AVClientSelfWantedActorComponent@pa@@` 를 낸다. 그러니 `+0x18` 은
> 그 컴포넌트의 칸이다.
>
> **하지만 on/off 가 아니다.** 표본 셋이 갈랐다 — **전단 둘째 줄과 맞는다.**
>
> | `+0x18` | 전단 둘째 줄 | 벌금 |
> |---|---|---|
> | 0 | (지도에서만 봄 — 둘째 줄 미확인) | 30.00 |
> | 1 | **수색** | 20.00 |
> | 2 | **체포** | 77.30 |
>
> 1 은 2026-09-20 15:2x 에 **클라·서버 두 realm 이 똑같이 1** 이었다. 화면의
> `UI_WitnessWanted_Arrest` · `UI_WitnessWanted_SearchState` 와 갱신 호출
> `UpdateWantedState` · `UpdateWantedSearchState` 가 이 열거형을 먹는다.
>
> 그러니 거부 조건 `cmp byte [r14+0x18], 2` 는 **"체포 단계에서는 상태를
> 못 바꾼다"** 는 뜻이다.
>
> 2026-09-19 에 "2 = 수배, 0 = 없음" 으로 읽은 것은 취소한다. 월드 화면에
> 전단이 없는 것을 보고 "풀렸다" 고 했는데, 수배 표시는 **지도 화면**에
> 있었다(§4.36). 0 의 뜻은 아직 모른다 — 그 표본은 지도에서만 봤다.


> 곁가지 — `grep -aoP` 로 설명을 뽑으려다 실패했다. 이 환경의 git-bash 에
> `grep -P` 가 없다. **그리고 문자열 인접으로 짝을 정하면 안 된다** — 풀에
> 섞여 있어 이름 바로 뒤가 그 설명이 아니다. 등록 루프를 디스어셈블해야 한다.

컴포넌트 쪽은 막혔다. `ClientSelfWantedActorComponent` 는 살아 있는 것이 하나
뿐이고 지금 **구역 벡터가 비어 있으며**(크기 0), `CommonWantedActorComponent`
는 살아 있는 인스턴스가 **없다**(후보 하나가 §4.33 의 낮은 주소 가짜).

> **정정 (2026-09-20)** — "커먼은 없다" 는 그때의 스냅숏이었다. 실제로 센 값은
> **서버 2 · 클라 2 · 커먼 1** 이고, 그중 낮은 주소는 객체가 아니라 등록표
> 행이다(위 §"진짜 컴포넌트와 등록표 행"). `ServerWantedActorComponent` 를
> 그때 안 세어 본 것이 두 벌을 못 본 원인이다.

```
+0x40 {ptr, 9, 41}   +0x50 {ptr, 14, 18}   +0x70 {ptr, 17, 18}
```

`CommonWantedActorComponent`(vtable RVA 0x5A9D460)도 따로 있다 — 아직 안 봤다.

#### 메시지도 인게임 미확인

- 벌금 **쓰기**(`+0x30` 에 직접)는 2026-09-18 에 확인됐다고 기록돼 있으나
  2944 에서 다시 재지 않았다.
- **수배 해제(`TrocTrClearWantedReq` 2837)·상태 변경(`…ChangeWantedStateReq`
  2983)이 먹는지는 모른다.** ID 는 런타임 해석값을 쓰고 로그도 맞는 값을
  찍지만(`메시지 ID 가 갈렸다` 경고 없음), 보내 본 적이 없다. 앞선 기록에
  **"`ClearWantedReq` 로는 안 지워진다 — 현행범 상태만 푼다"** 가 있으니
  그것부터 다시 재는 것이 맞다.

## 2. 게임에 대해 알아낸 것

### 2.1 PE 구조 (섹션 배치가 뒤섞여 있음 — 옛 빌드 기준. 2850 은 실행 섹션이 `.idata` 0x1000 · `.sbss` 0x7480000 둘뿐, `specs/2026-09-11-game-update-2850.md`)

| 이름 | RVA | VirtSize | RawSize | 속성 |
|---|---|---|---|---|
| `.rdata` | 0x00001000 | 0x0496B000 | 0x0496B000 | **XR** |
| `.text1` | 0x0496C000 | 0x014FC000 | 0x014FC000 | R |
| `.00cfg` | 0x05E68000 | 0x0083D000 | 0x00354000 | RW |
| `.sbss` | 0x06B32000 | 0x0EFEE910 | 0x0EFEEA00 | **XRW** |
| `.text` | 0x06959000 | 0x00003000 | 0x00003000 | R |

**실행 코드는 `.text` 가 아니라 `.rdata` 와 `.sbss` 에 있다.** 섹션
이름으로 코드 영역을 고르면 안 되고 `IMAGE_SCN_MEM_EXECUTE` 를 봐야
한다.

**뒤섞인 것은 배치이지 코드가 아니다.** 디스크 파일의 함수들이 그대로
디스어셈블된다 - 2026-09-03 에 확인했다. "Denuvo 라 못 본다" 고 두
세션을 보냈는데, 있는 도구(`tools/rtti/disasm.py`)를 대상에 겨누기만
하면 됐다. 자세한 것은 `specs/2026-09-03-static-analysis.md`.

VirtSize > RawSize 인 섹션(`.00cfg`)에서 RVA→파일오프셋 변환에
`max(VirtSize, RawSize)` 를 쓰면 raw 밖 주소가 엉뚱한 파일 위치로
매핑된다. RawSize 로 잘라야 한다.

### 2.2 출시 빌드에 남아 있는 개발자 흔적

**아직 안 판 광맥이다.** 렌더 디버그 옵션 UI 가 통째로 남아 있고,

### 2.2.1 디버그 콘솔 (2026-09-03 실험, 보류)

`PearlAbyssEngine.ShowDebugConsole` 액션은 출시 빌드에서도 **실제로
등록된다** (전역 `RVA 0x625B288` 이 살아 있고, 핸들러 노드가 힙에
있으며 컨텍스트는 `pa::WinAppLauncher`). 그러나 그 콜백은 마우스
커서를 보이고 상태 객체의 `+0x119` 를 세울 뿐 콘솔 UI 를 만들지
않는다. 콘솔 UI 컨트롤러 `UiDebugCommandConsole`(입력창 · 히스토리 ·
자동 완성 · 백틱 토글)은 클래스로 등록돼 있지만 **인스턴스가 0개**라
플래그를 읽는 코드가 없다. `+0x118/+0x119` 를 직접 써 봐도 소비되지
않았고 화면 변화도 없었다.

앞 문서의 전역 주소 `0x1465BB288` 은 오기다(`0x14625B288`). `+0x50`
도 콘솔 플래그가 아니라 커서 표시 여부다.

살리려면 `DebugConsole` 이름의 UI 페이지를 만드는 경로가 필요하다.
자세한 것은 `specs/2026-09-03-debug-console.md`.

### 2.3 게임이 필드 이름을 알려 준다 (2026-09-03)

데이터 역직렬화 함수가 필드마다 실패 메시지를 들고 있다 -
`"ItemInfo의 _maxEndurance를 읽어들이는데 실패했다."` 직전의
`lea rdx,[rsi+0x400]` 과 짝지으면 **이름 -> 오프셋 표**가 나온다.

```
python tools/rtti/fields.py <exe> ItemInfo
  _maxStackCount        +0x18     _itemType             +0xA3
  _itemTier             +0x210    _isDestoryWhenBroken  +0x1FC
  _SharpnessData        +0x2E8    _maxEndurance         +0x400
```

`ItemInfo` 109개를 뽑았고 오프셋이 겹치는 자리는 0이다. 이미
실측으로 알던 칸(`+0x18` 최대 스택, `+0xA3` 분류, `+0x210` 등급)과
전부 맞는다. 실패 메시지가 있는 클래스면 무엇이든 된다
(`EquipTypeInfo` 19개 등).

**내구도의 이름이 여기서 나왔다** - `_maxEndurance` 는 아이템 표
`+0x400` 의 u16 이고 **0xFFFF 면 내구도가 없는 아이템**이다.
`_isDestoryWhenBroken`(`+0x1FC`) 과 `_repairDataList`(`+0x408`) 도
같이 나왔다. 전체 표는 `specs/2026-09-03-field-names.md`.

문자열은 UTF-8 이다. 콘솔이 CP949 라 그냥 찍으면 깨져 보이는데,
그것을 파일 인코딩 문제로 잘못 읽은 적이 있다 - 터미널 코드페이지와
파일 인코딩은 다른 이야기다.

### 2.4 카메라 (미해결)

카메라 객체의 지역 변환은 **항등**이다 — 스케일 (1,1,1), 회전 항등,
위치 (0,0,0). 이미지 전수 조사에서도 그 칸에 쓰는 코드가 0곳이었다.
큰 오픈월드가 흔히 쓰는 카메라 상대 렌더링으로 보인다.

확인된 필드: 이름 `+0x48`, FOV `+0x9C`, 뷰포트 `+0x7C`/`+0x80`,
근접 `+0xB4`, 원거리 `+0xB8`, 활성 플래그 `+0xBC`, 렌더 뷰 `+0xE0`.
지역 변환은 `+0x50`(스케일) `+0x5C`(회전 쿼터니언) `+0x6C`(위치)이고
소유 컴포넌트는 `+0x10`, `PlayerCameraComponent+0x88` 은 활성 카메라의
내부 포인터(카메라+0x28)다 - camera.h 에 상수로 있던 것을 안 쓰여 여기로
옮겼다.

`PlayerCameraComponent+0x360` 은 `현재 = lerp(현재, 목표, t)` 로
갱신되는 좌표이고 `t` 는 `+0x35C` 다. 갱신 함수는 `0x140A58540` 이다.

`컴포넌트+0x328` 은 `PlayerCameraComponentScript` 를 가리키고, 그
객체는 0xA0 간격 블록 두 벌에 쿼터니언·월드 좌표·재기준 좌표 세 벌을
담는다.

**그런데 이 값들 어느 것도 렌더를 구동하지 않는다.** 전부 우리 값으로
고정해도 화면이 변하지 않았다. double 좌표는 메모리 전체에 0곳이다.
자세한 것은 3 을 볼 것.

## 3. 보류: 프리카메라

기능은 코드에 있으나 **설치하지 않는다**(`freecam.cpp` 의 `kDeferred`).
답을 못 찾은 기능이 게임 코드에 훅을 걸고 있을 이유가 없다.

### 시도했고 안 된 것

| 대상 | 결과 |
|---|---|
| `컴포넌트+0x360` (월드 좌표) | 우리 값 유지되나 화면 무반응 |
| 변환 객체 월드 `+0x8C` | 유지되나 무반응 |
| 변환 객체 재기준 `+0x08` / `+0xA8` | 유지되나 무반응 |
| 변환 객체 회전 `+0x38` / `+0xD8` | 유지되나 무반응 |
| double 좌표 | 메모리 11.9 GB 에 **0곳** |

### 다음에 볼 곳

카메라 객체 `+0xE0` 가 가리키는 **렌더 뷰 객체**. FOV·뷰포트·근평면을
들고 있는 카메라가 뷰 행렬을 넘기는 곳으로 가장 유력하다. 한 번
봤을 때는 변화가 0이었으나 **그때 게임이 멈춰 있었다** — 유효한
측정이 아니었다.

### 되풀이하지 말 것

**검증하지 않은 주소에 대량으로 쓰지 말 것.** 좌표와 일치하는 497곳에
한꺼번에 값을 밀어 넣었다가 게임이 죽었다. 예외는
`0xC0000005`, 접근 주소 `0x10` — **널 포인터 역참조**다. 후보 중에
좌표가 아니라 우연히 그 비트 패턴을 가진 포인터가 섞여 있었다.
이분법이 효율적이라는 것만 보고 첫 라운드부터 전부에 쓴 것이 잘못이다.

**오프셋을 매 프레임 다시 재지 말 것.** 재기준 좌표의 원점을 매 프레임
`재기준 - 월드` 로 구했는데, 같은 프레임에 월드를 우리 값으로 덮어쓰고
있었으므로 두 번째 프레임부터 오프셋이 폭주했다. 게임이 크래시 없이
정지했다. 원점은 켤 때 한 번만 구하면 된다.

## 4. 작업 규율 (실측으로 얻은 것)

- **화면을 확인하지 않고 "동작한다"고 말하지 말 것.** probe 로 값이
  되돌아오는 것을 보고 "카메라가 움직인다"고 했으나 틀렸다. 사용자가
  보내 준 화면 캡처 한 장이 방향을 바로잡았다.
- **한 빌드에 변경을 묶지 말 것.** 폰트 추가와 진단 계산을 함께 넣어
  크래시가 났을 때 이등분이 불가능했다.
- **NaN 을 먼저 거를 것.** `fabs(NaN - x) > eps` 는 거짓이라 비교만으로는
  전부 통과한다. `cmd_diff` 에서 겪고 주석까지 달았는데 `findvec3` 에서
  똑같이 당했다.
- **VEX 접두사 바이트 순서.** `C5 FB 11 87` 에서 `b[i-3]` 이 `0xFB`,
  `b[i-4]` 가 `0xC5` 다. 뒤집어 쓰면 AVX 저장을 전부 놓친다. 이 게임은
  AVX 로 컴파일돼 있어 float 저장 대부분이 VEX 다. 이 버그 하나가
  "0x360 에 쓰는 곳은 구조체 복사뿐"이라는 틀린 결론을 만들었다.
- **disp8 은 부호 있는 값이다.** 0x80 이상 오프셋은 disp32 로 인코딩된다.
- **테스트 통과를 확인한 뒤에 배포할 것.** 실패 2건을 놓친 채 배포한
  적이 있다.
- **`DllMain` 에서 스레드를 join 하지 말 것.** 로더 락 안에서 교착한다.

이 절은 요약이다. 실제로 겪은 문제 전체(크래시·멈춤·오진·도구·절차)는
`docs/TROUBLESHOOTING.md` 에 있다.

### 치트를 부를 때 반드시 지킬 것

**스레드.** 작업 함수 안쪽이 TLS 를 쓴다(`gs:[0x58] -> [0] -> [+0x250]`).
렌더 스레드에는 그 블록이 없어 널을 참조하고 죽는다. 요청을 걸어
두고 TLS 가 선 게임 스레드가 집어 간다.

**세션.** 서버 세션이어야 한다. 클라이언트 세션은
`[[[세션+0xA0]+0x68]+0x130]` 이 비어 처리기가 조용히 되돌아간다.

**세션 표.** 훅이 본 세션은 16칸짜리 표(`kSeenCap`)에 쌓인다. 월드에 한 번
들어가면 11칸이 차므로 **축출이 있어야 한다** - 없던 동안에는 인플레이스
저장/로드가 만든 살아 있는 세션이 표에 못 들어와 지급이 먹통이었다
(2026-09-10 해결). 칸은 언제든 다른 세션 것이 될 수 있으니 **세션은 칸
번호가 아니라 주소로 기억한다.**

고를 때는 `pick_drive_session()` 하나를 쓴다 - 서버 + **게이트 통과**. 새
기준을 만들지 말 것(그래서 세 번 깨졌다). 게이트만이 믿을 수 있는 생존
신호다: 로드 뒤 죽은 세션에 `session_looks_live` 는 "예" 를 주고 freshness 도
통과시킨다. 표가 의심스러우면 명령 파일에 `sessions` 를 넣어 그대로 찍는다
(읽기 전용). 자세히는 `specs/2026-09-10-session-table-saturation.md`.

**교착.** 게임 함수를 후킹 안에서 부르면 그 자리가 락을 쥐고 있을 때
자기 자신과 물린다 - 실측에서 게임 조작이 통째로 멈췄다. 중첩 금지 ·
한 번에 하나 · 2초 간격으로 줄였다. 완전한 해결은 아니다.

**프레임 경계 후보 둘 다 막다른 길이다 (2026-09-04 실측 확정).**
호출 스택에서 뽑은 두 후보가 모두 프레임 경계가 아니었다. 메시지
펌프(`0x2369170`)는 메시지 구동이라 유휴 시 안 돌고, 작업 실행
래퍼(`0xB1D2DE0`)는 스레드 풀 초기화라 시작 때 총 4회 뒤 정지했다.
한 번 뜬 스택의 프레임은 그 순간의 사슬이지 매 프레임 루프가 아니다 -
전제가 틀렸다. 별도의 깨끗한 경계를 찾으려면 게임 메인 로직 틱(세션
업데이트)을 직접 추적해야 한다(별도 과제, 급하지 않음 - 교착 재발
없음). 액터 조회 자리가 여전히 유일하게 확인된 실행 지점이고 지급이
1~3초에 안정적으로 된다.

**⚠️ 계측 훅이 지급을 막았다.** 펌프 훅이 `g_detour_depth` 를 건드려
지급의 실행 조건(액터 조회 `depth==1`)을 깼다. 조사 훅은 camera.cpp
에서 기본으로 껐다. 다시 켤 때는 계측 훅이 `g_detour_depth` 를
건드리지 않도록 먼저 고쳐야 한다. 자세한 것은
`specs/2026-09-04-frame-boundary.md`.

**구조체 크기.** `TrItemValue` 생성자가 `+0x1B4` 까지 쓴다. 0x100 으로
잡았다가 스택을 180바이트 넘겨 써서 게임이 나중에 죽었다. 호출이
정상 반환하고 SEH 도 안 걸렸는데 나중에 죽으면 그런 종류다.

### 6.1 인벤토리 식별자 (2026-09-02, 해결)

**인벤토리 레코드 `+0x08` 은 {u16 순번, u16 담금질} 이다.** 아랫
u16 이 `ItemInfoManager` 목록에서의 위치(0부터)이고 윗 u16 이
담금질이다. 담금질은 화면과 대조해 확인했다 - 바르그란 방패의
윗값이 3 이고 툴팁의 담금질 게이지가 10칸 중 3칸이었다. 같은
아이템이 윗값 0 인 인스턴스로도 있어 타입 속성이 아니다.

확정 근거는 실측 둘이다.

- 순번 5915 가 그로테반트 판금 투구이고, 같은 인벤토리의 5911 ·
  5912 · 5913 · 5914 가 그 세트의 갑옷 · 망토 · 장갑 · 신발이다.
  값이 좁은 대역에 몰려 있던 이유가 이것이다
- 대응표 레코드 6,810칸을 아이템 표와 전부 대조해 한 칸도 다르지
  않았다. 중복 0건, 표에 없는 키 0건

이제 `probe invlist` 가 인벤토리를 이름과 담금질까지 낸다.

```

주소를 안 주면 RTTI 로 찾아 내용이 있는 컴포넌트를 쓴다. 컨테이너는
`컴포넌트 +0x18` 의 포인터 배열을 따라간다 - 앞부분을 훑는 방식은

### 지급에 담금질을 실을 자리 (코드에 반영함)

`TrItemValue +0x0C` 가 u16 담금질이다. 작업 함수(RVA `0x26A2600`)가
아이템 키를 순번으로 바꾼 직후 그 칸을 읽고, 아이템 표의 상한
(`+0x250`)과 비교해 넘으면 거절한다.

```
0 <= TrItemValue+0x0C <= [아이템표+0x250] - 1
장비는 +0x250 = 11 이라 0..10 - 툴팁의 10칸 게이지와 같다
표 +0x42 가 0xFFFF 면 담금질이 없는 아이템이다 (재료 등)
```

**지금까지 지급이 담금질 0 인 장비만 준 이유도 이것이다.** 생성자는
`+0x08` 만 0 으로 만들고 `+0x0C` 는 건드리지 않는데, 버퍼가 0 으로
초기화되므로 0 인 채로 갔다. `fill_item_value` 가 이제 그 칸을 채운다.

상한은 아이템 표에서 읽어 `ItemCatalogEntry::max_temper` 로 들고 있다
(`[+0x250] - 1`, 상한 0 이면 담금질 없는 아이템).

> 이고, 단일 쓰기가 저장·재시작을 넘어 살아남는다** - 보석 박기(2026-09-06)
> 와 소켓 언락(2026-09-08, 열린 칸 0개짜리 장비를 5칸으로) 둘 다 실측했다.
>
> 당시 "게임이 되쓴다" 고 본 것은 **착용 장비** 쪽이었을 가능성이 크다.
> 착용 장비는 클라·서버 두 사본이 있어 한쪽만 쓰면 되돌아간다 - 그래서
> equip 경로는 both-realms 로 쓴다. 인벤토리 레코드에는 그 문제가 없다.
> 근거: `specs/2026-09-07-socket-grant-unlock-research.md` 9절.

그러므로 남은 것들은 **게임 자신의 경로**를 찾아야 한다.

### 레코드를 빈 칸으로 만들어 봤다 (안 된다)

지급분 미로숲의 한손검(ID 1000283, 칸 74)의 레코드 앞 10바이트를
빈 칸 표식으로 덮었다 - 인스턴스 ID 전부 0xFF, 순번 0xFFFF.

```
poke 0x...9D0 FFFFFFFFFFFFFFFFFFFF
  invlist    86개 -> 85개, 그 한 자루가 목록에서 사라짐
  컨테이너   표시 91 / 140 그대로 (사용 개수 +0x12 는 안 줄었다)
  화면       변화 없음. 가방에 두 자루 그대로
```

**게임이 되쓰지도 않았다.** 소켓 때는 몇 분 뒤 우리 값이 되돌아왔는데
이번엔 0xFF 가 그대로 남았다. 즉 이 배열은 **화면이 읽는 곳이 아니다** -
되쓰기조차 안 하는, 우리 도구만 보는 사본이다. 소켓 때보다 더 강한
증거다.

> ⚠️ **정정 (2026-09-08).** "이 배열은 화면이 읽는 곳이 아니다" 는 **틀렸다.**
> 같은 배열의 소켓 칸을 고치면 화면·스탯에 그대로 나오고 저장까지 넘어간다
> (실측: 열린 칸 0개짜리 검을 5칸으로 열어 재시작 뒤 확인). 여기서 안 먹은
> 것은 **"레코드를 빈 칸으로 만들기"** 라는 특정 조작이지 배열 자체가 아니다
> - 인스턴스 ID 를 0xFF 로 덮는 것은 게임이 칸을 비우는 방식이 아니었던
> 것으로 보인다. "아이템 하나를 지우는 길은 메모리 쓰기로는 없다" 는 결론은
> 그대로 유효하다.

원본 10바이트를 되돌려 두 자루 다 복구했다.

**그러므로 아이템 하나를 지우는 길은 메모리 쓰기로는 없다.** 남은 것은
게임 UI 의 버리기뿐이다. 치트 `TrocTrDeleteItemCheatReq`(ID 2503)는
인자가 (인벤토리 종류, 플래그)라 **가방 단위**이고, 개별 아이템을
고를 수 없다.

### 소켓 개수는 고칠 수 있다 (아이템 표 `+0x238`) — **기능으로 들어옴**

인스턴스가 아니라 **아이템 종류**의 값이고 툴팁의 원 개수와 맞는다
(한손 무기 3, 방패 2, 재료 0). 군주의 검을 3 -> 5 로 쓰고 가방을
다시 여니 원이 5개가 됐다.

```
probe poke <아이템표레코드 + 0x238> 05 00 00 00 05 00 00 00
```

**아이템 종류 전체에 걸리고, 5 를 넘기면 안 된다** - 인스턴스의 소켓
배열이 5칸이라 그보다 크면 배열 밖을 읽는다. 표는 메모리에만 있어
게임을 다시 켜면 원래대로 돌아온다.

2026-09-08 에 이것을 **부위별 기능**으로 만들었다(인벤토리 패널의
"소켓 상한"). 손으로 poke 할 일은 이제 없다.

- 부위 = **(분류 `+0xA3`, 장비타입 `+0x42`) 쌍**. 분류만으로는 갑옷(3:5)과
  망토(3:75)가 안 갈린다. 이 빌드의 장비 묶음은 **92개**(`probe items cats`).
- 설정 `socket_cap_parts = 3:5=5,24:4=5` 에 저장하면 표가 올라온 뒤 세션마다
  자동으로 걸린다(표는 매 실행 exe 에서 다시 읽히므로 세이브에 안 남는다).
- **표 상한이 정하는 것은 툴팁의 소켓 목록뿐이다.** 스탯 계산은 레코드의
  실제 소켓을 그대로 더한다 - 실측: 표 상한 3인 검에 3·3·3·1·1 을 박으니
  목록은 3줄인데 치명타 확률은 Lv.11(=합계)이었다. 그래서 모드를 빼도
  효과는 남고 표시만 줄어든다.
- 전문: `specs/2026-09-07-socket-grant-unlock-research.md` 5·9·10절.

### export (동작 확인)

```
probe invexport [파일]     기본 cdtoybox_export.txt
```

보관함(`Stash`) 형식을 그대로 쓴다. 옛 파일이 읽히도록 `item` 줄
뒤에 토큰만 덧붙였다.

```
item <키> <개수> [t<담금질>] [s<슬롯>:<보석키>:<원본12hex>]...

item 721506 5
item 200914 1 t1 s0:1002569:240DFFFF00FF s1:1002785:8E0CFFFF01FF
```

파일에는 순번이 아니라 **아이템 키**를 쓴다. 순번은 표에서의 위치라
게임이 패치되면 달라진다.

실측: 세트 6개 · 아이템 504개 · 박힌 소켓 6개 · 담금질 14개.

기본 파일은 덮어쓰지만 **경로를 직접 주면 이미 있을 때 거절**한다 -
모드의 `cdtoybox_stash.txt` 를 가리켰다가 세트를 날리는 일을 막는다.

소켓도 같이 낸다. 가방 503개 중 박힌 것은 6개였다.

```
[ 54] 순번 6438 담금질 1  키 200914  군주의 검
      소켓[0] 순번 3364  키 1002569  바람 가르기  (24 0D FF FF 00 FF)
      소켓[1] 순번 3214  키 1002785  파괴 I       (8E 0C FF FF 01 FF)
```

값으로 레코드를 집을 때는 `probe invfind` 를 쓴다.

```
probe invfind 202529:1    # {순번 5921, 담금질 3} 을 든 레코드
```

전역(`RVA 0x6331358`)은 박아 두지 않고 변환 함수 본문 패턴으로
찾는다. 현지화와 달리 **한 곳만 일치하지 않는다 - 34곳이다.** 후보를
전부 모아 표의 개수가 6,810 인 것을 고른다. 자세한 것은
`specs/2026-09-02-inventory.md`.

### 지급이 무엇을 싣는가 (2026-09-03, 전부 화면 확인)

`TrItemValue` -> 레코드 변환 함수(RVA `0x2094050`)가 무엇을 옮기는지가
전부다. 근거는 `specs/2026-09-03-static-analysis.md`.

| 레코드 | <- | TrItemValue | 지금 |
|---|---|---|---|
| `+0x0A` 담금질 | | `+0x0C` u16 | **싣는다** (표 `max_temper` 로 자름) |
| `+0x60` 소켓 5칸 | | `+0x40`..`+0x5D` (6바이트 x 5) | **싣는다** |
| `+0x70` 소켓 개수 | | `+0x5E` u8 | **싣는다** (표 `+0x238` 로 자름) |
| `+0x40` 현재 내구도 | | `+0x2A` u16 | **싣는다** (표 `_maxEndurance` 로 자름) |
| `+0x58` 예리도 | | `+0x1AE` i16 (표 `+0x2E8` 로 자름) | 안 채운다 |
| `+0x28` / `+0x2C` | | `+0x134` / `+0x130` u32 | 안 채운다 |

세 가지가 **지급 패널과 보관함 양쪽**에서 되고, export/import 로도
왕복한다.

```
지급 패널   담금질 · 소켓을 골라서 지급 (보석은 분류 74 에서 검색)
보관함      "지금 고른 아이템 담기" 가 담금질 · 소켓까지 담는다
파일 형식   item <키> <개수> [t<담금질>] [e<내구도>] [s<슬롯>:<키>:<12hex>]
```

실측 확인:

```
군주의 검     담금질 10 + 보석 3개    공격력 30 +18, 판매가 127.38
미로숲 한손검  e12 -> 12/30            공격력 22 -12 (닳은 만큼 벌점)
타리브 천 장갑 소켓 2 (태산 II · 철벽 II)  원본과 같은 바이트
```

소켓 6바이트는 **보석 키에서 지급 시점에 다시 조립한다**
(`make_socket_bytes`). 첫 u16 이 아이템 표에서의 순번이라 파일에 든
원본 바이트를 그대로 쓰면 그 파일을 만든 빌드에 묶인다.

### 악세서리의 초록 줄은 담금질 효과다 (2026-09-03 실측)

툴팁의 `용기 : 1 초마다 0.3 회복` 같은 줄이 어디서 오는지 찾았다.
**별도 기전이 아니라 담금질이다.**

```
백사자 목걸이 담금질 0    공격력 0 -5   치명타 Lv.0   판매가 9.50     줄 없음
백사자 목걸이 담금질 10   공격력 5      치명타 Lv.4   판매가 165.69   줄 있음
```

**같은 아이템이고 담금질만 다르다.** 담금질 10 으로 지급한 것이
장착 중인 원본과 완전히 같아진다. 공격력 · 치명타 · 판매가도 전부
같은 원인이다.

어떤 효과가 붙는지는 아이템 표의 `_enchantDataList`(`+0x248`, 개수
`+0x250`)가 정하고, `EnchantData` 안에 `_enchantStatData` ·
`_equipBuffs` 가 있다.

**그러므로 "악세서리의 능력을 다른 장비에" 는 그 장비의
`_enchantDataList` 를 바꾸는 일이다.** 아이템 표 수정이라 종류
전체에 걸리고 게임을 끄면 사라진다 - 소켓 개수(`+0x238`)와 같은
성질이다. 아직 안 해 봤다.

### 오버레이 UI/UX 리뷰 (2026-09-03, 화면 확인 전)

창이 여섯 개로 늘어난 뒤 처음 훑었다. 6건 나왔고 전부 고쳤다.

| | 영향 | 무엇이 문제였나 |
|---|---|---|
| F1 | High | 창을 닫을 수 없었다 - `Begin` 에 `p_open` 을 안 넘겼다 |
| F2 | High | 무슨 창이 있는지 알 방법이 없었다 |
| F3 | Medium | 본창 이름이 `CDToybox — 0단계` 로 낡아 있었다 |
| F4 | Medium | 본창의 내용이 FPS + 개발 진단뿐이었다 |
| F5 | Medium | 지급 창에 개발 실험 "내구도 (뜻 확인 중)" 가 남아 있었다 |
| F6 | Polish | 첫 실행에 여섯 창이 같은 자리에 겹쳤다 |

F1 과 F2 는 한 쌍이다. **닫는 길을 만들면 다시 여는 길이 반드시
있어야 한다.** 그래서 본창을 창 목록으로 바꾸고(체크박스 5개) 본창
자신은 닫히지 않게 두었다. 카메라 분석은 개발 진단이라 기본 꺼짐이다.

F5 는 인자 두 칸의 뜻을 모르던 때 값을 바꿔 눌러 보려고 만든 것이다.
이제 뜻을 안다(슬롯 번호, 개수). 치트 자체는 남겨 두었다.

- **C. 소켓: 장기 영향 미측정.** 표 상한을 올린 채 저장하고 **모드 없이**
  오래 굴렸을 때 게임이 칸 수를 정리하는지 모른다. 한 번의 저장·로드로는
  아무 일도 없었다. 아끼는 세이브는 백업 권장.

1. **"수리 불가" 뱃지.** 아직 모른다. **인스턴스 단위인 것은
   확인됐다** - 같은 백사자 목걸이인데 담금질 0 짜리에는 안 붙고
   담금질 10 지급분에는 붙는다. "아이템 종류의 성질" 이라던 앞선
   짐작은 이것으로 반증됐다.

   다만 그 둘은 담금질 말고도 다르다(갓 지급한 쪽은 `+0x2C` ·
   `+0x38` · `+0x40` 이 아직 0 이다). 원인을 하나로 못 좁혔다. 표에
   **수리 데이터를 가진 종류가 0 / 6,810** 이라(내구도 100 짜리조차
   비어 있다) 이 빌드에서는 무엇도 수리할 수 없어 보인다.
   `_maxEndurance` 로 갈린다는 가설도 틀렸다 - 내구도 30 짜리에도
   붙었다.

   **다음 수:** 저장 · 재시작을 한 바퀴 돌린 뒤 같은 담금질 10 짜리를
   다시 보면 `+0x2C` · `+0x38` · `+0x40` 이 채워진다. 그때도 뱃지가
   남아 있으면 담금질이 원인이고, 사라지면 "갓 지급" 이 원인이다.
   대조군 문제 없이 갈린다.
2. **`_enchantDataList` 옮겨 붙이기.** 악세서리의 초록 줄이 담금질
   효과라는 것까지 왔다. 한 아이템의 효과 목록을 다른 아이템에
   얹으려면 표를 고쳐야 하는데, 표는 게임이 되쓰지 않는 정적 데이터로
   보인다. 아직 안 건드렸다.
3. **레코드 `+0xA8` 의 `{원소 재료, 스탯}` 목록.** 자리는 알지만
   아무것도 이걸 쓰지 않는다. 뜻 미상.
