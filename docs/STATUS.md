## 1. 되는 것

### 1.1 인게임 오버레이 (완료, 안정)

`xinput1_4.dll` 프록시로 주입하고 D3D12 스왑체인에 ImGui 를 얹는다.
한글이 정상 표시되고(맑은 고딕), Insert 로 켜고 F10 으로 비활성화한다.
비활성화 뒤 다시 켜는 것도 된다.

성능은 실측 63 FPS 유지, 예외 0회, 해체·재초기화 14회 반복 통과.

**주입 경로:** `dinput8.dll` 은 이 게임의 임포트 테이블(92개 DLL)에
없다. `xinput1_4.dll` 이 있고 ordinal 2·3 을 쓴다. 그래서 그것을
프록시한다.

**D3D12 훅에서 반드시 지킬 것 두 가지.** 둘 다 실측으로 배웠다.

1. 커맨드 큐를 `ExecuteCommandLists` 에서 추측하면 안 된다. 실행마다
   다른 큐가 잡혔다(0x8e2ba10 / 0x120a26d0 / 0x52e67800 / 0x8bd0e30).
   NVIDIA Streamline 문서도 이를 금지한다. `CreateSwapChain`(vtbl 10)과
   `CreateSwapChainForHwnd`(vtbl 15)를 후킹해 (큐, 스왑체인) 쌍을
   확정적으로 얻는다.
2. 펜스 동기화 없이는 안 된다. 프레임 컨텍스트마다 fence_value 를 두고,
   `allocator->Reset()` 전에 대기하고 `ExecuteCommandLists` 뒤에
   `Signal` 한다. 리소스 해제 전에는 전부 대기한다. 이걸 빠뜨리면
   런타임이 "drop the call and remove the device" 한다.

이 두 가지를 빠뜨려 0xC0000005 로 죽었고, 원인을 찾는 데 시간이 걸렸다.
당시 변경 두 개를 한 빌드에 묶어 이등분이 불가능했던 것이 화근이었다.

### 1.2 RTTI 객체 탐색 (완료, 신뢰 가능)

MSVC x64 RTTI 를 따라 클래스 이름에서 살아있는 인스턴스까지 내려간다.
사람이 값을 바꿔 줄 필요가 없는 결정론적 탐색이라, 모드가 실행될 때마다
스스로 객체를 찾는다.

게임에는 RTTI 클래스 **14,901개**, 그중 `pa` 네임스페이스가 **5,025개**
있다. (초기에 468개로 잘못 셌다. 정규식이 네임스페이스·템플릿이 붙은
이름을 제외해 Havok 것만 남았던 것이다.)

카메라 객체 지도를 이것만으로 특정했다:

| 클래스 | 역할 |
|---|---|
| `pa::CameraManager` | 카메라 보유 |
| `pa::FreeCamCamera` | 개발자 프리카메라. **할당돼 있으나 비활성** |
| `pa::PhotoCamera` | 포토 카메라 |
| `pa::PlayerCameraComponent` | 플레이어 카메라 컴포넌트 |
| `pa::PlayerCameraComponentScript` | 스크립트 계층 |

**후보를 고를 때 가장 작은 주소를 쓰면 안 된다.** vtable 값을 우연히
담은 메모리가 가짜 후보로 잡히고, 그게 진짜보다 낮은 주소면 그것을
집는다. 실측에서 11회 연속 어긋났다. 카메라는 `+0x48` 에 자기 이름을
들고 있으므로(SSO, `+0x18` 에 인라인) 그것으로 검증한다.

### 1.3 함수 후킹 (완료, 실증)

MinHook 으로 게임 함수를 후킹했다. 대상은 바이트 패턴으로 찾는다 —
RVA 를 박으면 게임이 갱신될 때마다 깨진다.

카메라 좌표 갱신 함수 `0x140A58540` 에 걸어 **108,000회 호출 동안
안정**했다. Denuvo 무결성 검사에 걸리지 않았다.

**패턴 찾기 절차:** 저장 명령 22바이트로 위치를 잡고(실행 섹션 전체에서
한 곳만 일치하는 것을 확인), 거기서 `CC CC CC` 패딩까지 거슬러 함수
시작을 구한 뒤 프롤로그(`48 8B C4`)로 검증한다.

**인자 규약은 디스어셈블로 확인한다.** 이 함수는 RDX/R8/R9 를 읽기
전에 전부 덮어쓰고 XMM1 만 읽으므로 `void __fastcall f(컴포넌트*, float)`
가 정확하다. 추측하지 않았다.

`MH_CreateHook` 이 코드 9(트램폴린 메모리 할당 실패)로 3회 실패한 뒤
4회째에 성공한 적이 있다. 재시도 로직이 필요하다.

### 1.4 외부 분석 도구 `cdtb_probe` (완료)

게임에 붙어 메모리를 읽는 명령줄 도구. **인게임 UI 가 아니라 명령줄인
이유는 이 작업의 조작자가 사람이 아니라 에이전트이기 때문이다.**
반복 실행할 수 있어야 값을 찾는 일을 자율적으로 한다.

| 명령 | 용도 |
|---|---|
| `info` `regions` | 프로세스·메모리 요약 |
| `types` `vtable` `instances` `objects` `whatis` | RTTI 탐색 |
| `dump` `floats` | 메모리 덤프 |
| `diff` | 시간차로 변하는 float 슬롯 |
| `setf` | float 쓰기 |
| `camera` | 모드와 **같은 탐색 코드**를 돌린다 (배포 전 검증용) |
| `findvec3` / `findvec3d` | 좌표와 일치하는 float3 / double3 |
| `findmat` | 좌표 근처의 정규직교 4x4 |
| `findquat` | 시점을 돌리는 동안 변하는 단위 쿼터니언 |
| `hold` / `holdmany` | 값을 눌러 써서 화면 반응을 본다 |
| `dumpimage` | 실행 중 프로세스의 이미지를 PE 로 뜬다 |
| `loc` | 현지화 표를 읽어 이름을 푼다 (1.6) |
| `items` | 아이템 표를 키+이름으로 나열·검색 (1.7). 모드와 **같은 목록 함수**를 돌린다 |

`camera` 가 모드와 같은 코드를 돌리는 것이 중요하다. 배포하기 전에
탐색 결과를 확인할 수 있다.

### 1.5 하드웨어 브레이크포인트 (구현 완료, 이 게임에는 부적합)

디버그 레지스터 4개(DR0~DR3)를 동시에 걸어 "누가 이 주소에 쓰는가"를
찾는다. 자체 테스트 8종 통과.

**이 게임에서는 쓸 수 없다.** 보호 코드가 250ms 마다 121개 스레드 중
약 47개의 디버그 레지스터를 지운다(한 창에서 2,274회 다시 걸었다).
어떤 값은 잡히고 어떤 값은 영원히 히트 0으로 보여 결과를 신뢰할 수
없다. 자동 분석 경로에서는 뺐고 클래스와 테스트는 남겼다 — 보호가
없는 대상에는 여전히 유효하다.

**자체 테스트가 링크 배치에 민감하다 (미해결).** 2026-09-01, 무관한
소스 파일을 테스트 대상에 더했더니 `watchpoint_shutdown_is_idempotent`
가 `0xC0000005` 로 죽었다 — 4회 연속 재현. 그 파일을 빼면 통과하고,
전체 재링크로 배치가 바뀌자 다시 통과했다(6회 연속). 즉 코드 논리가
아니라 `g_target` 이 어디 놓이느냐에 달려 있다.

`on_exception` 의 주석이 이 실패 모양을 이미 적어 두었다 — 처리되지
않은 단일 스텝 예외로 프로세스가 죽는 경우. `shutdown()` 이 핸들러를
떼는 것과 낙오 스레드의 예외가 겹치는 창이 의심된다. **지금은 나타나지
않을 뿐 고쳐진 것이 아니다.** 워치포인트를 다시 쓸 일이 생기면 여기서
시작할 것.

### 1.6 현지화 조회 (완료, 실측)

게임의 현지화 표를 **읽기만으로** 걸어 이름을 푼다. 게임의 조회 함수는
부르지 않는다 — 그 함수는 잠금을 잡고 못 찾은 키의 항목을 표에 끼워
넣는다.

```
$ cdtb_probe loc item 2200
  필드 0x70  키 9448928051312 :  [카테고리 7] '편전'
  필드 0x71  ...              :  '일반 화살보다 짧고 날렵한 형태로 ...'
```

키는 `(엔티티키 << 32) | 필드번호` 이고 0x70 이 이름, 0x71 이 설명이다.
문자열 풀은 11.9 MB 한 덩어리이고 이름은 `풀기준 + 오프셋` 이다.

전역 주소는 박지 않는다. `LocalizationStringBase::str()` 본문 28바이트가
이미지 전체에서 한 곳만 일치하고, 그 disp32 가 곧 전역이다.

자세한 것은 `specs/2026-09-01-localization-lookup.md`.

### 1.7 아이템 표 (완료, 실측)

`pa::ItemInfoManager` 를 RTTI 로 찾아 레코드 포인터 배열을 걷는다.
**6,810개 중 6,738개(98.9%)의 이름이 풀린다.**

```
$ cdtb_probe items find 비약
  1000028   프레야의 하급 비약
  1000030   아프로니아의 하급 비약
  1000034   멜리아라의 하급 비약
```

이름 키는 조립하지 않는다. 레코드 `+0x28` 이 게임 자신의 64비트
현지화 키를 들고 있다.

후보를 그대로 믿지 않는다 — 색인 표의 첫 키와 첫 레코드의 키가 같은지
보고, 개수가 터무니없으면(0 이거나 2^20 초과) 거부한다.

**argv 는 시스템 ANSI 코드페이지로 온다**(이 기계 ACP 949). 게임
문자열은 UTF-8 이라 그대로 비교하면 한글이 절대 맞지 않는다. probe 의
검색은 비교 전에 UTF-8 로 옮긴다. 오버레이는 ImGui 입력도 UTF-8 이라
변환이 필요 없다.

### 1.9 탈것·캐릭터 카탈로그 뷰어 (완료, 화면 확인 2026-09-04)

`VehicleInfoManager`·`CharacterInfoManager` 를 아이템과 같은
`StaticInfoManager2` 컨테이너로 읽어 오버레이 "탈것·용병·캐릭터" 창에
낸다. 화면 확인했다 - 탈것 34개(Dragon·Wolf·Wyvern…), 캐릭터
7251개(Kliff=1·Damian=4…)가 키·**내부 이름**과 함께 뜬다. FPS 62.5,
예외 0.

레코드 구조가 아이템과 다르다: 키가 u16(record +0x00), 이름은
`_stringKey`(+0x08)가 가리키는 엔진 문자열 객체(+0x00 char*, +0x08
길이)의 **내부 이름**이다(한글 표시명 아님 - 현지화 경로가 달라
Tier 1b). **용병은 키가 +0x00 이 아니고 색인이 정렬/해시라 아직 못
읽는다**(Tier 1b). 자세한 것은
`specs/2026-09-04-vehicle-pet-review.md`. probe 검증: `probe roster`.

### 1.8 인게임 아이템 목록 (완료, 화면 확인)

오버레이에 "아이템 목록" 패널. 검색창 + 목록, 줄을 누르면 키가
클립보드로 간다. **쓰는 버튼은 없다** - 지급 경로를 아직 안 팠다.

화면에서 확인했다. 한글 정상, **70.0 FPS**, 경고·오류 0건.

```
[12:01:18.992] INFO  아이템 표: 6810개, 이름 풀린 것 6738개
```

프레임마다 게임 메모리를 읽지 않는다. 배경 분석 루프가 만들어 둔
목록을 걸러 보여주기만 하고, 6,810줄 중 보이는 줄만 그린다
(`ImGuiListClipper`).

**배경 루프에 얹었다.** 그 루프가 이미 350MB 이미지를 읽고 힙을
훑고 있어, 두 번 할 이유가 없다.

**모드는 자기 프로세스를 읽는다.** 잘못된 포인터 하나가 게임을
죽이는데, 읽기는 전부 `mem::Reader` 를 거치고 `LocalReader::read` 는
`safe_read_bytes`(SEH) 라 크래시 대신 false 다.

자세한 것은 `specs/2026-09-01-item-table.md`.

## 2. 게임에 대해 알아낸 것

### 2.1 PE 구조 (섹션 배치가 뒤섞여 있음)

| 이름 | RVA | VirtSize | RawSize | 속성 |
|---|---|---|---|---|
| `.rdata` | 0x00001000 | 0x0496B000 | 0x0496B000 | **XR** |
| `.text1` | 0x0496C000 | 0x014FC000 | 0x014FC000 | R |
| `.00cfg` | 0x05E68000 | 0x0083D000 | 0x00354000 | RW |
| `.sbss` | 0x06B32000 | 0x0EFEE910 | 0x0EFEEA00 | **XRW** |
| `.text` | 0x06959000 | 0x00003000 | 0x00003000 | R |

**실행 코드는 `.text` 가 아니라 `.rdata` 와 `.sbss` 에 있다.** 섹션
이름으로 코드 영역을 고르면 안 되고 `IMAGE_SCN_MEM_EXECUTE` 를 봐야
한다.

**뒤섞인 것은 배치이지 코드가 아니다.** 디스크 파일의 함수들이 그대로
디스어셈블된다 - 2026-09-03 에 확인했다. "Denuvo 라 못 본다" 고 두
세션을 보냈는데, 있는 도구(`tools/rtti/disasm.py`)를 대상에 겨누기만
하면 됐다. 자세한 것은 `specs/2026-09-03-static-analysis.md`.

VirtSize > RawSize 인 섹션(`.00cfg`)에서 RVA→파일오프셋 변환에
`max(VirtSize, RawSize)` 를 쓰면 raw 밖 주소가 엉뚱한 파일 위치로
매핑된다. RawSize 로 잘라야 한다.

### 2.2 출시 빌드에 남아 있는 개발자 흔적

| 문자열 | 뜻 |
|---|---|
| `eErrNoFreeCamModeEnabled` | 프리캠 모드 게이트가 존재 |
| `FREECAM_MODE_ACTION_XXX` | 액션 상태 이름 |
| `_debugCameraState` / `debugCameraState` | 리플렉션 필드/표시 이름 |
| `showEngineOption`, `B: Debug Information` | 엔진 디버그 옵션 UI |
| `_renderCollisionGeometry`, `_viewMode` 등 수십 개 | 렌더 디버그 옵션 |

리플렉션 시스템도 있다 — `ReflectMetaObjectBind`,
`ReflectObjectPropertyBind`, `EnumReflectPropertyBind`,
`PascriptComponentProperty_TYPE`.

**아직 안 판 광맥이다.** 렌더 디버그 옵션 UI 가 통째로 남아 있고,
그 옵션들은 `.00cfg` 의 런타임 전역에 매달려 있다.

### 2.2.1 디버그 콘솔 (2026-09-03 실험, 보류)

`PearlAbyssEngine.ShowDebugConsole` 액션은 출시 빌드에서도 **실제로
등록된다** (전역 `RVA 0x625B288` 이 살아 있고, 핸들러 노드가 힙에
있으며 컨텍스트는 `pa::WinAppLauncher`). 그러나 그 콜백은 마우스
커서를 보이고 상태 객체의 `+0x119` 를 세울 뿐 콘솔 UI 를 만들지
않는다. 콘솔 UI 컨트롤러 `UiDebugCommandConsole`(입력창 · 히스토리 ·
자동 완성 · 백틱 토글)은 클래스로 등록돼 있지만 **인스턴스가 0개**라
플래그를 읽는 코드가 없다. `+0x118/+0x119` 를 직접 써 봐도 소비되지
않았고 화면 변화도 없었다.

앞 문서의 전역 주소 `0x1465BB288` 은 오기다(`0x14625B288`). `+0x50`
도 콘솔 플래그가 아니라 커서 표시 여부다.

살리려면 `DebugConsole` 이름의 UI 페이지를 만드는 경로가 필요하다.
자세한 것은 `specs/2026-09-03-debug-console.md`.

### 2.3 게임이 필드 이름을 알려 준다 (2026-09-03)

데이터 역직렬화 함수가 필드마다 실패 메시지를 들고 있다 -
`"ItemInfo의 _maxEndurance를 읽어들이는데 실패했다."` 직전의
`lea rdx,[rsi+0x400]` 과 짝지으면 **이름 -> 오프셋 표**가 나온다.

```
python tools/rtti/fields.py <exe> ItemInfo
  _maxStackCount        +0x18     _itemType             +0xA3
  _itemTier             +0x210    _isDestoryWhenBroken  +0x1FC
  _SharpnessData        +0x2E8    _maxEndurance         +0x400
```

`ItemInfo` 109개를 뽑았고 오프셋이 겹치는 자리는 0이다. 이미
실측으로 알던 칸(`+0x18` 최대 스택, `+0xA3` 분류, `+0x210` 등급)과
전부 맞는다. 실패 메시지가 있는 클래스면 무엇이든 된다
(`EquipTypeInfo` 19개 등).

**내구도의 이름이 여기서 나왔다** - `_maxEndurance` 는 아이템 표
`+0x400` 의 u16 이고 **0xFFFF 면 내구도가 없는 아이템**이다.
`_isDestoryWhenBroken`(`+0x1FC`) 과 `_repairDataList`(`+0x408`) 도
같이 나왔다. 전체 표는 `specs/2026-09-03-field-names.md`.

문자열은 UTF-8 이다. 콘솔이 CP949 라 그냥 찍으면 깨져 보이는데,
그것을 파일 인코딩 문제로 잘못 읽은 적이 있다 - 터미널 코드페이지와
파일 인코딩은 다른 이야기다.

### 2.4 카메라 (미해결)

카메라 객체의 지역 변환은 **항등**이다 — 스케일 (1,1,1), 회전 항등,
위치 (0,0,0). 이미지 전수 조사에서도 그 칸에 쓰는 코드가 0곳이었다.
큰 오픈월드가 흔히 쓰는 카메라 상대 렌더링으로 보인다.

확인된 필드: 이름 `+0x48`, FOV `+0x9C`, 뷰포트 `+0x7C`/`+0x80`,
근접 `+0xB4`, 원거리 `+0xB8`, 활성 플래그 `+0xBC`, 렌더 뷰 `+0xE0`.

`PlayerCameraComponent+0x360` 은 `현재 = lerp(현재, 목표, t)` 로
갱신되는 좌표이고 `t` 는 `+0x35C` 다. 갱신 함수는 `0x140A58540` 이다.

`컴포넌트+0x328` 은 `PlayerCameraComponentScript` 를 가리키고, 그
객체는 0xA0 간격 블록 두 벌에 쿼터니언·월드 좌표·재기준 좌표 세 벌을
담는다.

**그런데 이 값들 어느 것도 렌더를 구동하지 않는다.** 전부 우리 값으로
고정해도 화면이 변하지 않았다. double 좌표는 메모리 전체에 0곳이다.
자세한 것은 3 을 볼 것.

## 3. 보류: 프리카메라

기능은 코드에 있으나 **설치하지 않는다**(`freecam.cpp` 의 `kDeferred`).
답을 못 찾은 기능이 게임 코드에 훅을 걸고 있을 이유가 없다.

### 시도했고 안 된 것

| 대상 | 결과 |
|---|---|
| `컴포넌트+0x360` (월드 좌표) | 우리 값 유지되나 화면 무반응 |
| 변환 객체 월드 `+0x8C` | 유지되나 무반응 |
| 변환 객체 재기준 `+0x08` / `+0xA8` | 유지되나 무반응 |
| 변환 객체 회전 `+0x38` / `+0xD8` | 유지되나 무반응 |
| double 좌표 | 메모리 11.9 GB 에 **0곳** |

### 다음에 볼 곳

카메라 객체 `+0xE0` 가 가리키는 **렌더 뷰 객체**. FOV·뷰포트·근평면을
들고 있는 카메라가 뷰 행렬을 넘기는 곳으로 가장 유력하다. 한 번
봤을 때는 변화가 0이었으나 **그때 게임이 멈춰 있었다** — 유효한
측정이 아니었다.

### 되풀이하지 말 것

**검증하지 않은 주소에 대량으로 쓰지 말 것.** 좌표와 일치하는 497곳에
한꺼번에 값을 밀어 넣었다가 게임이 죽었다. 예외는
`0xC0000005`, 접근 주소 `0x10` — **널 포인터 역참조**다. 후보 중에
좌표가 아니라 우연히 그 비트 패턴을 가진 포인터가 섞여 있었다.
이분법이 효율적이라는 것만 보고 첫 라운드부터 전부에 쓴 것이 잘못이다.

**오프셋을 매 프레임 다시 재지 말 것.** 재기준 좌표의 원점을 매 프레임
`재기준 - 월드` 로 구했는데, 같은 프레임에 월드를 우리 값으로 덮어쓰고
있었으므로 두 번째 프레임부터 오프셋이 폭주했다. 게임이 크래시 없이
정지했다. 원점은 켤 때 한 번만 구하면 된다.

## 4. 작업 규율 (실측으로 얻은 것)

- **화면을 확인하지 않고 "동작한다"고 말하지 말 것.** probe 로 값이
  되돌아오는 것을 보고 "카메라가 움직인다"고 했으나 틀렸다. 사용자가
  보내 준 화면 캡처 한 장이 방향을 바로잡았다.
- **한 빌드에 변경을 묶지 말 것.** 폰트 추가와 진단 계산을 함께 넣어
  크래시가 났을 때 이등분이 불가능했다.
- **NaN 을 먼저 거를 것.** `fabs(NaN - x) > eps` 는 거짓이라 비교만으로는
  전부 통과한다. `cmd_diff` 에서 겪고 주석까지 달았는데 `findvec3` 에서
  똑같이 당했다.
- **VEX 접두사 바이트 순서.** `C5 FB 11 87` 에서 `b[i-3]` 이 `0xFB`,
  `b[i-4]` 가 `0xC5` 다. 뒤집어 쓰면 AVX 저장을 전부 놓친다. 이 게임은
  AVX 로 컴파일돼 있어 float 저장 대부분이 VEX 다. 이 버그 하나가
  "0x360 에 쓰는 곳은 구조체 복사뿐"이라는 틀린 결론을 만들었다.
- **disp8 은 부호 있는 값이다.** 0x80 이상 오프셋은 disp32 로 인코딩된다.
- **테스트 통과를 확인한 뒤에 배포할 것.** 실패 2건을 놓친 채 배포한
  적이 있다.
- **`DllMain` 에서 스레드를 join 하지 말 것.** 로더 락 안에서 교착한다.

### 치트를 부를 때 반드시 지킬 것

**스레드.** 작업 함수 안쪽이 TLS 를 쓴다(`gs:[0x58] -> [0] -> [+0x250]`).
렌더 스레드에는 그 블록이 없어 널을 참조하고 죽는다. 요청을 걸어
두고 TLS 가 선 게임 스레드가 집어 간다.

**세션.** 서버 세션이어야 한다. 클라이언트 세션은
`[[[세션+0xA0]+0x68]+0x130]` 이 비어 처리기가 조용히 되돌아간다.

**교착.** 게임 함수를 후킹 안에서 부르면 그 자리가 락을 쥐고 있을 때
자기 자신과 물린다 - 실측에서 게임 조작이 통째로 멈췄다. 중첩 금지 ·
한 번에 하나 · 2초 간격으로 줄였다. 완전한 해결은 아니다.

**프레임 경계 후보 둘 다 막다른 길이다 (2026-09-04 실측 확정).**
호출 스택에서 뽑은 두 후보가 모두 프레임 경계가 아니었다. 메시지
펌프(`0x2369170`)는 메시지 구동이라 유휴 시 안 돌고, 작업 실행
래퍼(`0xB1D2DE0`)는 스레드 풀 초기화라 시작 때 총 4회 뒤 정지했다.
한 번 뜬 스택의 프레임은 그 순간의 사슬이지 매 프레임 루프가 아니다 -
전제가 틀렸다. 별도의 깨끗한 경계를 찾으려면 게임 메인 로직 틱(세션
업데이트)을 직접 추적해야 한다(별도 과제, 급하지 않음 - 교착 재발
없음). 액터 조회 자리가 여전히 유일하게 확인된 실행 지점이고 지급이
1~3초에 안정적으로 된다.

**⚠️ 계측 훅이 지급을 막았다.** 펌프 훅이 `g_detour_depth` 를 건드려
지급의 실행 조건(액터 조회 `depth==1`)을 깼다. 조사 훅은 camera.cpp
에서 기본으로 껐다. 다시 켤 때는 계측 훅이 `g_detour_depth` 를
건드리지 않도록 먼저 고쳐야 한다. 자세한 것은
`specs/2026-09-04-frame-boundary.md`.

**구조체 크기.** `TrItemValue` 생성자가 `+0x1B4` 까지 쓴다. 0x100 으로
잡았다가 스택을 180바이트 넘겨 써서 게임이 나중에 죽었다. 호출이
정상 반환하고 SEH 도 안 걸렸는데 나중에 죽으면 그런 종류다.

### 6.1 인벤토리 식별자 (2026-09-02, 해결)

**인벤토리 레코드 `+0x08` 은 {u16 순번, u16 담금질} 이다.** 아랫
u16 이 `ItemInfoManager` 목록에서의 위치(0부터)이고 윗 u16 이
담금질이다. 담금질은 화면과 대조해 확인했다 - 바르그란 방패의
윗값이 3 이고 툴팁의 담금질 게이지가 10칸 중 3칸이었다. 같은
아이템이 윗값 0 인 인스턴스로도 있어 타입 속성이 아니다.

확정 근거는 실측 둘이다.

- 순번 5915 가 그로테반트 판금 투구이고, 같은 인벤토리의 5911 ·
  5912 · 5913 · 5914 가 그 세트의 갑옷 · 망토 · 장갑 · 신발이다.
  값이 좁은 대역에 몰려 있던 이유가 이것이다
- 대응표 레코드 6,810칸을 아이템 표와 전부 대조해 한 칸도 다르지
  않았다. 중복 0건, 표에 없는 키 0건

이제 `probe invlist` 가 인벤토리를 이름과 담금질까지 낸다.

```
[ 0] 순번 5915 담금질 0  키 1955057078 x1 ID 18510  그로테반트 판금 투구
```

주소를 안 주면 RTTI 로 찾아 내용이 있는 컴포넌트를 쓴다. 컨테이너는
`컴포넌트 +0x18` 의 포인터 배열을 따라간다 - 앞부분을 훑는 방식은
플레이어 가방을 못 잡았다. 실측 18개 중 6개에 내용이 있고, 용량이
화면 표시와 같다(종류 4 가 "중요물품 : 144").

### import (담금질까지, 화면 확인 끝)

보관함 세트를 꺼내면 담금질까지 실려 나간다. 배선은
`파일 -> Stash -> 보관함 패널 큐 -> request_give -> TrItemValue+0x0C`.

아이템별 상한을 넘는 값이 파일에 있으면 **깎아서 보낸다**. 넘긴 채로
보내면 게임이 조용히 거절해 큐가 그 자리에서 멈춘다.

절차 (export 한 것을 다시 넣기):

```
1. probe invexport                 게임 실행 중에 파일로 뺀다
2. 게임 종료
3. scripts\deploy.ps1              담금질을 싣는 DLL 을 배포한다
4. type cdtoybox_export.txt >> bin64\cdtoybox_stash.txt
   (형식이 같고 `#` 줄은 주석으로 넘어가므로 이어붙이면 된다)
5. 게임 실행 -> 보관함 패널에서 세트 꺼내기
```

실측으로 확인했다(2026-09-03). 갖고 있지 않은 값을 골라 지급했다.

```
지급     군주의 검(200914) 담금질 2 / 카이로스 판금 장갑(1000560) 담금질 4
로그     인벤토리 지급: ... 키 200914 개수 1 담금질 2
메모리   [80] 순번 6438 담금질 2 ID 1000240 군주의 검   (기존 t1 은 ID 1000085)
         [145] 순번 5919 담금질 4 ID 1000241 카이로스 판금 장갑
화면     아이콘 눈금 2칸, 담금질 게이지 앞 2칸이 금색,
         공격력 14 +2 / 공격 속도 Lv.1 +1  - 스탯에 반영된다
```

**소켓도 실린다** (2026-09-03 실측). 개수 칸(`TrItemValue +0x5E`)을
채우면 게임의 복사 루프가 `+0x40` 부터 6바이트씩 다섯 칸을 레코드로
그대로 옮긴다. 지급분에 소켓 줄이 없었던 것은 그 칸이 0 이라 루프가
한 칸도 안 돈 것이었다.

```
[ 54] ID 1000085 군주의 검   소켓[0] 바람 가르기 (24 0D FF FF 00 FF)  <- 원본
[ 87] ID 1000248 군주의 검   소켓[0] 바람 가르기 (24 0D FF FF 00 FF)  <- 지급분
```

세 칸이 바이트 단위로 같다. 상한은 아이템 표 `+0x238` 이고 넘기면
게임이 조용히 거절하므로 보관함 큐에서 미리 자른다.

**내구도도 안 실린다.** 지급된 장비는 툴팁에 "수리 불가" 가 붙는다.
export 도 내구도를 안 읽는다 - 레코드 어느 칸인지 모른다.
`VaryEnduranceItemByCheatReq` 가 있으므로 그쪽으로 갈 수 있어 보인다.

### 지급에 담금질을 실을 자리 (코드에 반영함)

`TrItemValue +0x0C` 가 u16 담금질이다. 작업 함수(RVA `0x26A2600`)가
아이템 키를 순번으로 바꾼 직후 그 칸을 읽고, 아이템 표의 상한
(`+0x250`)과 비교해 넘으면 거절한다.

```
0 <= TrItemValue+0x0C <= [아이템표+0x250] - 1
장비는 +0x250 = 11 이라 0..10 - 툴팁의 10칸 게이지와 같다
표 +0x42 가 0xFFFF 면 담금질이 없는 아이템이다 (재료 등)
```

**지금까지 지급이 담금질 0 인 장비만 준 이유도 이것이다.** 생성자는
`+0x08` 만 0 으로 만들고 `+0x0C` 는 건드리지 않는데, 버퍼가 0 으로
초기화되므로 0 인 채로 갔다. `fill_item_value` 가 이제 그 칸을 채운다.

상한은 아이템 표에서 읽어 `ItemCatalogEntry::max_temper` 로 들고 있다
(`[+0x250] - 1`, 상한 0 이면 담금질 없는 아이템).

### 무엇이 먹고 무엇이 안 먹는가 (2026-09-03 정리)

실측을 모으면 이렇게 갈린다.

- **게임의 생성 경로로 넣은 값은 남는다** - 담금질이 그랬다
  (`TrItemValue +0x0C` -> 레코드 `+0x0A`, 화면까지 확인)
- **아이템 표를 고치면 즉시 먹는다** - 소켓 개수(`+0x238`). 그릴 때마다
  읽기 때문이다. 대신 아이템 종류 전체에 걸린다
- **사후에 인벤토리 레코드를 고치는 것은 안 먹는다** - 소켓은 게임이
  되쓰고(사본이다), 내구도로 짐작한 칸들은 써도 아무 일이 없다
- **레코드를 통째로 비워도 안 먹는다** (2026-09-03 실측). 아래 참고

그러므로 남은 것들은 **게임 자신의 경로**를 찾아야 한다.

### 레코드를 빈 칸으로 만들어 봤다 (안 된다)

지급분 미로숲의 한손검(ID 1000283, 칸 74)의 레코드 앞 10바이트를
빈 칸 표식으로 덮었다 - 인스턴스 ID 전부 0xFF, 순번 0xFFFF.

```
poke 0x...9D0 FFFFFFFFFFFFFFFFFFFF
  invlist    86개 -> 85개, 그 한 자루가 목록에서 사라짐
  컨테이너   표시 91 / 140 그대로 (사용 개수 +0x12 는 안 줄었다)
  화면       변화 없음. 가방에 두 자루 그대로
```

**게임이 되쓰지도 않았다.** 소켓 때는 몇 분 뒤 우리 값이 되돌아왔는데
이번엔 0xFF 가 그대로 남았다. 즉 이 배열은 **화면이 읽는 곳이 아니다** -
되쓰기조차 안 하는, 우리 도구만 보는 사본이다. 소켓 때보다 더 강한
증거다.

원본 10바이트를 되돌려 두 자루 다 복구했다.

**그러므로 아이템 하나를 지우는 길은 메모리 쓰기로는 없다.** 남은 것은
게임 UI 의 버리기뿐이다. 치트 `TrocTrDeleteItemCheatReq`(ID 2503)는
인자가 (인벤토리 종류, 플래그)라 **가방 단위**이고, 개별 아이템을
고를 수 없다.

### 소켓 개수는 고칠 수 있다 (아이템 표 `+0x238`)

인스턴스가 아니라 **아이템 종류**의 값이고 툴팁의 원 개수와 맞는다
(한손 무기 3, 방패 2, 재료 0). 군주의 검을 3 -> 5 로 쓰고 가방을
다시 여니 원이 5개가 됐다.

```
probe poke <아이템표레코드 + 0x238> 05 00 00 00 05 00 00 00
```

**아이템 종류 전체에 걸리고, 5 를 넘기면 안 된다** - 인스턴스의 소켓
배열이 5칸이라 그보다 크면 배열 밖을 읽는다. 표는 메모리에만 있어
게임을 다시 켜면 원래대로 돌아온다.

### export (동작 확인)

```
probe invexport [파일]     기본 cdtoybox_export.txt
```

보관함(`Stash`) 형식을 그대로 쓴다. 옛 파일이 읽히도록 `item` 줄
뒤에 토큰만 덧붙였다.

```
item <키> <개수> [t<담금질>] [s<슬롯>:<보석키>:<원본12hex>]...

item 721506 5
item 200914 1 t1 s0:1002569:240DFFFF00FF s1:1002785:8E0CFFFF01FF
```

파일에는 순번이 아니라 **아이템 키**를 쓴다. 순번은 표에서의 위치라
게임이 패치되면 달라진다.

실측: 세트 6개 · 아이템 504개 · 박힌 소켓 6개 · 담금질 14개.

기본 파일은 덮어쓰지만 **경로를 직접 주면 이미 있을 때 거절**한다 -
모드의 `cdtoybox_stash.txt` 를 가리켰다가 세트를 날리는 일을 막는다.

소켓도 같이 낸다. 가방 503개 중 박힌 것은 6개였다.

```
[ 54] 순번 6438 담금질 1  키 200914  군주의 검
      소켓[0] 순번 3364  키 1002569  바람 가르기  (24 0D FF FF 00 FF)
      소켓[1] 순번 3214  키 1002785  파괴 I       (8E 0C FF FF 01 FF)
```

값으로 레코드를 집을 때는 `probe invfind` 를 쓴다.

```
probe invfind 202529:1    # {순번 5921, 담금질 3} 을 든 레코드
```

전역(`RVA 0x6331358`)은 박아 두지 않고 변환 함수 본문 패턴으로
찾는다. 현지화와 달리 **한 곳만 일치하지 않는다 - 34곳이다.** 후보를
전부 모아 표의 개수가 6,810 인 것을 고른다. 자세한 것은
`specs/2026-09-02-inventory.md`.

### 지급이 무엇을 싣는가 (2026-09-03, 전부 화면 확인)

`TrItemValue` -> 레코드 변환 함수(RVA `0x2094050`)가 무엇을 옮기는지가
전부다. 근거는 `specs/2026-09-03-static-analysis.md`.

| 레코드 | <- | TrItemValue | 지금 |
|---|---|---|---|
| `+0x0A` 담금질 | | `+0x0C` u16 | **싣는다** (표 `max_temper` 로 자름) |
| `+0x60` 소켓 5칸 | | `+0x40`..`+0x5D` (6바이트 x 5) | **싣는다** |
| `+0x70` 소켓 개수 | | `+0x5E` u8 | **싣는다** (표 `+0x238` 로 자름) |
| `+0x40` 현재 내구도 | | `+0x2A` u16 | **싣는다** (표 `_maxEndurance` 로 자름) |
| `+0x58` 예리도 | | `+0x1AE` i16 (표 `+0x2E8` 로 자름) | 안 채운다 |
| `+0x28` / `+0x2C` | | `+0x134` / `+0x130` u32 | 안 채운다 |

세 가지가 **지급 패널과 보관함 양쪽**에서 되고, export/import 로도
왕복한다.

```
지급 패널   담금질 · 소켓을 골라서 지급 (보석은 분류 74 에서 검색)
보관함      "지금 고른 아이템 담기" 가 담금질 · 소켓까지 담는다
파일 형식   item <키> <개수> [t<담금질>] [e<내구도>] [s<슬롯>:<키>:<12hex>]
```

실측 확인:

```
군주의 검     담금질 10 + 보석 3개    공격력 30 +18, 판매가 127.38
미로숲 한손검  e12 -> 12/30            공격력 22 -12 (닳은 만큼 벌점)
타리브 천 장갑 소켓 2 (태산 II · 철벽 II)  원본과 같은 바이트
```

소켓 6바이트는 **보석 키에서 지급 시점에 다시 조립한다**
(`make_socket_bytes`). 첫 u16 이 아이템 표에서의 순번이라 파일에 든
원본 바이트를 그대로 쓰면 그 파일을 만든 빌드에 묶인다.

### 악세서리의 초록 줄은 담금질 효과다 (2026-09-03 실측)

툴팁의 `용기 : 1 초마다 0.3 회복` 같은 줄이 어디서 오는지 찾았다.
**별도 기전이 아니라 담금질이다.**

```
백사자 목걸이 담금질 0    공격력 0 -5   치명타 Lv.0   판매가 9.50     줄 없음
백사자 목걸이 담금질 10   공격력 5      치명타 Lv.4   판매가 165.69   줄 있음
```

**같은 아이템이고 담금질만 다르다.** 담금질 10 으로 지급한 것이
장착 중인 원본과 완전히 같아진다. 공격력 · 치명타 · 판매가도 전부
같은 원인이다.

어떤 효과가 붙는지는 아이템 표의 `_enchantDataList`(`+0x248`, 개수
`+0x250`)가 정하고, `EnchantData` 안에 `_enchantStatData` ·
`_equipBuffs` 가 있다.

**그러므로 "악세서리의 능력을 다른 장비에" 는 그 장비의
`_enchantDataList` 를 바꾸는 일이다.** 아이템 표 수정이라 종류
전체에 걸리고 게임을 끄면 사라진다 - 소켓 개수(`+0x238`)와 같은
성질이다. 아직 안 해 봤다.

### 오버레이 UI/UX 리뷰 (2026-09-03, 화면 확인 전)

창이 여섯 개로 늘어난 뒤 처음 훑었다. 6건 나왔고 전부 고쳤다.

| | 영향 | 무엇이 문제였나 |
|---|---|---|
| F1 | High | 창을 닫을 수 없었다 - `Begin` 에 `p_open` 을 안 넘겼다 |
| F2 | High | 무슨 창이 있는지 알 방법이 없었다 |
| F3 | Medium | 본창 이름이 `CDToybox — 0단계` 로 낡아 있었다 |
| F4 | Medium | 본창의 내용이 FPS + 개발 진단뿐이었다 |
| F5 | Medium | 지급 창에 개발 실험 "내구도 (뜻 확인 중)" 가 남아 있었다 |
| F6 | Polish | 첫 실행에 여섯 창이 같은 자리에 겹쳤다 |

F1 과 F2 는 한 쌍이다. **닫는 길을 만들면 다시 여는 길이 반드시
있어야 한다.** 그래서 본창을 창 목록으로 바꾸고(체크박스 5개) 본창
자신은 닫히지 않게 두었다. 카메라 분석은 개발 진단이라 기본 꺼짐이다.

F5 는 인자 두 칸의 뜻을 모르던 때 값을 바꿔 눌러 보려고 만든 것이다.
이제 뜻을 안다(슬롯 번호, 개수). 치트 자체는 남겨 두었다.

### 다음에 이어갈 지점

1. **"수리 불가" 뱃지.** 아직 모른다. **인스턴스 단위인 것은
   확인됐다** - 같은 백사자 목걸이인데 담금질 0 짜리에는 안 붙고
   담금질 10 지급분에는 붙는다. "아이템 종류의 성질" 이라던 앞선
   짐작은 이것으로 반증됐다.

   다만 그 둘은 담금질 말고도 다르다(갓 지급한 쪽은 `+0x2C` ·
   `+0x38` · `+0x40` 이 아직 0 이다). 원인을 하나로 못 좁혔다. 표에
   **수리 데이터를 가진 종류가 0 / 6,810** 이라(내구도 100 짜리조차
   비어 있다) 이 빌드에서는 무엇도 수리할 수 없어 보인다.
   `_maxEndurance` 로 갈린다는 가설도 틀렸다 - 내구도 30 짜리에도
   붙었다.

   **다음 수:** 저장 · 재시작을 한 바퀴 돌린 뒤 같은 담금질 10 짜리를
   다시 보면 `+0x2C` · `+0x38` · `+0x40` 이 채워진다. 그때도 뱃지가
   남아 있으면 담금질이 원인이고, 사라지면 "갓 지급" 이 원인이다.
   대조군 문제 없이 갈린다.
2. **`_enchantDataList` 옮겨 붙이기.** 악세서리의 초록 줄이 담금질
   효과라는 것까지 왔다. 한 아이템의 효과 목록을 다른 아이템에
   얹으려면 표를 고쳐야 하는데, 표는 게임이 되쓰지 않는 정적 데이터로
   보인다. 아직 안 건드렸다.
3. **레코드 `+0xA8` 의 `{원소 재료, 스탯}` 목록.** 자리는 알지만
   아무것도 이걸 쓰지 않는다. 뜻 미상.
4. **레코드 `+0x28`.** 원본 1 / 지급분 0 으로 갈리지만 정상 아이템
   507개 중 200개도 0 이다. 화면에 드러나는 차이가 없다.
5. **내구도 치트(ID 2736)** 는 (장비 슬롯 번호, 개수)를 받는다.
   장착 중인 것에만 듣는데 이 캐릭터의 장착품에는 내구도가 없다.
   내구도 있는 장비를 장착하면 확인할 수 있다.
6. 컨테이너의 사용 개수(`+0x12`)가 종류 1 에서 13개, 종류 7 에서
   1개 많다. 되풀이해도 같은 차이라 경합은 아니다.

### 되풀이하지 말 것 (2026-09-03)

**막혔다고 적기 전에 한 번 겨눠 볼 것.** "디스크 PE 는 Denuvo 라
못 본다" 를 확인 없이 두 세션 동안 들고 다녔다. 실행 이미지와
대조하니 실행 섹션 311 MB 중 다른 바이트가 5,211개(0.0016%)뿐이다.

**초기화만 보고 결론 내지 말 것.** 변환 함수 앞부분이 레코드
`+0x28` 을 0 으로 만들지만 200줄 뒤에 덮어쓴다.

**대조군이 진짜 대조군인지 확인할 것.** "늑대의 한손검 · 검은 운명은
원본이니 원본에도 뱃지가 붙는다" 고 적었는데 그 둘도 지급분이었다.

**변하는 상태를 두 시점만 찍고 판정하지 말 것.** 인벤토리 스냅샷에
없는 것을 "게임이 조용히 거절했다" 고 단정했는데, 그 사이 정리 ·
재지급이 계속 일어나고 있었다. 실제로는 전부 들어와 있었다.

**갓 지급한 레코드로 판단하지 말 것.** `+0x2C` · `+0x38` · `+0x40` 은
저장 · 재시작을 한 바퀴 돌아야 게임이 채운다. 같은 이유로 export 의
내구도 판정도 레코드 값이 아니라 **아이템 표**로 해야 한다 - 그렇게
안 했다가 내구도 없는 아이템이 `e0` 으로 적혔다.

보류: 캐릭터 발밑 좌표(지금은 카메라 초점이라 화면 중앙에 생긴다),
SpawnCharacter 의 인자 배치, 디버그 콘솔 페이지 생성 경로(2.2.1).
