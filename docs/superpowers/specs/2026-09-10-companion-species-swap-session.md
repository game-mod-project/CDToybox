# 동반자 종 교체 — 완결 세션 기록 (2026-09-09 ~ 09-10)

앞선 세션에서 "이미 가진 동반자의 종을 바꿔 원하는 탈것·펫을 얻는다"는
길을 열었지만, **야생에서 잡은 개체는 종을 바꾸면 소환할 때 게임이
죽는다**는 문제가 남아 있었다. 이 세션은 그것을 닫았다.

결론부터: **야생 획득분도 종을 바꿔 탈 수 있다.** 원인은 우리 코드가
아니라 **게임의 빠진 널 검사**였고, 게임 자신이 다른 자리에서 하는
처리를 그 한 자리에 넣어 해결했다.

---

## 1. 검증된 결과

전부 사용자가 화면으로 확인했다.

| 대상 | 출신 | 바꾼 종 | 결과 |
|---|---|---|---|
| 혹멧돼지 1000414 | 부적 | `Animal_Lion_Domestic_30374` (3436) | 소환·탑승·리로드 생존 |
| 까마귀 1000602 | **야생 획득** | `Riding_Wolf_1001` (6799) | 소환·탑승·리로드 생존 |
| 회색 앵무새 1000605 | **야생 획득** | `Riding_Wyvern_1000` (6804) | 소환·탑승·리로드 생존 |
| 까마귀 1000616 | **야생 획득** | `Riding_Wyvern_1000` (6804) | 소환 |
| 까마귀 → 1000621 | **야생 획득** | `Animal_Tiger_Wild_1` (3438) | 소환·탑승 |
| (같은 시험) | | `Animal_Tiger_Wild_2` (7038) | 소환 O, **탑승 X** |

- **반려동물(타입행 9) → 특수 탑승물(타입행 5)** 교차 교체가 된다.
- 종 교체는 **저장·재시작을 넘는다**.

쓰는 법은 그대로다.

```
오버레이: 내 동반자 탭 -> [바꾸기]
probe:    charfind <이름조각>    새 종의 **행 번호** (키가 아니다)
          clan                    내 동반자의 용병번호
          setspecies <번호> <행>  바꿔 쓴다
```

명부 주소는 휘발성이라 **생 `poke` 를 쓰면 안 된다** — `setspecies`
와 오버레이는 매번 용병번호로 레코드를 다시 찾고 표식(`+0x22 ==
0xFFFF`)을 확인한 뒤에 쓴다.

## 2. 소환 크래시 — 원인과 수정

### 2.1 죽은 자리

크래시 로거(§3)가 찍었다.

```
RIP 0x0000000142AD520F  = 모듈+0x02AD520F
코드 0xC0000005 접근 위반 · 읽기 주소 0x0000000000000028
```

주소가 정확히 `0x28` 이라는 것이 곧 답이었다 — 베이스가 널이다.

```
0x2AD51F8  call 0x208F5C0          ; 용병번호 -> 레코드 해시 조회
0x2AD520F  cmp  [rax+0x28], -1     ; rax = 0 -> 죽음
0x2AD521F  cmp  word [rax+0x20], 0xFFFF
0x2AD5229  mov  r15d, [rax+0x50]
```

`+0x28`·`+0x20`·`+0x50` 이 우리가 매핑해 둔 명부 레코드 필드와 그대로
맞는다(§5).

### 2.2 왜 널이 나오나

호출자 `0x2ABD850` 에 넘기는 번호의 출처가 있다.

```
0x2ABD8C0  mov rdi, -1                    기본값
0x2ABD98A  call 0x2095600                 종류로 등록된 동반자 찾기
0x2ABD9A2  cmovne rdi, [찾은것+0x28]       못 찾으면 -1 그대로
0x2ABDBB9  call 0x2AD4F70(.., rdi, ..)    -1 을 그대로 넘긴다
```

`0x2095600` 은 **종류별 색인**(`0x208FC30`, 키 = `CharacterInfo +0xBE`)을
뒤지고, 없으면 전역 **빈 레코드**(`0x6BB3F70`)를 낸다. 우리가 레코드의
종(`+0x20`)을 제자리에서 바꾸면 **그 색인이 따라오지 않아** 조회가
빈다. 그러면 `-1` 이 넘어가고, 해시에 `-1` 은 없으니 널이 된다.

### 2.3 게임 자신이 하는 처리

같은 조회를 쓰는 **다른 두 자리에는 널 검사가 있다.**

```
0x2ABD8EB  call 0x208F5C0        0x2AD531D  call 0x208F5C0
0x2ABD8F0  lea rbx,[0x6BB3F70]   0x2AD5322  lea rcx,[0x6BB3F70]
0x2ABD8F7  test rax, rax         0x2AD5329  test rax, rax
0x2ABD8FA  cmovne rbx, rax       0x2AD532C  cmovne rcx, rax
```

죽는 `0x2AD51F8` 한 자리에만 없다. **게임 버그다.**

### 2.4 수정 (`src/game/spawnguard.cpp`)

그 `call rel32` 하나를 우리 썽크로 돌려 같은 처리를 넣는다. 널이면
빈 레코드를 돌려주고, 뒤따르는 `cmp [rax+0x28], -1` 이 맞아 정상
분기로 빠진다.

조회 함수 자체는 건드리지 않으므로 **다른 호출자는 그대로다.**
설치 전에 두 가지를 확인하고, 아니면 조용히 다음 프레임에 다시
시도한다.

1. 그 자리가 정말 `call 0x208F5C0` 인가 (바이트·대상 확인)
2. 전역 빈 레코드가 `+0x28 == -1`, `+0x20 == 0xFFFF` 로 초기화됐는가

썽크는 `alloc_near` 로 모듈 근처에 잡는다(`specguard` 와 같은 방식).

## 3. 진단 도구 — 이게 없었으면 못 풀었다

이 프로젝트의 크래시는 그동안 **"로그가 끊긴 자리"만** 남겼다. 그래서
같은 문제를 두 번 잘못 진단했다. 이번에 도구부터 만들었다.

### 3.1 크래시 로거 (`src/core/crashlog.cpp`)

`bin64/CDToybox.crash.txt` 에 **덧붙여** 쓴다. 남기는 것:
예외 코드 · **RIP 를 `모듈+0xRVA` 로 환산한 값** · 접근하려던 주소 ·
주요 레지스터 · RSP 부터 훑어 찾은 **게임 모듈 안 복귀 주소 후보**.

세 갈래로 잡는다.

- **벡터 예외 처리기** — 게임 모듈 **안**에서 난 치명적 예외만.
  밖은 버린다(우리 스캐너가 매핑 안 된 페이지를 훑을 때 나는 양성
  예외가 전부 그쪽이었다 — 첫 판에 8건).
- **처리되지 않은 예외 필터** — 위치를 가리지 않고 마지막 한 번.
- **감시 스레드** — `watch_begin` 으로 감싼 호출이 12초 안에 돌아오지
  않으면 **모든 스레드의 스택**을 뜬다. 예외 없이 멈추는 교착은
  앞의 둘로는 아무것도 안 남는다. 소환 작업 디투어를 여기에 걸었다.

**CRT 를 한 줄도 쓰지 않는다.** `CreateFileW`/`WriteFile` 뿐이다.
힙이 깨진 채 죽을 때 `std::format`·`ofstream` 은 힙 락에서 멈추고,
그러면 게임이 죽는 대신 **굳어** 강제 종료해야 한다. 같은 이유로
스레드를 세운 채로 파일을 쓰지 않는다 — 문맥을 다 뜬 **뒤에** 되살리고
그다음에 쓴다.

예외는 처리하지 않고 `EXCEPTION_CONTINUE_SEARCH` 로 흘려보내므로
게임의 원래 동작은 그대로다.

### 3.2 로그 보관

`CDToybox.log` 는 실행마다 `.prev`·`.prev2` 로 민다. 죽은 판의 기록이
남아야 원인을 짚는다 — 실제로 이번에 그 덕에 `18:02:45 까마귀 소환`
직후 로그가 끊긴 것을 봤다.

### 3.3 probe 명령

| 명령 | 하는 일 |
|---|---|
| `clan` | 명부 전체 + 소유자 + 소유 갈래 집계 |
| `charfind <조각> [수]` | 캐릭터를 이름으로. 행·타입행·장비·소유판·셈 |
| `setspecies <번호> <행>` | 종 교체 (안전한 유일한 경로) |
| `gate` | 타입행별 전수 집계 + 장비 없는 1/5/9 종 목록 |
| `playable` | 주인공 행 + 용병 표 `_isPlayable` + Mercenary_Main 목록 |
| `unspawn <번호> [read]` | 레코드 `+0x50` 핸들 정리 |

## 4. 분류 체계 — 명부에 무엇이 왜 있나

명부에는 탈것·펫만 있는 게 아니다. **플레이어블 캐릭터들이 속한
용병대의 멤버**가 같이 산다. 칼·루소·루크가 그것이다.

기준은 용병 표(`MercenaryInfo`)의 `_mercenaryType` 이다(21행 전수).

| 갈래 | `_mercenaryType` | 보기 |
|---|---|---|
| **용병대원** | 1 플레이어블 · 6 근접 · 7 원거리 · 8 일꾼 · 9 상점 · 12 객원 | 데미안 · 루크 · 칼 |
| **탈것·펫** | 2 탈것 · 3 마차 · 4 펫 · 5 가축(어류·곤충 포함) | 사자 · 새끼 와이번 |
| **시스템** | 10 관찰자 · 11 회복 | WorldObserver |

오버레이 내 동반자 탭에서 세 갈래로 접는다. **시스템만 기본으로
접는다.** 체크박스마다 개수를 늘 찍으므로 무엇이 접혀 있는지는
숨겨지지 않고, 분류가 안 되는 것(미상)은 **어느 체크박스로도 숨기지
않는다** — 새 타입이 생겼을 때 필터가 삼키면 안 된다.

### 용병대 규모 (실측)

| 타입 | 캐릭터 표 | 현재 명부 |
|---|---|---|
| 용병(근접) | 24 | 3 |
| 용병(원거리) | 14 | 3 |
| 용병(일꾼) | 1 | 0 |
| 용병(상점) | 16 | 6 |
| **용병 소계** | **55** | **12** |
| 플레이어블 | 6 | 1 (데미안) |
| **합계** | **61** | **13** |

사용자가 말한 "약 60여명"이 정확했다.

## 5. 명부 레코드 지도

용병단 컴포넌트 `+0x18` 이 레코드 포인터 배열, `+0x20` 개수,
`+0x24` 용량. 레코드는 개별 할당이고 블록에 따라 간격이 `0x180`·`0x1C0`
으로 관찰됐다 — **작은 쪽이 0x180 이므로 레코드 크기는 0x180 이하다.**

| 오프셋 | 크기 | 뜻 | 근거 |
|---|---|---|---|
| `+0x20` | u16 | **종** = 캐릭터 표 행 번호 | 종 교체가 여기 쓴다 |
| `+0x22` | u16 | `0xFFFF` 표식 | 레코드 검증에 쓴다 |
| `+0x28` | u64 | **용병번호** | `cmp [rax+0x28], -1` |
| `+0x50` | u32 | 액터 핸들. 0 이 아니면 월드에 있다 | |
| `+0x148` | u16 | **소유자 캐릭터 행**. `0xFFFF` 면 개인 임자 없음 | 게임 판정 `0x209FE40` |

### 소유자 판정 (`0x209FE40(레코드, 행) -> bool`)

종(`+0x20`)으로 CharacterInfo 를 찾아 `_mercenaryInfo`(`+0xBE`) ->
MercenaryInfo 의 `_summonOwnerOption`(`+0x5D`) 분류를 보고 분기한다.

| 분류 | 비교 |
|---|---|
| 0 | 무조건 거짓 |
| 1 | 넘긴 행 == 주인공 행, 그다음 `+0x148` == 주인공 행 |
| 2 | `+0x148` == 주인공 행 |
| 3 | `+0x148` == 넘긴 행 |

**어느 분류든 비교 대상은 `+0x148` 하나**다. 그래서 그 자리가 소유자다.

### 실측 (명부 39명)

```
소유: 플레이어블 4 · 용병대(임자 없음) 35 · NPC 0
```

**NPC 개인 소유가 0이다.** 개인 임자가 기록된 것은 전부 플레이어블
캐릭터였다(브리안토의 주인 데미안도 플레이어블). 즉 갈래는 둘뿐이다 —
**플레이어블 개인 소유** 아니면 **개인 임자 없음**.

`0xFFFF` 를 UI에서 **"용병대"** 로 찍는다. 실측으로 아는 것은 "개인이
기록되지 않았다" 까지이고, '용병대' 라는 이름은 사용자의 게임 안
지식으로 붙인 의미다 — 코드 주석에도 그렇게 갈라 적었다.

## 6. 플레이어블 캐릭터 구분

두 갈래다. **이름을 박지 않으므로 DLC·모드로 늘어도 따라간다.**

**1) 주인공 클리프는 용병 표에 없다** (캐릭터 행 0 `Kliff`,
`_mercenaryInfo` = `0xFFFF`). 게임이 소유자 판정에서 쓰는 사슬로
**지금 조종 중인 캐릭터 행**을 읽는다. 실측값 0.

```
전역 0x6C29AF8 (또는 0x6C29B00) -> [+0] -> [+8] -> [+0x28] -> +0x100 u16
```

**2) 바꿔 탈 수 있는 나머지**는 `_mercenaryType == 1`(Mercenary_Main).
지금 6행뿐이다.

| 캐릭터 행 | 내부 이름 | 표시명 |
|---|---|---|
| 3 | `Damian` | 데미안 |
| 5 | `Oongka` | 웅카 |
| 6 | `Yann` | 얀 |
| 7 | `Yahn` | 얀 |
| 8 | `Nairah` | 나이라 |
| 9 | `Witch` | 마녀 |

아직 게임에 안 나온 셋(얀·나이라·마녀)이 데이터에 이미 있다.

**`_isPlayable`(MercenaryInfo `+0x22`)은 이 용도로 못 쓴다.**
Mercenary_Main 뿐 아니라 Vehicle_Horse·Vehicle_Dragon·
Vehicle_WarMachine·Vehicle_Special·Vehicle 까지 전부 1이다
(Vehicle_Ship·펫·가축·용병은 0). 뜻은 **"플레이어가 조종하는가"** 에
가깝다.

## 7. 종을 고를 때의 기준

### 목록에 뜨는가 → **동반자 타입**

낙타(3583)·성체 와이번(4214)이 게임 목록에 안 뜨는 이유는 **타입행 6
(Vehicle)** 이라서다. 사용자가 요청한 1/5/9 필터(말·특수 탑승물·
반려동물)가 이미 그것을 거른다.

### 탈 수 있는가 → `_equipInfo`

한때 `_equipInfo`(`+0x6A`) 를 "목록에 뜨는가"의 기준으로 쓰고 있었다.
틀렸다 — 성체 와이번은 그 값이 9 인데도 안 뜬다. 실제 뜻은 **탑승
가능 여부**다.

| 종 | 행 | 타입행 | `_equipInfo` | 결과 |
|---|---|---|---|---|
| `Animal_Tiger_Wild_1` | 3438 | 5 | 9 | **탑승 O** |
| `Animal_Tiger_Wild_2` | 7038 | 5 | 65535 | 소환 O, **탑승 X** |

전수 집계(`probe gate`): 타입행 1·9 는 `_equipInfo` 없는 것이 **0건**,
타입행 5 는 63 중 **4건**뿐이다.

```
행 6703  Riding_Balloon_Summoner_1   열기구
행 6704  Riding_Balloon_Summoner_2   구름길 열기구
행 6705  Riding_Balloon_Summoner_3   하늘길 열기구
행 7038  Animal_Tiger_Wild_2         호랑이
```

그래서 **숨기지 않는다.** 팝업에 `탑승 가능/불가` 로 찍어 알고 고르게
한다. 소환 널 가드(§2)가 있어 잘못 골라도 게임이 죽지 않으므로 시험이
안전하다.

> 주의: "안 움직인다"는 근거가 아니다 — 탈것은 타지 않으면 원래
> 움직이지 않는다(사용자 지적). 실측된 것은 **탑승 불가** 하나다.

## 8. 필드 이름 (`tools/rtti/fields.py`)

역직렬화 실패 메시지에 필드 이름이 문자열로 박혀 있어 **게임을 켜지
않고** 이름→오프셋을 얻는다. `*Info` 클래스에서 통한다
(`*SaveData` 는 그 메시지가 없어 안 통한다).

### `CharacterInfo`

| 오프셋 | 이름 | 비고 |
|---|---|---|
| `+0x6A` | `_equipInfo` | 탑승 가능 여부와 상관(§7) |

## 10. 내가 틀렸던 것들

되풀이하지 않도록 남긴다. 코드 주석에도 같은 내용이 있다.

| # | 틀린 것 | 실제 |
|---|---|---|
| 1 | 레코드 `+0x30~+0x4F` 가 0 이 아니면 "야생 획득분" | 출신과 무관. 야생인 까마귀·대형늑대는 0이고, 야생 아닌 사자·카모라는 0이 아니다. 여러 필드가 겹친 구간이었다 |
| 2 | 표시 관문이 `CharacterInfo +0x16A` | 오프셋은 `+0x6A` 이고 이름은 `_equipInfo` |
| 3 | 성체 와이번의 `_equipInfo` 는 `0xFFFF` | 9 다. 재지 않고 낙타와 같다고 단정했다 |
| 4 | `_equipInfo` 가 "목록에 뜨는가"의 기준 | 기준은 **동반자 타입**. `_equipInfo` 는 **탑승 가능 여부** |
| 5 | 19:19 건은 "예외 없는 멈춤" | 같은 크래시였다. 내 예외 필터가 모듈 밖만 거르도록 좁아 놓쳤다 |
| 6 | 소환 코드 `0xFAABC030` 은 거부 | **성공이었다.** 121곳이 쓰는 범용 코드다. 사용자가 화면으로 알려 주지 않았으면 계속 실패로 팠다 |
| 7 | "안 움직인다"를 근거로 씀 | 탈것은 타지 않으면 원래 안 움직인다(사용자 지적) |
| 8 | `_isPlayable` 이 플레이어블 캐릭터 표시 | 탈것 타입도 전부 1. 뜻은 "플레이어가 조종하는가" |
| 9 | 리플렉션 워커로 이름표를 얻자고 제안 | 속성 이름이 **해시**로 저장돼 인턴 표까지 리버스해야 한다. 제안 전에 확인하지 않았다 |
| 10 | 야생 획득분의 바꾸기를 **막았다** | 막을 게 아니라 고칠 것이었다. 게다가 그 판정은 정작 죽는 레코드를 못 막고 멀쩡한 것만 막았다 |

특히 **10번**이 이 세션의 교훈이다. 근거 없는 판정으로 기능을 막아
두면, 막힌 쪽도 잘못 막히고 진짜 문제도 그대로 남는다.

## 11.5 "내 동반자 탭이 게임을 멈춘다" — 원인과 수정 (2026-09-10)

증상: 탭을 열면 게임이 멈출 정도로 오래 걸린다. 앞서 "바꾸기 하면
변환 완료까지 멈춘다"고 했던 것과 **같은 뿌리**다.

### 원인

명부 컴포넌트를 **RTTI 인스턴스 스캔**으로 찾는데 그 비용이 크다.
시작 로그가 그대로 증거다.

```
[09:00:49.396] INFO  탐색 [동반자 명부] 10688ms
```

그래서 캐시(`g_cached_server`/`g_cached_client`)를 두었는데,
**캐시를 다시 채우는 길이 없었다.**

| 자리 | 무엇이 빠졌나 |
|---|---|
| `discover_clan` | `g_clan` 이 차 있으면 **즉시 반환**. 다시 안 돈다 |
| `refresh_clan_roster` | 재탐색해도 **`g_clan` 만** 갱신. 캐시 슬롯은 그대로 |
| `clan_component_cached` | **간격 제한 없음.** 캐시가 상하면 호출마다 스캔 |

동반자를 얻으면 게임이 컴포넌트를 통째로 새로 만들어 캐시가 상한다
(명부가 33 -> 39 로 늘어난 상태였다). 그 상태에서
`tick_hire_cleanup` 이 15초마다 `clan_component_cached` 를 부르니
**15초마다 10초씩 멈췄다.** 재탐색은 로그도 안 남겨 조용했다.

`resolve_species_write` 는 같은 함수를 네 번(서버·클라 × 쓰기·재확인)
부른다 - 바꾸기가 유독 오래 걸린 이유다.

### 수정

- 컴포넌트 갈무리를 `store_component` **한 자리**로 모았다. 캐시와
  `g_clan` 이 따로 갱신되던 것이 뿌리였다.
- 캐시가 상하면 **배경 스레드**에서 다시 찾는다. 그동안 부르는 쪽은
  `false` 를 받고 화면은 옛 목록을 그대로 쓴다 - 멈추는 것보다 낫다.
  걸린 시간을 로그에 남긴다(다시는 조용하지 않게).
- `refresh_clan_roster` 의 인라인 재탐색도 같은 경로로 넘겼다.
- 배경 재탐색은 **DLL 만** 켠다(`enable_background_clan_rescan`).
  probe 는 짧게 살고 그 자리에서 훑어도 되므로 종전대로다.

### 계측 (`src/core/slowlog.h`)

문턱을 넘을 때만 남기는 RAII 타이머. 내 동반자 탭 · 명부 갱신 ·
종 바꾸기 팝업 · 획득 뒤처리에 걸었다. "느리다"를 코드만 읽고 짚다가
이 세션에서 두 번 헛다리를 짚었기 때문이다 - **숫자를 보고 정한다.**

> **주의: 증상만 없앴다.** 스캔이 10초라는 사실은 그대로다. 근본은
> §12-1 이다.


## 12. 남은 것

### 12-1. 명부 컴포넌트를 스캔 없이 찾기 (가장 값어치 있는 것)

지금은 `find_clan_of_class` 가 **RTTI 인스턴스 스캔**으로 11GB 힙을
훑는다. 실측 **10.7초**(서버), 클라이언트는 더 길다(probe 로 두 번
재 보니 합쳐 1분 8초). §11.5 에서 배경으로 옮겨 화면이 멈추지는
않게 했지만, **비용 자체는 그대로다.** 동반자를 얻을 때마다 컴포넌트가
새로 만들어지므로 이 값은 계속 치른다.

게임은 당연히 스캔하지 않는다. 포인터로 간다. 찾을 실마리:

1. **디스어셈블에 이미 있다.** `0x2ABD850` 은 컴포넌트를 첫 인자
   (`rcx` -> `r15`)로 받고 `lea r14, [r15 + 0x18]` 로 컨테이너를 잡는다.
   **그 함수를 부르는 쪽**을 거슬러 올라가면 컴포넌트가 어디서 오는지
   나온다. 아직 안 팠다.
2. **기억에 적어 둔 사슬**: 런타임 명부는 `[[세션 + 0x68] + 0x110]` 의
   용병단 컴포넌트에 산다([[engine-reflection-savedata]] 2026-09-09
   갱신분). 세션 객체를 잡는 길이 필요하다 - 인벤토리 쪽이 세션을
   훑는 코드를 이미 갖고 있다(로그의 `세션 1 0x... -> 액터 ...`).
3. **주인공을 찾는 전역 사슬**이 이미 검증돼 있다(§6).
   `0x6C29AF8`/`0x6C29B00` -> `[+0]` -> `[+8]` -> `[+0x28]`.
   그 `+0x28` 객체가 세션 성격이면 거기서 `+0x110` 을 볼 수 있는지
   확인할 값어치가 있다. **게임을 켜고 그 주소를 덤프하면 몇 분 안에
   갈린다.**

성공하면 얻는 것: 시작 10.7초 단축, 컴포넌트가 바뀔 때마다의 재탐색이
공짜가 됨, 배경 스레드·간격 제한 같은 우회 장치를 걷어낼 수 있음.

### 12-2. 종류별 색인이 따라오지 않는다

종을 제자리에서 바꾸면 게임의 종류별 색인(`0x208FC30`, 키 =
`CharacterInfo +0xBE`)이 갱신되지 않는다. 지금은 소환 널 가드(§2)가
크래시를 막고 게임이 넘어가며, 실사용에 지장은 확인되지 않았다.
색인에서도 옮겨 주면 가드 없이도 깨끗해진다.

### 12-3. 타입행 6(Vehicle)이 게임 UI에서 왜 배제되는가

낙타·성체 와이번이 여기다. 열 수 있는지 안 팠다.

### 12-4. `_ownedMercenaryCharacterInfo`(`+0x100`)

읽어만 두고 쓰지 않았다. 야생판을 고르면 소유판으로 돌려주는 데 쓸 수
있을지 미확인.
