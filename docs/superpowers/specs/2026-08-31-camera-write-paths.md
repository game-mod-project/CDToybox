# 카메라 쓰기 경로 정적 분석

> **정리 (2026-09-21) — ❌ 반증.** 주 결론("좌표를 쓰면 카메라가 따라 움직인다 → 갱신
> 직후 덮어쓰면 프리카메라")은 틀렸다 — 우리 값으로 고정해도 화면이 변하지 않았다
> (`STATUS.md` §2.4, `TROUBLESHOOTING.md` §7.3). "`+0x360` 에 쓰는 곳은 구조체 복사뿐" 은
> VEX 접두사를 거꾸로 읽은 버그가 만든 결론이고(`TROUBLESHOOTING.md` §4.2), 월드 좌표
> 자리도 패치 뒤 `+0x378` 로 밀렸다(§4.19). 프리카메라는 보류다(`STATUS.md` §3).

**날짜:** 2026-08-31
**대상:** CrimsonDesert.exe (Enhanced 2.00.01), 이미지 베이스 0x140000000
**방법:** PE 파싱 + 바이트 패턴 스캔. 디버거·디스어셈블러 없이 파일만 읽음.

## 출발점

인게임 하드웨어 브레이크포인트가 활성 카메라 `+0xA4` 를 쓰는 명령
하나를 잡았다: RIP `0x140A59516`. 데이터 브레이크포인트는 쓰기가
**끝난 뒤** 보고하므로 실제로 쓴 명령은 그 앞이다.

```asm
0x140A594FB  48 8B 83 88 00 00 00   mov   rax, [rbx+0x88]
0x140A59502  48 8D 48 7C            lea   rcx, [rax+0x7C]
0x140A59506  BA A4 00 00 00         mov   edx, 0xA4        ; null 폴백
0x140A5950B  48 85 C0               test  rax, rax
0x140A5950E  48 0F 44 CA            cmovz rcx, rdx
0x140A59512  C5 FA 11 09            vmovss [rcx], xmm1     ; <- 실제 쓰기
0x140A59516  0F B6 97 80 00 00 00   movzx edx, [rdi+0x80]  ; <- 보고된 RIP
```

## 핵심: +0x28 어긋남

감시 주소는 `active + 0xA4` 였는데 명령은 `rax + 0x7C` 에 썼다.
따라서 **`rax == active + 0x28`** 이다.

이는 탐색 로직과 일치한다 — `discover_with()` 는
`PlayerCameraComponent + 0x88` 을 읽어 **0x28 을 빼서** 카메라를
얻는다. 즉 `rbx == PlayerCameraComponent` 이고,
`[rbx+0x88]` 은 카메라 객체의 내부 포인터(카메라+0x28)다.

**이 함수에서 본 오프셋은 전부 +0x28 을 더해야 카메라 기준이 된다.**

## 함수 0x140A59230 ~ 0x140A5976C

int3 패딩으로 잡은 경계. 널 안전 필드 복사 관용구가 12번 반복된다:

```asm
mov   rax, [rbx+0x88]        ; 대상 카메라(+0x28)
lea   rcx, [rax+OFFSET]      ; disp8 또는 disp32
mov   edx, OFFSET            ; rax 가 null 이면 쓸 더미 주소
test  rax, rax
cmovz rcx, rdx
vmovss [rcx], xmmN           ; 또는 mov [rcx], dl
```

| 함수 기준 | 카메라 기준 | 소스 | 종류 |
|---|---|---|---|
| +0x78 | +0xA0 | `[rdi+0x80]` | byte |
| +0x7C | **+0xA4** | `[rdi+0x70]` | float — 실측 히트 지점 |
| +0x80 | +0xA8 | | float |
| +0x84 | +0xAC | `[rdi+0x78]` | float |
| +0x88 | +0xB0 | | float |
| +0x8C | +0xB4 | | float (근접평면) |
| +0x94 | +0xBC | `[rdi+0x9A]` | byte |
| +0xA4 | +0xCC | | float |
| +0xC0 | +0xE8 | `[rdi+0x54]` | |
| +0xCC | +0xF4 | `[rdi+0x60]` | |
| +0xD8 | +0x100 | | |

**FOV(+0x9C)도 위치(+0x6C)도 회전(+0x5C)도 이 함수에 없다.**

### 스캔 함정

처음에 `lea rcx,[rax+disp8]`(`48 8D 48 XX`)만 찾아 +0x7C 와 +0x78 만
나왔다. disp8 은 **부호 있는** 값이라 0x80 이상 오프셋은
`lea rcx,[rax+disp32]`(`48 8D 88 XX XX XX XX`)로 인코딩된다.
두 형태를 다 봐야 한다.

## 이미지 전수 조사

실행 가능 섹션(`.rdata` 76MB, `.sbss` 251MB) 전체에서 같은 관용구를
찾았다. 총 57곳.

| 카메라 오프셋 | 곳 | 대표 주소 |
|---|---|---|
| **+0x9C (FOV)** | 6 | 0x1409854ED, 0x1409855A5, 0x14098565D, 0x140985715 |
| +0xA8 | 8 | 0x1409854AD … |
| +0xAC | 8 | 0x1409854CD … |
| +0xB0 | 8 | 0x14098550A … |
| +0xA4 | 2 | 0x140A594FB, 0x142DCB90D |
| +0x50 (스케일) | 2 | 0x142DCDAB4, 0x1517F38C4 |
| **+0x5C (회전)** | 0 | — |
| **+0x6C (위치)** | 0 | — |

FOV 쓰기는 `+0xA8 → +0xAC → +0x9C → +0xB0` 순서로 연달아 나오고 그
블록이 4번 복제돼 있다(0x1409854AD, 0x140985565, 0x14098561D,
0x1409856D5). 하나의 "카메라 파라미터 적용" 루틴이다.

**위치와 회전은 이 경로(컴포넌트+0x88)로 설정되지 않는다.** 다른
방식이므로 정적으로는 더 좁힐 수 없다. 런타임 하드웨어
브레이크포인트로 찾아야 한다.

## FOV 히트 0회의 해석

이전 실행에서 FOV 감시가 히트 0회였는데, 정적으로는 쓰는 코드가
6곳 있다. 두 가지가 가능하다.

1. 그 코드가 8초 관찰 창 안에 돌지 않았다.
2. **감시 설치 후 만들어진 스레드가 썼다.**

2번은 실제 결함이었다. `WriteWatch::install()` 이 설치 시점의
스레드에만 디버그 레지스터를 걸고 이후 생성 스레드를 방치했다.
`refresh_threads()` 로 메웠고 회귀 테스트를 붙였다
(`watchpoint_catches_write_from_thread_created_after_install`).

## 프리카메라 활성화 단서 (문자열)

| 문자열 | 위치 | 뜻 |
|---|---|---|
| `eErrNoFreeCamModeEnabled` | 0x145091AD8 | 프리캠 모드 게이트가 존재 |
| `FREECAM_MODE_ACTION_XXX` | 0x1450645F0 | 액션 상태 이름 |
| `_debugCameraState` | 0x1452EF0F8 | 리플렉션 필드 |
| `debugCameraState` | 0x1452F2558 | 표시 이름 |
| `PearlAbyssEngine.Debug.DebugCameraState` | — | 스크립트 타입 |

`eErrNoFreeCamModeEnabled` 의 두 참조는 전부 **열거형 이름 등록
테이블**이라 런타임 게이트가 아니다.

`debugCameraState` 는 `0x142C76768` 에서 참조되고, 주변이
`_renderCollisionGeometry`·`_viewMode`·`showEngineOption`·
`B: Debug Information` 같은 **엔진 렌더 디버그 옵션 목록**이다.
출시 빌드에 개발자 옵션 UI가 남아 있다는 뜻이지만, 렌더 디버그
문맥이므로 컬링 카메라 고정에 가깝지 날아다니는 프리캠은 아니다.

참조 지점 디코딩:

```asm
0x142C7673C  lea  rdx, "_debugCameraState"
0x142C76743  lea  rcx, [0x1465E8EA0]
0x142C7674A  call 0x142C86260
...
0x142C76768  lea  rdx, "debugCameraState"
0x142C7676F  lea  rcx, [0x1465E8EC8]
0x142C76776  call 0x1403390F0
```

`0x1465E8EA0` / `0x1465E8EC8` 는 RVA 0x65E8Exx 로 **`.00cfg`(RW)
섹션의 초기화되지 않은 영역**이다(RawSize 0x354000 < 섹션 내
오프셋 0x780Exx). 파일에는 없고 런타임에만 존재하는 전역이다.

### 섹션 표 (Denuvo 로 뒤섞여 있음)

| 이름 | RVA | VirtSize | RawSize | 속성 |
|---|---|---|---|---|
| `.rdata` | 0x00001000 | 0x0496B000 | 0x0496B000 | **XR** |
| `.text1` | 0x0496C000 | 0x014FC000 | 0x014FC000 | R |
| `.00cfg` | 0x05E68000 | 0x0083D000 | 0x00354000 | RW |
| `.sbss` | 0x06B32000 | 0x0EFEE910 | 0x0EFEEA00 | **XRW** |
| `.text` | 0x06959000 | 0x00003000 | 0x00003000 | R |

실행 플래그는 `.rdata` 와 `.sbss` 에 있다. **섹션 이름으로
코드 영역을 고르면 안 된다** — `IMAGE_SCN_MEM_EXECUTE` 를 봐야 한다.

VirtSize > RawSize 인 섹션(`.00cfg`)에서 RVA→파일오프셋 변환에
`max(VirtSize, RawSize)` 를 쓰면 raw 밖 주소가 엉뚱한 파일 위치로
매핑된다. 실제로 한 번 쓰레기 값을 읽었다. RawSize 로 잘라야 한다.

# 실행 중인 게임 실측 (같은 날, cdtb_probe)

게임이 켜진 채로 남아 있어 외부 도구로 직접 읽었다. 아래는 전부
읽기 전용 측정이며, 프로세스에 아무것도 쓰지 않았다.

## 카메라 객체 실제 값

활성 카메라 `0x3BAB469BB80` (`PlayerCamera`):

| 오프셋 | 값 | 뜻 |
|---|---|---|
| +0x10 | `0x3BAAF1BF000` | PlayerCameraComponent 백포인터 |
| +0x28 | vtable `0x14539B0B8` | 인터페이스 서브객체 |
| +0x48 | `0x3BABBF6BE20` | 이름 객체 |
| +0x50 | `(1, 1, 1)` | 지역 스케일 |
| +0x5C | `(0, 0, 0, 1)` | 지역 회전 — **항등** |
| +0x6C | `(0, 0, 0)` | 지역 위치 — **원점** |
| +0x7C / +0x80 | 1920 / 1080 | 뷰포트 |
| +0x9C | 45.0 | FOV |
| +0xB4 / +0xB8 | 0.2 / 100000 | 근접 / 원거리 |
| +0xBC | `0x00000101` | 바이트 플래그 |
| +0xE0 | `0x3BAAE87CB30` | 렌더 뷰 (컴포넌트+0x60 과 동일) |
| +0xE8~+0x10C | ±0.003 내외 | TAA 지터 — 매 프레임 변동 |

**지역 변환이 항등이라는 것이 이 측정의 핵심이다.** 정적 전수
조사에서 `+0x5C`·`+0x6C` 에 쓰는 코드가 0곳이었던 것과 맞물린다.
큰 오픈월드 엔진이 흔히 쓰는 카메라 상대 렌더링으로 보인다.

## 활성 카메라 vs 프리카메라

`FreeCamCamera 0x3BAAF2A2A00` (`FreeCamera`) 과 비교:

| 오프셋 | 활성 | 프리캠 | 해석 |
|---|---|---|---|
| +0x10 | 컴포넌트 포인터 | **0** | 프리캠은 소유자가 없다 |
| +0x38 | 5 | 1 | 상태 코드 |
| +0x9C | 45.0 | 60.0 | FOV |
| +0xA4 | 7.64 (변동) | 0.0 | 매 프레임 갱신 여부 |
| +0xAC | 32.0 | 8.0 | |
| +0xBC | `0x0101` | **0** | **활성 플래그 후보** |
| +0xD0~ | 값 있음 | 0 | 파생 데이터 |
| +0xE0 | 렌더 뷰 포인터 | **0** | 프리캠은 뷰가 없다 |
| +0xE8~ | 지터 값 | 0 | 렌더에 안 쓰이는 증거 |

프리카메라는 **할당만 되어 있고 어떤 파이프라인에도 연결돼 있지
않다.** 소유자(+0x10), 렌더 뷰(+0xE0), 활성 플래그(+0xBC)가 전부
비어 있다.

## 카메라 월드 좌표를 찾았다

`PlayerCameraComponent` 전체를 float 격자로 훑어 큰 값을 찾았다.

```
+0x340        3.0000      45.0000      32.0000       3.0000
+0x350        0.0000       0.0000       0.0000       0.0503
+0x360   -10483.4902     610.7071   -4380.5215       0.0000   <- 월드 좌표
```

0.7초 간격 비교로 변하는 칸을 추렸다. **컴포넌트 0x600 바이트 중
변하는 것은 딱 4칸이다:**

```
+0x35C      0.1912 ->      0.1064
+0x360 -10496.6104 -> -10500.5830   X
+0x364    610.8876 ->    610.7080   Y
+0x368  -4365.0786 ->  -4363.2056   Z
```

`+0x340` 의 `45.0 / 32.0 / 3.0` 은 카메라 `+0xA8 / +0xAC / +0xB0` 과
같은 값이다. **정적 분석에서 본 복사 함수(0x140A59230)의 소스
구조체 `rdi` 가 이 컴포넌트다.**

지난 자동 분석이 `컴포넌트+0x360` 을 감시하고도 히트 0이었던 것은
스레드 커버리지 결함 때문이었다. 값은 처음부터 맞았고 계측이
틀렸다.

## 아직 못 찾은 것

**회전.** 다음을 전부 확인했으나 변하는 회전 값이 없었다.

- 컴포넌트 0x600 바이트: 변하는 칸 4개(위치 3 + `+0x35C`)뿐
- 컴포넌트가 속한 힙 이웃 8KB: 같은 3칸뿐
- 컴포넌트+0x10 이 가리키는 객체 0x3BAB54DA2B0: 변화 0
- 카메라+0xE0 == 컴포넌트+0x60 의 공유 뷰 객체: 변화 0

측정 중 카메라는 **회전 없이 이동만** 하고 있었다(느린 팬). 회전이
변하지 않으면 시간차 비교로는 잡히지 않는다.

`컴포넌트+0x360` 을 쓰는 명령을 하드웨어 브레이크포인트로 잡으면
그 함수가 회전도 함께 쓸 것이다. `+0xA4` 에서 그 방법이 통했다.

### 정적으로 시도했으나 실패한 것

disp32 == 0x360 인 메모리 쓰기를 실행 섹션 전체에서 찾았다. 384곳
중 xmm 저장은 39곳이고, `rbp`(스택 지역변수)를 빼면 넷뿐이다.

```
0x143B21F39  movups [rbx+0x360], xmm1
0x143B71B36  movups [rdi+0x360], xmm0
0x143D65EBB  movups [rcx+0x360], xmm0
0x15399657F  movups [rax+0x360], xmm0
```

넷 다 `[reg+0x2D0], [reg+0x2E0], … [reg+0x360], [reg+0x370] …` 로
연속 16바이트 블록을 줄줄이 쓰는 **구조체 복사/초기화 루틴**이다.
매 프레임 갱신 코드가 아니다. 갱신 코드는 다른 베이스 오프셋을
쓴다. 여기까지가 정적 분석의 한계다.

# 크래시 원인 규명 (22:01)

배포 후 첫 실행에서 게임이 죽었다. 추측하지 않고 미니덤프를 직접
파싱해 예외 레코드를 읽었다.

```
예외 코드 : 0x80000004  =  STATUS_SINGLE_STEP
예외 주소 : 0x140A59516  ->  CrimsonDesert.exe+0xA59516
스레드    : 39580
```

**예외 주소가 대조군이 1262회 잡았던 바로 그 명령이다.** 크래시는
우리 하드웨어 브레이크포인트다.

## 근본 원인

`remove()` 가 `OpenThread` 에 실패한 스레드의 디버그 레지스터를
지우지 못한 채 예외 핸들러를 내렸다. 그 스레드가 다음에 감시 주소를
쓰는 순간, 받아 줄 핸들러가 없는 단일 스텝 예외가 되어 프로세스가
죽었다.

`program_thread()` 가 실패를 조용히 삼킨 것(`continue`)이 시작이다.
같은 결함이 두 번째 증상도 만들었다. 감시 1은 스레드 90개, 감시 2는
86개에 걸었다. 4개가 감시 1의 주소를 그대로 들고 있었고, 그 히트가
감시 2의 슬롯 0 라벨(`컴포넌트+0x88`)에 붙었다. **로그의 "705회"는
사실 여전히 `+0xA4` 쓰기였다.**

## 로컬 재현

수정 과정에서 테스트 프로세스가 **같은 코드(0x80000004)로 죽었다.**
게임 없이 재현·수정·검증할 수 있게 된 것이 이 단계의 가장 큰 소득이다.

두 번째 원인이 여기서 드러났다. 히트가 나서 예외가 전달되는 도중에
그 스레드의 디버그 레지스터를 지우면, 핸들러가 볼 때 `Dr0~3` 은 이미
0인데 `Dr6` 에는 비트가 남는다. "우리 주소와 일치하는가"로만 판별하면
이 경우를 남의 것으로 넘겨 버려 똑같이 죽는다.

## 고친 것

1. **예외 핸들러를 DLL 수명 동안 유지한다.** 감시를 해제해도 떼지
   않는다. 낙오 스레드가 때렸을 때 받아 줄 곳이 없으면 죽는다.
2. **핸들러가 현장에서 고친다.** 낙오분을 만나면 감시 중이면 현재
   설정으로 맞추고, 아니면 무장 해제한다. `SetThreadContext` 로 닿지
   못한 스레드를 되찾는 유일한 경로다.
3. **`Dr0~3 == 0` 인 히트도 우리 것으로 처리한다.** 위의 경합 때문에
   반드시 필요하다.
4. **한 번이라도 건 주소를 집합으로 기억한다.** 슬롯 배열은 마지막
   창 것만 남아, 여러 창 전의 주소를 든 낙오분을 못 알아본다.
5. **되읽어 확인한다.** `SetThreadContext` 가 성공을 보고하고도 값이
   안 들어갈 수 있다. `Dr7` 을 다시 읽어 대조한다.
6. **실패를 센다.** `OpenThread` 실패와 설정 실패를 로그에 남긴다.
   못 건 스레드가 있으면 "히트 0"을 "안 쓴다"로 읽을 수 없다.
7. **우리 것이 아닌 단일 스텝 예외는 건드리지 않는다.** 보호 코드도
   디버그 레지스터를 쓸 수 있고, 그것을 삼키면 게임이 깨진다.
8. **`DllMain` 에서 join 하지 않는다.** 로더 락 안에서 스레드를
   기다리면 교착한다. 디버그 레지스터만 내린다.

검증: 같은 테스트 바이너리가 수정 전 `0x80000004` 로 죽었고, 수정 후
8회 연속 `71 tests, 0 failures` 로 통과한다. 매회 "현장 복구 7회" 가
찍힌다 - 낙오 스레드는 실제로 존재하며, 이제 죽는 대신 복구된다.

## 이번 실행에서 건진 것

계측이 어긋났지만 아래는 유효하다.

| 관측 | 값 |
|---|---|
| 대조군 `+0xA4` | 1262회 @ `0x140A59516` |
| `컴포넌트+0x35C` | 56회 @ `0x140A5878C` |
| 프리캠 `+0xBC` | 56회 @ `0x140A58796` |
| `컴포넌트+0x360/+0x368` | 0회 (오염된 창이라 재측정 필요) |
| FOV `+0x9C` | 0회, 그런데 47 -> 40 으로 되돌아옴 (재측정 필요) |

넣으면:

- 게임의 파라미터 복사 루틴이 프리카메라를 대상으로 돌기 시작한다
  (프리캠 `+0xA4` 가 3 -> 6.239 로 갱신)
- 활성 플래그 `+0xBC` 가 0 -> 1 이 된다
- 게임은 3초 동안 슬롯을 되돌리지 않았다

답을 얻은 실험이므로 자동 경로에서 뺐다. 앞으로는 사용자가 원할 때만
도는 기능(단축키)으로 만든다.

# 돌파 (09-01 07:25)

## 보호 코드가 디버그 레지스터를 지운다

감시 중 250ms 마다 모든 스레드의 설정을 확인하도록 바꾸자 답이 나왔다.

```
스레드 통계: 총 121 | OpenThread 실패 0 | 설정 실패 0
             지워져 다시 건 횟수 2274
250ms 마다 121개 중 약 47개가 지워져 있었다
```

**게임의 보호 코드가 스레드 절반가량의 디버그 레지스터를 계속
지운다.** 다시 걸어도 그 사이에 또 지운다. `+0xA4` 를 쓰는 스레드는
살아남고 다른 스레드는 지워지는 쪽에 있어, 어떤 값은 잡히고 어떤
값은 영원히 히트 0으로 보였다.

메모리는 `type=0x20000`(MEM_PRIVATE)이라 별칭 매핑이 아니고,
같은 주소를 4바이트·8바이트로 동시에 감시해도 둘 다 0이라 SIMD 폭
문제도 아니다. **이 게임에서 하드웨어 브레이크포인트는 신뢰할 수
없는 도구다.**

## 내 스캐너 버그가 답을 가리고 있었다

VEX 접두사 판별에서 바이트 순서를 뒤집어 썼다. `C5 FB 11 87` 에서
`b[i-3]` 은 `0xFB`, `b[i-4]` 가 `0xC5` 인데 반대로 비교했다. 그래서
**AVX 로 인코딩된 저장을 전부 놓쳤다.** 게임은 AVX 로 컴파일돼 있어
float 저장 대부분이 VEX 다. 앞선 "0x360 에 쓰는 곳은 구조체 복사뿐"
이라는 결론은 이 버그의 산물이다.

## 카메라 위치는 보간된다

바로잡고 다시 훑으니 나왔다. 함수 `0x140A58540` ~ `0x140A588B0`
(880바이트), `rdi` = PlayerCameraComponent.

```asm
0x140A5872C  vaddss  xmm0, xmm12, [rdi+0x35C]   ; t 누적
0x140A58734  vminss  xmm1, xmm0, xmm5           ; 상한
0x140A58738  vmaxss  xmm6, xmm7, xmm1           ; 하한
0x140A5873C  vmovss  [rdi+0x35C], xmm6          ; t 저장
0x140A58744  vmovss  xmm2, [rdi+0x368]          ; 현재 Z
0x140A5874C  vsubss  xmm0, xmm4, xmm2           ; 목표Z - 현재Z
0x140A58750  vmulss  xmm1, xmm0, xmm6           ;   * t
0x140A58754  vaddss  xmm5, xmm1, xmm2           ;   + 현재Z
0x140A58758  vmovss  xmm3, [rdi+0x364]          ; 현재 Y  (같은 꼴)
0x140A5876C  vsubss  xmm2, xmm10, xmm8          ; X 도 같은 꼴
0x140A58780  vunpcklps xmm0, xmm1, xmm4         ; (X, Y) 묶기
0x140A58784  vmovsd  [rdi+0x360], xmm0          ; X, Y 저장
0x140A58790  mov     [rdi+0x368], eax           ; Z 저장
0x140A58796  jmp     0x140A5879E                ; +0x35C 저장을 건너뜀
0x140A58798  mov     [rdi+0x35C], esi           ; (다른 분기)
```

**`현재 = lerp(현재, 목표, t)`, `t` 는 `+0x35C`.** 두 값이 붙어 있고
함께 변하던 이유다. 그리고 `+0x35C` 와 `+0x360` 저장은 **서로 배타적인
분기**여서, 한 창에서 `+0x35C` 만 1510회 잡히고 `+0x360` 이 0회인
것도 설명된다. 디버그 레지스터 문제와는 별개의 원인이었다.

이 함수는 `[rdi+disp32]` 로 위 네 곳만 쓴다. 회전은 여기 없다.

## 실행 중인 게임에서 확인

```
쓰기 전   t=0.0000   좌표 (-10381.70, 619.90, -4498.55)
Y=700 쓰기 -> 실제 700.0000 반영
직후      t=0.0607   Y=688.53
다시      t=0.1228   Y=665.14
또        t=0.1834   Y=642.27
```

**좌표를 우리가 쓸 수 있고, 카메라가 실제로 따라 움직인다.** 게임은
`t` 를 0부터 올리며 원래 자리로 되돌린다. 해독한 모델과 실측이 맞다.

## 프리카메라 구현 방향

게임이 자기 이전 값을 읽어 보간하므로, **게임의 갱신 직후에 우리
좌표를 쓰면 보간이 이길 수 없다.**

- 후킹 지점: `0x140A58540` (표준 MSVC 프롤로그, 첫 인자 = 컴포넌트)
- 원본을 부른 뒤 `+0x360/364/368` 을 우리 값으로 덮는다
- 코드 패치가 아니라 함수 후킹이므로 무결성 검사에 걸릴 위험이 낮다

회전은 아직 못 찾았다. 위치만 잡아도 "마우스로 조준하며 카메라만
떼어 놓는" 형태는 성립한다.
