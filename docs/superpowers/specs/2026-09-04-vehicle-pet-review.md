# 탈것·반려동물·용병 관리 기능 검토 (2026-09-04)

> **정리 (2026-09-21) — 📐 설계 → 일부.** Tier 1 뷰어는 들어왔고 한글 표시명·용병 키도
> 이후 풀렸다(`STATUS.md` §1.9). **Tier 2 소환 치트를 "안전하다" 고 적은 것은
> 틀렸다** — 반복하면 처리기가 돌아오지 않아 게임이 멈춘다. 금지하고 코드를
> 걷어냈다(`TROUBLESHOOTING.md` §1.9 · §9). ID 2510 · 처리기 `0x278B860` 은 갱신 전 값이다.

게임 실행 파일(2.00.01)의 RTTI·치트 표만 보고 판단했다. 실측 전이다.

## 무엇이 있나

- **데이터 표(아이템처럼 읽힌다):** `VehicleInfoManager`,
  `MercenaryInfoManager`, `CharacterInfoManager` 가 전부
  `StaticInfoManager2` 다 - `ItemInfoManager` 를 읽는 코드가 그대로
  일반화된다. 탈것·용병·캐릭터 카탈로그를 이름(현지화)까지 낼 수 있다.
- **플레이어 소유 컴포넌트(인벤토리처럼 읽힌다):**
  `ClientMercenaryActorComponent`, `ClientVehicleActorComponent`,
  `ClientMercenaryClanActorComponent`. RTTI 로 찾아 내용을 걷으면
  "지금 가진 용병/탈것"을 낼 수 있다 - 인벤토리 컴포넌트와 같은 패턴.
- **반려동물은 독립 체계가 아니다.** `Pet` 관련은
  `TrocTrUnSetMainPetAndUnSpawnReq`, `ConditionData_IsPetLooting`,
  `UIGamePlayControlRootPet` 뿐이다. 반려동물은 소환/용병 체계에
  얹힌 것으로 보인다("메인 펫" = 소환된 동반자).
- **네트워크 요청 메시지 1085개 중 탈것·용병·소환 관련 104개.**
  `RideOnVehicleReq`, `HireMercenaryFromInventoryReq`,
  `FireMercenaryReq`, `ChangeMercenaryNameReq`, `MercenaryEquipItemReq`,
  `MoveItemInventoryToVehicleReq` 등 실제 관리 동작이 전부 여기 있다.

## 무엇이 되고 무엇이 안 되나

### Tier 1 — 읽기 전용 관리 뷰 (지금 가능, 위험 낮음)

탈것/용병/캐릭터 카탈로그와 **내가 가진 것**을 이름·스탯까지 보여주는
패널. 아이템 목록·인벤토리 패널과 **완전히 같은 인프라**(RTTI 탐색 +
안전 읽기 + 현지화)를 쓴다. 프레임마다 게임 메모리를 읽지 않고 배경
분석 루프에 얹으면 된다. 새 위험이 없다.

### Tier 2 — 캐릭터/탈것/반려동물 소환 (가능, 중간)

`SpawnCharacterCheatReq`(ID 2510)는 **살아 있는 처리기**(0x278B860 ->
0x2381330)가 있고, 열려 있는 치트 문을 지난다. 페이로드는
`캐릭터키(4) · ?(4) · 위치(12) · 플래그(1)`. 탈것·반려동물·NPC 는 전부
캐릭터(`CharacterInfo`)이므로, 특정 캐릭터를 월드에 소환하는 것은
아이템 바닥 스폰과 **같은 직접 호출 경로**로 가능하다. 실행 지점도
같다(액터 조회 자리). STATUS 에 이미 "SpawnCharacter 인자 배치"가
남은 일로 적혀 있다 - 그것을 마치면 된다.

### Tier 3 — 실제 관리(고용·해고·이름·장비·탑승) — 치트 경로로 불가, 큰 작업

- **용병 치트 3종은 껍데기다.** `RequestHireMercenaryForCheatReq`,
  `RequestDischargeMercenaryForCheatReq`,
  `ChangeHiredMercenaryWithSummonForCheatReq` 모두 처리기가 스텁
  (`0x12255F0` [마지막 호출], 실제 작업 없음)이다. 아이템 지급처럼
  직접 부를 처리기가 없다.
- 진짜 동작은 100+개의 **일반 요청 메시지**(`*Req`)에 있는데, 이것들은
  치트 처리기처럼 직접 못 부른다 - 게임의 **메시지 전송 경로**(요청
  객체를 만들어 큐에 넣고 보내기)를 태워야 한다. 우리는 지금까지
  치트 처리기를 **직접 호출**만 했지, 정상 요청을 **보낸** 적이 없다.
  그 전송 인프라를 새로 파는 것은 별도의 큰 과제이고, 형식이 틀리면
  상태를 망가뜨릴 위험이 있다.

## 권고 순서

1. **Tier 1 부터.** 탈것·용병·반려동물 뷰어. 기존 패널 구조에 그대로
   맞고 위험이 없다. 소유물 컴포넌트 읽기가 인벤토리와 같은 패턴이라
   빠르다.
2. **Tier 2.** SpawnCharacter 인자 배치를 실측으로 확정하고, 탈것/반려/
   NPC 소환을 붙인다. 검증된 치트 호출 경로를 재사용한다.
3. **Tier 3 는 별도 조사로 승격.** 메시지 전송 경로를 먼저
   리버스해야 한다. 되면 고용·장비·이름·탑승까지 열리지만, 지금
   당장의 추가가 아니다.

## Tier 1b·Tier 2 착수 조사 (2026-09-04, 실측)

### Tier 1a 완료 - 탈것·캐릭터 뷰어 (화면 확인)

`game/roster` + `render/roster_panel`. 레코드 실측 구조로 읽는다:
키는 u16(record +0x00), 이름은 `_stringKey`(+0x08)가 가리키는 엔진
문자열 객체(+0x00 char*, +0x08 u32 길이)의 **내부 이름**이다.
화면 확인: 탈것 34개, 캐릭터 7251개. `probe roster` 로 검증.

### Tier 1b - 아직 (둘 다 추가 RE 필요)

**한글 표시명.** 레코드 첫 0x80바이트 어디에도 resolve() 가 먹는
직접 현지화 키가 없다(`probe roster loc` 로 0x08~0x78 전수 확인, 0건).
아이템은 record +0x28 에 조립된 64비트 키를 들고 있었는데, 이 표들은
없다. 키를 `(엔티티<<32)|필드` 로 조립해야 하거나, 내부 이름 문자열의
해시(문자열 객체 +0x0C)로 조회하는 다른 경로로 보인다. 미해결.

**용병 키.** 레코드 +0x00 이 키가 아니라 포인터다(탈것·캐릭터와 다름).
`_key`(fields.py +0x70)도 record[0]=0, record[1]=0xE0C7 로 일정하지
않다. 색인은 정렬된 {u32 키, u32 오프셋} 배열이라(키가 순증:
0x9440,0x944E,0x944F…) 단순 레코드 오프셋으로 안 나온다. 이름은
`_stringKey`(+0x08)로 똑같이 읽힌다("Mercenary_Main"). 키만 미해결 -
색인을 걷어 {키, 레코드} 를 잇는 편이 맞아 보인다.

### Tier 2 - SpawnCharacterCheatReq 구조 (정적 확인)

ID 2510. 역직렬화 `0x2563430`, 처리기 `0x278B860`. **cheat_report 의
"작업 함수 0x2381330" 은 오분류다** - 그것은 ~100곳이 부르는 공용
헬퍼(점프 썽크)다. 진짜 소환 로직은 처리기(0x560바이트) 안에 있다.

페이로드 21바이트 = `{u32 캐릭터키, u32 B, float3 위치, u8 플래그}`
(역직렬화가 4→[+0x48], 4→[-0x40], 12→[-0x38] 로 읽는다).

처리기 인자: `(rcx=서술자, rdx=패킷{[0]=세션}, r8=파싱데이터)`.
`cmp [r8], 0; jne 소환경로` - **캐릭터키가 0이면 거부**한다(아이템
스폰의 키 검사와 같다). 소환 경로(0x278B947)는 세션 vtable +0x160 으로
스포너를 얻어 진행한다.

**아이템 바닥 스폰(`SpawnItemToGround`, 동작 확인됨)과 같은 꼴이다.**
구현은 `run_spawn` 을 본떠: (1) "SpawnCharacterCheatReq" 서술자를
resolve, (2) 파싱데이터 버퍼 조립(키·B=0·위치·플래그=0 시작),
(3) 게임 스레드(액터 조회 자리)에서 처리기 호출. 뷰어에서 줄을 골라
"월드에 소환" 을 누른다.

### 실측 (2026-09-04) - 안전하게 돌지만 개체가 안 생긴다

구현해 배포하고 여러 키(Wolf 16966, Elephant 16983, Dragon 16984,
Wyvern 16975)로 눌렀다.

- **처리기가 안전하게 돈다.** `캐릭터 소환: 세션 … 키 … 위치 …` ->
  `캐릭터 소환 끝` 이 ~1ms 에 찍히고, **크래시도 교착도 없다**(게임
  응답 정상). 미시도 치트가 처음으로 무사히 실행됐다.
- **그러나 화면에 아무것도 안 생긴다.** 처리기는 스텁이 아니라 실제
  소환 경로(0x278B947~)를 다 밟는다: 스포너 획득(세션 vtable+0x160),
  게이트(`[스포너+0x68]+0x130` vtable+0x140), **캐릭터 키를
  `[0x6331360]+0x68` 표에서 조회**(그 표는 개수 7251 = 캐릭터 표가
  맞다 - 키 조회는 성공한다), 디스크립터 조립(위치·회전), 그리고 실제
  소환 호출. 이 뒤 어딘가에서 조용히 빠지거나, 소환이 요청되나
  개체가 실체화되지 않는다.

**no-op 의 원인은 이 세 중 하나로 보인다:** (a) B(r9)·플래그가 0 이라
후반 조건에서 빠진다, (b) 후반 결과 코드(`[rbp+0x4b8]`)를 세우는 호출
(0x278BB65 의 `call [rax+0x20]`)이 실패한다, (c) 소환은 되나 팩션·스폰
컨텍스트가 없어 개체가 즉시 제거되거나 안 보이는 곳에 생긴다.

**다음 수: 처리기를 후킹해 추적한다.** 처리기 안의 분기 결과(게이트
통과 여부, 키 조회 결과, `[rbp+0x4b8]` 결과 코드)를 로그로 남겨 어디서
빠지는지 실측한다. 정적 분석만으로는 조용한 실패 지점이 많아 못
가린다. B·플래그를 1·다른 값으로 바꿔 보는 것도 값싼 시험이다.

**성과는 분명하다:** 미시도 소환 치트를 크래시·교착 없이 안전하게
부르는 경로를 확보했다. 개체 실체화만 남았다.

### 실패 사슬을 직접 추적했다 (2026-09-04, 처리기 판정 재현)

B·플래그 실험은 사람에게 시행착오를 떠넘긴 것이라 접고, `run_char_spawn`
안에서 처리기의 판정 4단계를 그대로 재현해(`trace_char_path`, SEH)
로그로 남겼다. 소환 한 번에 다음이 드러났다.

```
[추적] 스포너 0x… 컨텍스트+0x10=1 게이트결과=1 키조회레코드 0x0 순번=-1
```

**앞 세 단계(스포너·컨텍스트·게이트)는 다 통과하고 키 조회에서만
빠졌다.** 그 표(`[0x6331360]+0x68`, 개수 7251)를 읽어 보니 레코드가
`{+0x04 CharacterKey, +0x08 순번}` 이고 키 1(Kliff, 순번 0) · 키 4
(Damian, 순번 3) 로 **로스터 캐릭터 탭과 일치**했다.

**원인 1: 키 타입.** 눌렀던 16966·16988·16999 는 탈것 탭의
**VehicleKey** 라 이 캐릭터 표에 없다 - 조회 실패. **CharacterKey**
(Damian 4 등)로는 조회가 통과한다(레코드·순번이 나온다).

**원인 2: 깊은 소환 로직의 널 참조.** CharacterKey 로 키 조회를
통과한 뒤, 처리기가 더 들어가 **RVA 0x388C32 에서 크래시**한다
(0xC0000005, SEH 로 잡힘). 그 지점은 데이터 해시 함수(0x388BF0,
xxHash 상수 0x9E3779B1·0x85EBCA77)의 `imul eax,[rcx]` 이고 **rcx(해시
대상)가 널**이다. 즉 소환이 어떤 버퍼(이름·리소스로 추정)를 해시하려다
그게 없어 죽는다. Damian(순번3) · 순번19 둘 다 같은 지점.

**다음 수:** SEH `__except` 에서 크래시 시점의 호출 스택을 떠서
0x388BF0 을 부른 자리를 찾으면, 어느 버퍼가 널인지(레코드의 어떤
필드/리소스인지) 나온다. 그게 스폰에 필요한 이름·액션차트 리소스라면
B 필드나 다른 인자로 채워야 할 수 있다. 스폰 UI 는 **캐릭터 탭 키**로
제한/안내해야 한다(탈것 키는 이 경로로 안 된다).

## 주의

- 지급과 같은 실행 지점(액터 조회 자리)을 쓰므로, Tier 2 는 오늘
  드러난 실행 지점 성질(게임 로직 스레드 활동에 묶임)을 그대로
  물려받는다.
- 소환은 아이템 바닥 스폰처럼 **위치**가 필요하다. 지금은 카메라 초점
  좌표라 3인칭에서 캐릭터와 떨어진 곳에 생긴다 - 바닥을 보고 소환하는
  식으로 완화한다.
