# 스토리 탈것 소환 바퀴 — 등록·소환 경로 리서치 (2026-09-12)

원본 확보·대조 없이 복제 드래곤·ATAG 를 게임 소환 바퀴에서 부를 수
있는가. 읽기 전용(정적 디스어셈블 + 라이브 probe)으로 조사했다. 세이브에
쓰지 않았다. RVA 는 1.0.0.2850 디스크 exe 기준(라이브 로그의 부르기
후킹 RVA 0x2964B30 과 일치).

## 0. 한 줄 결론

소환 바퀴는 **색인 둘**을 쓴다. **부르기 실행은 번호 해시**(종 교체와
무관)로 하고, **바퀴 UI 목록 채우기는 종류별 색인**(종 교체가 안 따라옴)
으로 한다. 그래서 종 교체 개체는 **거점에 스폰되는데 바퀴 목록에는 안
뜬다** — 사용자 실측과 정확히 맞는다.

## 1. 소환 바퀴 = 부르기 메시지

게임 소환 메뉴(바퀴)에서 탈것을 고르면 클라이언트가
`TrocTrCallSpecialVehicleByQuickSlotReq` 를 보낸다(역직렬화 RVA
**0x2964B30**, 캡처 훅 이름 "부르기"). 기존 문서가 "이미 가진 탈것을
등록 목록에서 부른다"고 적어 둔 그 메시지다
(`2026-09-04-session-handoff.md`, `2026-09-05-vehicle-pet-add-review.md`).

## 2. 부르기 처리 사슬 (정적, 전 구간)

```
0x2964B30  부르기 역직렬화
  본문 파싱: 첫 u32 [rbp-0x49]  + float3 [rbp-0x21] 12B + u32 + u8
  게이트: [r15+0x21]==0 검사(0x2964B84)
  0x2964D03  mov rcx,[rsi+0x68] / mov rcx,[rcx+0x110]   ← 용병단 컴포넌트
  0x2964D1D  mov r8d,[rbp-0x49]                          ← 본문 첫 u32 = 키
  0x2964D2C  call 0x2AD3270                              ← 부르기 작업 함수
```

첫 인자 사슬 `[[액터+0x68]+0x110]` 은 고용·소환 작업과 같은 용병단
컴포넌트다(`companion.h`).

## 3. 부르기 작업 함수 0x2AD3270 = 전역 번호 해시 조회

```
0x2AD329D  mov  r11, [rip+..]           ; 전역 0x6C2E300  (해시 헤더 포인터)
0x2AD32AB  mov  r10d,[r11+0x68]         ; 버킷 수
0x2AD32B9  div  r10d                     ; r8d(키) % 버킷수
0x2AD32BF  shl  r10,8 ; add r10,[r11+0x78]  ; 버킷 배열
0x2AD32D6  cmp  [r10+rax*8+8], r8d       ; 버킷 항목의 키 == r8d
0x2AD32E2  mov  rax,[r11+0x80]           ; 레코드 포인터 배열
0x2AD32E9  mov  r9,[rax+rcx*8]           ; 레코드
0x2AD32ED  cmp  [r9+4], r8d              ; 레코드 +4 == r8d 최종 확인
```

즉 **전역 해시 `0x6C2E300` 에서 키 r8d(부르기 본문 첫 u32)로 레코드를
찾는다.** 없으면 실패 반환(0x2AD32F9). 이 전역·조회는 `clan.h` 가 적어
둔 "용병번호 → 레코드 해시 조회(없으면 0)"(2760 `0x208F5C0` →
2850 `0x2090A50`, spawnguard `kLookupRva`)와 같은 성격의 **번호 색인**
이다. 키는 용병번호로 강하게 추정된다(최종 확인 = 라이브 캡처, §6).

## 4. 두 색인 — 이것이 핵심이다

| 색인 | 함수/전역 | 키 | 누가 쓰나 | 종 교체 영향 |
|---|---|---|---|---|
| **번호 해시** | `0x6C2E300` (조회 2850 `0x2090A50`) | 용병번호(레코드 `+0x28`) | 부르기 **실행**, spawnguard | **없음** — 번호는 안 바뀐다 |
| **종류별 색인** | `0x208FC30` (조회 `0x2095600`) | `_mercenaryInfo` = 타입행(`CharacterInfo +0xBE`) | 바퀴 UI **목록 채우기** | **깨짐** — 종 바꿔도 옛 타입 무리에 남음 |

종 교체는 명부 레코드 `+0x20`(종=캐릭터 행)만 바꾸고 `+0x28`(번호)는
그대로 둔다. 그래서:

- **번호 해시**: 우리 개체가 그대로 있다 → 번호로 부르면 찾는다.
- **종류별 색인**: 게임이 종을 바꿀 때 이 색인을 갱신하지 않는다
  (`2026-09-10-companion-species-swap-session.md` §12-2). 드래곤(타입행 2)
  으로 바꿔도 색인상 옛 타입(펫 9) 무리에 남아, 바퀴가 "드래곤 목록"을
  종류별 색인으로 만들 때 빠진다.

### 4.1 소환 경로는 두 조회의 연쇄 — 부르기는 앞 단계를 건너뛴다

종 교체 크래시(`spawnguard.cpp`, species-swap §2.2)가 이 구분을 못 박아
준다. 게임의 "종류로 소환" 경로(`0x2ABD850`)는 이렇게 돈다.

```
0x2ABD98A  call 0x2095600        ← 종류별 색인: 종류로 등록 동반자 찾기
0x2ABD9A2  cmovne rdi,[찾은것+0x28]  그 번호, 못 찾으면 -1
0x2AD51F8  call 0x208F5C0        ← 번호 해시: 번호로 레코드 (rdi=-1 이면 0)
0x2AD520F  cmp [rax+0x28],-1     rax=0 → 크래시(가드가 메움)
```

즉 **종류별 색인 → 번호 → 번호 해시** 연쇄다. 종 교체가 비게 하는 것은
**첫 단계(종류별 색인)뿐**이고, 번호 해시(`0x208F5C0`/`0x6C2E300`)는
멀쩡하다.

**부르기(0x2AD3270)는 번호를 본문으로 직접 받아 곧장 번호 해시로 간다**
— 종류별 색인 단계가 아예 없다(§3). 그래서 종 교체로 색인이 어긋난
개체라도 **번호만 알면 부르기 작업이 찾는다.** 이것이 경로 B 의 정적
근거다.

## 5. 방증 — 거점 자동 스폰

사용자 실측(2026-09-12): 종 교체한 블랙스타가 **거점에 실제로
나타났다가 드래곤 AI 로 날아가버렸다**(원래 그 자리에 없던 개체). 거점
대기·자동 스폰은 게임이 그 개체를 **번호로 인식**해 월드에 올린다는
뜻이다 — §4 의 "번호 경로는 살아 있다"를 화면으로 뒷받침한다. 안 되는
것은 **바퀴 UI 표시**(종류별 색인)와 **AI 통제**(날아감) 둘이다.

## 6. 미확정 / 다음 실측

라이브 모듈 데이터 전역(`0x1406B32000`~ 등)이 probe 로 **전부 읽기
실패**했다 — 2850 섹션 재배치(실행 섹션이 `.idata`·`.sbss` 둘뿐,
STATUS §2.1)로 현재 읽기 경로가 그 영역에 안 닿는다. 그래서 다음은
라이브 캡처·구동으로만 확정된다.

1. **부르기 본문·ID 확정 (사용자 조작)**: 소환 바퀴로 탈것을 실제로
   부르면 캡처 훅 "부르기"가 본문을 로그로 낸다. 첫 u32 가 용병번호인지
   퀵슬롯 인덱스인지가 여기서 갈린다. (2026-09-12 시도 때는 부르기가 안
   잡히고 알 조작 2676/2386 만 잡혔다 — 소환 바퀴를 정확히 쓰지 않았을
   가능성.)
2. **번호 직접 부르기 실험**: 본문이 번호 기반이면, 복제 개체 번호로
   부르기 와이어를 만들어 구동한다. 소환되면 §4·§5 가 확정된다.
3. **종류별 색인 갱신 함수**: `0x2095600`/`0x208FC30` 이 개체를 타입
   무리에 넣는/빼는 코드. 종 교체 때 이걸 함께 부르면 바퀴 UI 에도
   뜰 수 있다(경로 A).

## 7. 원본 없이 구성하는 두 경로

| 경로 | 방법 | 이점 | 남은 위험·미지 |
|---|---|---|---|
| **A. 종류별 색인 갱신** | 종 교체 때 `0x208FC30` 색인에서 옛 타입 무리 제거 + 새 타입 무리 추가 | 바퀴 UI 에 정상 표시, 게임 그대로 소환 | 색인 조작 함수 미특정, 자료구조 미확인(전역 읽기 막힘), 잘못 쓰면 크래시 |
| **B. 번호 직접 부르기** | 오버레이 버튼이 부르기 메시지를 복제 개체 번호로 구동 | 바퀴 UI 우회, 색인 안 건드림, 번호 경로는 이미 살아 있음(§5) | 부르기 본문 확정 필요(§6-1), 드래곤 AI 통제(날아감)는 별개 문제 |

**권고 순서**: B 를 먼저 실증한다(작고, 번호 경로가 이미 방증됨). B 가
소환·탑승까지 되면 그것으로 "원본 없이 복제 드래곤 소환"이 성립한다.
바퀴 UI 통합(A)은 그 위에 얹는 개선으로, 색인 자료구조를 읽을 수 있게
된 뒤에 판정한다.

## 8. AI 통제 (별개 과제)

드래곤은 나는 탈것이라 거점 대기 개체로 두면 날아가버린다. 경로 B 로
플레이어 옆에 정상 소환하면 이 문제가 없을 수 있다(정상 소환 위치·상태로
나오므로) — 실험 2 에서 함께 확인한다.

## 9. 경로 A 정적 해부 — 종류별 색인은 컴포넌트 내부 해시 (2026-09-12)

경로 A(색인 갱신)를 게임 조작 없이 정적으로 팠다. 종류별 색인의
정체가 드러났다.

### 조회 사슬 (2850 실주소, 크래시 콜사이트에서 역산)

```
0x2ABF890  "종류로 소환" 호출자 (2760 0x2ABD850, +0x2040)
  0x2ABF92B  call 0x2090A50      번호 해시 조회 (형제 자리)
  0x2ABF930  lea  rbx,[0x6BB80C0] 빈 레코드 (2850)
  0x2ABF9CA  call 0x2096C30      ← 종류별 색인 조회 (2760 0x2095600, +0x1630)

0x2096C30  종류별 색인 조회
  add  rcx,0x18                  용병단 컴포넌트 +0x18 (명부 records)
  call 0x20910C0                 {버킷배열, 개수} getter
  순회하며 call 0x20A1470(항목, 종류)  종류 매칭
  못 찾으면 0x6BB80C0 (빈 레코드)

0x20910C0  색인 getter (입력 rcx = 컴포넌트+0x18)
  [컴포넌트+0x48] = 버킷 수      [컴포넌트+0x58] = 버킷 배열
  키(종류 16비트) % 버킷수 → 해시 조회
```

### 결론 — 색인은 용병단 컴포넌트 안에 산다

종류별 색인은 별도 전역이 아니라 **용병단 컴포넌트 `+0x48`(버킷 수)·
`+0x58`(버킷 배열) 의 해시 테이블**이다. 키는 종류(타입행), 값은 그
종류의 동반자 레코드 목록. 종 교체는 명부 레코드 `+0x20`(종)만 바꾸고
이 해시는 건드리지 않으므로, 드래곤(타입행 2)으로 바꿔도 해시상 옛
종류(펫 9) 버킷에 남아 바퀴 목록 조회에서 빠진다.

### 색인 기계 확정 (서브에이전트 정적 추적, 2850)

용병단 컴포넌트 `+0x18` 의 객체 M 안에 해시 서브인덱스가 **둘** 있다
(각 0x20바이트: `{버킷수, size, cap, ?, 버킷테이블, 슬롯배열}`).

| 서브인덱스 | 위치 | 조회 | 키 | 값 |
|---|---|---|---|---|
| A 핸들 색인 | M+0x10 (clan+0x28) | `0x2090A50` | 액터 핸들(qword) | 레코드 |
| **B 종류 색인** | M+0x30 (clan+0x48수 / +0x58표 / +0x60슬롯) | `0x20910C0` | 타입행(word) | `vector<record*>` |

- **getter `0x20910C0` 호출자 31곳은 전부 읽기**(조회·열거·카운트). 삽입은
  getter 를 거치지 않는다.
- **B 삽입 emplace = `0x140CBAAE0`**, **레코드 등록 = `0x2090AC0`**
  (AddRecord). 등록은 **종(`rec+0x20`) → `0x383820`(종→CharacterInfo) →
  `word[+0xBE]`(타입) 를 버킷키로 실시간 산출**해 emplace 하고 벡터에
  `record*` 를 append 한다. 즉 **색인 배치는 삽입 시점의 종에서 파생**된다 —
  제자리 종 교체는 이 계산을 다시 돌리지 않으므로 **옛 타입 버킷에 남는다.**
  이것이 바퀴 목록 누락의 확정 원인이다.
- **종류 매칭 `0x20A1470`** 은 카테고리 분기(`+0xBE`→`+0x5D`)만 종에서
  실시간 산출하고, **동일성 비교는 캐시 `word[rec+0x148]`**(= `CharacterInfo
  +0xBE` 를 캐시한 값)을 본다. 이 캐시를 다시 쓰는 로직이 이미 있다
  (`0x2099F60` 계열, 기록점 `0x0209A053`).

### 경로 A 판정 — 정적 실현 가능 (근거 강함)

필요한 원시 연산이 전부 특정됐다. 제자리 증분 재색인(신규 할당 없이):

1. `newType = word[CharacterInfo(새 종 rec+0x20)+0xBE]` (`0x383820` 로 산출)
2. 옛 타입 버킷에서 그 `record*` 제거 (**B erase 함수 위치는 미확정**)
3. 새 타입 버킷에 `0x140CBAAE0(clan+0x48, &newType, newType, …)` emplace +
   벡터 append (AddRecord 의 `0x2090C41`–`0x2090CBB` 블록과 동일)
4. `word[rec+0x148] = newType` 갱신 (매칭 동일성용)

버킷·슬롯 배열은 grow(`0x38B890`/`0x358B30`) 때 재할당되므로 쓰기 직전
번호로 재조회한다([[clan-roster-volatile-writes]] 와 같은 규율).

**미확정으로 남긴 것**: (1) B erase 전용 함수, (2) 전량 재구축 단일
진입점(후보 `0x2075320`), (3) `0x140CBAAE0` 의 r9(value) 정확한 용도.

### 라이브 관찰 — 명부 재구축은 실제로 일어난다 (2026-09-12)

조사 중 사용자가 동반자를 더 얻어 명부가 **47→49명**으로 늘며 용병단
컴포넌트가 통째로 새로 만들어졌다(주소 `0x2C566228E80` → `0x3553022B880`).
그런데도 종 교체한 블랙스타는 **행 7008(드래곤, 타입행 2)로 남아 있다.**

재구축이 AddRecord 경로를 타면 블랙스타의 B 버킷키가 **현재 종(드래곤)**
으로 다시 산출돼 드래곤 버킷에 들어갔을 수 있다(후보 2 가 저절로
일어났을 가능성). 그러나 매칭 캐시 `rec+0x148` 까지 새 타입으로 갱신됐는지는
별도다. **다음 실측**: 재구축된 명부에서 블랙스타가 드래곤 버킷에 있는지 +
`rec+0x148` 값, 그리고 바퀴 UI 표시 여부.

### 라이브 실측 2 — `+0x148` 은 매칭 캐시가 아니라 소유자 행 (2026-09-12)

블랙스타가 재구축 뒤에도 바퀴에 **안 뜬다**(사용자 확인). ReadProcessMemory
로 명부 레코드를 직접 읽었다(PID 18088, 컴포넌트 `0x3553022B880`).

- 블랙스타 레코드 `0x35530308C00`: `+0x20`=7008(드래곤)·`+0x22`=0xFFFF·
  **`+0x148`=0xFFFF**.
- **명부 49개 중 44개가 `+0x148`==0xFFFF.** 유효값은 둘뿐(로케이드=0,
  브리안토=3, 소유자가 플레이어블인 것).

즉 `+0x148` 은 `clan.h` 가 이미 적어 둔 **소유자 캐릭터 행**(0xFFFF=개인
임자 없음=용병대)이다. **서브에이전트가 "매칭 캐시 rec+0x148"로 지목한
자리는 명부 레코드의 이 자리가 아니다** — 매칭 `0x20A1470` 이 보는 rec 는
종류 색인 슬롯이 담은 다른 구조이거나 오프셋 혼동이다. 따라서 "안 보임"의
원인은 `+0x148` 캐시가 아니다.

**종류 색인 버킷 배치는 미확정으로 남는다.** getter `0x20910C0` 은 해시
버킷으로 **table(컴포넌트 `+0x58`, 버킷 0x100 간격)** 을 쓰는데(도입부
`call_once` 초기화 후 `[+0x30]`버킷수·`[+0x40]`table 로 `키%버킷수` 조회),
라이브에서 그 슬롯/벡터 레이아웃을 여러 원소 크기로 파싱해도 블랙스타
`record*` 를 담은 종류 벡터를 특정하지 못했다(컴포넌트 `+0x60` 슬롯 영역의
값이 유효 레코드 배열로 풀리지 않음). **정적 재검증 필요**: `0x20910C0`
반환값이 가리키는 벡터가 컴포넌트의 어느 오프셋에서 오는지, 그리고 종류
색인이 담는 `record*` 가 명부 레코드(clan+0x18 배열)와 같은 객체인지를
디스어셈블로 끝까지 확인한 뒤 라이브를 다시 본다.

### 정정 — 경로 A 판정에 미치는 영향

§9 "경로 A 판정"의 4단계 중 4번(`word[rec+0x148]=newType`)은 **철회**한다
(그 자리는 소유자다). 매칭 동일성이 실제로 보는 캐시의 위치가 재확정되기
전까지, 경로 A 의 완성 여부(색인 버킷만 고치면 뜨는가, 별도 캐시도
고쳐야 하는가)는 **미확정**이다. emplace(`0x140CBAAE0`)·등록
(`0x2090AC0`)·버킷키=종 실시간 파생이라는 색인 삽입 기계 자체는 유효하다.

### 라이브 실측 3 — 색인은 이미 드래곤으로 갱신됨, 원인은 소유자 판정 (2026-09-12)

종류 색인 런타임 레이아웃을 끝까지 확정하고 라이브로 순회했다.

**구조 (2850, getter `0x20910C0` 반환부 `0x209118D` 로 확정)**
- `table`(컴포넌트 `+0x58`): 버킷 배열, 버킷 `키 % 버킷수` 로 고르고 `0x100`
  간격. 버킷 항목 8바이트 `{키(u32)@+8+i*8, 인덱스@+0xc+i*8}`, count@버킷+0.
- `slots`(컴포넌트 `+0x60`): 원소 포인터 배열. `slots[인덱스]` = 원소.
- 원소: `{해시@+0, 키(u32)@+4, 벡터헤더@+8}`. 벡터헤더 `{begin@+0, count@+8}`.
  getter 는 **원소+8**(벡터헤더)을 반환. 벡터는 `record*` 배열.
- 그 `record*` 는 **명부 레코드와 같은 객체**(`+0x20` 종·`+0x148` 소유자로 확인).

**블랙스타는 이미 드래곤 벡터에 있다.** 라이브 순회(컴포넌트
`0x3553022B880`): type-key **2(드래곤) 벡터 count=1, 그 하나가 블랙스타
`0x35530308C00`.** type-key 9(펫) 벡터엔 없음. 즉 **명부 재구축(47→49)이
블랙스타를 드래곤 종류로 재색인했다** — §9 후보 2 가 저절로 일어났음이
실증됐다. **경로 A 의 "종류 색인 갱신"은 재구축으로 이미 해결된 셈이다.**

**그런데도 바퀴에 안 뜬다 → 원인은 종류 색인이 아니다.** 조회
`0x2096C30` 은 종류 벡터를 순회하며 각 레코드를 매칭 `0x20A1470` 으로
거른다. 그 매칭은 **소유자 판정**이다(정적 확정): 레코드 `+0x20` 종 →
`0x383820` → `word[+0xBE]`(=_mercenaryInfo) → `0x383460` →
`byte[+0x5D]`(=_summonOwnerOption) 로 분기하고, 분기에 따라 레코드
`+0x148`(소유자 행)을 **주인공 행**(전역 `0x6C2DD88` 사슬 `[+8]+0x28]+0x100`)
또는 검색키와 비교한다(`species-swap §5` 의 그 판정).

**새 가설 — 바퀴 누락은 소유자 필드다.** 블랙스타 `+0x148`=0xFFFF
(용병대, 개인 임자 없음). 드래곤의 `_summonOwnerOption` 이 "주인공 소유"를
요구하는 분기(cat1/2/3)면 0xFFFF 는 판정 실패라 목록에서 빠진다. 원본
드래곤은 소유자가 주인공(클리프)일 것이다.

**다음 실측**: (1) 드래곤 `MercenaryInfo[2]._summonOwnerOption`(+0x5D) 값 —
소유자 필수 분기인지. (2) 검증 실험: 블랙스타 `+0x148` 을 주인공 행(0)으로
세우고 바퀴에 뜨는지(소유자 필드라 무해·가역, 명부 주소는 번호로 재조회).
단, 특수 탑승물(사자 등, `+0x148`=0xFFFF)이 소환됐던 바 있어(종 교체
세션), **타입별 `_summonOwnerOption` 차이**가 관건이다 — 드래곤만 소유자
필수일 수 있다. 그렇다면 경로 A 의 최종 형태는 "종 교체 + 재구축 유발 +
소유자 필드 세우기"로 좁혀진다.

### 라이브 실측 4 — 재구축이 색인 갱신 실증 · 소유자 무관 · 드래곤은 전용 슬롯 (2026-09-14)

여분 새끼 와이번(1000483)을 드래곤(7008)으로 종 교체하고 전 과정을
라이브로 밟았다.

- **baseline (재구축 전)**: 종 교체 직후 1000483 은 `+0x20`=7008(드래곤)
  이지만 색인은 **펫(type-key 9) 버킷**에 그대로. 종 교체만으로는 색인
  미갱신 확정.
- **재구축 후 (세이브-로드)**: 1000483 이 **드래곤(type-key 2) 버킷으로
  재색인**됐다(1000724 도 동일). **§9 후보 2 실증** — 세이브-로드(명부
  재구축)가 색인을 현재 종으로 다시 빌드한다. 경로 A 의 색인 부분은
  재구축으로 저절로 해결된다.
- **소유자는 무관**: 서버 레코드 `+0x148` 을 0(주인공)으로 세워도 바퀴에
  안 뜬다. 그리고 특수 탑승물(사자·와이번, `+0x148`=0xFFFF 용병대)은
  바퀴에 **뜬다**(사용자 확인). 매칭 `0x20A1470` 은 소유자 판정이지만
  0xFFFF 를 거르지 않는다. `+0x148` 은 "안 보임"의 원인이 아니다.
- **드래곤·ATAG 는 바퀴 고정 전용 슬롯**(사용자 스크린샷): 7시 = 용
  '블랙스타', 5시 = A.T.A.G. 슬롯이 항상 자리하되 **비어 있다(회색
  안장)**. 특수 탑승물은 일반 목록(상단·하단)으로 뜨지만 드래곤·ATAG 는
  전용 슬롯이다.
- **슬롯 바인딩은 별도 UI 조건**: 바퀴 열거(`0x2ABB478`)는 종류 벡터 순회
  → 소유자 판정(`0x20A1470`) → **슬롯 매칭**(`0x2014CA0` 반환값 `di` 를
  UI 슬롯 데이터 `rbp+0x1F8`·`+0x208`·`+0x21C`·`+0x20C`·`+0x210`·`+0x218`·
  `+0x21A`·`+0x1FC` 여러 필드와 비교). `0x2014CA0` 은 `CharacterInfo`
  (`+0xAF`·`+0x88`·`+0xA0`·`+0xD0`…) 를 엮는다. 색인·소유자와 완전히 별개.

**경로 A 최종 판정.** 색인은 재구축으로 드래곤 버킷에 올바로 들어가고
소유자는 무관하지만, **드래곤·ATAG 전용 슬롯 바인딩은 종 교체·색인·
소유자로 넘을 수 없다.** 슬롯이 항상 자리하되 비어(회색) 있는 것은
원본을 스토리로 얻어야 슬롯이 활성화되는 구조를 강하게 가리킨다. 즉
**원본 없이 드래곤·ATAG 를 바퀴에 올리는 것은 불가**하다(전용 슬롯이
스토리 게이트). 슬롯 바인딩·활성 조건의 전량 규명은 UI 리버싱으로
별도 과제다.

**남은 길은 경로 B(번호 직접 부르기).** 부르기 작업 `0x2AD3270` 은 전역
번호 해시만 쓰고 전용 슬롯·종류 색인을 거치지 않으므로(§3·§4.1), 복제
개체 번호로 부르기를 구동하면 바퀴를 우회해 소환될 것으로 본다 — 다음
실증 대상.

### 라이브 실측 5 — 경로 B 시도: 소환 트리거 메시지 확정 미완 (2026-09-14)

복제 드래곤(1000483) 번호로 소환을 직접 구동해 바퀴 우회를 시도했다.

- **2962(등록 마무리)**: 결과 0 이지만 소환 안 됨. 이미 등록된 개체엔
  무효(등록 직후 전용).
- **2894(SelectMercenarySpawn)**: 코드 `0x7C181D9E` 거부. 여러 좌표
  (개활지·공중 y+100)에서 **동일**하고, **사자(1000414)도 같은 코드로
  거부**됐다. 즉 2894 는 새 소환이 아니라 **이미 나와 있는 동반자의 위치
  선택**이다. `0x7C181D9E` 는 exe 상수 검색 0건(런타임값)이라 좌표
  기반이 아니다.
- **소환 바퀴 부르기(사용자 조작)**: 부르기(`call_quick`,
  `TrocTrCallSpecialVehicleByQuickSlotReq`) 캡처에 안 걸리고 **2676
  (UseItem)** 만 잡혔다. 2676 본문의 대상값(0xF4638·0xF4366…)이 명부
  용병번호와 일치하지 않아, 소환 경로가 예상(부르기 번호 해시)과 다르거나
  한 겹 더 있다.

**판정.** 경로 B 의 번호 해시 소환 원리(§3·§4.1)는 유효하나, **실제
소환을 일으키는 메시지·본문이 이 세션에서 확정되지 않았다.** 부르기
(`0x2964B30`)가 싱글플레이에서 와이어 직렬화를 안 타는 것으로 보인다
(Req 인데 캡처 0). 다음 과제는 (1) 부르기 작업 `0x2AD3270` 을 세션 주입
으로 **직접 호출**(companion.cpp 에 구동 추가), 또는 (2) 소환 바퀴가
실제로 쓰는 메시지(2676 계열?)의 본문을 끝까지 해독하는 것이다.

**이 세션의 확정 성과**: 종류 색인 구조·재구축 갱신·소유자 무관·드래곤
전용 슬롯(스토리 게이트)을 전부 규명했다. 경로 A 는 원본 없이 바퀴
표시 불가로 판정됐고, 경로 B 는 소환 메시지 확정만 남았다.

### 라이브 실측 6 — 경로 B: 부르기로 전용 슬롯 등록 성공, 소환 실행은 클라이언트 로컬 (2026-09-14)

부르기(`TrocTrCallSpecialVehicleByQuickSlotReq`, ID **2318**, 역직렬화
`0x2964B30`)를 해석 표에 추가하고(빌드·배포·재시작), 처리기를 복제 드래곤
번호로 직접 구동했다.

- `msg` 로 부르기 와이어를 구동: 머리 5 + 본문 21바이트
  `[u32 번호][float3 좌표][u32=0][u8=0]`. 첫 u32 가 번호 해시 키(§3).
- 결과 코드 0(성공). 그리고 **소환 바퀴의 드래곤 전용 슬롯(7시)이
  회색 빈 안장에서 "블랙스타" 드래곤 아이콘으로 채워졌다**(사용자
  스크린샷). **원본 없이 전용 슬롯 등록·활성화에 성공** — 경로 A 에서
  막혔던 전용 슬롯 벽을 부르기가 넘었다.
- 그러나 **실제 소환(월드 스폰)은 안 된다.** 좌표를 공중(y+1500)·지면
  (y=577) 어디로 줘도 슬롯만 등록되고 개체는 안 나온다.
- **결정적**: 사용자가 그 슬롯을 게임 UI 로 직접 클릭했을 때 **캡처가
  0건**이다(로그 위치 대비 새 메시지 없음). 즉 슬롯에서의 소환 실행은
  서버 Req 가 아니라 **클라이언트 로컬 로직**이다. 부르기 Req 가 애초에
  캡처 안 됐던 것도 같은 이유다.

**경로 B 판정.** 부르기(서버 메시지)는 **전용 슬롯 등록**까지 한다(원본
없이 슬롯을 채우는 데 성공). 하지만 **실제 소환은 클라이언트 로컬**이라
서버 메시지로 강제되지 않는다. 종 교체 드래곤이 그 클라이언트 소환에서
안 나온다. 다음 과제는 클라이언트 소환 로직(월드 스폰)인데, 서버 쪽보다
훨씬 깊은 리버싱이다.

**이 세션 총결산.** 종류 색인 구조·재구축 갱신·소유자 무관·전용 슬롯
구조를 전부 규명했고, **부르기로 원본 없이 드래곤 전용 슬롯을 등록**하는
데까지 도달했다. 남은 유일한 벽은 클라이언트 로컬 소환 실행이다.

### 라이브 실측 7 — 소환의 진짜 벽: 플레이어 소유 타입 레지스트리 (2026-09-14)

부르기 소환 사슬을 서브에이전트가 정적으로 끝까지 추적했다(RTTI 클래스명
확정).

```
0x2964B30 부르기 핸들러
 └0x2AD3270 → 0x2AD9890 → 0x2ADBA00  소환 실행자
    ├ 0x2AB9020  "부른 탈것" 리스트에 append = 슬롯 등록(무조건, 아이콘)
    ├ 0x2964DC8 → 0xFB7F060  AsyncRequestSend msg 0x3f5 = 클라 알림(무조건)
    └ 0x2ACA250  ★ 게이트: 플레이어 소유 타입 레지스트리 매칭
        ├ 매칭   → 0x2A22DE0  실제 CommonActor 필드 스폰
        └ 무매칭 → mov [rsi],0 (성공 0) 후 리턴, 아무것도 안 만듦
```

**즉 슬롯 등록·클라 알림은 항상 되고(아이콘 채움), 실제 월드 스폰만
`0x2ACA250` 게이트에서 걸린다.** 이것이 "결과 0(성공) + 슬롯 채워짐 +
소환 안 됨 + 거부 메시지 없음"의 정확한 코드 실체다 — 사용자가 짚은
"거부 문구 없이 반응 없음"이 바로 이 무매칭 성공-0 경로다.

**게이트 `0x2ACA250` 이 보는 것**: 플레이어 소유 탈것 **타입 레지스트리**
(전역 `0x6C2DD88`, TLS `gs:[0x58]+0x1ec` 로 선택 → `[+8]` → 그룹 배열).
검색 키 = 종의 `_mercenaryInfo` 타입행(`CharacterInfo+0xBE`). 이 레지스트리는
**스토리 획득으로만 채워진다.** 사자·와이번(타입행 5)이 소환되는 것은
플레이어가 특수 탑승물을 실제 소유해 레지스트리에 5 가 있기 때문이고,
드래곤(2)·ATAG(3·4)는 미획득이라 없다.

**종 교체로 못 넘는다.** 종 교체는 명부 레코드의 종(`+0x20`)만 바꾸고 이
레지스트리는 안 건드린다. 부차 게이트(`+0x6E`·`+0xBE`·MercenaryInfo `+0x20`
카테고리)는 현재 종에서 실시간 파생돼 통과하지만, `0x2ACA250` 의 소유
레지스트리 매칭이 최종 벽이다. **이것이 전용 슬롯 스토리 게이트의 코드
실체다.**

**ATAG 슬롯 미표시(2026-09-14)**: ATAG(1000602→6818)는 종 교체만 하고
재구축(세이브-로드)을 안 해 슬롯 아이콘도 안 떴다. 드래곤은 재구축 후에
아이콘이 떴다 — 슬롯 등록에도 종류 색인 재구축이 얽힌 것으로 보인다(부차).

**라이브 레지스트리 특정 미완**: `0x6C2DD88` → `[+8]`(=0x3616829E000)까지
읽히나 서브에이전트의 `+0x2F8` 은 라이브에서 0 이었다(정적 오프셋 어긋남).
게이트 전역이 TLS 로 선택되는 것이라 정적 읽기로 배열을 못 잡았다.

**남은 해결 경로**: 이 소유 타입 레지스트리에 드래곤(2)·ATAG(3·4) 타입행을
넣으면 `0x2ACA250` 매칭 → `0x2A22DE0` 실제 스폰. 다만 (1) TLS 기반 라이브
자료구조 재특정, (2) 안전한 쓰기(스토리 세이브 데이터일 수 있어 오염 위험)가
큰 작업으로 남는다. 라이브 대조(소환되는 사자 vs 안 되는 드래곤에서
`0x2ACA250` 진입 시 레지스트리 매칭 결과 비교)로 게이트 유일성을 먼저
확정한 뒤 조작하는 것이 안전하다.

### 라이브 실측 8 — 소유 타입 레지스트리 사슬 확정 (2026-09-14)

게이트 `0x2ACA250` 을 직접 디스어셈블해 레지스트리 사슬을 라이브로 잡았다
(서브에이전트 정적 오프셋 정정: `[+0]` 단계가 하나 더 있었다).

```
0x2ACA28E  rax = [0x6C2DD88]          전역 (모듈 데이터, 읽힘)
0x2ACA2A1  rax = [rax]                [+0]  ← 이 단계를 프리 리서치가 빠뜨렸다
0x2ACA2A4  rcx = [rax+8]
0x2ACA2A8  rax = [rcx+0x2f8]          = reg
0x2ACA2AF  rdi = [reg+0xc0]           begin (그룹 인덱스 배열, word)
           end = begin + [reg+0xc8]*2  count = [reg+0xc8] (u32)
0x2ACA2C8  각 인덱스 -> call 0x382A30(->0x86F79B0) 그룹 getter -> 그룹 객체
0x2ACA2DA  r8 = [그룹+0x58]           그룹의 타입행 배열
0x2ACA2E2  cmp bx, [r8+rax*2]         검색 타입행 == 그룹 타입행? 매칭 -> 스폰
```

**라이브 값(2026-09-14, 컴포넌트 세션)**:
- `[0x6C2DD88]`=0x3616B1A7440 → `[+0]`=0x3616833D340 → `[+8]`=0x3615FA67300 →
  `[+0x2F8]`=reg 0x3615F860700.
- `reg+0xc0`=begin 0x361BDE48710, `reg+0xc8`=count **3**.
- **그룹 인덱스 배열 = [24, 25, 26]**. 게이트는 이 세 그룹의 `+0x58` 타입행
  배열에서 검색 타입행(드래곤=2)을 찾는다.

**남은 것 — 안전한 쓰기 지점 미완**: 그룹 getter `0x86F79B0` 이 **번호 해시
전역 `0x6C2E300`**(부르기 작업이 쓰는 그 전역)을 거쳐 그룹 인덱스→그룹 객체를
조회한다. 즉 소유 타입 레지스트리가 별도 자료구조가 아니라 여러 색인이
공유하는 전역 위에 얹혀 있어, 드래곤(2)·ATAG(3·4)를 어느 그룹의 `+0x58`
배열에 어떻게 안전히 넣을지(배열 grow·재할당·공유 오염)가 이 세션에서
확정되지 않았다. 다음 집중 과제: 그룹 24/25/26 의 `+0x58` 배열을 라이브로
읽어 사자(타입행 5)가 든 그룹을 찾고, 그 배열에 드래곤 타입행을 추가하는
안전한 방법(게임 함수 재사용 vs 제자리 배열 확장)을 특정.
