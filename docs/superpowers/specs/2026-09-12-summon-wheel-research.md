# 스토리 탈것 소환 바퀴 — 등록·소환 경로 리서치 (2026-09-12)

원본 확보·대조 없이 복제 드래곤·ATAG 를 게임 소환 바퀴에서 부를 수
있는가. 읽기 전용(정적 디스어셈블 + 라이브 probe)으로 조사했다. 세이브에
쓰지 않았다. RVA 는 1.0.0.2850 디스크 exe 기준(라이브 로그의 부르기
후킹 RVA 0x2964B30 과 일치).

## 0. 한 줄 결론

소환 바퀴는 **색인 둘**을 쓴다. **부르기 실행은 번호 해시**(종 교체와
무관)로 하고, **바퀴 UI 목록 채우기는 종류별 색인**(종 교체가 안 따라옴)
으로 한다. 그래서 종 교체 개체는 **거점에 스폰되는데 바퀴 목록에는 안
뜬다** — 사용자 실측과 정확히 맞는다.

## 1. 소환 바퀴 = 부르기 메시지

게임 소환 메뉴(바퀴)에서 탈것을 고르면 클라이언트가
`TrocTrCallSpecialVehicleByQuickSlotReq` 를 보낸다(역직렬화 RVA
**0x2964B30**, 캡처 훅 이름 "부르기"). 기존 문서가 "이미 가진 탈것을
등록 목록에서 부른다"고 적어 둔 그 메시지다
(`2026-09-04-session-handoff.md`, `2026-09-05-vehicle-pet-add-review.md`).

## 2. 부르기 처리 사슬 (정적, 전 구간)

```
0x2964B30  부르기 역직렬화
  본문 파싱: 첫 u32 [rbp-0x49]  + float3 [rbp-0x21] 12B + u32 + u8
  게이트: [r15+0x21]==0 검사(0x2964B84)
  0x2964D03  mov rcx,[rsi+0x68] / mov rcx,[rcx+0x110]   ← 용병단 컴포넌트
  0x2964D1D  mov r8d,[rbp-0x49]                          ← 본문 첫 u32 = 키
  0x2964D2C  call 0x2AD3270                              ← 부르기 작업 함수
```

첫 인자 사슬 `[[액터+0x68]+0x110]` 은 고용·소환 작업과 같은 용병단
컴포넌트다(`companion.h`).

## 3. 부르기 작업 함수 0x2AD3270 = 전역 번호 해시 조회

```
0x2AD329D  mov  r11, [rip+..]           ; 전역 0x6C2E300  (해시 헤더 포인터)
0x2AD32AB  mov  r10d,[r11+0x68]         ; 버킷 수
0x2AD32B9  div  r10d                     ; r8d(키) % 버킷수
0x2AD32BF  shl  r10,8 ; add r10,[r11+0x78]  ; 버킷 배열
0x2AD32D6  cmp  [r10+rax*8+8], r8d       ; 버킷 항목의 키 == r8d
0x2AD32E2  mov  rax,[r11+0x80]           ; 레코드 포인터 배열
0x2AD32E9  mov  r9,[rax+rcx*8]           ; 레코드
0x2AD32ED  cmp  [r9+4], r8d              ; 레코드 +4 == r8d 최종 확인
```

즉 **전역 해시 `0x6C2E300` 에서 키 r8d(부르기 본문 첫 u32)로 레코드를
찾는다.** 없으면 실패 반환(0x2AD32F9). 이 전역·조회는 `clan.h` 가 적어
둔 "용병번호 → 레코드 해시 조회(없으면 0)"(2760 `0x208F5C0` →
2850 `0x2090A50`, spawnguard `kLookupRva`)와 같은 성격의 **번호 색인**
이다. 키는 용병번호로 강하게 추정된다(최종 확인 = 라이브 캡처, §6).

## 4. 두 색인 — 이것이 핵심이다

| 색인 | 함수/전역 | 키 | 누가 쓰나 | 종 교체 영향 |
|---|---|---|---|---|
| **번호 해시** | `0x6C2E300` (조회 2850 `0x2090A50`) | 용병번호(레코드 `+0x28`) | 부르기 **실행**, spawnguard | **없음** — 번호는 안 바뀐다 |
| **종류별 색인** | `0x208FC30` (조회 `0x2095600`) | `_mercenaryInfo` = 타입행(`CharacterInfo +0xBE`) | 바퀴 UI **목록 채우기** | **깨짐** — 종 바꿔도 옛 타입 무리에 남음 |

종 교체는 명부 레코드 `+0x20`(종=캐릭터 행)만 바꾸고 `+0x28`(번호)는
그대로 둔다. 그래서:

- **번호 해시**: 우리 개체가 그대로 있다 → 번호로 부르면 찾는다.
- **종류별 색인**: 게임이 종을 바꿀 때 이 색인을 갱신하지 않는다
  (`2026-09-10-companion-species-swap-session.md` §12-2). 드래곤(타입행 2)
  으로 바꿔도 색인상 옛 타입(펫 9) 무리에 남아, 바퀴가 "드래곤 목록"을
  종류별 색인으로 만들 때 빠진다.

### 4.1 소환 경로는 두 조회의 연쇄 — 부르기는 앞 단계를 건너뛴다

종 교체 크래시(`spawnguard.cpp`, species-swap §2.2)가 이 구분을 못 박아
준다. 게임의 "종류로 소환" 경로(`0x2ABD850`)는 이렇게 돈다.

```
0x2ABD98A  call 0x2095600        ← 종류별 색인: 종류로 등록 동반자 찾기
0x2ABD9A2  cmovne rdi,[찾은것+0x28]  그 번호, 못 찾으면 -1
0x2AD51F8  call 0x208F5C0        ← 번호 해시: 번호로 레코드 (rdi=-1 이면 0)
0x2AD520F  cmp [rax+0x28],-1     rax=0 → 크래시(가드가 메움)
```

즉 **종류별 색인 → 번호 → 번호 해시** 연쇄다. 종 교체가 비게 하는 것은
**첫 단계(종류별 색인)뿐**이고, 번호 해시(`0x208F5C0`/`0x6C2E300`)는
멀쩡하다.

**부르기(0x2AD3270)는 번호를 본문으로 직접 받아 곧장 번호 해시로 간다**
— 종류별 색인 단계가 아예 없다(§3). 그래서 종 교체로 색인이 어긋난
개체라도 **번호만 알면 부르기 작업이 찾는다.** 이것이 경로 B 의 정적
근거다.

## 5. 방증 — 거점 자동 스폰

사용자 실측(2026-09-12): 종 교체한 블랙스타가 **거점에 실제로
나타났다가 드래곤 AI 로 날아가버렸다**(원래 그 자리에 없던 개체). 거점
대기·자동 스폰은 게임이 그 개체를 **번호로 인식**해 월드에 올린다는
뜻이다 — §4 의 "번호 경로는 살아 있다"를 화면으로 뒷받침한다. 안 되는
것은 **바퀴 UI 표시**(종류별 색인)와 **AI 통제**(날아감) 둘이다.

## 6. 미확정 / 다음 실측

라이브 모듈 데이터 전역(`0x1406B32000`~ 등)이 probe 로 **전부 읽기
실패**했다 — 2850 섹션 재배치(실행 섹션이 `.idata`·`.sbss` 둘뿐,
STATUS §2.1)로 현재 읽기 경로가 그 영역에 안 닿는다. 그래서 다음은
라이브 캡처·구동으로만 확정된다.

1. **부르기 본문·ID 확정 (사용자 조작)**: 소환 바퀴로 탈것을 실제로
   부르면 캡처 훅 "부르기"가 본문을 로그로 낸다. 첫 u32 가 용병번호인지
   퀵슬롯 인덱스인지가 여기서 갈린다. (2026-09-12 시도 때는 부르기가 안
   잡히고 알 조작 2676/2386 만 잡혔다 — 소환 바퀴를 정확히 쓰지 않았을
   가능성.)
2. **번호 직접 부르기 실험**: 본문이 번호 기반이면, 복제 개체 번호로
   부르기 와이어를 만들어 구동한다. 소환되면 §4·§5 가 확정된다.
3. **종류별 색인 갱신 함수**: `0x2095600`/`0x208FC30` 이 개체를 타입
   무리에 넣는/빼는 코드. 종 교체 때 이걸 함께 부르면 바퀴 UI 에도
   뜰 수 있다(경로 A).

## 7. 원본 없이 구성하는 두 경로

| 경로 | 방법 | 이점 | 남은 위험·미지 |
|---|---|---|---|
| **A. 종류별 색인 갱신** | 종 교체 때 `0x208FC30` 색인에서 옛 타입 무리 제거 + 새 타입 무리 추가 | 바퀴 UI 에 정상 표시, 게임 그대로 소환 | 색인 조작 함수 미특정, 자료구조 미확인(전역 읽기 막힘), 잘못 쓰면 크래시 |
| **B. 번호 직접 부르기** | 오버레이 버튼이 부르기 메시지를 복제 개체 번호로 구동 | 바퀴 UI 우회, 색인 안 건드림, 번호 경로는 이미 살아 있음(§5) | 부르기 본문 확정 필요(§6-1), 드래곤 AI 통제(날아감)는 별개 문제 |

**권고 순서**: B 를 먼저 실증한다(작고, 번호 경로가 이미 방증됨). B 가
소환·탑승까지 되면 그것으로 "원본 없이 복제 드래곤 소환"이 성립한다.
바퀴 UI 통합(A)은 그 위에 얹는 개선으로, 색인 자료구조를 읽을 수 있게
된 뒤에 판정한다.

## 8. AI 통제 (별개 과제)

드래곤은 나는 탈것이라 거점 대기 개체로 두면 날아가버린다. 경로 B 로
플레이어 옆에 정상 소환하면 이 문제가 없을 수 있다(정상 소환 위치·상태로
나오므로) — 실험 2 에서 함께 확인한다.

## 9. 경로 A 정적 해부 — 종류별 색인은 컴포넌트 내부 해시 (2026-09-12)

경로 A(색인 갱신)를 게임 조작 없이 정적으로 팠다. 종류별 색인의
정체가 드러났다.

### 조회 사슬 (2850 실주소, 크래시 콜사이트에서 역산)

```
0x2ABF890  "종류로 소환" 호출자 (2760 0x2ABD850, +0x2040)
  0x2ABF92B  call 0x2090A50      번호 해시 조회 (형제 자리)
  0x2ABF930  lea  rbx,[0x6BB80C0] 빈 레코드 (2850)
  0x2ABF9CA  call 0x2096C30      ← 종류별 색인 조회 (2760 0x2095600, +0x1630)

0x2096C30  종류별 색인 조회
  add  rcx,0x18                  용병단 컴포넌트 +0x18 (명부 records)
  call 0x20910C0                 {버킷배열, 개수} getter
  순회하며 call 0x20A1470(항목, 종류)  종류 매칭
  못 찾으면 0x6BB80C0 (빈 레코드)

0x20910C0  색인 getter (입력 rcx = 컴포넌트+0x18)
  [컴포넌트+0x48] = 버킷 수      [컴포넌트+0x58] = 버킷 배열
  키(종류 16비트) % 버킷수 → 해시 조회
```

### 결론 — 색인은 용병단 컴포넌트 안에 산다

종류별 색인은 별도 전역이 아니라 **용병단 컴포넌트 `+0x48`(버킷 수)·
`+0x58`(버킷 배열) 의 해시 테이블**이다. 키는 종류(타입행), 값은 그
종류의 동반자 레코드 목록. 종 교체는 명부 레코드 `+0x20`(종)만 바꾸고
이 해시는 건드리지 않으므로, 드래곤(타입행 2)으로 바꿔도 해시상 옛
종류(펫 9) 버킷에 남아 바퀴 목록 조회에서 빠진다.

### 색인 기계 확정 (서브에이전트 정적 추적, 2850)

용병단 컴포넌트 `+0x18` 의 객체 M 안에 해시 서브인덱스가 **둘** 있다
(각 0x20바이트: `{버킷수, size, cap, ?, 버킷테이블, 슬롯배열}`).

| 서브인덱스 | 위치 | 조회 | 키 | 값 |
|---|---|---|---|---|
| A 핸들 색인 | M+0x10 (clan+0x28) | `0x2090A50` | 액터 핸들(qword) | 레코드 |
| **B 종류 색인** | M+0x30 (clan+0x48수 / +0x58표 / +0x60슬롯) | `0x20910C0` | 타입행(word) | `vector<record*>` |

- **getter `0x20910C0` 호출자 31곳은 전부 읽기**(조회·열거·카운트). 삽입은
  getter 를 거치지 않는다.
- **B 삽입 emplace = `0x140CBAAE0`**, **레코드 등록 = `0x2090AC0`**
  (AddRecord). 등록은 **종(`rec+0x20`) → `0x383820`(종→CharacterInfo) →
  `word[+0xBE]`(타입) 를 버킷키로 실시간 산출**해 emplace 하고 벡터에
  `record*` 를 append 한다. 즉 **색인 배치는 삽입 시점의 종에서 파생**된다 —
  제자리 종 교체는 이 계산을 다시 돌리지 않으므로 **옛 타입 버킷에 남는다.**
  이것이 바퀴 목록 누락의 확정 원인이다.
- **종류 매칭 `0x20A1470`** 은 카테고리 분기(`+0xBE`→`+0x5D`)만 종에서
  실시간 산출하고, **동일성 비교는 캐시 `word[rec+0x148]`**(= `CharacterInfo
  +0xBE` 를 캐시한 값)을 본다. 이 캐시를 다시 쓰는 로직이 이미 있다
  (`0x2099F60` 계열, 기록점 `0x0209A053`).

### 경로 A 판정 — 정적 실현 가능 (근거 강함)

필요한 원시 연산이 전부 특정됐다. 제자리 증분 재색인(신규 할당 없이):

1. `newType = word[CharacterInfo(새 종 rec+0x20)+0xBE]` (`0x383820` 로 산출)
2. 옛 타입 버킷에서 그 `record*` 제거 (**B erase 함수 위치는 미확정**)
3. 새 타입 버킷에 `0x140CBAAE0(clan+0x48, &newType, newType, …)` emplace +
   벡터 append (AddRecord 의 `0x2090C41`–`0x2090CBB` 블록과 동일)
4. `word[rec+0x148] = newType` 갱신 (매칭 동일성용)

버킷·슬롯 배열은 grow(`0x38B890`/`0x358B30`) 때 재할당되므로 쓰기 직전
번호로 재조회한다([[clan-roster-volatile-writes]] 와 같은 규율).

**미확정으로 남긴 것**: (1) B erase 전용 함수, (2) 전량 재구축 단일
진입점(후보 `0x2075320`), (3) `0x140CBAAE0` 의 r9(value) 정확한 용도.

### 라이브 관찰 — 명부 재구축은 실제로 일어난다 (2026-09-12)

조사 중 사용자가 동반자를 더 얻어 명부가 **47→49명**으로 늘며 용병단
컴포넌트가 통째로 새로 만들어졌다(주소 `0x2C566228E80` → `0x3553022B880`).
그런데도 종 교체한 블랙스타는 **행 7008(드래곤, 타입행 2)로 남아 있다.**

재구축이 AddRecord 경로를 타면 블랙스타의 B 버킷키가 **현재 종(드래곤)**
으로 다시 산출돼 드래곤 버킷에 들어갔을 수 있다(후보 2 가 저절로
일어났을 가능성). 그러나 매칭 캐시 `rec+0x148` 까지 새 타입으로 갱신됐는지는
별도다. **다음 실측**: 재구축된 명부에서 블랙스타가 드래곤 버킷에 있는지 +
