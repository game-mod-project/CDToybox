# 인벤토리 구조와 아이템 인스턴스

2026-09-02. 담금질·소켓이 반영된 장비를 게임 밖으로 빼내고 다시
넣으려면(export/import) 아이템 인스턴스를 읽어야 한다. 그 조사 기록.

## 왜 필요한가

지금 지급은 **담금질·소켓이 빈 장비**를 준다. 이 게임은 레벨이 없고
스탯이 장비에서 오므로, 캐릭터가 손댄 장비를 그대로 보관했다 꺼내는
것이 실질적인 기능이다.

## 인벤토리 레코드 (결론)

서버 인벤토리 컴포넌트(`pa::ServerInventoryActorComponent`)가
컨테이너를 여럿 들고 있고, 각 컨테이너가 레코드 배열을 든다.
**레코드 간격은 0xC8.**

```
레코드 +0x00  u64  인스턴스 ID
       +0x08  u16  아이템 표에서의 순번   <- "아래 답" 절
       +0x0A  u16  담금질                 <- "화면과 대조" 절
       +0x10  i64  개수
       +0x38  u64  ?
       +0x60  ptr  소켓 배열              <- "소켓" 절
       +0x68  u32 5 / u32 5               소켓 5칸
```

컨테이너로 가는 길은 "컨테이너로 가는 길" 절에 있다. 빈 칸은
인스턴스 ID 가 전부 `0xFF` 이고 순번이 `0xFFFF` 다.

아래는 여기까지 온 과정이다. 헛짚은 것도 같이 남긴다.

## 두 가지 헛짚음 (같은 실수를 반복하지 않도록)

**간격을 0x190 으로 잡았다.** 그러면 한 칸씩 건너뛰어 37개 중 19개만
보인다. 0x190 이 정확히 0xC8 의 두 배라 레코드가 그럴듯하게 정렬돼
보였다. 레코드 `+0xC8` 에 다음 레코드의 ID 가 있는 것을 보고 알았다.

**화면의 "99 / 130" 을 메모리에서 찾으려 했다.** 그 값은 UI 가 여러
컨테이너를 합산해 만든 것이라 메모리에 그대로 없다. u32 쌍
`(99, 130)` 을 검색했더니 유일한 후보가 연속된 정수 표였다.

## 식별 체계가 둘이다

인벤토리 레코드의 `+0x08` 은 아이템 표 키가 아니다.

```
loc item 1163042  ->  늑대의 한손검 (이름·설명 있음)
loc item 5915     ->  없음
loc item 202518   ->  없음
배열 범위에서 1163042 검색  ->  없음
레코드 전체에서 6810표 키 검색 -> 없음
```

### 변환 함수 (RVA 0x12F9570)

표 조회 함수를 후킹해 잡았다. 인벤토리 툴팁을 띄우면 걸린다.

```
스트림에서 u32 읽기        아이템 키 (1163042)
rcx = [0x6331358] + 0x68   아이템 표
call 0x31BBF0              조회
movzx eax, word ptr [rax]  결과의 첫 u16
mov word ptr [rbx], ax     그게 인벤토리가 저장하는 값
```

실측 로그:

```
표 조회: 키 1163042 표 0x31F65CB6DE8 부른 곳 모듈+0x12F95B1
표 조회: 키 1163044 ...
표 조회: 키 1163045 ...
표 조회: 키 1163046 ...
```

## 답: `+0x08` = {u16 순번, u16 담금질}

아랫 u16 이 `ItemInfoManager` 목록에서의 위치(0부터)이고, **윗 u16 이
담금질**이다.

실측으로 확정했다.

```
인벤토리 [0] +0x08 = 5915  ->  순번 5915  =  그로테반트 판금 투구
         [1]        5911  ->            5911     그로테반트 판금 갑옷
         [2]        5913  ->            5913     그로테반트 판금 장갑
         [3]      202518  ->  {3, 5914}          그로테반트 판금 신발
         [4]        5912  ->            5912     그로테반트 망토
```

**한 벌 방어구가 통째로 나온다.** 값이 5911~5922 라는 좁은 대역에
몰려 있던 것이 이것으로 설명된다 - 세트 부위는 표에서 이웃이다.

## 윗 u16 은 담금질이다 (화면과 대조)

게임 창을 `PrintWindow` 로 떠서 툴팁과 맞췄다. 담금질은 툴팁에서
**10칸 게이지**로, 아이콘 좌상단에서는 **눈금(`|` `||` `|||`)**으로
나온다.

```
바르그란 방패   아이콘 |||   담금질 게이지 3칸   레코드 +0x08 = 0x00031721
                                                  = {순번 5921, 3}
늑대의 한손검   눈금 없음    게이지 0칸          순번 6496, 윗값 0
검은 운명(장착) 눈금 없음    게이지 0칸
```

레코드 원본:

```
0x57D772A6BD0  58 42 0F 00 00 00 00 00 | 21 17 03 00 | 15 2C 00 00
               인스턴스 ID 1000536       순번 5921  담금질 3
```

**같은 아이템이 윗값 0 과 3 인 인스턴스로 둘 다 존재한다.** 다른
컨테이너의 바르그란 방패(인스턴스 18242)는 윗값이 0 이다. 타입
속성이 아니라 인스턴스 상태라는 뜻이고, 이것이 담금질의 성질이다.

### 등급이 아니라는 것도 확인했다

가장 그럴듯한 경쟁 가설이었다. 아이템 표의 등급(`+0x210` 의 첫
바이트)을 읽어 잘라냈다.

```
카이로스 망토(1000546)       등급 2   윗값 1
카이로스 판금 장갑(1000560)  등급 2   윗값 3
카이로스 판금 투구(1000521)  등급 2   윗값 0
```

셋 다 등급 2 인데 윗값이 갈린다.

### 헷갈렸던 것

`invlist` 로 읽히는 41칸 컨테이너에는 **같은 값이 반복**된다 -
카이로스 망토 17개가 전부 윗값 1, 카이로스 판금 장갑 6개가 전부 3
이다. 인스턴스 ID 는 다 다르다. 담금질이 인스턴스 상태라면 이상해
보이지만, 그 컨테이너는 **플레이어 가방이 아니다** - 화면의 가방에
있는 늑대의 한손검(순번 6496)이 거기 없다. 같은 담금질로 찍힌
재고 뭉치로 보인다.

플레이어 가방의 레코드는 `invfind <순번|담금질<<16>:<개수>` 로
찾는다. 컨테이너 목록에 안 잡히는 것도 이렇게 집을 수 있다.

### 대응표의 실체

```
전역 [RVA 0x6331358] -> 객체
객체 +0x68  표
표   +0x00  u32 ?              307
     +0x04  u32 개수           6810 (아이템 표 개수와 같다)
     +0x08  u32 해시 용량      8088
     +0x0C  u32 레코드 개수    6810
     +0x10  ptr 해시 슬롯 배열  {u32 아이템 키, u32 순번} × 8088
     +0x18  ptr 레코드 포인터 배열 × 6810
레코드 (16바이트)
     +0x00  u32 ?   순번이 아니다 (순번 5915 의 레코드가 946)
     +0x04  u32 아이템 키
```

해시 슬롯의 빈 칸은 키가 `0xFFFFFFFF` 다 - 배열 끝이 그 값으로 찬다.

**레코드 순서는 `ItemInfoManager` 의 순서와 같다.** 6,810칸을 전부
대조해 한 칸도 다르지 않았다. 그래서 역조회는 목록의 `[순번]` 을
집는 것으로 끝난다.

```
$ cdtb_probe itemmap
아이템 표 6810개
표       0x57CCA317B68   개수 6810 / 용량 8088
채워진 칸 6810개
순번 최대 6809, 중복 0건
아이템 키 중복 0건, 아이템 표에 없는 키 0건
아이템 표와 순서가 6810칸 전부 같습니다
```

### 전역은 패턴으로 찾는다

RVA `0x6331358` 을 박아 두지 않는다. Denuvo 가 빌드마다 섹션을
뒤섞으므로 현지화 전역과 같이 변환 함수 본문에서 `disp32` 를 읽는다.

다만 현지화와 달리 **한 곳만 일치하지 않는다 - 실측 34곳이다.**
같은 꼴의 조회 코드가 표마다 있다. 후보를 전부 모은 뒤 표의 개수가
아이템 개수(6810)인 것을 고른다.

개수가 판별자인 이유는 용량으로는 갈리지 않기 때문이다 - 용량이
8,088 인 후보만도 셋이었고(개수 6810 · 7251 · 6703), 개수가 6,810 인
것은 하나뿐이었다.

### 헛짚음 셋 (같은 실수를 반복하지 않도록)

**슬롯의 두 번째 u32 를 짧은 식별자로 읽었다.** 그것은 순번이다.
키 1163042 의 슬롯 값 6496 은 "늑대의 한손검의 짧은 id" 가 아니라
"목록에서 6496번" 이라는 뜻이다.

**레코드의 첫 u16 을 짧은 식별자로 읽었다.** 순번 5915 의 레코드는
946 을 들고 있는데, 인벤토리에 있는 값은 5915 다. `movzx eax, word
ptr [rax]` 의 `rax` 는 레코드가 아니라 슬롯의 값 칸으로 보인다.

**16진수를 손으로 10진수로 옮겼다.** `0xF4DD9` 를 1002457 로,
`0x46D43` 을 289603 으로 적었다. 각각 1002969 · 290115 이다.
도구가 낸 값과 어긋나 한참을 헤맸다. 변환은 도구에 맡긴다.

## 도구

```
probe invlist [주소]                       인벤토리를 이름·담금질까지
probe itemvalue [최대]                     힙에서 아이템 인스턴스 서명 검색
probe itemmap [최대]                       순번 <-> 아이템 키 대응표
probe itemmap id <순번> ...                순번으로 아이템 되찾기
probe itemmap key <아이템키> ...           아이템 키의 순번
probe itemmap cand                         변환 함수 패턴 후보 전부
probe invexport [파일]                     인벤토리를 보관함 파일로
```

주소를 안 주면 RTTI 로 찾아 내용이 있는 첫 컴포넌트를 쓴다.

## 컨테이너로 가는 길 (플레이어 가방)

```
컴포넌트 +0x18  ptr 컨테이너 포인터 배열
         +0x20  u32 개수 / +0x24 u32 용량      실측 18 / 18
컨테이너 (포인터 배열이 가리키는 것, 서로 0x30 간격으로 이어져 있다)
         +0x00  ptr 레코드 배열
         +0x08  u32 배열 칸 수                 실측 1460
         +0x0C  u32 같은 값
         +0x10  u16 종류
         +0x12  u16 사용 개수
         +0x14  u16 용량                       화면에 나오는 값
```

**컴포넌트 앞부분을 훑어 `{포인터, 사용, 용량}` 꼴을 찾던 방식은
걷어냈다.** 그렇게 하면 엉뚱한 컨테이너(41칸짜리 재고 뭉치)가 걸리고
정작 플레이어 가방은 못 잡는다. 가방은 `+0x18` 너머에 있다.

찾는 길은 실측 레코드에서 거슬러 올라가 냈다. 화면에서 담금질을 본
바르그란 방패의 레코드를 `invfind` 로 집고, 그 주소에서 `0xC8` 간격
앞뒤를 훑어 배열 시작(`0x57D772A0000`, 페이지 정렬)을 찾고,
`heapptr` 로 그 배열을 가리키는 곳 → 컨테이너, 다시 `heapptr` 로
컨테이너 배열을 가리키는 곳 → 컴포넌트 `+0x18` 이 나왔다.

용량이 화면과 맞는 것으로 확인했다.

```
[종류 1]  ... (표시 102 / 130)     화면의 장비 칸
[종류 4]  144개 (표시 144 / 300)   화면의 "중요물품 : 144"
[종류 9]  169개 (표시 169 / 300)
```

`invlist` 출력:

```
컴포넌트 0x57D76194B00
[종류 4] 0x57D772A0000  144개  (표시 144 / 300, 칸 1460)
  [ 130] 순번 6496 담금질 0  키 1163042 x1 ID 2183     늑대의 한손검
  [ 138] 순번 5921 담금질 3  키 13604   x1 ID 1000024  바르그란 방패
```

두 줄 다 화면과 같다 - 늑대의 한손검은 눈금이 없고 게이지가 비었고,
바르그란 방패는 `|||` 에 게이지 3칸이다.

### 사용 개수를 믿지 않는다

레코드는 칸 전체(1460)를 훑는다. 배열에 **구멍이 섞여 있어서**
사용 개수에서 멈추면 뒤가 잘린다 - 실측에서 78 · 80 · 81 · 82 · 84 번
칸이 비어 있는데 그 뒤로 레코드가 이어졌다.

`+0x12` 의 값과 실제 레코드 수는 컨테이너 넷(종류 0 · 4 · 9 · 13)에서
정확히 같았고, 종류 1 은 13개, 종류 7 은 1개 적었다. **차이는
되풀이해도 같다** - 경합이 아니다. 무엇을 더 세는지는 모른다.

모드 쪽 후킹(`table_probe_install`)은 찾는 키가 들어올 때만, 8회까지만
남긴다. 이 조회 함수는 초당 수천 번 불린다.

## 소켓 (레코드 +0x60)

```
레코드 +0x60  ptr 소켓 배열
       +0x68  u32 개수 5 / +0x6C u32 용량 5
소켓   6바이트
       +0x00  u16  박힌 것의 아이템 표 순번. 0xFFFF 면 빈 칸
       +0x02  u16  뜻 모름
       +0x04  u8   뜻 모름
       +0x05  u8   뜻 모름
```

순번이 보석 이름으로 풀리는 것으로 배치를 확인했다.

```
[ 54] 순번 6438 담금질 1  키 200914  군주의 검
      소켓[0] 순번 3364  키 1002569  바람 가르기   (24 0D FF FF 00 FF)
      소켓[1] 순번 3214  키 1002785  파괴 I        (8E 0C FF FF 01 FF)
      소켓[2] 순번 3216  키 1002810  질풍 I        (90 0C FF FF 02 FF)
[137] 순번 5919 담금질 3  키 1000560  카이로스 판금 장갑
      소켓[0] 순번 3223  키 1002822  숨결 I        (97 0C FF FF 00 00)
[ 72] 순번 5620 담금질 2  키 121054  학살의 기사 판금 장갑
      소켓[0] 순번 3214  키 1002785  파괴 I        (8E 0C FF FF 00 FF)
      소켓[1] 순번 3215  키 1002791  간파 I        (8F 0C FF FF 01 FF)
```

가방 503개 중 박힌 소켓은 6개였다. 무기와 장갑에 붙어 있고 이름이
전부 강화 보석이라 앞뒤가 맞는다.

### 나머지 네 바이트에 대해 아는 것

```
빈 칸    FF FF | 00 00 | FF | 03     (첫 칸)
빈 칸    FF FF | 00 00 | FF | 00     (나머지 칸)
박힌 것  ?? ?? | FF FF | NN | FF     NN 이 소켓 번호와 같았다 (0·1·2)
         97 0C | FF FF | 00 | 00     다만 이것만 마지막이 00 이다
```

`+0x02` 가 빈 칸에서는 `0000`, 박힌 칸에서는 `FFFF` 로 뒤집힌다.
`+0x04` 는 박힌 칸에서 소켓 번호와 같았고 빈 칸에서는 `FF` 였다.
**뜻은 모른다** - 표본이 6개뿐이다.

그래서 `InventorySocket` 은 6바이트 원본을 그대로 들고 있는다.
export 는 뜻을 모르는 칸까지 되돌려야 한다.
