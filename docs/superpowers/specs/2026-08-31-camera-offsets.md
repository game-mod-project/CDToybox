# 카메라 구조 실측 기록 — M1·M2 결과

> **정리 (2026-09-21) — ❌ 반증.** 아래 정정의 위치·회전 결론에 더해, 정정이 가리킨
> 월드 좌표 `PlayerCameraComponent + 0x360` 도 패치 뒤 **`+0x378`** 로 밀렸다
> (`2026-09-05-session-companion-handoff.md` §10.1, `TROUBLESHOOTING.md` §4.19).
> 카메라는 지금도 렌더가 읽는 값을 못 찾아 미해결이다 — `STATUS.md` §2.4 · §3.

> **정정 (2026-08-31, 재측정)**
>
> 이 문서의 위치·회전 오프셋은 **틀렸다.** 실행 중인 게임을
> `cdtb_probe` 로 다시 읽어 확인한 결과:
>
> - 카메라 객체 `+0x50`(스케일) / `+0x5C`(쿼터니언) / `+0x6C`(위치)는
>   활성 카메라에서 **항상 `(1,1,1)` / 항등 / `(0,0,0)`** 이다.
> - 실행 이미지 전수 조사에서도 `+0x5C`·`+0x6C` 에 쓰는 코드가
>   **0곳**이었다. 죽은 칸이다.
> - 카메라의 진짜 월드 좌표는 **`PlayerCameraComponent + 0x360`**
>   (float3 + 패딩)이고, 0.7초 간격 비교에서 매 프레임 변한다.
>   실측값 예: `(-10489.06, 610.40, -4372.72)`.
> - 회전은 아직 못 찾았다. 컴포넌트와 그 힙 이웃 8KB 안에는 없다.
>
> 확인된 오프셋(FOV `+0x9C`=45, 뷰포트 `+0x7C`=1920 / `+0x80`=1080,
> 근접 `+0xB4`=0.2, 원거리 `+0xB8`=100000, 이름 `+0x48`)은 유효하다.
>
> 자세한 근거: `2026-08-31-camera-write-paths.md`


- 측정일: 2026-08-31
- 대상: Crimson Desert Enhanced 2.00.01, 인게임(월드 진입) 상태
- 도구: `cdtb_probe` (외부 프로세스 RTTI 분석)

## 1. 결론 먼저

- 카메라 구조를 **값 스캔 없이** RTTI 탐색만으로 특정했다. 사람의 조작이 필요 없었다.
- **게임은 카메라 필드를 매 프레임 덮어쓴다.** 이것이 M3 접근을 결정하는 증거다.
- 게임에 **개발자 프리카메라(`FreeCamCamera`)가 할당된 채로 존재**하며, 활성화 스위치만 남았다.

## 2. 카메라 객체 지도

힙 10.4GB 전수 조사(30초) 결과, 살아 있는 카메라 객체는 넷뿐이다.

| 주소 | 클래스 | 역할 |
|---|---|---|
| `0x48057DA2D80` | `CameraManager` | 디버그·특수 카메라 보유 |
| `0x48057C25B80` | `FreeCamCamera` | **프리카메라. 할당돼 있으나 비활성** |
| `0x48057F2B2C0` | `PhotoCamera` | 포토카메라. 비활성 |
| `0x48057F2BB80` | (RTTI 미노출) | **활성 카메라** |
| `0x48057C1E400` | `PlayerCameraComponent` | 플레이어 카메라 컴포넌트 |

주소는 실행마다 바뀐다. 재현하려면 RTTI 탐색을 다시 돌린다.

### CameraManager 레이아웃

```
+0x010  PhotoCamera*
+0x018  FreeCamCamera*          ← 프리카메라를 직접 보유
+0x028  int32 1, int32 1        (의미 미상)
+0x030  FreeCamCamera  (ICamera 서브객체, base+0x28)
+0x038  PhotoCamera    (ICamera 서브객체)
+0x040  SceneObjectClient*
+0x070  float 0.2, 10000.0      near / far
```

`PlayerCamera` 포인터가 없다. 이 관리자는 디버그·특수 카메라 전용이다.

## 3. 카메라 객체 공통 레이아웃

`FreeCamCamera`와 활성 카메라가 **동일한 레이아웃**을 쓴다. 공통 기반 클래스가 있다는 뜻이다.

| 오프셋 | 필드 | FreeCam | 활성 카메라 |
|---|---|---|---|
| `+0x000` | vtable (기반) | | |
| `+0x028` | vtable (ICamera 서브객체) | | |
| `+0x048` | 이름 객체 포인터 | → "FreeCamera" | → "PlayerCamera" |
| `+0x050` | scale (3 float) | 1, 1, 1 | 1, 1, 1 |
| `+0x05C` | 회전 쿼터니언 (4 float) | 0,0,0,1 | 0,0,0,1 |
| `+0x06C` | 위치 (3 float) | 0,0,0 | 0,0,0 |
| `+0x07C` | 뷰포트 폭 (int) | 1920 | 1920 |
| `+0x080` | 뷰포트 높이 (int) | 1080 | 1080 |
| `+0x09C` | **FOV (도)** | 60.0 | **40.0** |
| `+0x0A4` | (매 프레임 변동) | 3.0 | 3.62 → 3.61 |
| `+0x0A8` | | 45.0 | 45.0 |
| `+0x0AC` | | 8.0 | 32.0 |
| `+0x0B4` | near clip | 0.2 | 0.2 |
| `+0x0B8` | far clip | 100000.0 | 100000.0 |
| `+0x0C0` | | 360.0 | 360.0 |
| `+0x0C4` | | 512.0 | 512.0 |

**주의**: `+0x05C`(회전)와 `+0x06C`(위치)는 두 카메라 모두 항등/원점이다. 실제 카메라 변환은 이 필드가 아니라 다른 곳에서 계산된다. 실시간 위치는 `PlayerCameraComponent + 0x360` (x, y, z)에서 관측된다.

### 카메라 이름 테이블

카메라는 `+0x48`에 이름 객체를 들고 있다. 이름 객체는 0x30 바이트이고 짧은 문자열을 인라인으로 담는다(SSO).

```
0x48057BA4BC0  ptr→+0x18, len=10   "FreeCamera"
0x48057BA4BF0  ptr→+0x18, len=11   "PhotoCamera"
0x48057BA4C20  ptr→+0x18, len=12   "PlayerCamera"
```

문자열 리터럴 주소(`0x144D43808` 등)를 힙에서 찾으면 0건이다. 이름은 참조가 아니라 **복사**되어 들어간다. 이 사실을 모르면 탐색이 막힌다.

## 4. M3 결정 증거 — 게임은 매 프레임 덮어쓴다

활성 카메라의 FOV(`0x48057F2BB80 + 0x9C`)에 20을 썼다.

```
쓰기 직후 읽기      20.0   (쓰기는 성공한다)
별도 프로세스 재조회 40.0   (100ms 이내에 이미 복구됨)
```

60fps 기준 16ms마다 갱신되므로, **외부에서 값을 쓰는 방식으로는 유지할 수 없다.**

계획서 §5 M3의 세 후보 중 판정:

| 후보 | 판정 |
|---|---|
| (a) Present 훅에서 쓰기 | **불가.** 게임이 매 프레임 덮어쓰고, Present 시점에는 이미 투영 행렬이 만들어진 뒤다 |
| (b) 카메라 갱신 함수 후킹 | **유력.** 갱신 직후에 우리 값을 덮어쓰면 이긴다 |
| (c) 쓰기 명령 NOP | 차선. 부작용 범위를 알 수 없다 |

**(b)로 간다.** 다만 `FreeCamCamera`가 이미 존재하므로, 그것을 활성화하는 경로가 더 낫다면 그쪽이 우선이다.

## 5. 코드 위치 (정적 분석)

카메라 모드 문자열을 RIP 상대로 참조하는 명령을 찾았다. 세 모드가 모두 한 함수 안에 있다.

```
0x140926A50  lea rcx, ["FreeCamera"]
0x140926B77  lea rcx, ["PhotoCamera"]
0x140926D40  lea rcx, ["PlayerCamera"]
```

같은 영역(`0x14092xxxx`)에서 디버그 입력도 참조된다.

```
0x1409258E3, 0x140926003  Debug_MouseRbutton
0x14092578C               GameDebug_Dot_DownOnce
```

`FreeCamCamera` 생성자를 특정했다. 다중 상속 vtable 두 개를 설치하는 것이 관측된 객체 레이아웃과 일치한다.

```asm
0x1409269C9  lea rax, [rip+0x441C8F0]   ; → 0x144D432C0  vtable #2
0x1409269CC  mov [rbx], rax
0x1409269D3  lea rax, [rip+0x441C566]   ; → 0x144D42F40  vtable #1
0x1409269D6  mov [rbx+0x28], rax
```

## 6. 다음에 할 일

1. `0x140925000`~`0x140927000` 영역을 디스어셈블해 카메라 모드 전환 진입점을 찾는다.
2. 그 함수를 후킹하거나 직접 호출해 `FreeCamera` 모드를 켠다.
3. 켜지면 `FreeCamCamera`의 위치·회전 필드에 값을 쓰고, 갱신 함수 후킹으로 유지한다.

## 7. 방법론 기록

이번 M1·M2는 계획서가 정한 값 스캔이 아니라 **RTTI 탐색**으로 수행했다. 값 스캔은 원리적으로 사람이 게임 상태를 바꿔 주어야 좁혀지지만, RTTI 탐색은 메모리 구조만 따라가면 되므로 에이전트가 단독으로 끝낼 수 있다. 사용자에게 필요한 조작은 "게임을 켜고 월드에 들어가는 것" 하나뿐이었다.

인게임 ImGui 스캔 패널은 이 목적에 맞지 않는 설계였다. 조작자가 사람이라는 전제가 들어 있었기 때문이다. 도구는 `cdtb_probe`(외부 명령줄)로 대체한다.
