# CDToybox 1단계 설계 — 실시간 분리 프리카메라

- 작성일: 2026-08-31
- 대상: Crimson Desert Enhanced 2.00.01
- 선행: `2026-08-31-stage0-scaffold-design.md` (완료), `2026-08-31-d3d12-overlay-research.md`

## 1. 목표와 비목표

### 목표

카메라를 캐릭터에서 분리해 자유 이동시킨다. **게임은 계속 돌아간다** — 시간 정지는 하지 않는다.

이것은 0단계가 세운 네 접점(`mem` · `hook` · `overlay` · `guard`) 위에 올라가는 **첫 번째 게임 상태 접근 계층**이다. 1단계의 진짜 산출물은 카메라 자체가 아니라 **게임 자료구조를 찾고 다루는 방법론과 도구**이며, 2단계 이후가 전부 그 위에서 돌아간다.

### 비목표

- 시간 정지, 포토모드 UI
- 캐릭터 이동(Trinity의 free flight와 다르다 — 우리는 카메라만 다룬다)
- 컷신 카메라 제어
- FOV 외의 렌더 파라미터

## 2. 실측된 역공학 진입점

바이너리를 직접 조사해 확인한 사실이다.

| 사실 | 확인 방법 | 함의 |
|---|---|---|
| 게임 코드에 RTTI 없음 | RTTI 클래스 468개 전수 확인 — 전부 `hk*`/`hkx*`/`hct*` (Havok SDK) | 클래스 열거로 카메라를 찾을 수 없다 |
| `ReflectStrings` 클래스 존재 | `.?AVReflectStrings@@` — Havok이 아닌 유일한 게임 클래스 | 런타임 리플렉션 시스템의 단서 |
| 리플렉션 필드명이 문자열로 존재 | `_fov` `_fovDegree` `_cameraDistance` `_pitch` `_yaw` `_lookAt` `_isLinkZoomDistanceRateWithFov` `_enableFrameGeneration` `EngineOptionVideo` `_upscaleModeSelect` | 문자열 참조에서 코드를 역추적할 수 있다 |
| Havok 정적 링크 | RTTI 목록 | 물리·애니메이션은 Havok 규약을 따른다 |
| 실행 섹션이 313MB | 0단계 진단 (`.rdata` 73.4MB + `.sbss` 239.9MB) | 시그니처 스캔 범위가 넓다. 스캐너 최적화로 40ms 수준 |

`hkxCamera` RTTI가 존재하지만 `hkxScene`/`hkxMesh`/`hkxNode`와 함께 나오는 **Havok 에셋 교환 포맷(HKX)** 클래스이므로, 런타임 게임플레이 카메라가 아니다. 이 이름을 좇지 않는다.

## 3. 접근안

### A. 값 기반 메모리 스캔 — 채택

Cheat Engine 방식이다. 쓰기 가능한 메모리 전체에서 특정 float을 찾고, 게임에서 값을 변화시킨 뒤 재스캔해 후보를 좁힌다.

- **장점**: 게임 내부 지식이 전혀 필요 없다. 실패해도 안전하다(읽기만). 한 번 만들면 이후 모든 역공학에 재사용된다.
- **단점**: 수동 반복이 필요하다. 주소가 실행마다 달라 시그니처로 안정화하는 후속 작업이 따로 필요하다.

### B. 리플렉션 시스템 역공학 — 2단계 후보로 보류

`ReflectStrings`를 파고들어 이름→오프셋 매핑을 얻는다. 성공하면 카메라뿐 아니라 **모든 구조체 레이아웃**이 열린다. ToyBox가 .NET 리플렉션에서 공짜로 얻는 것에 해당한다.

- **장점**: 성공 시 2단계 이후 전체를 바꾼다.
- **단점**: 성공 여부를 지금 알 수 없다. 검증되지 않은 것에 1단계를 걸 수 없다.

**1단계에서는 착수하지 않는다.** A로 파이프라인을 증명한 뒤 별도로 탐색한다.

### C. 문자열 참조 역추적 — 보조

`_fov` 문자열의 주소를 구하고, 그 주소를 참조하는 `lea` 명령을 실행 섹션에서 찾아 코드로 거슬러 올라간다. A가 막히거나 M3에서 갱신 함수를 찾아야 할 때 쓴다.

## 4. 아키텍처

0단계 계층 위에 두 모듈이 추가된다.

```
  proxy → core → mem → render/input        (0단계, 변경 없음)
                  ↑
                  ├── mem/value_scanner    (신규) 값 기반 메모리 스캔
                  └── game/camera          (신규) 카메라 접근 계층
```

`game/`은 이 프로젝트에서 **게임 지식을 담는 유일한 곳**이다. 오프셋과 시그니처가 전부 여기 모여, 게임 패치 때 손볼 범위가 한정된다.

### 4.1 `mem/value_scanner` (신규)

float 전용으로 시작한다. 필요한 것은 카메라 좌표와 FOV이고 둘 다 float이다. 정수형은 실제로 필요해질 때 추가한다.

```cpp
namespace cdtb::mem {

// VirtualQuery로 커밋되고 쓰기 가능한 영역을 모은다.
// PAGE_GUARD / PAGE_NOACCESS / 실행 전용 페이지는 제외한다.
//
// 모듈 이미지의 데이터 섹션은 제외하지 않는다. 카메라 구조체를
// 가리키는 전역 포인터는 실행 파일의 .data 계열에 있을 가능성이
// 높고, 그것을 빼면 정작 필요한 것을 놓친다.
std::vector<Range> writable_regions();

class FloatScan {
public:
    // 전체 영역에서 |*addr - target| <= eps 인 주소를 모은다.
    std::size_t first(float target, float eps);

    // 현재 후보만 다시 본다. 반환값은 남은 개수.
    std::size_t narrow_equals(float target, float eps);
    std::size_t narrow_changed();      // 직전 스냅샷과 다른 것
    std::size_t narrow_unchanged();    // 직전 스냅샷과 같은 것
    std::size_t narrow_increased();
    std::size_t narrow_decreased();

    void reset();
    std::size_t count() const;
    const std::vector<std::uintptr_t>& results() const;

private:
    std::vector<std::uintptr_t> addrs_;
    std::vector<float> prev_;   // narrow_changed 등을 위한 직전 값
};

}  // namespace cdtb::mem
```

**안전**: `VirtualQuery`로 걸러도 스캔 도중 영역이 해제될 수 있다. 스캔 루프 전체를 SEH로 감싸고, 예외가 나면 그 영역을 건너뛴다. 0단계에서 확인했듯 SEH 껍데기와 본문은 분리해야 한다(C2712).

**성능**: 쓰기 가능 영역은 게임 메모리 전체(수 GB)일 수 있다. 최초 스캔은 수 초가 걸릴 수 있으므로 **워커 스레드에서 돌리고 진행률을 오버레이에 표시한다.** 렌더 스레드를 막으면 안 된다.

### 4.2 `game/camera` (신규)

```cpp
namespace cdtb::game {

struct CameraView {
    float pos[3];
    float rot[3];     // pitch, yaw, roll (라디안 여부는 M2에서 확정)
    float fov;
};

// 카메라 구조체를 찾았는가.
bool camera_found();
// 찾은 구조체의 베이스 주소. 못 찾았으면 0.
std::uintptr_t camera_base();

// M2에서 오프셋이 확정되면 채워진다.
bool read_view(CameraView& out);

}  // namespace cdtb::game
```

M1에서는 `camera_base()`와 FOV 읽기·쓰기만 구현한다. 나머지는 M2에서 채운다.

### 4.3 `overlay` 확장

"메모리 스캔" 패널을 추가한다.

- 대상 값 입력(float), 오차 입력
- `첫 스캔` / `같음` / `변함` / `안 변함` / `증가` / `감소` / `초기화` 버튼
- 남은 후보 개수와 상위 20개 주소·현재값 목록
- 후보 하나를 고정(pin)해 실시간 값 관찰
- 스캔 진행률(워커 스레드)

이 패널이 M1~M2의 작업 도구이자 산출물이다.

### 4.4 `guard` 변경

```cpp
bool is_safe_to_modify() { return true; }
```

근거: Crimson Desert는 2026-03-19 출시 시점부터 현재 빌드까지 **co-op·PvP·매치메이킹이 전무한 순수 싱글플레이**다. 0단계에서 온라인 인프라로 의심한 `PartyManager`·`GuildManager`는 BlackSpace 엔진이 BDO와 공유하는 스캐폴딩이고, `LinkingCheckAsync`는 계정 연동이지 게임 세션이 아니다.

**관문 자체는 남긴다.** Pearl Abyss가 멀티플레이를 검토 중이라고 밝혔으므로(빨라도 2026 말~2027), 출시되면 이 함수만 고쳐 전체 쓰기 기능을 한 곳에서 차단할 수 있어야 한다.

## 5. 마일스톤

### M1 — 값 스캐너 + 카메라 구조체 확보

**산출물**: `mem/value_scanner`, 오버레이 스캔 패널, `game/camera`의 베이스 주소와 FOV 접근, 그리고 §4.4의 `guard` 변경(FOV 쓰기가 첫 쓰기 기능이므로 이때 관문을 연다).

**절차**:
1. `mem/value_scanner`를 TDD로 만든다. `writable_regions()`를 뺀 순수 로직(후보 좁히기)은 합성 버퍼로 테스트한다.
2. 오버레이에 스캔 패널을 붙인다.
3. 게임에서 FOV가 바뀌는 상황(줌인/줌아웃, 질주)을 만들며 스캔을 좁힌다.
4. 후보 주소에 값을 써 화면이 변하는지 확인한다.

**완료 기준**: FOV로 추정되는 주소에 값을 썼을 때 **화면 시야각이 눈에 띄게 변한다.** 이것이 카메라 구조체를 찾았다는 증거다.

**위험**: 낮음. 읽기가 대부분이고, 쓰기는 float 하나이며 잘못 써도 화면만 이상해진다.

### M2 — 위치·회전 오프셋 확정

**산출물**: `CameraView` 전 필드의 오프셋, 오버레이 실시간 표시.

**절차**: M1에서 얻은 베이스 주소 주변을 덤프하고, 캐릭터를 움직이며 어떤 float이 좌표처럼 변하는지 관찰한다. 회전은 카메라를 돌리며 관찰한다.

**완료 기준**: 오버레이에 표시된 좌표가 게임 내 이동과 일치하고, 회전이 시점 조작과 일치한다.

**위험**: 없음. 읽기 전용이다.

### M3 — 쓰기 경로 결정

게임이 매 프레임 카메라를 덮어쓰므로, 단순히 값을 쓰는 것만으로는 부족할 수 있다. **접근을 지금 확정하지 않는다.** M2가 만들어내는 증거로 고른다.

| 후보 | 선택 조건 | 비용 |
|---|---|---|
| (a) Present 훅에서 쓰기 | M2에서 값을 쓴 뒤 다음 프레임에 유지되면 | 가장 싸다 |
| (b) 카메라 갱신 함수 후킹 | (a)가 덮어써지고, 접근 C로 갱신 함수를 찾을 수 있으면 | 중간. 정석 |
| (c) 쓰기 명령 NOP | (b)의 함수를 못 찾고, 쓰기 명령 자체는 특정되면 | 부작용 위험이 크다 |

**결정 절차**: M2 완료 직후, 카메라 좌표에 값을 한 번 써 보고 다음 프레임에 유지되는지 관찰한다. 유지되면 (a), 덮어써지면 (b)를 시도하고, (b)의 함수 탐색이 막히면 (c)를 검토한다.

**이 마일스톤의 구현 계획은 M2 결과를 본 뒤에 작성한다.** 지금 쓰면 셋 중 둘은 버리는 계획이 된다.

### M4 — 입력과 통합

**산출물**: 프리카메라 토글, 이동·회전 입력, 속도 조절, 해제 시 원상 복구.

**절차**: WASD + 마우스로 카메라를 움직인다. 오버레이가 열려 있으면 입력이 ImGui로 가므로, 프리카메라 모드는 오버레이를 닫은 상태에서 동작해야 한다. 별도 키(기본 `F7`)로 토글한다.

**완료 기준**: 카메라가 캐릭터에서 분리되어 자유 이동하고, 토글을 끄면 원래 카메라로 정확히 돌아간다. 게임은 그동안 정상 동작한다.

## 6. 계획 수립 방식

**M1과 M2를 먼저 계획해 실행하고, M2 결과를 본 뒤 M3·M4를 계획한다.**

M3의 접근이 셋 중 무엇인지에 따라 M4의 입력 처리와 복원 방식도 달라진다. 지금 전부 계획하면 절반은 버려진다. 0단계에서 "인게임 검증이 필요한 변경은 한 번에 하나만"이라는 규칙을 얻었는데, 계획에도 같은 원리가 적용된다.

## 7. 검증 규칙 (0단계에서 계승)

1. 인게임 검증이 필요한 변경은 한 번에 하나만 배포한다.
2. `deploy.ps1`이 산출물이 소스보다 오래됐거나, 없거나, 게임이 실행 중이면 거부한다.
3. 배포마다 로그를 지우고 시작한다.
4. **게임 실행은 사용자가 직접 한다. 자동 실행하지 않는다.**
5. 값을 쓰는 실험 전에는 게임을 저장한다.

## 8. 리스크

| # | 리스크 | 완화 |
|---|---|---|
| 1 | 최초 스캔이 수 GB를 훑어 오래 걸린다 | 워커 스레드 + 진행률 표시. 렌더 스레드를 막지 않는다 |
| 2 | 스캔 중 메모리 영역이 해제된다 | `VirtualQuery` 필터 + SEH로 영역 단위 건너뛰기 |
| 3 | 찾은 주소가 실행마다 달라진다 | M1은 절대주소로 진행하고, 안정화(시그니처·포인터 체인)는 M2 이후 별도 작업 |
| 4 | M3에서 세 접근이 모두 막힌다 | 그 시점에 사용자와 재설계를 논의한다. (c)는 부작용이 커 마지막 수단이다 |
| 5 | 게임 패치로 오프셋이 무효화된다 | 게임 지식을 `game/`에 격리해 손볼 범위를 한정한다 |

## 9. 이후 단계와의 접점

1단계가 남기는 것 중 카메라보다 중요한 것들이다.

- `mem/value_scanner` — 이후 모든 자료구조 탐색의 도구
- `game/` 계층 — 게임 지식의 격리 지점
- 오버레이 스캔 패널 — 반복 가능한 역공학 작업대
- M3에서 확정될 "게임이 매 프레임 덮어쓰는 값을 이기는 법" — 스탯·버프 등 이후 모든 쓰기 기능에 그대로 적용된다
