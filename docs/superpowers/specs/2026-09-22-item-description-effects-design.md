# 아이템 설명 · 효과 컬럼 설계 (2026-09-22)

> **상태 — 🔨 PR1(설명 열 · 검색) 구현 · PR2(효과) 실측 전 (2026-09-22).** 화면 · 데이터 · 검증 · 진행 네 부분을
> 하나씩 승인받았다. 실측으로 **확정된 것**과 구현 첫 단계에서 **잴 것**을 절마다 나눠 적었다.
> 실측은 전부 exe **1.0.0.2949**, 게임 실행 중 읽기 전용(ReadProcessMemory)이다.
> 구현 계획: `plans/2026-09-22-item-description-effects.md`.

## 0. 요약

- 아이템 목록 창 · 인벤토리 창에 **"설명" 열 하나**를 넣는다. 칸은 한 줄 요약, 마우스를 올리면
  설명 전문과 **효과 목록(수치 포함)**.
- 설명은 게임 현지화 표의 아이템 설명(필드 0x71)이다 — **경로 확정**.
- 효과 수치는 게임 표를 따라가 읽는다: 아이템 → 아이템 사용 → 스킬 → 단계 → 버프 데이터.
  **경로는 확정**, 버프 데이터 종류별 필드의 뜻은 구현 첫 단계에서 실측으로 정한다.
- 필터 바 검색이 설명 · 효과 문구에도 걸린다.
- PR 둘: ① 설명 열 + 검색 ② 효과.

| 사실 | 실측 |
|---|---|
| 설명 현지화 키 자리 | 아이템 레코드 **+0xB8** (u64). `_itemDesc`(+0xB0) 객체의 키 칸 — 이름 키 +0x28 이 `_itemName`(+0x20) 의 키 칸인 것과 같은 꼴 |

| 길이 | 최대 **503바이트**, 중앙 180 — 지금 읽기 상한 `kMaxText = 512` 안이지만 여유가 없다 |
| 내용 | 어비스 기어는 효과 문장이 들어 있다(바람 가르기: "…바람 가르기 : 전방으로 바람을 베어내는 검기를 날려 추가적인 피해를 입힌다."). 음식은 맛 묘사뿐, 비약은 효과를 말로만 |
| 표기 (전수, 2026-09-22) | 태그는 **`<br/>` 하나**(2656회, 연속 `<br/><br/>` 196건, 맨앞·맨끝 0건, 옆에 공백이 붙은 것 10건). 자리표시 **`{Staticinfo:<표>:<키>#<표시 문구>}`** 56건(설명 56개에 한 번씩, 표는 Knowledge 12 · Item 44, `#` 는 늘 하나, 전부 닫힘) — 예 `{Staticinfo:Knowledge:Knowledge_Hp#생명}`, `{Staticinfo:Item:Recipe_Item_Skill_AbyssGear_SwordAura_LV1#기어 제작법 : 바람 가르기}`. 그 밖의 `{` 는 없다. `[효과]` 139건 · `[QA]` 14건은 평문. 엔티티(`&…;`)·제어 문자 없음 |

구현:

- `ItemCatalogEntry` 에 `desc`(std::string) — `build_item_catalog` 가 이름과 **같은 자리에서**
  `resolve()` 로 푼다. 현지화가 늦게 오면 이름과 함께 다시 만든다(기존 `should_rebuild_catalog`).
- 설명용 읽기 상한을 **2048바이트**로 둔다(지금 최장 503 의 네 배) — `resolve` 에 상한 인자를
  더하고 기본값은 지금의 512 로 두어 이름 조회는 그대로 둔다. 상한에 걸려 널 종단을 못 찾으면
  지금처럼 실패로 친다(잘린 문장을 보이지 않는다).
- 메모리 ≈ 1.2MB(6736 × 평균 180).
- 문구 정리(순수 함수, 시험 대상): `<br/>` → `\n`, 자리표시 → `#` 뒤 표시 문구, 줄 앞뒤 공백
  제거, 요약 = 첫 줄(빈 줄은 건너뛴다). 위 "표기" 전수에 없는 표기는 손대지 않고 그대로 둔다.

## 4. 데이터 — 효과

### 4.1 경로 (확정, 2949 실측)

```
ItemInfo 레코드 +0x80  u32* 사용 행 목록,  +0x88 u32 개수          (_itemUseInfoList 자리)
  -> ItemUseInfoManager 레코드[행]   (StaticInfo 는 행 첨자 - staticinfo-index-not-key)
       +0x00 u32 키 · +0x08 _stringKey 객체 · +0x18 ItemUseData_* 객체(다형, RTTI 로 종류)
  -> ItemUseData_Skill  +0x30 {u32 스킬행, u32 값2}* ,  +0x38 u32 개수
  -> SkillInfoManager 레코드[스킬행]
       +0x18 단계 목록 {ptr, u32 개수} x N (16바이트 칸),  +0x20 u32 단계 수
  -> 단계[i] = BuffData 객체 포인터 배열 -> *BuffData(다형, RTTI 로 종류)
```

표는 모두 RTTI 로 찾는다(`find_static_manager`): `ItemUseInfoManager`(10140행) · `SkillInfoManager`
(2069) · `BuffInfoManager`(292) · `StatusInfoManager`(84). 모두 `+0x30` 개수 · `+0x58` 레코드 배열로
읽혔다(아이템 표와 같은 꼴).

홉마다 무엇을 가리키는지(2026-09-22 재실측, 헤딘 · 프레야 · 떡고기구이 · 편전):

- `+0x80` 은 u32 배열 **포인터**, 사용 레코드 `+0x18` 은 ItemUseData 객체 **포인터**다(그 자리가
  vtable 이 아니다). 사용 레코드 `+0x00` 키 = 1000000 + 행.
- `ItemUseData_Skill +0x30` 은 8바이트 칸 배열 포인터, 스킬 레코드 `+0x18` 은 16바이트 칸 배열
  포인터, 단계 칸 `{ptr, u32}` 의 ptr 은 BuffData **포인터 배열**이다.
- `ItemUseInfoManager` · `SkillInfoManager` 둘 다 `looks_like_static_manager`(색인[0] 의 u16 == 첫
  레코드의 u16)를 통과한다 — 1000000 / 999999.
- RTTI 이름: `.?AVItemUseData_Skill@pa@@`, 버프는 `.?AV<클래스>@pa@@`(예
  `.?AVVaryDataDefinedStatBuffData@pa@@`).

전체 6816개 전수(2026-09-22):

| 항목 | 최대 | 아이템 |
|---|---|---|
| 아이템당 사용 | 17 | 1003542 |
| ItemUseData_Skill 칸 | 1 | 1001245 |
| 스킬 단계 | 15 | 1000142 |
| 단계당 버프 | 4 | 1000142 |
| 값2 | 10 | 777001 |

- 스킬 사용이 있는 아이템 606개, 범위 밖 행 0건.
- 사용 종류 20가지 — Skill 3656 · RegisterReserveSlot 1604 · PlaySequencerOnly 1404 ·
  FeedToTarget 1155 · Inspect 1111 · RandomBox 441 · SealToEquip 412 · 나머지 13종 합 357.
- **값2 는 1-기준 단계 번호다.** 3656칸 전부 1 ≤ 값2 ≤ 단계 수이고, 값2 == 0 은 0건,
  값2 == 단계 수는 37건(예 아이템 777001 · 스킬 행 1536 · 값2 10 · 단계 10)이다. 0-기준이면 그 37건이
  범위 밖이 된다. 툴팁 캡처(§7)에서 수치를 대조할 때 한 번 더 본다.

| `VoidActiveBuffData` | 2521 |

  필드가 BuffInfo 행인지는 첫 단계에서 확인**. 되돌아 도는 것을 막게 깊이를 제한한다(2).
- `VoidActiveBuffData` 는 무엇인지 모른다. 해석해 본 뒤 효과 목록에 넣을지 정한다.

### 4.3 능력치 이름

> 2026-09-23 실측으로 갱신됐다 — 어긋나는 곳은 §4.7 이 이긴다.

능력치 표(84행)에는 영문 내부 이름만 있다: Hp · Mp · Stamina · DDD · DPV · AttackSpeedRate ·
MoveSpeedRate · CriticalRate · FireResistance · IceResistance · Fullness … 현지화 표에서 이 행들의
한글 이름을 찾지 못했다("정신력" 은 풀 전체에서 3건, 전부 대사).

**한글은 게임 데이터 안에 근거가 있을 때만 붙인다.** 근거 없는 능력치는 내부 이름 그대로.

| 내부 이름 | 한글 | 근거 |
|---|---|---|
| DDD | 공격력 | 프레야의 하급 비약 제작법 설명 "[효과] 공격력 증가" + 그 비약의 스킬이 `Item_Active_Potion_DDD` |
| Mp | 용기 | `Item_Active_MP_Ignore_Use` 단계 이름표 "용기 고정 · 용기 리젠 무시" |
| Stamina | (미정) | 이름표는 "스테미나"(`SP_Ignore`). 화면 용어인지 모른다 — 툴팁 캡처로 정한다 |

제작법(레시피) 설명의 "[효과]" 문단(예: 고기찜 "생명/용기 회복")도 근거로 쓴다 — 종류만 있고
수치는 없다.

설명 자리표시(§3 표기)에 `Knowledge_Hp#생명` · `Knowledge_Sp#기력` 이 있다 — **지식 항목**의 화면
이름이다. 능력치 행(Hp · Stamina)과 같은 것인지는 1단계 실측에서 확인한다. 지금은 이름이 닮았을
뿐 연결 근거가 없다.

### 4.4 안 하는 것

- 스킬이 아닌 사용(슬롯 등록 · 먹이 주기 · 상자 열기 · 봉인 · 소환 …)은 효과로 치지 않는다.
- 해석기가 없는 종류는 목록에서 빼고 "해석 못 한 효과 N개" 로만 알린다.
- 개발용 이름표는 표시하지 않는다(§4.1).

### 4.5 계산 시점 · 게시

- 아이템 표를 만든 뒤 **배경 분석 스레드**에서 한 번 계산한다(스킬 사용이 있는 606개).
- 결과는 **따로 게시하는 불변 스냅샷**(`item_effects_for(key)`)이다. 아이템 표는 게시 뒤 바뀌지
  않는 것이 약속이라(`item_catalog` 참조를 쥔 채 그린다) 거기에 나중에 써 넣지 않는다.
- 표 중 하나라도 못 찾으면 효과만 비고 설명은 그대로 보인다. 다음 재시도 주기에 다시 계산한다.

### 4.6 실행 파일에서 뽑은 필드 지도 · 효과는 두 갈래다 (2026-09-23 추가 실측)

`tools/rtti/fields.py` 는 **역직렬화 함수의 실패 메시지**에서 데이터 클래스의 필드 이름과 오프셋을

**효과의 입구가 종류마다 다르다** (2026-09-23 실측, `%TEMP%\cdtb_items.bin` 6816 레코드 덤프):

즉 §4.1 의 경로는 **소모품 전용**이다. 어비스 기어는 `_enchantDataList` → `EnchantData` 를 따로
걸어야 한다. `EnchantData` 원소는 0x70 바이트 스트라이드로 보이고(`_buyPriceList +0x48` 이 맞는

조립된 것이다. 우리도 같은 규칙으로 조립해야 한다.

곁가지로 확인된 관련 클래스: `EnchantStatData`(`_statList_DataDefinedStatic +0x20` 등),
`SkillInfo`(`_buffLevelList +0x18` — §4.1 의 그 자리, `_maxLevel +0xF8`),
`BuffInfo`(`_buffDataList +0x28` · `_maxLevel +0x2C` · `_uiTemplateName +0x3A`),
`StatusInfo`(`_statType +0x30` · `_usePercent +0x61` · `_mustShowInUITooltip +0x89`).

### 4.7 조립 규칙 — 실측 확정 (2026-09-23, 탐침 실측 R1 · R2)

게임 툴팁 여섯 줄을 **글자까지 재현**해 검증했다(빨간 파두 3줄 · 별미 정식 3줄 — 숫자 · 시간 ·
조사 · 띄어쓰기 일치, 스탯 이름 넷만 미치환). 아래가 우리가 구현할 규칙이다. 앞의 §4.2 · §4.3 과
어긋나면 **이 절이 이긴다**. 근거 전문은 장부의 `r1-consumable-effects.md`(47k자) ·
`r2-abyss-gear.md`(28k자).

**A. 입구가 둘이다**

| 종류 | 입구 | 표본 |
|---|---|---|
| 소모품(요리 · 연금술 …) | `_itemUseInfoList` +0x80 (u32 행 배열, +0x88 개수) | 빨간 파두 · 별미 정식 = 14칸 |
| 어비스 기어 | `_enchantDataList` +0x248 (EnchantData 0x70 인라인 배열) | 관통 I·II·III = 1칸 |

**B. 소모품 사슬**

```
ItemInfo +0x80 → ItemUseInfoManager.records[행] (0x20) → +0x18 ItemUseData_* (0x40)
  +0x18 종류: Skill=0x00 · FeedToTarget=0x08 · RegisterReserveSlot=0x10
  +0x19 문맥: 0x00 · 0x07 · 0x0C   ← **툴팁 줄은 0x00 짜리다**
  ItemUseData_Skill +0x30 {u32 스킬행, u32 레벨(1-기반)}, +0x38 개수
→ SkillInfo.records[스킬행] +0x18 레벨 목록(16바이트 칸) → BuffData* 배열 → BuffData
```

같은 효과 스킬이 문맥만 달리해 **세 번씩** 등록된다(0x00/0x07/0x0C). `+0x19 == 0x00` 만 채택하거나
(스킬행, 레벨) 중복을 지우면 툴팁과 같은 줄 수가 나온다. 패턴이 없는 스킬(퀵슬롯 등록 등)은 저절로
빠지므로 예외 처리가 필요 없다.

`ChangeBuffLevelBuffData` 는 **다른 BuffInfo/레벨로 넘기는 링크**다(`+0x94` = 대상 레벨). 자기에게
패턴 행이 있으면 거기서 멈추고, 없으면 `BuffInfo._buffDataList`(+0x28)의 그 레벨로 한 단 더 간다
(관측 최대 2단).

**C. 어비스 기어 사슬**

```
ItemInfo +0x248 → EnchantData +0x58 `_equipBuffs` (0x20 스트라이드)
      원소 +0x00 하위 u16 = BuffInfo 행, +0x04 u32 = 레벨
→ BuffInfo._buffDataList[레벨] → BuffData
```
`EnchantData` 안에 `EnchantStatData` 가 **포인터가 아니라 통째로** 들어 있다. `_buyPriceList +0x48`
(관통 I = 1980 → 툴팁 `판매가 1.98`)로 레이아웃을 교차 검증했다.

**D. BuffData 공통 자리**

| 자리 | 뜻 |
|---|---|
| `+0x18` u32 | 지속 ms (0 = 즉발) |
| `+0x38` **하위 u16** | PatternDescriptionInfo **행 번호** (상위 바이트는 잔여물 — 반드시 마스크) |
| `+0x98` u64 | 스탯 수치형 = 값×1000 · 비율형 = 비율×10⁷ · 어비스(관통) = 25000/50000/75000 |
| `+0xA0` | 레벨형 = 레벨 원값(나눗셈 없음) |
| `+0x94` | `ChangeBuffLevel` 의 대상 레벨 |
| `+0x28` | `Damage` 의 주기 ms |
| `+0x90` | StatusInfo 행 — **클래스에 따라 잔여물이라 믿지 말 것** |

지속시간 표기(실측): `ms >= 60000 → "({ms/60000}분)"`, 아니면 `"({ms/1000}초)"`, **정수 내림**,
0 이면 접미 없음(90000 → "1분").

**E. 문구는 형식 문자열 + 파라미터다**

- `PatternDescriptionInfo` 레코드 0x60: `_stringFormat +0x18` · `_descriptionParsed +0x38` ·
  `_iconName +0x40` · **`_paramList +0x48`(포인터) · `+0x50`(개수)** — 항목은 **2바이트**
  `{_paramType, _isDisplayAbsoluteNumber}`. (`fields.py` 가 `_paramList` 를 `+0x58` 로 잡은 것은
  `_uiPassiveShowLevel` 과의 오귀속이다. 2026-09-23 실측: 행 5 `[(1,0)]` · 행 4 `[(8,0),(5,1)]` ·
  행 61 `[(1,0)]` — 개수와 종류가 형식 문자열의 토큰과 정확히 맞는다.)
- 현지화는 **카테고리 15 / 필드 0xF0**, 엔티티는 아이템 키가 아니라 레코드 `+0x00`/`+0x24` 의 u32
  해시다. cat 15 항목 수 352 = 표 행 수(전수 대조 불일치 0).
- 자리표시자: `{Param0..3}` = 타입 0..3, `{|Param0..3|}` = 4..7(절대값 표시), `{RepeatTick}` = 8.
  파싱본의 `{pN}` 의 N 은 **`_paramList` 안의 순번**이다(토큰 이름이 아니다).
- 치환 안 되는 토큰 셋: `{Staticinfo:<표>:<키>}` · `{Key:<액션>}` · `{Money:<통화>:<n>}`.
- 실제 예: `'{Staticinfo:SubLevel:Hp} 최대치 {Param1} 증가'` ·
  `'{Staticinfo:SubLevel:AttackSpeedRate} : Lv{Param1} 증가'` ·
  `'천 갑옷 타격 시 치명타 확률 {Param1}% 증가'`(관통 I).

**F. 장착 가능 부위 (어비스 기어)**

`_equipAbleHash` +0x68 → `EquipTypeInfo`(117행)의 `_equipAbleHashList`(+0x48)에 그 해시가 든 행들.
관통 I(0xBB5411B9) = 35행(무기 33 + 장갑 + 신발), 신속 I(0xB1DDF576) = 투구·갑옷·장갑·신발.
부위 이름은 cat 46 / 필드 0x2E0, 줄 문구는 cat 11 / 필드 0xB0(`%0# 장착 가능`).
탈락시킨 후보: `_occupiedEquipSlotDataList` · `_itemTagList` · `_reserveSlotTargetDataList`
(어비스 190개 전부 비었다).

**G. 비용 · 시점**

실행 중 상태가 **전혀 필요 없다**(정적 표 + 현지화 풀뿐). 표 단위로 한 번 펼치면 6만~10만 역참조,
그 뒤 아이템당 14 조회 + 문자열 포맷. 캐시는 1MB 미만. 단 `_descriptionParsed` 와 현지화 풀이 찬
**뒤에** 돌려야 한다 — 매니저 `+0x08` 개수와 현지화 풀 크기를 게이트로 재시도한다
([[staged-data-load-retry]] 와 같은 함정).

**H'. 컨트롤러 재실측으로 닫은 것 (2026-09-23 오후, 게임 실행 중)**

파이썬 참조 구현으로 두 아이템의 여섯 줄을 **전부 재조립해 게임 툴팁과 글자까지 맞췄다**
(스크래치 `lines.py` · `assemble.py`):

```
생명 최대치 45 증가(1분)     생명 : 1 초마다 15 감소(20초)     공격 속도 : Lv3 증가(20초)
용기 : 75% 회복              용기 고정(6초)                    냉기 저항 Lv6(1분)
```

닫은 세 가지:

1. **스탯 이름 치환 규칙 — 확정.**
   ```
   {Staticinfo:SubLevel:<키>}  → SubLevelInfo(40행)에서 _stringKey == <키> 인 행
                               → 그 행 _knowledgeInfo(+0x46) = 지식 행 번호
   {Staticinfo:Status:<키>}    → StatusInfo(84행)에서 같은 방식, 지식은 _activeKnowledgeInfo(+0x34)
   지식 행 → KnowledgeInfo +0x08 = 문자열 객체 {char*, u32 len, u32 hash}
          → 그 hash 를 엔티티로 **현지화 cat 9 / 필드 0x490** = 표시 이름
   ```
   실측: Hp→생명 · Mp→용기 · Sp→기력 · IceResistance→냉기 저항 · AttackSpeedRate→공격 속도 ·
   CriticalRate→치명타 확률. 지식 행 0 은 "없음" 이 아니라 **유효한 행**이다(Knowledge_Hp) —
   없음은 0xFFFF 다. 지식 매니저는 전역 RVA `0x06D69AB8`(우리 `knowledge.h` 가 이미 쓴다).

2. **값 슬롯은 파생 클래스로 고른다(vtable).** 그리고 **u32 로 읽어야 한다** — u64 로 읽으면
   상위 4바이트가 잔여물이라 값이 터무니없어진다(Lv3 이 Lv72057594037927939 로 나왔다).

   | 클래스(vtable) | 파라미터 |
   |---|---|
   | `ChangeBuffLevel` 0x1458FD040 | `+0x94` 대상 레벨 |
   | `VaryStaticStatLevel` 0x1458FC1C0 | `+0xA0` u32 원값 |
   | `VaryDataDefinedStatRate` 0x1458FB5A0 | `+0x98` ÷ 10⁷ |
   | `VaryStatMaxValue` 0x1458FBD20 · `Damage` 0x1458FC370 | `+0x98` ÷ 1000 |

3. **BuffInfo 의 레벨 목록은 `+0x18`**(`+0x28` 이 아니다), 개수는 `+0x20`. 칸은 16바이트
   `{i32 레벨, u32 잔여물, BuffData*}` 이고 **레벨이 음수일 수 있어 첨자가 아니라 값으로 찾는다**.

어비스 기어도 같은 기계로 나온다 — 관통 I/II/III = BuffInfo 242
(`BuffLevel_Socket_AddCriticalRateByMaterialKey_FabricArmor`) 레벨 1/2/3, 패턴 61
`'천 갑옷 타격 시 치명타 확률 {Param1}% 증가'`, `+0x98` = 25000/50000/75000, 클래스 vtable
**0x1458FA908**(위 표에 없는 종류). 배율만 미정이다(아래 3번).

**H''. 배율은 게임 코드에서 뽑는다 (2026-09-23, 실행 이미지 역어셈블)**

`cdtb_probe dumpimage` 로 실행 중 이미지를 뜨면(372MB, PE, 기준 0x140000000) 코드가 보인다 —
디스크 exe 는 Denuvo 로 안 보이지만 이건 보인다.

- 문구 조립 함수(RVA 0x01F29xxx)가 파라미터 종류(1~8)마다 **BuffData 가상 함수 슬롯 11**
  (`call qword ptr [rax + 0x58]`)을 부른다. 인자: `rcx` = BuffData, `rdx` = 결과 자리,
  `r8b` = 파라미터 종류, `r9b` = `_isDisplayAbsoluteNumber`. 같은 함수가
  `[rax + r15*2 + 1]` 로 `_paramList` 를 읽어 §4.7-E 의 2바이트 구조도 재확인해 준다.
- **그 슬롯 11 함수 안에 "어느 칸을 어떤 배율로" 가 그대로 있다.** 정수 나눗셈은 컴파일러
  매직 상수로 보인다(`0x20C49BA5E353F7CF` = ÷1000, `0x346DC5D63886594B` = ÷10⁴),
  실수 경로는 `vdivsd`/`vmulsd` 의 상수로 보인다.
- 실측 확인: `VaryStatMaxValue` ÷1000 · 소켓 치명타(0x1458FA908) ÷10⁴ · 광물 드랍률
  (0x1458FC440) ÷10⁴ · `VaryDataDefinedStatRate` ÷10⁷. **배율은 클래스마다 다르므로
  표를 만들어야 하고, 그 표는 추측이 아니라 이 역어셈블로 뽑는다.**
- 전수 census(실행 중, 1.3초): 패턴에 닿는 효과 줄 **1459개**, 관련 클래스 **28종**. 상위 셋이
  73%(`ChangeBuffLevel` 437 · 0x1458FBD88 357 · 0x1458FC230 275). 효과 줄이 나오는 아이템은
  **890개**. `_enchantDataList` 는 있는데 `_equipBuffs` 가 없는 아이템이 **2972개**(어비스 밖의
  장비류 포함) — 이들은 `EnchantStatData` 의 스탯 목록을 쓴다(§4.7-H 4번).
- 주의: 슬롯 11 이 점프 섬프(thunk)인 클래스가 있고(0x1458FC230 · 0x1458FC1C0), 분기마다
  상수가 달라 **단순 정규식으로 읽으면 틀린다**. 표 생성기는 분기를 따라가고, 이미 아는 셋
  (÷1000 · ÷10⁴ · ÷10⁷)으로 **자기 검증**해야 한다.

**H'''. 배율의 분기 선택자는 `BuffData +0x3A` 다 (2026-09-23 실측)**

슬롯 11 의 네 번째 인자(`r9b`)는 호출부에서 `movzx r9d, byte ptr [rdi + 0x3a]` 로 오는데
`rdi` 가 **BuffData 자신**이다(바로 뒤 `mov rcx, rdi`). 파라미터의 `_isDisplayAbsoluteNumber`
가 아니다. 그 바이트는 0 또는 1 이고(전수 분포 **0: 2881 · 1: 232**), 클래스에 따라 **같은 칸을
다른 배율로** 내준다.

툴팁과 글자까지 맞은 줄들의 값(= 구현이 재현해야 하는 기준):

| 클래스 | `+0x3A` | 칸 | 배율 | 확인한 문구 |
|---|---|---|---|---|
| `VaryStatMaxValue` 0x1458FBD20 | 0 | +0x98 | ÷1000 | 생명 최대치 45 증가(1분) |
| 소켓 치명타 0x1458FA908 | 0 | +0x98 | ÷10⁴ | 치명타 확률 2 · 5 · 7% |
| `VaryDataDefinedStatRate` 0x1458FB5A0 | 1 | +0x98 | ÷10⁷ | 용기 : 75% 회복 |

그래서 배율 표의 키는 **(vtable, 파라미터 종류, `+0x3A`)** 이다. 파라미터 종류에 따라 칸이 다른
클래스도 있다(`Damage` 종류 3 = `+0xF8`, `SetStatMinRate` 종류 2 = `+0xA0`).

**H. 남은 것 (다음 게임 세션에 닫는다)**

1. ~~스탯 이름 치환~~ — **닫혔다**(H' 1번).
2. 파라미터 배율 표: 자리(vtable 슬롯 11)와 방법은 H'' 에서 확정했다. **28종 전부의 표를 뽑는
   생성기**를 만드는 것이 남았다(분기 · thunk 처리 + 자기 검증).
3. ~~어비스 `{Param1}` 의 배율~~ — **닫혔다**(사용자 툴팁 2026-09-23): 관통 II = `5%`, III = `7%`.
   내부값 25000 · 50000 · 75000 → 화면 2 · 5 · 7 이므로 **`÷10⁴` 뒤 내림**이다(2.5→2 · 7.5→7 —
   반올림이면 3 · 8 이 됐을 것이다). 이 배율은 소켓 치명타 클래스(vtable 0x1458FA908)의 것이고,
   `VaryDataDefinedStatRate`(÷10⁷)와 다르다 — **배율은 클래스마다 따로 확인해야 한다**는 증거가
   하나 더 늘었다.
4. `_equipBuffs` 가 없는 어비스 30개(파괴 I · 간파 I · 신속 I 계열)의 효과 출처 — 실측으로 좁혔다:
   `EnchantStatData._statList_DataDefinedStatic`(EnchantData 기준 `+0x28`)에 16바이트 칸이 있고
   `{u16 StatusInfo 행(+잔여물), …, u64 값 @+0x08}` 꼴이다(파괴 I = 행 4, 값 1000). 간파 I · 신속 I 은
   `_statList_DataDefinedStaticLevel`(`+0x38`)도 쓴다. 이 값들이 어떤 문구로 그려지는지가 남았다.
5. 35행이 `무기 · 장갑 · 신발` 세 줄로 접히는 규칙(데이터가 아니라 UI 코드에 있다).

## 5. 검색

`game::passes()` 가 이름 · 키에 더해 **설명 · 효과 문구**에도 검색어를 건다. 두 창이 같은 규칙을
쓴다(인벤토리의 "키로는 안 찾는다" 는 그대로). 효과 문구는 효과 스냅샷이 준비된 뒤부터 걸린다.

## 6. 오류 처리

| 상황 | 동작 |
|---|---|
| 현지화가 아이템 표보다 늦다 | 기존 재빌드가 이름과 설명을 함께 채운다 |
| 설명 키가 0 이거나 문자열이 안 풀린다 | 칸 빈칸, 툴팁 없음(80개 정도) |
| 사용·스킬·버프 표를 못 찾는다 | 효과 없음, 설명만. 로그 한 줄(한 번) |
| 모르는 ItemUseData / BuffData 클래스 | 건너뛰고 셈만 한다 |
| 목록 개수·행 번호가 말이 안 된다(갱신으로 구조가 밀림) | 그 아이템의 효과를 버린다 — 개수 상한 · 행 < 표 개수 검사 |
| 게임 갱신 | 오프셋은 이 문서 §4.1 과 시험이 못박는다. 어긋나면 효과가 비어 보인다(쓰기 없음 · 게임 함수 호출 없음 — 읽기만) |
