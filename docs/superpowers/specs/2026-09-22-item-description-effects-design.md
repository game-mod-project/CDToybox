# 아이템 설명 · 효과 컬럼 설계 (2026-09-22)

> **상태 — 📐 설계 (2026-09-22 사용자 승인, 구현 전).** 화면 · 데이터 · 검증 · 진행 네 부분을
> 하나씩 승인받았다. 실측으로 **확정된 것**과 구현 첫 단계에서 **잴 것**을 절마다 나눠 적었다.
> 실측은 전부 exe **1.0.0.2949**, 게임 실행 중 읽기 전용(ReadProcessMemory)이다.

## 0. 요약

- 아이템 목록 창 · 인벤토리 창에 **"설명" 열 하나**를 넣는다. 칸은 한 줄 요약, 마우스를 올리면
  설명 전문과 **효과 목록(수치 포함)**.
- 설명은 게임 현지화 표의 아이템 설명(필드 0x71)이다 — **경로 확정**.
- 효과 수치는 게임 표를 따라가 읽는다: 아이템 → 아이템 사용 → 스킬 → 단계 → 버프 데이터.
  **경로는 확정**, 버프 데이터 종류별 필드의 뜻은 구현 첫 단계에서 실측으로 정한다.
- 필터 바 검색이 설명 · 효과 문구에도 걸린다.
- PR 둘: ① 설명 열 + 검색 ② 효과.

## 2. 화면

- **넣을 곳**: 두 창 모두 정렬 색인이 열 차례에 묶여 있어(`item_sort_from_specs` · 인벤토리
  `apply_sort` 의 case 0~7) **기존 색인을 안 미는 자리**에 넣고, 정렬은 안 한다(`NoSort`).
  - 아이템 목록(`item_panel.cpp`, 지금 ★·키·등급·분류·전용·이름): **맨 끝**(이름 뒤, 색인 6).
  - 인벤토리(`inventory_panel.cpp`, 지금 이름·분류·전용·개수·담금질·내구도·연마·소켓·버튼):
    **소켓 뒤 · 버튼 열 앞**(색인 8). 버튼 열은 `NoSort` 라 색인이 9 로 밀려도 정렬과 무관하다.
- **칸**: 한 줄 요약. 효과를 해석한 아이템은 효과 요약(예: "생명 회복 · 화염 저항"), 아니면 설명의
  첫 줄. 칸 폭에서 잘린다.
- **툴팁**: 설명 전문 — `<br/>` 는 줄바꿈으로. 그 아래 효과 목록(같은 스킬·단계는 한 번만), 해석
  못 한 효과가 있으면 "해석 못 한 효과 N개".
- 설명이 없는 아이템(표에 설명 키가 없거나 문자열이 안 풀림)은 칸을 비우고 툴팁도 없다.

## 3. 데이터 — 설명 (확정)

| 사실 | 실측 |
|---|---|
| 설명 현지화 키 자리 | 아이템 레코드 **+0xB8** (u64). `_itemDesc`(+0xB0) 객체의 키 칸 — 이름 키 +0x28 이 `_itemName`(+0x20) 의 키 칸인 것과 같은 꼴 |
| 전수 확인 | 6816개 **전부** +0xB8 = `(아이템 키 << 32) \| 0x71`. 그중 설명 문자열이 풀리는 것 6736개 |
| 길이 | 최대 **503바이트**, 중앙 180 — 지금 읽기 상한 `kMaxText = 512` 안이지만 여유가 없다 |
| 내용 | 어비스 기어는 효과 문장이 들어 있다(바람 가르기: "…바람 가르기 : 전방으로 바람을 베어내는 검기를 날려 추가적인 피해를 입힌다."). 음식은 맛 묘사뿐, 비약은 효과를 말로만 |

구현:

- `ItemCatalogEntry` 에 `desc`(std::string) — `build_item_catalog` 가 이름과 **같은 자리에서**
  `resolve()` 로 푼다. 현지화가 늦게 오면 이름과 함께 다시 만든다(기존 `should_rebuild_catalog`).
- 설명용 읽기 상한을 **2048바이트**로 둔다(지금 최장 503 의 네 배) — `resolve` 에 상한 인자를
  더하고 기본값은 지금의 512 로 두어 이름 조회는 그대로 둔다. 상한에 걸려 널 종단을 못 찾으면
  지금처럼 실패로 친다(잘린 문장을 보이지 않는다).
- 메모리 ≈ 1.2MB(6736 × 평균 180).
- 문구 정리(순수 함수, 시험 대상): `<br/>` → `\n`, 요약 = 첫 줄.

## 4. 데이터 — 효과

### 4.1 경로 (확정, 2949 실측)

```
ItemInfo 레코드 +0x80  u32* 사용 행 목록,  +0x88 u32 개수          (_itemUseInfoList 자리)
  -> ItemUseInfoManager 레코드[행]   (StaticInfo 는 행 첨자 - staticinfo-index-not-key)
       +0x00 u32 키 · +0x08 _stringKey 객체 · +0x18 ItemUseData_* 객체(다형, RTTI 로 종류)
  -> ItemUseData_Skill  +0x30 {u32 스킬행, u32 값2}* ,  +0x38 u32 개수
  -> SkillInfoManager 레코드[스킬행]
       +0x18 단계 목록 {ptr, u32 개수} x N (16바이트 칸),  +0x20 u32 단계 수
  -> 단계[i] = BuffData 객체 포인터 배열 -> *BuffData(다형, RTTI 로 종류)
```

표는 모두 RTTI 로 찾는다(`find_static_manager`): `ItemUseInfoManager`(10140행) · `SkillInfoManager`
(2069) · `BuffInfoManager`(292) · `StatusInfoManager`(84). 모두 `+0x30` 개수 · `+0x58` 레코드 배열로
읽혔다(아이템 표와 같은 꼴).

실측 표본:

| 아이템 | 사용 | 스킬 | 비고 |
|---|---|---|---|
| 헤딘의 하급 비약(1000085) | 행 6680 `Potion_StatBuff_Tier1_0004_item_use_0` · Skill | 행 1494 `Item_Active_MP_Ignore_Use`(키 5105), 값2=2, 단계 15 | 단계 칸마다 개발용 한글 이름표 "N초간 용기 고정 · N초간 용기 리젠 무시 · 자연 친화 상태 체크 버프 · 포만 증가" (칸 0 = 2초, 칸 1 = 4초 …) |
| 프레야의 하급 비약(1000028) | 행 6675 · Skill | 행 1530 `Item_Active_Potion_DDD`(6700), 값2=1, 단계 4 | 이름표 **없음**. 단계 0 의 버프 데이터 = `ChangeBuffLevelBuffData`(+0x08 u32 0x24F, +0x18 u32 300000 …) |
| 가득 담은 떡고기구이(1003488) | 11개: RegisterReserveSlot 2 · Skill 7 · FeedToTarget 2 | `Active_ReserveSlot` · `Item_Active_Food_HP_4`(값2=8) ×3 · `Item_Active_ColdFood_FireResistance_2`(값2=1) ×3 | 같은 (스킬, 값2) 가 세 번 — 한 번만 보인다 |
| 편전(2200) | RegisterReserveSlot 2 · DestroyOnly 1 | — | 효과 없음 |
| 바람 가르기(1002569) | 0개 | — | 효과는 설명 문장에 있다 |

**개발용 이름표는 쓰지 않는다.** 헤딘 스킬 단계 5 의 넷째 이름표가 "14초간 용기 고정" 으로 값과
어긋나 있다 — 이름표는 실제 값과 틀릴 수 있다. 수치는 버프 데이터의 **값**에서 읽는다.

### 4.2 해석기 — 9종

스킬 사용이 있는 아이템 606개(사용 3656건)의 단계 안 버프 데이터 클래스 분포(값2-1 · 값2 두 칸
합산이라 대략치):

| 클래스 | 건수 |
|---|---|
| `VaryDataDefinedStatBuffData` | 5429 |
| `VoidActiveBuffData` | 2521 |
| `ChangeBuffLevelBuffData` | 2255 |
| `VaryStatBuffData` | 2004 |
| `IgnoreUseResourceStatBuffData` · `BlockRegenerateStatBuffData` | 186 · 186 |
| `VaryDataDefinedStatRateBuffData` · `VaryStatRateBuffData` · `VaryStatOverMaxValueBuffData` | 72 · 38 · 36 |
| 나머지 7종 | 합 17 |

위 9종이 약 99.9% 다. **종류마다 필드(능력치 행 · 값 · 지속 시간 · 비율 단위)의 뜻은 구현 첫
단계에서 실측으로 정하고 이 문서에 근거를 적은 뒤 구현한다.** 지금 아는 것은 클래스 이름과 개수,
`ChangeBuffLevelBuffData` 한 건의 바이트뿐이다.

- `ChangeBuffLevelBuffData` 는 다른 버프(BuffInfo)를 가리킨다고 보고 한 단계 더 따라간다 — **그
  필드가 BuffInfo 행인지는 첫 단계에서 확인**. 되돌아 도는 것을 막게 깊이를 제한한다(2).
- `VoidActiveBuffData` 는 무엇인지 모른다. 해석해 본 뒤 효과 목록에 넣을지 정한다.

### 4.3 능력치 이름

능력치 표(84행)에는 영문 내부 이름만 있다: Hp · Mp · Stamina · DDD · DPV · AttackSpeedRate ·
MoveSpeedRate · CriticalRate · FireResistance · IceResistance · Fullness … 현지화 표에서 이 행들의
한글 이름을 찾지 못했다("정신력" 은 풀 전체에서 3건, 전부 대사).

**한글은 게임 데이터 안에 근거가 있을 때만 붙인다.** 근거 없는 능력치는 내부 이름 그대로.

| 내부 이름 | 한글 | 근거 |
|---|---|---|
| DDD | 공격력 | 프레야의 하급 비약 제작법 설명 "[효과] 공격력 증가" + 그 비약의 스킬이 `Item_Active_Potion_DDD` |
| Mp | 용기 | `Item_Active_MP_Ignore_Use` 단계 이름표 "용기 고정 · 용기 리젠 무시" |
| Stamina | (미정) | 이름표는 "스테미나"(`SP_Ignore`). 화면 용어인지 모른다 — 툴팁 캡처로 정한다 |

제작법(레시피) 설명의 "[효과]" 문단(예: 고기찜 "생명/용기 회복")도 근거로 쓴다 — 종류만 있고
수치는 없다.

### 4.4 안 하는 것

- 스킬이 아닌 사용(슬롯 등록 · 먹이 주기 · 상자 열기 · 봉인 · 소환 …)은 효과로 치지 않는다.
- 해석기가 없는 종류는 목록에서 빼고 "해석 못 한 효과 N개" 로만 알린다.
- 개발용 이름표는 표시하지 않는다(§4.1).

### 4.5 계산 시점 · 게시

- 아이템 표를 만든 뒤 **배경 분석 스레드**에서 한 번 계산한다(스킬 사용이 있는 606개).
- 결과는 **따로 게시하는 불변 스냅샷**(`item_effects_for(key)`)이다. 아이템 표는 게시 뒤 바뀌지
  않는 것이 약속이라(`item_catalog` 참조를 쥔 채 그린다) 거기에 나중에 써 넣지 않는다.
- 표 중 하나라도 못 찾으면 효과만 비고 설명은 그대로 보인다. 다음 재시도 주기에 다시 계산한다.

## 5. 검색

`game::passes()` 가 이름 · 키에 더해 **설명 · 효과 문구**에도 검색어를 건다. 두 창이 같은 규칙을
쓴다(인벤토리의 "키로는 안 찾는다" 는 그대로). 효과 문구는 효과 스냅샷이 준비된 뒤부터 걸린다.

## 6. 오류 처리

| 상황 | 동작 |
|---|---|
| 현지화가 아이템 표보다 늦다 | 기존 재빌드가 이름과 설명을 함께 채운다 |
| 설명 키가 0 이거나 문자열이 안 풀린다 | 칸 빈칸, 툴팁 없음(80개 정도) |
| 사용·스킬·버프 표를 못 찾는다 | 효과 없음, 설명만. 로그 한 줄(한 번) |
| 모르는 ItemUseData / BuffData 클래스 | 건너뛰고 셈만 한다 |
| 목록 개수·행 번호가 말이 안 된다(갱신으로 구조가 밀림) | 그 아이템의 효과를 버린다 — 개수 상한 · 행 < 표 개수 검사 |
| 게임 갱신 | 오프셋은 이 문서 §4.1 과 시험이 못박는다. 어긋나면 효과가 비어 보인다(쓰기 없음 · 게임 함수 호출 없음 — 읽기만) |

## 7. 검증

- **단위 시험**(`cdtb_tests`)
  - 문구 정리: `<br/>` → 줄바꿈, 요약 첫 줄, 빈 설명
  - 검색: 설명 · 효과 문구 일치, 인벤토리 `match_key = false` 유지
  - 해석기: 이번에 게임에서 읽은 **실제 바이트**를 시험에 박아 필드 해석을 고정(캡처 시험 관례)
  - 경로 걷기: 가짜 메모리(`fake_memory.h`)로 행 목록 → 사용 → 스킬 → 단계 연결 · 깊이 제한 · 상한
- **실측**: 해석기 9종의 필드 뜻을 읽기 전용 탐침으로 정한다 — 근거를 이 문서 §4.2 에 적은 뒤 구현.
- **게임 화면 대조 한 번**: 사용자가 툴팁을 캡처(헤딘의 하급 비약 · 프레야의 하급 비약 · 가득 담은
  떡고기구이 · 바람 가르기). 이 한 번으로 **값2 가 1-기준인지 0-기준인지**(헤딘 값2=2 가 4초면
  1-기준), 수치, 능력치 한글 이름을 정한다.

## 9. 실측 기록 (근거)

- 설명 키 전수 · 길이: 2949 실행 중, 아이템 매니저에서 6816 레코드를 읽어 +0xB8 을 대조하고 현지화
  풀에서 길이를 쟀다.
- 표 인스턴스: `cdtb_probe instances .?AVItemUseInfoManager@pa@@` 등 넷. 주소는 판마다 다르다 —
  구현은 RTTI 로 찾는다.
- 클래스 분포: 606개 아이템의 스킬 사용 전수(§4.2).
- 현지화 문구: `cdtb_probe loc <키>` / `loc item <엔티티>` / `loc find <문자열>`.
- 공개 스키마(NattKh/CrimsonDesertModdingTools `pabgb_complete_schema.json`)에서 `ItemInfo.
  _itemUseInfoList` · `ItemUseInfo._itemUseInfoData` · `BuffInfo` 필드 **이름**을 참고했다. 스키마는
  구버전 기준이라 오프셋은 쓰지 않았다.

관련: `STATUS.md` §1.6(현지화) · §1.7(아이템 표) · `specs/2026-09-01-localization-lookup.md` ·
