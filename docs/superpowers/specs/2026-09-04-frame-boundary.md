# 게임 로직 프레임 경계 찾기 (2026-09-04)

치트 실행을 액터 조회 후킹 한복판에서 하는 대신, 락이 없고 TLS 가
서 있는 "프레임 경계"에서 하려 했다. **결론: 후보로 본 메시지 펌프와
그 디스패처는 메시지 처리 작업 전용이라 싱글플레이 유휴 상태에서는
아예 돌지 않는다. 매 프레임 경계가 아니다.** 액터 조회 자리가 여전히
유일하게 확인된 실행 지점이다.

## 출발점: 호출 스택 (2026-09-03, 20:58)

액터 조회 후킹(`0x1DF6940`)이 실제로 동작할 때 스택을 한 번 떴다.
그때 프레임이 이 작업의 지도였다.

```
[6] 모듈+0x278A44E   치트 처리기
[7] 모듈+0x253D028   역직렬화
[8] 모듈+0x236A3E4   메시지 하나 처리
[9] 모듈+0x236A31E   ↑
[10] 모듈+0x23692DB  메시지 펌프 루프 본문
[11] 모듈+0xF685585  작업 콜백 (펌프를 부른다)
[12] 모듈+0x121F653  작업 실행 (call rdx)
[14] 모듈+0x1202A52  스레드 본체
[15+]               커널·ntdll (스레드 시작)
```

여기서 두 함수를 골랐다.

- `0x2369170` **메시지 펌프.** [10]의 함수. 세션 큐를 걷어 메시지를
  `0x236A160` 으로 하나씩 역직렬화·처리기까지 돌린다.
- `0x121F640` [12]의 "작업 실행". `mov rax,[rcx+0x78] / mov rdx,[rax+8]
  / test / call rdx`.

## TLS+0x250 의 정체 (정적)

작업 실행 래퍼가 작업마다 TLS 를 세우고 지운다.

```
0xB1D2DF0  작업 시작   TLS+0x250 = 작업 컨텍스트   (0xB1D2E26)
   ... 작업 본체 ...
0x121F660  작업 끝     TLS+0x250 = 0
```

디스패처 자리(스택 [12])에서 요청이 실행되지 않던 이유가 이것이다 -
그 자리는 작업 실행 래퍼 **밖**이라 TLS 가 아직/이미 널이다. 액터
조회 자리는 작업 본체 한복판이라 TLS 가 서 있다.

## 실측: 펌프도 디스패처도 돌지 않는다

펌프(`0x2369170`)와 디스패처(`0x121F640`)를 MinHook 으로 걸고, 돌아온
자리에서 요청을 실행하도록 했다. 계측으로 호출 횟수와 작업별
콜백·컨텍스트·TLS 상태를 로그에 남겼다.

```
07:12:58  메시지 펌프 후킹 설치 (RVA 0x2369170)
07:15:02  자동 분석 완료           (월드 진입)
07:21:51  인벤토리 지급 요청을 걸었다 - 게임 스레드를 기다린다
...
펌프 호출 0회 · 작업 #(디스패처) 0회 · 펌프 경계 실행 0회
```

**월드에서 수 분, 지급 요청을 건 뒤에도 둘 다 호출 0회다.** 같은
동안 액터 조회 후킹은 세션·문 줄을 계속 찍으며 수백 번 불렸다. 스택
[6]에서 액터 조회의 조상이던 펌프·디스패처가, 정작 액터 조회가 수백
번 도는 이 시간대에는 한 번도 돌지 않았다.

즉 20:58 스택은 **치트 메시지가 처리되던 그 한순간**의 것이고, 그때만
펌프가 돌았다. 액터 조회가 늘 불리는 것은 메시지 처리가 아니라 **세션
스캔** 등 다른 647개 호출 지점 때문이다. 펌프는 세션 메시지 큐에
처리할 것이 있을 때만 도는, **메시지 구동** 함수다 - 프레임 구동이
아니다. 싱글플레이 유휴 상태에는 처리할 메시지가 없어 돌지 않는다.

### 되풀이하지 말 것

**"돌아온 자리"에서만 실행하도록 게이트를 걸면, 그 함수가 안 돌 때
요청이 영영 실행되지 않는다.** 순수 펌프 빌드(028d2d9)에서 지급 요청이
집어가지지 않고 멈췄는데, 게임 탓이 아니라 펌프가 안 돌아서였다.
액터 조회 폴백을 껐던 것이 실수다. 새 실행 지점을 넣을 때는 기존
지점을 **끄지 말고** 보조로 두어, 새 지점이 실제로 도는 것을 확인한
뒤에 옮긴다.

**조상 프레임이 자주 보인다고 그 함수가 자주 도는 것은 아니다.** 한
번 뜬 스택에서 펌프가 액터 조회의 조상이었지만, 그 스택은 드물게만
성립했다.

## 남은 길

진짜 매 프레임 경계는 **작업 실행 래퍼**(`0xB1D2DF0` 가 TLS 를 세우고
`0x121F660` 이 지우는 그 함수)다. 이건 메시지 작업만이 아니라 모든
작업을 감싸므로, 매 프레임 여러 번 돈다. 다음에 볼 때는:

1. `0xB1D2DF0`(또는 그 함수의 시작)를 후킹해 호출 빈도를 먼저 잰다 -
   펌프처럼 안 도는 함수인지 로그로 확인한 **뒤에** 실행 지점으로
   쓴다.
2. 이 래퍼는 여러 워커 스레드에서 돌 수 있다. TLS+0x250 이 세워진
   작업이라도 그 작업이 게임 로직 스레드의 것인지 가려야 한다 -
   계측이 남기는 스레드 ID·컨텍스트로 좁힌다.
3. 래퍼가 감싸는 작업 본체 안에서 우리 요청을 실행하면 TLS 가 서
   있고 그 작업의 락은 그 작업 것뿐이라, 치트 처리기의 락과 겹치지
   않는다 - 지금 액터 조회 자리에서 겹치던 문제를 피한다.

## 펌프 훅이 지급을 막았다 (2026-09-04, 통제 대조로 확정)

**계측용으로 걸어 둔 펌프 훅이 지급을 통째로 막았다.** 조사 훅을
켠 빌드에서는 지급 요청이 10분 넘게 큐에서 안 빠졌고, 훅을 끄니
연속 지급이 2~8초에 전부 완료됐다.

| 빌드 | 지급 |
|---|---|
| 펌프·작업 래퍼 훅 켜짐 | 10분+ 미완료 |
| 훅 꺼짐 (액터 조회 자리만) | 2~8초 완료 (여러 번 재현) |

원인은 `g_detour_depth` 간섭이다. 지급은 `det_actor_getter` 에서
**깊이가 정확히 1일 때만** 실행된다. 그런데 펌프는 치트 처리 경로의
조상 프레임이라(20:58 스택 [10]), 지급을 처리하는 그 시점에 함께
돈다. 펌프 훅의 `++g_detour_depth` 가 그 창에서 깊이를 밀어 올려,
액터 조회의 `depth == 1` 조건이 깨졌다. 요청이 영영 실행되지 않았다.

**펌프 호출이 로그에 0회로 보인 것에 속았다.** 펌프 훅의 로그는
`depth == 1` 일 때만 찍는데, 펌프가 늘 중첩 진입(다른 훅 안)이라
`++` 뒤 깊이가 2 이상이었다. 로그만 안 찍혔을 뿐 **깊이는 계속
건드리고 있었다.** "호출 0회 = 안 돈다" 는 틀린 해석이었다 - 실제로는
돌면서 지급의 실행 조건만 깨고 있었다.

### 되풀이하지 말 것 (2026-09-04)

- **계측 훅도 공유 상태를 건드리면 기능을 깬다.** "실행은 안 하고
  로그만 남긴다" 고 해도, `g_detour_depth` 같은 실행 게이트를 건드리면
  다른 실행 지점이 죽는다. 계측은 자기만의 카운터를 써야 한다.
- **"호출 0회" 를 "안 돈다" 로 읽지 말 것.** 로그 조건(`depth==1`)이
  못 맞았을 뿐 함수는 돌고 있었다. 로그가 안 나오는 것과 코드가 안
  도는 것은 다르다.
- **잘 되던 기능이 갑자기 안 되면 내 변경부터 의심할 것.** "게임
  활동에 묶인 성질" 이라고 환경 탓으로 돌렸으나, 통제 대조(훅
  껐다 켰다)로 재니 내 훅이 원인이었다. 사용자의 "말이 되냐" 는
  지적이 맞았다.

## 작업 실행 래퍼도 막다른 길이다 (2026-09-04, 실측 확정)

`0xB1D2DE0` 을 시간 기반 계측으로 걸어 재니, **시작 때 워커 스레드마다
한 번씩 총 4회 불리고 그 뒤로는 안 불렸다.** 월드에서 지급을 여러 번
눌러도 첫 6초의 4회 이후 새 호출이 0이었다. 즉 이 함수는 매 프레임
작업 러너가 아니라 **스레드 풀 초기화**(워커 스레드가 자기 작업
컨텍스트를 처음 세우는 자리)다. `[rcx+0x70]=1` 과 TLS+0x250 설정도
스레드마다 한 번 하는 것으로 읽힌다.

그러므로 20:58 호출 스택에서 뽑은 프레임 경계 후보 **둘 다 막다른
길**이다.

| 후보 | 실측 |
|---|---|
| 메시지 펌프 `0x2369170` | 메시지 구동. 유휴 시 안 돎 |
| 작업 실행 래퍼 `0xB1D2DE0` | 스레드 풀 초기화. 총 4회 뒤 정지 |

한 번 뜬 호출 스택의 프레임들은 **그 순간의 사슬**이지 매 프레임 도는
루프가 아니었다. 프레임 경계를 그 스택에서 뽑으려던 접근 자체가 틀린
전제였다.

### 그러면 어디가 매 프레임인가

지급이 액터 조회 자리에서 1~3초에 실행되는 것으로 보아, **액터 조회
자리 자체가 게임 로직 스레드에서 사실상 매 틱 도는 실행 지점**이다.
별도의 "더 깨끗한" 프레임 경계를 찾으려면 이 스택이 아니라 게임의
메인 로직 틱(세션 업데이트 루프)을 직접 추적해야 한다 - 별도 과제다.
지금은 교착이 완화 뒤 재발하지 않으므로 급하지 않다.

## 게임 로직 스레드의 매 프레임 경로 (2026-09-04, 실측 매핑)

지급이 안 걸린 **평소 플레이 중** 액터 조회 스택을 잡았다. 20:58
스택(치트 처리 중)과 **완전히 같은 경로**였다. 즉 액터 조회는
평소에도 오직 메시지 처리 경로로만 불린다 - 게임이 매 프레임 세션
메시지를 처리하고, 그 핸들러가 액터 조회를 부른다. 스레드는 37452
하나다.

```
[15] 0x120296E  스레드 본체 (워커 루프)
[13] 0x121F640  디스패처 (작업 하나 실행: call [ [rcx+0x78]+8 ])
[12] 0xF685580  작업 콜백 (펌프를 부른다) -> 복귀 0xF685585
[10] 0x2369170  메시지 펌프 (세션 큐를 비운다)
[9]  0x236A160  메시지 하나 처리
[8]  0x236A3C0
[7]  0x253CD90  역직렬화
[6]  0x2789EB0  치트/메시지 핸들러
[4]  0x160B040
[3]  0x1D467F0
[2]  0x1E12450  -> 액터 조회 0x1DF6940
```

**이 스레드의 매 프레임 작업은 `0xF685580`(메시지 펌프 콜백)이다.**
그 위(디스패처·스레드 본체)는 일반 워커 루프다.

### 그런데 계측 로그가 라이브 스택과 어긋난다 (미해결)

프로세스 메모리로 확인하니 펌프(`0x2369170`)·디스패처(`0x121F640`)·
작업 래퍼·액터 조회 네 함수 **모두 `E9` jmp 로 실제 후킹**돼 있다.
그런데 펌프·디스패처 훅의 "호출 후" 로그는 0회인데, 위 라이브 스택에는
둘 다 활성 프레임으로 들어 있다. 즉 **함수는 도는데 우리 detour 의
g_orig 호출 뒤 코드가 안 찍힌다.** 작업 래퍼는 반대로 잘 찍혔다(초기
4회).

가설(미검증): 게임 워커 스레드는 우리 DLL 주입 전부터 있던 스레드라,
DLL 의 `thread_local`(g_pump_depth 등)이 그 스레드에서 0 으로 초기화
안 돼 로그 조건(`depth==1`)이 안 맞을 수 있다. 그렇다면 g_detour_depth
도 같은 문제일 텐데 지급은 되므로(depth==1 이 맞아야 실행됨) 완전한
설명은 아니다. **이 어긋남을 풀려면 detour 진입 첫 줄에 무조건 로그를
한 줄 넣어 detour 자체가 도는지부터 봐야 한다** - 다음 과제.

이 어긋남이 중요한 이유: **펌프 훅이 지급을 막은 진짜 원인이 depth
간섭이 아니라 이 thread_local 문제일 수 있다.** 그렇다면 depth 분리
수정은 증상만 가린 것이고, 계측 훅을 이 스레드에서 다시 쓰려면 근본을
봐야 한다. 지금 지급이 되는 것은 확인됐으나(회귀 검증 통과), 원인
규명은 열려 있다.

### thread_local 가설은 틀렸다 - 펌프는 안 돌아온다 (진단 확정)

detour 진입 첫 줄에 게이트 없는 로그를 넣어 확인했다.

```
[디스패처진단] 진입 1회 스레드 19512 g_detour_depth=0
[디스패처진단] 진입 N회 스레드 38172/35060/31368 g_detour_depth=0
[펌프진단]     진입 1회 스레드 19512 g_pump_depth(++전)=0
```

**depth 는 0 으로 정상 초기화된다** - thread_local 미초기화 가설은
틀렸다. 대신 둘이 드러났다.

1. **펌프·디스패처는 전용 워커 스레드들(19512·38172·35060·31368)에서
   돈다.** 게임 로직 스레드가 아니다.
2. **`g_orig_pump` 이 돌아오지 않는다.** detour 진입은 찍히는데
   `g_orig_pump` 뒤의 "메시지 펌프 호출" 로그는 끝내 0회다. 이
   함수들은 워커 스레드의 **장기 실행 메시지 루프**라, 호출 후 코드가
   관측 구간에 실행되지 않는다.

**이것이 펌프 경계가 못 쓰이는 진짜 이유다.** 스레드 초기화도 depth
간섭도 아니고, `g_orig_pump` 이 안 돌아와 그 뒤에서 무엇을 하든
실행되지 않는다. (그러므로 앞서 "펌프 훅이 지급을 막았다"의 원인도
depth 간섭이 아닐 수 있다 - 워커 스레드의 이 루프를 후킹한 것이
메시지 파이프라인 타이밍을 흔들어 게임 로직 스레드로의 메시지 흐름을
막았을 가능성이 더 크다. 어느 쪽이든 계측 훅을 이 워커 루프에 거는
것은 위험하다.)

### 결론: 이 경로에 더 깨끗한 경계는 없다

매 프레임 경로의 모든 지점이 **메시지 처리 작업 안**이다 - 액터 조회와
같은 활동 의존성(메시지가 흘러야 돎)과 같은 락 성질을 공유한다.
`0xF685580` 진입이나 펌프 복귀도 결국 같은 작업 안이라, 액터 조회보다
분명히 나은 점이 없다. 게다가 이 스레드의 thread_local 문제가 풀리기
전에는 어떤 depth 기반 게이트도 못 믿는다. **액터 조회 자리가 여전히
현실적인 실행 지점이고, 지급이 1~3초에 된다.**

## depth 안전 계측은 지급을 막지 않는다 (2026-09-04, 회귀 검증)

계측 훅을 `g_detour_depth` 대신 펌프 전용 `g_pump_depth` 로 분리하고
다시 켠 뒤, 지급이 계속 되는지 확인했다. 켠 채로 지급 3건이 1~3초에
완료됐고 예외 0건이다. depth 간섭 수정이 맞다.

## 현재 상태

- 액터 조회 자리를 **유일한 실행 지점으로 되돌렸다.** 지급이 1~3초에
  안정적으로 된다(실측, 계측 훅 켠 상태 포함).
- 조사용 훅(`pump_hook_install`·`taskrun_hook_install`)은 코드에
  남기되 **camera.cpp 에서 기본으로 껐다**(주석). 다시 켤 때는 위
  depth 간섭부터 없애야 한다 - 계측 훅은 `g_detour_depth` 를 건드리지
  않도록 고쳐야 한다.
- 작업 실행 래퍼(`0xB1D2DE0`)는 시간 기반 계측까지 넣었으나, 초당
  0.5회 미만으로 매 프레임 러너가 아니었다(로딩·메뉴 구간 측정).
  월드에서의 빈도는 아직 못 쟀다.
- 도구: `find_message_pump_rva`, `find_task_run_rva`(34바이트로 유일),
  `pump_hook_install`, `taskrun_hook_install`.
