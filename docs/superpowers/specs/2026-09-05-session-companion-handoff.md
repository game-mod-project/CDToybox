## 5. 남은 일 (우선순위 순)

1. **Phase 1 실측**: 게임에서 야생 개체를 한 마리 길들이면 로그에
   `획득 대상: 액터 핸들 …`. 그 핸들로 `[0x6C29C70]+0x48` 표를 역추적해
   핸들 ↔ 액터 포인터 대응을 만든다(근처 탭에 핸들 열 추가).
2. **Phase 2 획득**: (a) 2338 구동 — 근처 탭의 핸들로 버릴 세이브에서 1회.
   서버 게이트(`+0x3B0` 플래그·상태표) 통과 여부가 관건. (b) 즉시 포획
   패치 — 우리 exe 에서 게이지 저장 지점을 다시 찾아야 함.
3. **소유 탭**: Ack 캡처가 안 되므로 부르기(2894) 캡처의 MercenaryNo 와
   스폰된 액터를 짝지어 학습하거나 진영 컴포넌트 구조를 다시 본다.
4. 근처 탭에 **거리**(액터 월드 좌표) 추가.
5. 로스터 한글 표시명(캐릭터 현지화 키) — 미해결 유지.

## 7. 2026-09-06 실측 — 3022 구동은 서버가 계정을 로그아웃시킨다

획득한 동반자가 "소환된 상태"로 걸려 다른 개체를 소환할 수 없는
문제를 풀려고 소환 해제 메시지를 구동했다. 결론부터: **하지 말 것.**

### 7.1 무슨 일이 있었나

1차(13:07) — `TrocTrUnSetMainPetAndUnSpawnReq`(3022)를 1000465에
구동. 로컬 결과 0. 그 뒤 모든 구동이 `0xC0000005` 로 죽었고, 네 번
반복한 끝에 클라이언트가 오류를 내며 메인 화면으로 떨어졌다.

2차(13:42) — 세션 문제를 고친 새 빌드로 같은 와이어를 구동. 로컬
결과 0, 예외 없음. **16초 뒤 서버가 로그아웃시켰다.**

```
게임을 진행할 수 없는 오류가 발생하여 로그아웃됩니다.
오류 코드(4205559856)      = 0xFAABC030
```

### 7.2 인과가 뒤집혔다

1차 때는 "풀린 세션 포인터"를 원인으로 봤다. 틀렸다. 순서는 이렇다.

```
3022 구동 -> 서버가 접속을 끊는다 -> 세션 객체가 풀린다
          -> 그 다음 구동이 [세션+0x88] 에서 죽는다 (결과)
          -> 반복 -> 오류 대화상자
```

풀린 세션은 **결과**였다. 2차에서 세션을 제대로 고르게 하자 예외는
사라졌고, 남은 것은 서버의 로그아웃뿐이었다 - 그것이 진짜 원인이다.

세션 수정(커밋 0934f21·4ed40f6)은 그대로 가치가 있다. 끊긴 뒤의
연쇄 예외를 막는다. 다만 끊김 자체를 막지는 못한다.

### 7.3 무엇이 안전하고 무엇이 아닌가

| 메시지 | 실측 |
|---|---|
| 2338 획득/대상 | 안전. 여러 번 성공, 서버가 2107로 응답 |
| 2992 소환 상태 전환 | 두 번 구동, 즉시 끊기지는 않음. 효과 미확인 |
| 3022 펫 해제+소환 해제 | **두 번 모두 로그아웃**. 쓰지 말 것 |
| 2962 등록 후 소환 계산 | 미시도. 같은 부류라 위험 |

와이어가 틀렸을 수도 있고(본문이 단순 u64가 아닐 수 있다), 서버가
정상 경로 밖의 요청을 규약 위반으로 볼 수도 있다. 어느 쪽이든
살아 있는 서버에 대고 시험할 일이 아니다.

### 7.4 그래서 방침

- 소환 해제를 메시지로 풀지 않는다. 게임의 **반려동물 풀어주기**로
  정리한다(사용자 확인된 경로).
- 걸린 상태를 푸는 대신 **만들지 않는 쪽**을 본다. 정상 포획을 한 번
  하고 캡처 훅으로 게임이 실제로 보내는 순서를 배운 뒤, 그 순서를
  그대로 따라가야 한다. 지금 획득은 2338 하나만 보내므로 게임이 그
  뒤에 보내는 것을 빠뜨리고 있을 가능성이 크다.
- 계정 위험을 감수할 일인지 사용자가 먼저 판단한다. 서버가 거부하는
  요청을 반복해 보내는 것은 온라인 게임에서 좋게 보이지 않는다.

## 8. 2026-09-06 정정 — 온라인이 아니다, 그리고 치트 경로는 막혀 있다

### 8.1 온라인 게임이 아니다

§7 에서 "살아 있는 서버에 대고 시험할 일이 아니다, 계정 위험"이라고
적었다. 근거 없는 말이었다. 실측:

```
Get-NetTCPConnection -OwningProcess <CrimsonDesert PID>  ->  연결 없음
```

붉은사막은 싱글플레이다. 로그의 `ServerInventoryActorComponent` /
`ClientInventoryActorComponent` 는 같은 프로세스 안의 두 계층이다.
계정 위험은 없고 실험 비용은 재접속 한 번이다. §7.4 의 "계정 위험을
먼저 판단하라"는 문장은 폐기한다.

### 8.2 3022 로그아웃의 진짜 뜻

와이어 형식은 맞았다. 역직렬화(RVA 0x2962430)를 읽으면 본문 8바이트를
u64 하나로 읽고 커서가 본문 길이와 같은지까지 확인한다. 우리 와이어는
그 검사를 전부 통과했다.

```
call 0x2AD05B0          ; 작업 함수
mov  ebx, [rbp+0x77]    ; 돌려준 코드
test ebx, ebx
je   ...                ; 0 이면 조용히 끝
mov  eax, 0x3f5         ; 아니면 오류 메시지 1013 을 만들고
mov  dword [rbp+2], ebx ; 코드를 실어 보낸다
```

즉 **0xFAABC030 은 작업 함수가 돌려준 실패 코드**다. 규약 위반이
아니라 그냥 실패이고, 이 클라이언트는 그 오류를 로그아웃으로 처리한다.
넘긴 용병 번호가 지금 유효하지 않을 가능성이 크다 - 그 번호들은 이전
게임 세션의 획득응답에서 주운 것이다.

### 8.3 개발자용 치트 메시지는 이 빌드에서 비어 있다

용병 관련 `...ForCheatReq` 가 세 개 있다.

| 클래스 | vtable[2] |
|---|---|
| TrocTrRequestHireMercenaryForCheatReq | RVA 0x2961E10 |
| TrocTrRequestDischargeMercenaryForCheatReq | RVA 0x2962010 |
| TrocTrChangeHiredMercenaryWithSummonForCheatReq | RVA 0x294B150 |

셋 다 모양이 같다. 머리를 검사하고, 본문 필드를 읽고, 커서를 확인한
뒤 `mov dword ptr [rbx], edi` (edi=0, 성공)로 끝난다. **작업 함수를
부르는 자리가 없다.** 나머지 호출은 전부 실패 경로의 로깅이다.

리테일 빌드에서 치트 처리기가 비워진 것이다. 메시지 클래스는 생성기가
찍어 내므로 남아 있지만 몸통이 없다. 이 경로는 막혔다.

(지급 계열 치트가 도는 것과 다르다 - 그쪽은 처리기가 살아 있다.
"치트 메시지"라고 다 되는 것이 아니라 메시지마다 확인해야 한다.)

### 8.4 남은 길

정상 경로 2338 하나뿐이다. 그것은 잘 된다. 문제는 등록 뒤 상태이므로,
게임이 정상 포획 때 2338 뒤에 무엇을 더 보내는지 배워서 그대로
따라가야 한다. 캡처 훅 11개가 이미 붙어 있으므로 정상 포획을 한 번
하면 순서가 로그에 남는다.

용병 번호는 추측하지 말 것. 소유 목록(TrocTrMercenaryDataListAck,
RVA 0xB63A40) 캡처로 현재 유효한 번호를 먼저 받는다.

## 9. 2026-09-06 결론 — 획득은 되고, 세이브/로드가 마무리다

### 9.1 증상과 답

획득(2338)으로 등록한 개체는 목록에는 들어가는데 소환에 아무 반응이
없다. 소환 상태 전환(2992)도, 펫 해제(3022)도 답이 아니었다.

**세이브/로드를 한 번 하면 정상 동작한다.** 실측 2026-09-06: 같은 날
추가한 진돗개(1000465)와 참새(1000466)가 그 자리에서는 반응이 없다가
세이브/로드 뒤 소환·해제가 모두 됐다.

등록 기록은 바로 생기지만 실행 시점 상태는 월드를 다시 불러올 때
완성되는 것으로 보인다. 부적 경로에는 등록 뒤 소환 단계가 있고
(SummonMercenaryAfterRegistAck 가 그 응답) 우리는 그것을 건너뛰는데,
월드 재적재가 그 자리를 대신 메운다.

### 9.2 왜 헤맸는가 - 기록

이 결론에 닿기까지 잘못 짚은 것들을 남긴다. 같은 길을 다시 걷지
않기 위해서다.

- **"부적으로 넣은 것은 되고 획득한 것은 안 된다"** - 근거 없이
  나눈 것이다. 부적 6종이 준 것은 특수 탑승물 5종 + 피닉스뿐이고,
  그레이하운드·잿빛 고양이·고양이는 전부 획득으로 넣은 것이다.
  같은 경로인데 되는 것과 안 되는 것이 갈렸고, 그 차이는 경로가
  아니라 **추가한 뒤 월드를 다시 불러왔는지**였다.
- **"온라인 게임이라 계정이 위험하다"** - TCP 연결이 없다. §8.1.
- **"풀린 세션이 튕김의 원인"** - 결과였다. §7.2.
- **번호를 옛 로그에서 주워 썼다** - 그 번호는 이미 풀려 재사용
  대기 중이었다. 실제로 새 획득이 같은 번호(1000465)를 받았다.
  용병 번호는 획득응답(2107)에서 그때그때 받을 것.

### 9.3 지금 상태

- 근처 탭 획득 버튼: 동작한다. 화면과 툴팁에 "세이브/로드 후에
  소환됩니다"를 적었다.
- `summon <번호> [x y z]` 명령: 2962 를 직접 걸어 재적재 없이
  마무리할 수 있는지 시험하는 용도로 넣어 두었다. **미검증**이고,
  작업 함수가 실패하면 게임이 오류 1013 으로 로그아웃하므로 번호가
  확실히 유효할 때만 쓸 것.
- 2992·3022 는 쓰지 말 것. 답이 아니고 3022 는 위험하다.

## 10. 2026-09-06 — 2962 는 답이 아니다 (실측 종료)

세이브/로드 없이 마무리할 수 있는지 보려고
`TrocTrCompleteCalculateSummonAfterRegistReq`(2962) 를 직접 걸었다.
**안 된다.**

시험은 두 번 했다.

| 시각 | 좌표 | 결과 |
|---|---|---|
| 15:15 | (32.0, 3.0, 0.0) — 틀림 | 구동 성공, 소환 안 됨 |
| 15:46 | (-10579.5, 628.3, -3821.7) — 정확 | 구동 성공, 소환 안 됨 |

두 번 다 결과 0 이고 로그아웃도 없었다. 좌표를 고친 뒤에도 마찬가지
이므로 좌표 탓이 아니다. 2962 는 등록 뒤 마무리의 답이 아니다.

**결론: 획득한 개체는 월드 재적재가 필요하다.**

처음에는 "세이브/로드가 필요하다"고 적었는데 조건이 더 넓다 - 실측
2026-09-06: **세이브/로드 없이 다른 지역으로 완전히 이동해도 소환된다.**
즉 필요한 것은 저장이 아니라 지역 적재다. 등록 기록은 2338 로 바로
생기지만 실행 시점 객체는 지역을 불러올 때 만들어지는 모양이다.

화면과 툴팁도 "다른 지역으로 이동하거나 세이브/로드하면 소환됩니다"로
고쳤다. 이동만으로 되면 플레이를 끊을 이유가 없다.

`summon` 명령은 남겨 두되 쓸 이유가 없다.

남은 후보가 없지는 않다 - 등록 응답(2107) 뒤에 게임이 무엇을 더
보내는지 정상 등록에서 잡아 보면 된다. 다만 부적 등록은 6종뿐이고
그것을 다시 관측하려면 부적을 또 써야 한다. 비용 대비 얻을 것이
적어 여기서 멈춘다.

### 10.1 부수 소득 - 카메라 좌표 오프셋이 밀려 있었다

좌표를 쓰려다 기존 버그를 찾았다. `component_offset::kWorldPosition`
이 0x360 을 가리키는데 그 자리는 움직이지 않는다. 실제 좌표는
+0x378 이다. probe 로 2.5초 간격 두 번을 떠서 확인했고, 다른 프로세스
에서도 같은 자리였다. 커밋 b0b18fe 에서 고쳤다.

이 상수는 프리카메라(읽기·쓰기)와 바닥 스폰도 쓴다. 셋 다 죽은 자리를
보고 있었다.

**주의:** 월드에 갓 들어온 직후에는 그 자리도 아직 (0, 0, 22.8) 같은
값이다. 카메라가 자리를 잡은 뒤에 읽어야 한다.

**남은 개선:** 오프셋을 상수로 박아 두는 것 자체가 약하다. 패치로 한
번 밀린 것을 확인했으니 또 밀리면 조용히 틀린 좌표가 나간다. 실행할
때마다 움직이는 float 세 칸을 찾아 스스로 잡게 하는 편이 낫다.

## 11. 2026-09-06 — 메시지로는 재적재를 대신할 수 없다 (실험 종료)

월드 재적재 없이 마무리하는 방법을 찾으려고 후보를 모두 시험했다.
**전부 실패다.** 더 두드리지 않는다.

| 메시지 | 구동 | 결과 |
|---|---|---|
| 2992 소환 상태 전환 | 성공(0) | 효과 없음 |
| 3022 펫 해제 | 실패 | 로그아웃. 죽은 번호를 넣은 탓 |
| 2962 등록 후 소환 | 성공(0) ×2 | 효과 없음. 좌표를 고친 뒤에도 같다 |
| 2894 스폰선택 | 성공(0) | 효과 없음 |

2894 는 정상 소환 때 게임이 실제로 보내는 것이라 가장 유력했다.
본문도 맞다(u64 + float3, deser RVA 0x29621E0, 치명적 오류 전송
없음). 그런데도 갓 획득한 까마귀(1000471)는 반응이 없었다. 같은 때
사용자가 획득한 검은꼬리딱새는 정상이었다 - 그쪽은 재적재를 거쳤다.

큰 구조체를 받는 Ack 계열(RefreshMercenaryData 0xB64060,
MercenaryDataList 0xB63A40)은 페이로드를 손으로 만들 수 없어 시도
자체가 불가능하다. 정상 재적재 때 캡처해 두면 언젠가 쓸 수 있겠지만,
그 목록에는 갓 획득한 개체가 안 들어 있으므로 재생해도 소용이 없다.

**남은 답은 하나다: 획득 뒤 지역을 한 번 넘어간다.** 세이브/로드도
같은 효과지만 이동만으로 되므로 플레이를 끊을 필요가 없다.

### 11.1 교훈

실험용 메시지를 계속 두드린 것이 이번 세션에서 가장 비싼 실수였다.
게임을 여러 번 재시작하게 만들었고 한 번은 로그아웃까지 시켰다.
정상 경로와의 차이를 먼저 관측했어야 했다 - 그것을 했을 때(포획 캡처
로그를 읽고, 잘 되는 개체와 안 되는 개체를 비교했을 때) 답이 바로
나왔다.
