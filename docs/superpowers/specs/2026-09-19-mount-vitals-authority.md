## 1. 탈것 체력·스태미나 — 거울과 권위

### 1-1. 신고와 첫 오진

신고: **"A.T.A.G.·드래곤은 체력·스태미나를 바꾸면 바로 복구된다."**

첫 구현(`mountvital.h`, PR #41)은 이렇게 적어 두고 있었다:

> 체력은 약 2초마다 권위 쪽이 덮어쓴다 … 스태미나는 한 번 쓰면 된다.

관찰은 맞았다(체력은 정말 곧 돌아왔고, 스태미나는 서 있는 동안 남았다). 그러나
**해석이 틀렸다.** 로그에는 사용자가 `[적용]` 을 여러 번 눌렀고 `[고정]` 은
한 번도 안 켰다는 것까지 남아 있었지만, 그것은 핵심이 아니었다.

### 1-2. 항목 0x90 을 통째로 떴다

쓰는 칸은 셋(`+0x00` 타입 · `+0x08` 현재 · `+0x18` 최대)뿐이었는데 항목은
0x90바이트다. 나머지를 봤다(A.T.A.G. 체력 항목, 한 틱 전후):

| 칸 | 값(예) | 뜻 |
|---|---|---|
| `+0x00` | 0 | 타입(0 = 체력) |
| `+0x08` | 1,332,800 → 1,333,200 | **현재** |
| `+0x10` | 200 | 회복량(틱당 적용분의 절반) |
| `+0x18` | 2,500,000 | **최대**(유도값) |
| `+0x28` | 250,000 | ? (서명에 쓴다 — §1-4) |
| `+0x38` | 1,597,274 → 1,599,278 | 시계(초당 약 2000) |
| `+0x48` | 444 → 445 | 틱 수 |
| `+0x58` | 2,500,000 | **기준최대** |
| `+0x80` | 200 | **기준회복** |

그리고 스태미나 항목([12])에서 이상한 것이 보였다 — 전에 최대를 560,000 으로
써 둔 뒤였는데:

```
현재 360,000   최대 560,000   기준최대 360,000
```

**현재치가 360,000 에서 안 올라간다.** 엔진이 보는 최대는 `+0x18` 이 아니다.

### 1-3. 결정적 증거 — "직전 값 + 증분"

체력 현재에 2,500,000 을 쓰고 다음 틱을 기다렸다.

```
쓰기 전   1,332,800   틱 444
쓴 직후   2,500,000   틱 444
+0.65s    1,333,200   틱 445      = 1,332,800 + 400
```

엔진은 우리 값에서 400 을 더한 것이 아니라 **자기가 알던 값**에서 더했다.
즉 **우리 쓰기를 아예 못 본다.** 이 한 줄이 "어딘가에 진짜 값을 든 사본이 있다"
를 증명한다.

같은 실험을 최대·회복에 했다(기준값 둘도 함께 써 두고 90초 관찰):

| 칸 | 쓴 값 | 틱 뒤 |
|---|---|---|
| `+0x18` 최대 | 5,000,000 | **2,500,000 으로 되돌아감** |
| `+0x10` 회복 | 20,000 | **200 으로 되돌아감** |
| `+0x58` 기준최대 | 5,000,000 | 그대로 |
| `+0x80` 기준회복 | 20,000 | 그대로 |

되돌아가는 쪽은 갱신마다 덮이고, 남는 쪽은 **아무도 안 읽는다**(남아도 효과가
없다). 이 배열은 통째로 **거울**이다.

### 1-4. 쌍둥이는 값이 아니라 서명으로 찾았다

현재치는 틱마다 흔들려서, 힙 전체를 그 값으로 훑으면 스캔이 끝나기 전에
값이 바뀐다. 그래서 **안 흔들리는 칸 여럿**으로 서명을 만들었다:

```
최대(+0x18) == 2,500,000   ·   회복(+0x10) == 200   ·   +0x28 == 250,000
```

`findu32 2500000` → 10.5GB 에서 203곳 → 각 자리의 `-0x18` 을 배열 머리로 보고
서명 대조:

| 배열 | 현재 | 틱 | 기준최대 | 기준회복 | |
|---|---|---|---|---|---|
| `0x2BCDE4C4800` | 1,414,000 | 647 | 5,000,000 | 20,000 | 우리가 쓰던 것(내 쓰기가 남아 있다) |
| `0x2BDA4029000` | 1,414,000 | 647 | **2,500,000** | **200** | **쌍둥이** |

현재치와 틱까지 한 치도 안 다른데 기준칸만 원래 값이다.

### 1-5. 거슬러 올라가 클래스로 층을 확정했다

`heapptr` 로 쌍둥이 배열을 가리키는 곳을 찾아 올라갔다:

```
배열 0x2BDA4029000  <- root 0x2BDA030ADC0 (+0x58)
root +0x00           -> 0x2BD406B6000  (컴포넌트)
컴포넌트 +0x08       -> 0x2BD880E0400  (액터)
```

각 vtable 을 이름으로 풀었다(`tools/rtti/vtname.py`):

| vtable | 클래스 | |
|---|---|---|
| `0x145585770` | `ClientChildOnlyInGameActor` | 우리가 쓰던 쪽 |
| `0x14558D828` | `ClientStatusActorComponent` | (예전 주석의 "마커") |
| `0x145B1E0C0` | `ServerChildOnlyInGameActor` | 진짜 값을 든 쪽 |
| `0x145B20208` | `ServerStatusActorComponent` | |

**탈것도 플레이어처럼 클라/서버 두 realm 이 있었다.** `player.cpp` 가 "사망
판정은 서버 게이지가 권위" 라고 적어 둔 바로 그것이다. 체력은 회복 틱이 1~1.5초
마다 돌아 곧바로 덮이고, 스태미나는 쓰는 동안만 틱이 돌아 서 있을 땐 남았다가
타면 사라진다 — 사용자가 본 그대로다.

### 1-6. 두 realm 을 잇는 열쇠 — 액터 `+0x60`

클라 액터에서 서버 사본으로 가는 길을 찾느라 여러 번 막혔다:

| 시도 | 결과 |
|---|---|
| 클라 사슬(액터·홀더 0x800, 컴포넌트·root 0x400)에서 서버 주소 찾기 | **없음** |
| 컴포넌트 `+0x20` 의 둘째 root | 게이지 배열이 없다 |
| `ServerActorManager` 버킷 걷기 | 후보 177개 중 `+0x60` 에 핸들을 든 것 **0개** — 서버 액터가 버킷에 없다 |
| `CommonActorManager` | 인스턴스 2개에 액터 **0개** |
| 서버 액터를 가리키는 55곳 주변 0x200 에서 클라 쪽 주소 찾기 | **없음** — 둘을 함께 든 객체가 없다 |

그러다 서버 액터 안에서 클라 핸들 값을 찾아 보니:

```
서버 액터 +0x60 = 0xB0100003
클라 액터 +0x60 = 0xB0100003      <- 같다
```

**두 realm 의 액터가 `+0x60` 에 같은 핸들을 든다.** 이것으로 짝짓는다.

### 1-7. 구현 (`src/game/mountvital.{h,cpp}`)

```
ServerStatusActorComponent 를 RTTI 로 훑는다 (상한 4096)
  후보마다 끝까지 내려가지는 것만 받는다:
    +0x08 액터 · 액터 +0x60 핸들이 0x9010/0xA010/0xB010 네임스페이스
    +0x18 root · root +0x58 배열 · 배열[0].타입 == 0(체력)
  {핸들 -> 컴포넌트} 로 캐시 (핸들로 중복 제거)

쓸 때마다 컴포넌트에서 **다시** 내려간다 - 주소를 들고 다니지 않는다
  컴포넌트 +0x08 액터의 +0x60 이 아직 그 핸들인지 확인(재사용 방지)

쓰기는 거울과 권위 **둘 다** - 거울은 화면이 곧바로 바뀌게 하려고
최대는 두 칸(+0x18 유도 · +0x58 기준)을 함께
```

`vp()`·`mount_handle_plausible()` 가 거르는 이유: RTTI 후보에는 다중 상속
서브객체 주소와 vtable 값을 우연히 담은 메모리가 섞인다.

### 1-8. 게임 확인

```
탈것 권위 사본: ServerStatusActorComponent 후보 352개 중 351개를 짝지었다
  B0100003 A.T.A.G.  거울 1,692,000/2,500,000  권위 0x5F60BFC9000 1,692,000/2,500,000
```

권위에 체력 2,500,000 · 최대 3,000,000(기준 포함) · 기력 최대 500,000 을 쓰고
20초(8틱) 관찰:

| | 결과 |
|---|---|
| 체력 현재 | 2,500,400 → 2,503,200 — **우리 값에서부터** 회복한다 |
| 최대·기준 | 3,000,000 유지 |
| 기력 최대·기준 | 500,000 유지 |
| 거울 | 다음 틱에 따라왔다(2,554,800 / 3,000,000) |

§1-3 과 나란히 보면 차이가 선명하다 — 전에는 엔진 **자기 값**에서 더했고,
이제는 **우리 값**에서 더한다.

### 1-9. "탑승하면 초기화된다" — 기능이 아니라 화면이 틀렸다

배포 뒤 다시 신고가 왔다. 150초 관찰(그 사이 탑승 포함)에서 값은 한 번도
안 흔들렸다:

```
+0.8s 핸들 B0100004
   거울 0x4F91E92F000  체력 12,500,000/12,500,000  기력 1,360,000/1,360,000
   권위 0x4F98A02D800  체력 12,500,000/12,500,000  기력 1,360,000/1,360,000
```

로그가 앞선 실패를 그대로 들고 있었다:

```
09:14:57  … 4칸 - 권위 사본 **없음(거울만, 곧 되돌아간다)**
09:16:18  탈것 권위 사본: 후보 653개 중 647개를 짝지었다   <- 탐색이 이때 끝남
09:16:29  … 8칸 - 권위 사본 포함
```

탐색이 끝나기 **전에** 써서 거울에만 갔다. 서 있는 동안은 틱이 안 돌아 그대로
보였고, 타는 순간 틱이 돌면서 덮였다. **진짜 결함은 그때 화면이 "썼습니다" 라고
한 것이다**(⚠ 는 흐린 글씨였다).

### 1-10. 화면이 지키게 한 것

| | PR |
|---|---|
| 적용 결과를 셋으로: 실패 / **거울만(경고)** / 권위 포함 | #48 |
| 사본이 없으면 `[적용]`·`[고정]` **잠금**. 경고만으로는 부족했다 | #49 |
| `MountAuthPhase{Idle,Waiting,Scanning,Done}` + 경과 초 — "1분쯤" 만으로는 도는 중인지 멈춘 것인지 못 가른다 | #49 |
| **고정을 끄는 것은 안 막는다** — 켠 채 탈것을 새로 부르면 사본이 사라져 끌 길이 없어진다 | #49 |
| 드래곤(타입행 2)·A.T.A.G.(3)만. 걸러서 0이면 전부 내고 그렇다고 적는다 — **드래곤 2 는 아직 눈으로 못 봤다** | #51 |

`take_refresh` 는 CAS 로 `Waiting→Scanning` 을 한 번만 집는다(부탁 하나에 훑기
하나). 훑는 중 부탁은 무시한다. 단계는 전역 하나라 시험을 쪼갰더니 앞 시험이
남긴 단계에 뒤 시험이 걸려 둘이 깨졌다 — 한 바퀴를 한 시험 안에서 돈다.

### 1-11. 기다림 — 훑기가 아니라 차례였다, 그리고 내 오산

창을 연 뒤 81초를 기다린 실측이 있었다. 로그의 누적 창 수로 속도를 셌다:

```
09:11:38 창 19,695 -> 09:13:12 창 36,523   16,828창 / 94초 = 179창/초 × 32MB
```

여기서 "힙 10.5GB → 한 바퀴 **2초**" 라고 결론 냈다. 요청은 분석 통과 **맨 끝**
에서만 집어 가는데 시작 무렵 통과 한 바퀴가 1분을 넘으니, 기다린 것은 훑기가
아니라 **차례**라는 판단이었다(#50: 쉬는 동안 100ms 간격으로 집기 + 월드
진입 때 미리 한 번).

**그 "2초" 는 틀렸다.** 다음 실행에서 로그가 실측을 찍었다:

```
탈것 권위 사본: … 415개를 짝지었다 (67.5초)
```

카운터가 섞인 여러 탐색의 합이었는데 한 탐색의 속도로 읽은 것이다. 안내를
"1분쯤" 으로 되돌렸다(#52). **#50 의 두 변경은 방향이 맞아 그대로 둔다** —
1분짜리라면 미리 해 두는 것이 더 필요하다.

## 2. 액터 매니저 후보 상한 8 → 256, 그리고 그 대가

재부팅 뒤 월드 안인데 `액터 매니저를 못 찾았습니다` 가 떴다. 넉넉히 뽑아 보니:

```
.?AVClientActorManager@pa@@  인스턴스 11개
  0x5ED8EBC0 0x892A8200 0xCE466820 0x16F503EB0 …   가짜 10개
  0x5F5B029A500                                    진짜 (11번째)
```

후보는 **주소 순**이고, vtable 값을 우연히 담은 메모리가 섞인다. 재부팅 전에는
힙이 `0x2BC…` 라 진짜가 앞이었고, `0x5F5…` 로 올라가자 가짜가 앞을 다 차지했다.
검사(`looks_like_actor_manager` + 버킷 걷기)는 제대로 있었는데 **검사할 기회를
못 받았다.** 상한을 256으로(`kActorManagerCandidates`), 시험이 하한 64를
못박는다.

**이것이 근처 액터 목록·휠 슬롯·체력 절이 전부 비어 보이던 이유이기도 했다.**

**대가** — `instances_of_class` 의 상한은 **도달했을 때만** 조기 종료다. 8일
때는 가짜 여덟으로 금방 찼는데, 256이면 실제 11개로는 절대 안 차서 **늘 힙을
끝까지 읽는다.** 모드(같은 프로세스)는 괜찮지만 원격 읽기인 프로브는
`nearby` 한 번이 4분을 넘었다. 24로 낮춰 봤지만 11 < 24 라 **아무 차이가
없었고**(실측) 되돌렸다. 제대로 고치려면 "쓸 만한 것을 찾으면 그만 읽는다"
(판정을 넘기는 형태)가 필요하다.

> **그 뒤(동료 세션, `752f51d`)** — 바로 그 오버로드가 들어갔다:
> `instances_of_class(name, max_accepted, accept)` 는 상한이 **훑은 수가 아니라
> 합격한 수**를 센다. items·roster 는 `(cls, 1, 판정)` 으로 **첫 합격에서 멈추고**,
> clan 은 합격 16 이다. **actors 만 옛 오버로드 256 그대로**다 — "액터가 가장
> 많은 매니저" 를 골라야 해서 첫 합격에 멈출 수 없다. 판정에 최소 액터 수
> (`kMinPlausibleActors`)를 넣으면 타이틀 화면의 빈 매니저를 거르면서 첫
> 합격에 멈출 수 있어 보이지만, 아직 시험하지 않았다.

## 5. 수배 탐색에 끝을 달았다

로그 줄의 3분의 1이 이 경고였다:

```
수배 컴포넌트를 못 찾았다 - 후보 8개, … 끝내 못 읽음 19,305,328KB
```

15초 간격 제한은 **있었다.** 그런데 한 번 훑는 데 ~45초 — *간격 < 한 번
비용* 이면 쉬는 것이 아니다. 월드 안에서 3회 해 보고 멈추고, 플레이어 창에

순간에는 아직 객체가 없을 수 있다(그래서 애초에 재시도를 넣었다).

> **그 뒤** — 동료 세션이 "값이 realm 두 벌이었다 - 클라만 쓰고 있었다"
> (#70)를 찾고 두 realm 쓰기·지우기·구역 이름까지 게임 확인했다(#71~#74).
> 이 세션이 "아직 한 번도 확인 안 됨" 으로 남긴 수배는 거기서 풀렸다.

## 7. 보스룸 — 이 세션의 몫과 그 뒤

### 7-1. 증상

A.T.A.G. 가 보스룸에서 호출이 안 되고, 타고 있으면 내려진다. **문구가 없다.**

### 7-2. 이 세션이 실측으로 못박은 것

| 관찰 | 어떻게 쟀나 | 배제되는 것 |
|---|---|---|
| 문구가 없다 | 화면 | `failmessageinfo` 조건층 전부 |
| 액터 메모리가 풀린다 | 값을 쓴 액터 주소를 나중에 읽으니 `+0x60` 이 float 1.0 | "내리기" 가 아니라 걷어내기(또는 재생성) |
| 휠은 열리고 선택도 된다 | 사용자에게 물음 | UI 조건층 |
| 드래곤·말·동물까지 **전부** | 사용자에게 물음 | 탈것 **종류별** 조건 전부 |
| 3번 눌러 메시지 **0건** | 로그 캡처 세기 — 앞선 실행엔 `[부르기/용병]`·`[부르기/프레임]` 가 찍혔다 | 서버 거부 |
| 스테이지 전환이 플레이어 액터를 재생성 | 나온 뒤 `[actor+0x68]` 이 쓰레기 | 주소 기반 안팎 비교 |
| 휠·예약슬롯 상태 안팎 **동일** | `probe wheel` 을 안/밖에서 — 28항목 필드 한 칸도 안 다름 | 예약 슬롯 층 |

> 처음에 "캡처 0건 = 클라가 안 보냈다" 고 단정했는데, `[부르기/용병]` 은
> `TrocTrCallVehicleMercenaryAck` 의 **받는 쪽** 후크라 엄밀히는 "오가지
> 않았다" 까지다. Req 쪽 후크(`슬롯사용/요청`)도 안 뜬 것으로 보내지 않았다는
> 쪽에 무게를 뒀다.

### 7-3. 반증된 후보 둘

둘 다 패치가 걸린 것을 확인한 뒤 눌러 봤다. **자리가 아니라 조건이 틀렸다.**

| 후보 | 판정 함수 | 패치 | 결과 |
|---|---|---|---|
| `AICondition_BlockByExclusiveStage` | RVA 0x22EA800 | `xor bl,1`(80 F3 01) → `mov bl,1;nop`(B3 01 90) @0x22EA84A, 창 `B6 D8 80 F3 01 48 8D 05` | 로그 `켬: 0x1422EA84A` · **무반응** |
| `AICondition_CheckIsRideLimit` | RVA 0x22E6B10 | `jne`(75 16) → `jmp`(EB 12) @0x22E6B4B — 프로브 `poke` 로 즉시 A/B | **무반응** · 원복 `poke 0x1422E6B4B 75 16` |

첫째는 토글로 배포까지 했다가(#53) 걷어냈다(#54). 아무 일도 안 하면서 코드만
건드리는 토글은 남기지 않는다.

**둘 다 이름으로 골랐다.** 화면을 물었으면(§7-2 의 두 답) 처음부터 안 갔을
길이다 — `TROUBLESHOOTING.md` §4.34.

### 7-4. 막힌 길

- **메시지 클래스 → 보내는 쪽**: `TrocTrUseItemReserveSlotReq`·
  `TrocTrFrameEventCallMercenaryReq` 의 vtable 참조는 각각 67바이트 **팩토리
  썽크** 한 곳이고, 그 썽크를 `call` 하는 자리가 **0곳**(`tools/rtti/callers.py`)
  — 표에 등록해 간접 호출한다.
- `actionrestrictionorderinfo`(2.5KB) · `stageinfo`(28MB): 탈것 관련 없음.
- `ServerActorManager` / `CommonActorManager`: §1-6 과 같이 쓸모없음.

### 7-5. 그 뒤 — 동료 세션이 이어받았다 (#80~#86)

이 세션은 남은 자리를 **"휠에서 골랐다" 와 "요청을 만든다" 사이**로 남기고
"프로브로는 못 쫓으니 모드 안에 진단을 넣어라" 고 적었다. 동료가 그대로 했다
(`src/game/callcheck.{h,cpp}`). 그쪽 기록(#86 커밋 메시지)의 요지:

- 벌판(대조군): 검증기 진입 1·통과, 휠 요청 **2166** 나감, 서버 응답 옴
- 보스룸: **셋 다 없다** — 차단이 검증기 **위**다
- 휠 UI `UIGamePlayControlRoot_ContentSlotMenu::[18]` (RVA 0x10BE8B0) 에서:
  `[this+0x1C8]==-1` 이면 나감 / **`0x64F490`(주 플레이어) 실패면 문구 없이 나감** /
  `[this+0x158]==2`(탈것)면 앞단 `0x9E0FC0` → 검증기 → 통과 시 `0xBE31F0` 이 2166 을 만든다

> **바로잡음 (2026-09-21, callcheck 세션) — 위 요지의 두 전제가 같은 날 둘 다 틀렸다.**
>
> 1. **`ContentSlotMenu::[18]` 은 탈것 휠의 처리기가 아니었다.** 호출 그래프와 클래스
>    이름으로 짐작했는데, 벌판 대조군(탈것 정상 호출·검증기 통과·2166 송신)에서 그
>    처리기는 **한 번도 안 불렸다.** 앞단 `0x9E0FC0` 의 남은 호출자는
>    `UIGamePlayControlRootPet` 아래 `0x10A0800` 이다.
> 2. **관문①(주 플레이어 `+0x5E` 의 `0x10`)은 보스룸 내내 막는 원인이 아니다.**
>    `+0x5E` 는 **한 방향으로만 나아가는 수명 단계**다 — `0x1436AA0..0x1436AD0` 의
>    전이 함수가 `1→2→4→8→0x10` 을 앞 단계에서만 넘긴다. 이 문서 §7-2 의 "스테이지
>    전환이 액터를 재생성" 대로 보스룸에 들어가면 새 액터가 생기는데, 그 액터는 `8` 로
>    시작해 **약 27초 뒤 `0x10`(활성)** 이 된다(밖에서 `ReadProcessMemory` 로 읽기만
>    해서 실측). 관문①은 그 27초만 막는다.
>
> 새로 나온 것: 탈것 요청 2166 은 `ClientFrameEventProcessor::[5]`(`0x4EDC40`)가
> 만드는 `ClientFrameEventCallMercenary` 가 보낸다 — "부르기" **동작의 프레임
> 이벤트**다. 보스룸 차단이 **동작층**(그 동작을 시작하지 못함)에 있을 수 있다.
> 확정은 아니다.

이후 진행은 `callcheck.h` 와 동료 문서를 볼 것.
