## 0. 결론 먼저

1. **소켓 지급은 죽지 않았다.** `specs/2026-09-04-game-update-break.md` 의
   "업데이트가 CreateItemFromTrItemValue 의 소켓 전달을 없앴다" 는 판정은
   **분기 하나만 보고 내린 오독**이다. 생성 함수 `0x2A70000` 은 갈래가
   **둘**이고, 그때 본 것은 **겹치는(non-equip) 아이템 갈래** 하나였다.
   장비 갈래는 지금도 소켓을 아이템표 상한까지 받는다.
2. **소켓 "락" 은 별도 플래그도 서버 토큰도 아니다.** 인벤토리 레코드의
   `+0x70`(u8, 열린 칸 수)과 소켓 벡터 각 칸의 `byte[4]`(0xFF=잠김,
   k=열림) **딱 두 곳**이다. 게임 자신의 지급 코드가 그 둘을 그대로 쓴다.
3. **슬롯 배열은 언제나 5칸 고정**이다(`+0x68`=5, `+0x6C`=5, 32바이트 풀
   블록). **5가 엔진 설계 상한**이고 그 위로는 재할당 없이는 못 간다.
4. **아이템별 상한은 아이템표 `ItemInfo+0x238`(max_sockets)** 이고, 게임이
   지급 때 `max_sockets >= socket_count` 로 검사한다. 이 값은 힙의 런타임
   표라 쓰기가 가능하다(= "슬롯 갯수 수정"의 유일한 레버).

즉 **지급 시 락 우회 = `request_give` 의 `safe.socket_count = 0;` 한 줄을
걷어내고 (장비 && ≤ max_sockets && ≤5) 로 자르는 것**이다. 나머지 배선
(`fill_item_value`, `GiveSocket`, 스태시 클램프)은 이미 다 있다.

## 2. 측정: 소켓 레코드 실제 레이아웃 (라이브 읽기)

### 2.1 인벤토리 레코드 (stride 0xC8)

`invlist raw` 로 잡은 레코드 21건의 `+0x60..+0x73` 을 전부 떴다. 예외 없이
같은 모양이다.

| 오프셋 | 크기 | 뜻 | 실측 |
|---|---|---|---|
| `+0x60` | u64 | 소켓 벡터 포인터 | 전부 `0x427CE05xxxx` 한 풀, **32바이트 정렬** |
| `+0x68` | u32 | 벡터 size | **항상 5** |
| `+0x6C` | u32 | 벡터 capacity | **항상 5** |
| `+0x70` | u8 | **열린 소켓 수** | 아이템·인스턴스마다 다름 (0~5) |

> ⚠️ `src/game/inventory.cpp` 의 `kRecSocketCount = 0x68` 은 **이름이 틀렸다.**
> `+0x68` 은 벡터 크기(늘 5)지 "소켓 칸 수"가 아니다. 실제 소켓 칸 수는
> `+0x70`(u8)이다. probe 의 `invlist raw` 는 `+0x70` 을 찍고 있어 맞다.
> `grant.h` 의 "`+0x5E` → 레코드 `+0x70`" 주석이 옳다.

### 2.2 소켓 칸 (6바이트 × 5, 30바이트가 32바이트 풀 블록 안에)

| 바이트 | 뜻 | 실측 |
|---|---|---|
| `[0..1]` u16 | 보석 순번 | 비면 `0xFFFF` |
| `[2..3]` u16 | 채움 표시 | 보석 있으면 `0xFFFF`, 비면 `0x0000` |
| `[4]` u8 | **칸 번호 = 열림 / `0xFF` = 잠김** | |
| `[5]` u8 | 미상 — **실행마다 바뀌는 세션 값** | 잠긴 칸은 풀 쓰레기값 |

`[5]` 가 잠긴 칸에서 제각각인 이유가 코드에 그대로 있다: 게임의 "전부 잠금"
초기화가 `[0..3]` 4바이트와 `[4]` 1바이트만 쓰고 `[5]` 는 **안 건드린다**.
`[5]` 는 오직 소켓을 열 때 복사된다.

> ⚠️ **2026-09-08 정정.** 처음에 "열린 칸은 전부 `0x04`" 라고 적었는데,
> 한 판만 보고 내린 결론이었다. **고정 상수가 아니다** - 한 판 안에서는
> 열린 칸이 전부 같은 값인데 판이 바뀌면 달라진다.
>
> | 실행 | PID | 열린 칸 `[5]` |
> |---|---|---|
> | 1 | 30644 | `0x04` (34칸 전부) |
> | 2 | 46132 | `0x05` (37칸 전부) |
> | 3 | 45216 | `0x03` (37칸 전부) |
> | 4 | 45552 | `0x02` (34칸 전부) |
> | 5 | 32604 | `0x02` (34칸 전부) |
>
> 4·5 가 같으므로 "매 실행 반드시 바뀐다" 까지는 말할 수 없다. 무엇이
> 정하는지 모른다. 확실한 것은 **한 판 안에서 균일하고, 판마다 달라질 수
> 있으며, 우리가 보낸 값은 남지 않는다**는 것이다 - 실행 2(판 값 `0x05`)에
> `0x04` 를 실어 지급했더니 정상으로 들어왔고, 저장·재시작한 실행 3 에서
> 그 아이템의 다섯 칸이 전부 `0x03` 으로 덮여 있었다. 게임이 로드할 때 다시
> 매긴다. 즉 이 바이트는 **맞출 필요가 없다**(예전에 쓰던 `0xFF` 만은
> 라이브 어디에도 없던 값이라 피한다).

실측 예 (순번 6776 혹한의 절망, 5칸 전부 열림·전부 보석):

```
F6 0C FF FF 00 04 | FB 0C FF FF 01 04 | F3 0C FF FF 02 04 |
4A 0D FF FF 03 04 | 93 0C FF FF 04 04
```

실측 예 (순번 6387 데메니스 친위대 방패, 표 상한 2 · 2칸 열림):

```
0D 0D FF FF 00 04 | 0E 0D FF FF 01 04 |
FF FF 00 00 FF 00 | FF FF 00 00 FF 00 | FF FF 00 00 FF DE   <- 잠김 3칸
```

### 2.3 "락" 은 인스턴스별 상태다 — 저장에서 살아 돌아온다

같은 아이템의 인스턴스끼리 열린 칸 수가 다르다. 이 값들은 **세이브에서
읽어 온 것**이므로 `+0x70` 과 `byte[4]` 는 **저장·복원되는 인스턴스 상태**다.

| 아이템 | 인스턴스 | 열림 / 표 상한 |
|---|---|---|
| 에세리온 활 (6529) | 1000423 | **5** / 5 |
| 에세리온 활 (6529) | 1000424 | **0** / 5 |
| 에세리온 활 (6529) | 1000425 | **5** / 5 |
| 타리브 천 신발 (5363) | 1000336 | **0** / 2 |
| 타리브 천 신발 (5363) | 1000337 | **2** / 2 |
| 신목의 가시 (6349) | 1000430 | **1** / 3 |

현재 세이브에 **잠긴 칸이 남은 아이템 16건**이 있다(실험 대상으로 쓸 수
있다). `0열림/상한 N` 이 15건, `1열림/상한 3` 이 1건(신목의 가시).

**그리고 열린 칸이 0인 아이템도 `+0x60` 벡터는 이미 5칸 할당돼 있다.**
→ 제자리 언락에 **힙 할당이 전혀 필요 없다.**

## 3. 정적 분석: 지급 경로를 다시 읽었다

### 3.1 `0x2A70000` (생성 함수)은 갈래가 둘이다

```
0x2A7021F  call 0x2358A70            ; isStackableLike(ItemInfo, ctxFlag)
0x2A70224  test al, al
0x2A70226  je   0x2A70335            ; al==0(=장비) -> 소켓 허용 갈래
;--- al!=0 : 겹치는 아이템 갈래 ------------------------------------
0x2A7022C  cmp  byte [r14+0x5E], dil ; dil=0
0x2A70230  jbe  0x2A7028A            ; 소켓수==0 이면 정상
0x2A70232  mov  eax,[rip+..]         ; >0 이면 오류코드 반환   <= 2026-09-04 에 본 자리
0x2A70285  jmp  epilogue
0x2A7028A  ... call 0x234F930 ...    ; 레코드 1개
;--- al==0 : 장비 갈래 --------------------------------------------
0x2A70335  lea rcx,[rbp+0x170]; call 0x3847D0   ; ItemInfo
0x2A70341  movzx ecx, byte [r14+0x5E]           ; 소켓수
0x2A70346  cmp  dword [rax+0x238], ecx          ; max_sockets >= 소켓수 ?
0x2A7034C  jae  0x2A703A6                       ; 통과
0x2A7034E  mov  eax,[rip+..]                    ; 넘치면 오류
0x2A703A6  ... 개수만큼 반복: call 0x234F930 ... ; 개당 레코드 1개
```

판별자 `0x2358A70 → 0xF090BC0` 전문:

```
if (ctxFlag == 0)            return ItemInfo->_maxStackCount(+0x18) > 1;
if (_maxStackCount != 1)     return _maxStackCount > 1;
// _maxStackCount == 1 인 경우
if (ItemInfo[+0x428] != <세션값 +0xA2>) return 0;
return ItemInfo->_equipTypeInfo(+0x42) == 0xFFFF;   // 0xFFFF = 장비 아님
```

→ **장비(`_equipTypeInfo != 0xFFFF`, maxStack==1)는 언제나 `al==0`**, 즉
소켓 허용 갈래를 탄다. 소켓을 거부하는 갈래는 **애초에 소켓이 없는
아이템 전용**이다(겹치는 아이템에 소켓을 실으면 거부 — 당연한 규칙).

### 3.2 `0x234F930` 이 소켓을 **지금도** 복사한다

`rcx=r14=`레코드, `rdx=r12=`TrItemValue (프롤로그에서 확인).

```
0x234FB9D  movzx ebx, byte [r12+0x5E]      ; 요청한 소켓수
0x234FBA3  mov   byte [r14+0x70], 0
0x234FBAA  mov   dword [r14+0x68], 0
0x234FBAE  mov   edx, 5
0x234FBB3  lea   rcx, [r14+0x60]
0x234FBB7  call  0xBA1D60                  ; 벡터를 5칸으로 확보
0x234FBDD  mov   dword [rax+rcx*2], 0xFFFF ; 남는 칸 [0..3] = FF FF 00 00
0x234FBE4  mov   byte  [rax+rcx*2+4], 0xFF ;         [4]    = 잠김
0x234FBFA  mov   dword [r14+0x68], 5       ; size = 5
0x234FC02  mov   byte  [r14+0x70], bl      ; **열린 칸 수 = 요청한 소켓수**
; k = 0..4 루프 (r8b=k, r9=k*6)
0x234FC10  cmp   bl, r8b ; ja  ...         ; k < 열린칸수 일 때만
0x234FC31  mov   ecx, [r9+r12+0x40]        ; TrItemValue+0x40+k*6 의 [0..3]
0x234FC36  movzx edx, word [r9+r12+0x44]   ;                       [4..5]
0x234FC40  mov   dword [r9+rax], ecx
0x234FC44  mov   word  [r9+rax+4], dx
0x234FC4E  mov   byte  [r9+rax+4], r8b     ; **[4] = k → 열림**
```

**즉 게임의 지급 코드가 하는 "소켓 열기" 는 정확히 이 둘이다:
`레코드+0x70 = N` 과 `칸[k][4] = k`.** 검증도, 체크섬도, 서버 토큰도 없다.

### 3.3 옛 판정이 왜 틀렸나

2026-09-04 기록은 "`0x234F930` 이 struct 에서 읽는 오프셋을 전부 뽑아 보니
소켓 배열(+0x40~0x5D)을 어디서도 안 읽는다" 였다. 실제로는 읽는다 —
`mov ecx, [r9+r12+0x40]` 처럼 **레지스터 인덱스**라서 상수 변위만 훑는
방식으로는 안 잡힌다(`tools/rtti/fields.py` 가 문서에 적어 둔 바로 그
실패 모드다). 그리고 `0x2A70000` 은 `je 0x2A70335` 를 안 따라가고
fall-through 갈래만 읽었다.

## 4. 지급 시 락 우회 — 두 갈래

### A. 지급 경로 복원 (권장, 한 줄 + 클램프)

`src/game/grant.cpp` `request_give` 의

```cpp
GiveExtras safe = extras;
safe.socket_count = 0;      // <- 이것만 걷어낸다
```

를 걷어내고 **부르는 쪽 클램프**를 강제한다. 게임이 조용히 거절하면 큐가
멈추므로 클램프는 필수다.

- 겹치는 아이템(`max_sockets == 0`)이면 **0**. (스태시 경로는 이미 그렇게 자른다.)
- 장비면 `min(요청, ItemCatalogEntry::max_sockets, kGiveMaxSockets=5)`.
- 각 칸 6바이트: `[0..1]` 보석 순번(빈 칸은 `0xFFFF`), `[2..3]` `0xFFFF`(보석
  있을 때)/`0x0000`(빈 칸), `[4]` 무시(게임이 k 로 덮어씀), **`[5]` = `0x04`**.

> ⚠️ `game::make_socket_bytes` 는 예전에 `out[2]=out[3]=0xFF`,
> **`out[5]=0xFF`** 를 썼다. `[2..3]` 은 채움 표시라 빈 칸이면 `0x0000`
> 이어야 하고, `[5]` 는 게임이 로드할 때 다시 매기지만 라이브에 없던
> `0xFF` 는 피한다. 지금은 `0x04` 를 보낸다(2.2 절 정정 참조).
> 빈 칸(락만 풀고 보석은 안 넣기)은 `FF FF 00 00 xx 04` 다.

효과: **지급 즉시 N칸이 열린 채로 나온다.** 보석까지 같이 실을 수 있다.
게임 자신의 코드가 쓰므로 저장 생존은 정상 획득과 동일하다.

### B. 제자리 언락 (이미 가진 아이템)

지급을 안 거치고 기존 아이템의 잠긴 칸을 연다. 레코드당 쓰기 2종:

```
레코드+0x70 = N                      (u8)
칸[k][4] = k,  칸[k][5] = 0x04       (k = 기존열림 .. N-1)
칸[k][0..3] = FF FF 00 00            (빈 칸으로 열 때)
```

- 힙 할당 불필요(벡터는 늘 5칸 확보돼 있다 — 2.3 실측).
- 인벤토리 레코드는 authoritative 라 **단일 쓰기로 저장 생존**한다는 것이
  이미 실측돼 있다(`inventory-inplace-write`, 보석 박기 기준).
  `+0x70` 도 같은 구조체의 이웃 칸이고, 2.3 의 인스턴스별 차이가 **세이브가
  이 값을 실어 나른다**는 증거다. 다만 **언락 자체의 저장 생존은 아직 미실측**.
- 착용 중인 장비는 equip 경로(both-realms + 재장착)가 따로 필요하다.

**A 와 B 는 배타적이지 않다.** A 는 새로 주는 것, B 는 이미 가진 것.

## 5. 슬롯 갯수 수정

| 무엇 | 어디 | 바꿀 수 있나 |
|---|---|---|
| 아이템별 소켓 상한 | 아이템표 `ItemInfo+0x238` (u32) | **가능** — 힙의 런타임 표. `cmp [rax+0x238], ecx; jae` 한 곳이 관문 |
| 인스턴스 열린 칸 수 | 레코드 `+0x70` (u8) | 가능 (4절) |
| 물리 슬롯 배열 | `+0x60` 5칸 / `+0x68`=5 / `+0x6C`=5 | **불가 — 5가 천장** |

`0x234F930` 은 벡터를 `5` 로 확보하고(`mov edx,5`) 루프도 `cmp r8b, 5` 로
끊는다. 풀 블록도 32바이트라 6칸(36바이트)이 안 들어간다. 따라서:

- **표 상한이 5 미만인 장비를 5칸으로 만드는 것: 가능.** 레코드(열린 칸·
  박힌 보석)는 세이브에 남고 **스탯 계산도 레코드를 본다** - 표 상한을
  안 본다(9절 효과 확인). 표는 실행할 때마다 exe 에서 다시 읽히므로
  올리기는 매 세션 다시 해야 하지만, 그것이 정하는 것은 **툴팁 소켓
  목록뿐**이다. 모드를 빼도 효과는 그대로다.
- **6칸 이상: 못 한다.** 배열을 우리가 새로 잡아 `+0x60` 을 갈아끼우면
  게임 할당자가 나중에 그 포인터를 해제하다 죽는다. 시도 가치 없음.

`+0x238` 은 **모든 인스턴스가 공유하는 카탈로그 값**이다. 되돌리려면 원래
값을 기억해 두고 세션 종료 시 복원해야 한다(세이브에는 안 들어간다 —
표는 실행할 때마다 다시 읽힌다).

> ⚠️ 모드의 아이템 카탈로그는 이름이 풀린 뒤 **다시 만들지 않는다**
> (`discover_items` 가 `g_named` 로 조기 반환). 표를 poke 해도 모드의
> `socket_room_for` 는 옛 값을 본다. 표 상한 올리기를 기능으로 만들려면
> 카탈로그 재생성 경로가 같이 필요하다.

## 9. 실험 1·3 결과 — 제자리 언락은 되고, 표 상한은 표시·사용을 정한다

한 번에 잰 실측(2026-09-08). 대상은 **글렌모어 한손검**(키 200021, 순번
6458, inst 1000479, 표 상한 3), **원래 열린 칸 0개**(다섯 칸 전부 `FF`).

### 한 것

```
세션 A (PID 45552)
  poke ItemInfo+0x238   3 -> 5        아이템표 상한
  poke 벡터             FF FF 00 00 0k 02  (k=0..4)   다섯 칸 열기
  poke 레코드+0x70      0 -> 5
  -> 게임이 되쓰지 않음. 툴팁 5칸.
저장 -> 종료 -> 재시작
세션 B (PID 32604)
  ItemInfo+0x238 = 3     (poke 사라짐 - 표는 매 실행 exe 에서 다시 읽힌다)
  레코드+0x70    = 5     ← 살아남았다
  벡터           = 00 02 | 01 02 | 02 02 | 03 02 | 04 02   ← 다섯 칸 열림
  툴팁           = 3칸
  poke ItemInfo+0x238  3 -> 5  (레코드는 안 건드림)
  -> 툴팁 5칸
```

### 결론 둘

**① 제자리 언락은 저장을 넘는다 (실험 1 확정).** 열린 칸 0개짜리 장비를
레코드 쓰기만으로 5칸으로 만들었고, 저장·종료·재시작을 넘어 그대로 남았다.
**"소켓 언락은 원리적 불가(게임/NPC 전용)" 라는 프로젝트의 기존 결론은
폐기한다.** 이미 가진 장비도 열 수 있다.

**② 표 상한은 세이브를 강제하지 않는다. 표시·사용 칸 수를 정한다.**
표 상한이 3인 채로 로드해도 레코드는 5칸을 그대로 들고 있었다 - 세이브에
강제가 없다. 그런데 툴팁은 3칸이었고, **레코드를 그대로 둔 채 표 상한만
5로 올리자 툴팁이 5칸이 됐다.** 즉 화면(그리고 아마 사용 가능 칸)을
정하는 것은 아이템표다.

> 처음에 툴팁만 보고 "5칸이 3으로 깎였다" 고 적었는데 틀렸다. 레코드를
> 읽었어야 했다. 화면과 데이터를 갈라 보지 않으면 이렇게 뒤집힌다.

### 그래서 "슬롯 갯수 수정" 은

| 목표 | 되나 | 방법 |
|---|---|---|
| 표 상한 **이하**로 칸 열기 | ✅ | 지급(A) 또는 제자리 쓰기(B). 저장 생존 |
| 표 상한을 **넘겨** 데이터에 심기 | ✅ | 레코드에 쓰면 그대로 남는다 |
| 넘긴 칸을 **화면·게임에서 쓰기** | ⚠️ 모드 상주 필요 | 세션마다 `ItemInfo+0x238` 을 올려야 한다 |
| 6칸 이상 | ❌ | 벡터가 5칸 고정(3.2 절) |

표는 매 실행 exe 에서 다시 읽히므로 상한 올리기는 **세이브에 안 남는다.**
모드가 매 세션 올려 주면 되지만 **모드를 빼면 그 아이템은 다시 표 상한까지만
보인다**(데이터는 남아 있다). 기능으로 만들 때 이 단점을 반드시 알린다.

### 효과 확인 — 늘어난 칸은 실제로 계산된다 (2026-09-08 실측)

같은 검(표 상한 3)의 다섯 칸에 보석을 박았다: 치명타 확률 **3** 짜리 셋,
**1** 짜리 둘.

| | 툴팁 소켓 목록 | 치명타 확률 |
|---|---|---|
| 상한 올리기 **전**(표=3) | **3줄만** (3짜리 셋) | **Lv.11** |
| 상한 올리기 **후**(표=5) | **5줄 전부** | Lv.11 |

`3+3+3+1+1 = 11`. **상한을 올리기 전에도 스탯은 이미 다섯 칸을 전부
더하고 있었다.** 즉 층이 셋으로 갈린다:

| 층 | 무엇이 정하나 |
|---|---|
| 데이터(열린 칸·박힌 보석) | 레코드 `+0x70`·벡터 — 세이브에 남는다 |
| **스탯 계산** | **레코드** — 표 상한을 안 본다 |
| 툴팁 소켓 목록 | 아이템표 `+0x238` — **여기만 잘린다** |

그래서 5절 표의 "넘긴 칸을 쓰려면 모드 상주 필요" 는 **표시에 한한 이야기**다.
모드를 빼도 효과는 그대로고 툴팁 목록만 원래 상한까지 보인다.

### 아직 안 잰 것

- 6칸 이상은 벡터가 5칸이라 애초에 불가(3.2 절).
- 상한을 올린 채 저장하고 **모드 없이** 오래 굴렸을 때 게임이 언젠가
  칸 수를 정리하는지. 한 번의 저장·로드로는 아무 일도 없었다.

## 10. 부위별 소켓 수 (2026-09-08 실측 + 구현)

### 부위는 (분류, 장비타입) 쌍이다

`ItemInfo+0xA3 _itemType`(분류)로 대부분 갈리는데 **한 분류에 장비타입이
여럿 섞이는 자리가 있다.** 그래서 `+0x42 _equipTypeInfo` 와 쌍으로 묶는다.
이 빌드에서 장비 묶음은 **92개**다(`probe items cats`).

### 소켓이 없는 부위에도 달 수 있다

반지 37종 중 **1종(번개의 반지)은 원래 상한 2**다. 악세서리 소켓은 게임에
이미 있는 개념이고 대부분이 0으로 꺼져 있을 뿐이다.

실측으로 확인했다. **마녀의 반지**(키 8506, 분류 49, 장비타입 10, 상한 0):

```
반지·귀걸이·목걸이·망토 전부 +0x60 유효, +0x68=5, +0x6C=5, +0x70=0
  poke ItemInfo+0x238  0 -> 2
  poke 벡터            FF FF 00 00 0k 05  (k=0,1)
  poke 레코드+0x70     0 -> 2
  -> 툴팁에 빈 소켓 2칸
```

즉 **모든 장비는 소켓 벡터를 이미 5칸 들고 있고**, 막고 있는 것은 아이템표의
`max_sockets = 0` 하나뿐이다.

### 구현

- `socket_parts()` 가 카탈로그를 (분류, 장비타입)으로 묶어 낸다 - 종수,
  소켓 있는 종수, 원래 상한, 보기 이름.
- `socket_cap_apply(reader, rules)` 가 부위별 규칙으로 표를 쓴다. `want == 0`
  인 부위는 안 건드린다. 낮추지 않는다.
- `socket_cap_target` 에서 **"원래 소켓이 있어야 한다" 조건을 뺐다.** 어느
  부위를 건드릴지는 규칙이 정할 일이지 여기서 막을 일이 아니다.
- 설정 `socket_cap_parts = 3:5=5,24:4=5` (분류:장비타입=칸수). 아이템표는
  매 실행 다시 읽히므로 이 설정으로 세션마다 다시 건다.
- UI: 인벤토리 패널 "소켓 상한 (실험)" 의 부위 표. 기본은 **소켓이 원래
  있는 부위만** 보여 준다(92줄은 너무 많다). 체크를 풀면 전체가 나온다.

### 게임 검증 (2026-09-08 저녁)

부위 92개를 전부 5칸으로 설정해 저장하고 재시작:

```
[21:03:56] 설정: ... socket_cap=0
[21:04:23] 아이템 표 6813개
[21:04:25] 소켓 상한: 부위 규칙 92개로 아이템 2965개를 올렸다 (대상 아님 3848)
```

버튼을 안 눌러도 **저절로** 걸렸다(주입 29초 뒤). 2965 + 3848 = 6813(표 전체).
소켓이 원래 있는 부위만 걸던 때(614개)에서 크게 는 것은 망토·귀걸이·
목걸이·반지·탈것장비까지 들어갔기 때문이다. ERROR 0건, 크래시 없음.

제자리 언락도 셋 다 정상 동작을 확인했다:
- 장비 소켓 창의 칸별 `[열기]` 와 `[전부 소켓 5칸]`(both-realms)
- 인벤토리 창 행별 `[소켓 5칸]`(단일 쓰기)
- 지급 창의 칸별 보석 목록 선택
