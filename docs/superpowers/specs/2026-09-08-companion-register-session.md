# 세션 정리 — 종을 골라 동반자로 (2026-09-08)

> **정리 (2026-09-21) — 📜 기록.** 소환 치트 금지(실측)와 등록 경로 구조는 유효하다
> (`TROUBLESHOOTING.md` §1.9). §4 C안(`ItemUseData_SummonCharacterWithCatch` 로 종
> 고르기)은 닫힌 길이다 — 그 객체에 캐릭터 키가 없다(`TROUBLESHOOTING.md` §9). 목표는
> 종 교체로 풀렸다(`STATUS.md` §1.10).

목표: **오버레이에서 고른 종을 탈것·특수탈것·반려동물로 등록하고 실제로
데리고/타고 다니기.** 길들일 수 있는 종과 아닌 종은 구분해서.

아직 안 된다. 다만 오늘 **금지선 하나를 실측으로 확정**했고, 등록 경로의
구조를 상당 부분 열었다.

## 1. 소환 치트는 금지가 유효하다 (재확인, 실측)

`2026-09-05-companion-summon-acquire-design.md` 가 `SpawnCharacterCheatReq`
를 "NPC 증발·무한로딩" 으로 금지해 두었고 `roster_panel.cpp` 에도 같은
경고가 있었다. **나는 그것을 읽지 않고 하루 종일 되살려 썼다.**

검증(2026-09-08):

| 증상 | 결과 |
|---|---|
| NPC 증발 | **없음.** 대조군 NPC 15·15·18 → 소환 10회 뒤 10→14, Object 170→174 |
| 무한로딩 | **재현.** 다섯 번째 구동이 반환하지 않았고 141초 뒤에도 게임 정지 |

처리기 주소가 바뀌어도(2510/`0x278B860` → 실측 2988/`0x2B6E530`) 결론은
같다. **몇 번은 정상으로 돈다** - 그래서 "된다"고 오판하기 쉽다. 실제로
고양이·양·염소를 등록하는 데까지 성공했지만 반복하면 멈춘다. 그날 세 번
멈췄고 두 번은 게임이 팅겼다.

구동·명령·훅·UI 를 전부 걷어냈다. `grant.h` 에 실측 근거와 함께 경고를
남겼다. **되살리지 말 것.**

## 2. 등록 경로의 구조

동반자를 명부에 올리는 길은 둘이고, 둘 다 앞단이 다를 뿐 검사는 같다.

```
2338 HireMercenaryToTarget   액터 핸들 → 액터 → 행번호 ┐
2454 HireMercenaryFromInv    슬롯 → 아이템 → 행번호   ┘→ 검사 → 각자 등록
```

### 2.1 검사 함수 (0x2097BC0, 본체 0xE13BA40)

```
u32* f(용병단, u32* 결과, u16 캐릭터표 행번호, 1, 1)
  0 이면 통과. 그 외는 거부 코드.
```

**인자는 캐릭터 키가 아니라 행 번호다.** 실측:

```
키 30024 (고양이)  -> 0x0D982DB0 거부
행 6511  (같은 놈) -> 0x00000000 통과
행 3551  (양)      -> 0x00000000 통과
```

본체는 행으로 레코드를 찾아 `+0xBE`(`_mercenaryInfo`)를 읽고, 용병단의
타입별 한도 목록(`+0xF8` 배열 · `+0x100` 개수)과 대조한다.

**통과해도 명부에는 아무것도 안 들어간다 - 검사이기 때문이다.** 나는 이
함수를 "등록의 실체"로 단정해 커밋까지 했고, 사용자가 목록을 확인해 주고서야
틀린 것이 드러났다.

`hirespecies <행번호>` 명령으로 게임에게 자격을 물을 수 있다. 목록 표시에
쓸 수 있다.

### 2.2 진짜 등록은 경로마다 다르다

검사 이후 공통 호출은 CRT 도우미 둘뿐이다(창을 6000바이트로 넓혀 확인).

- 2338 → `0x26B4FD0`. 첫 인자가 스택 구조체가 아니라 **엔진이 만들어 둔
  컨텍스트 객체**다. 그 객체부터 파야 부를 수 있다.
- 2454 → 다른 함수.

### 2.3 용병단 사슬

```
[[세션 + 0x68] + 0x110]     ← MercenaryClanActorComponent (RTTI 로 확인)
```

문 객체(`gate_object`)의 `+0xA0` 한 단계는 여기 없다. 그것은 세션
vtable[0x160] 이 돌려주는 스포너를 흉내낸 것이다.

## 3. 2454 는 종을 고를 수 없다

```
[ID 2454][00][본문길이 4][u16 A][u16 B]
  A = 컨테이너 종류 (1..21). 표 0x8752A40 이 A -> A-1 로 옮긴다.
      그 표는 키 1..21, 값 0..20 이 전부다(열어서 읽었다).
  B = 그 컨테이너의 슬롯 번호. 조회 0x2078A70 이 [컨테이너] + B*0xC8.
```

**종은 슬롯에 든 아이템이 정한다.** 동행의 부적이 6종뿐이니 한계도 6종이다.

## 4. 남은 길 (C안 진행 상황)

`ItemUseData_SummonCharacterWithCatch` — 게임이 아이템 사용으로 캐릭터를
소환하는 **정상 경로**. 치트가 아니라 게임을 멈추지 않는다.

오늘 연 것:

```
아이템
  └ ItemUseData_SummonCharacterWithCatch   0x40바이트, 살아있는 인스턴스 6개
      +0x30 = 소환 태그 해시 0x5B86A7C3 (여섯 개 전부 같다 - 종을 안 가린다)
      +0x08 → 아이템별 레코드 (여섯 개 전부 다르다)
  └ 역참조하면 이름 붙은 항목이 나온다: "Food_Marlin_item_use_0",
    "Node_Hellhound…"
      └ SummonCharacterTrackNode 가 CharacterKey 를 들고 있다(RTTI 확인)
        **살아있는 인스턴스 0개** - 타임라인 재생 때만 올라온다
```

막힌 지점: 이름 붙은 노드에서 CharacterKey 까지. 그 노드는 평소 메모리에
없다.

다음 수 후보:

1. 해당 아이템을 실제로 써서 노드가 올라온 순간에 읽는다. 청새치(29612)를
   지급해 봤으나 **식재료라 직접 사용이 안 된다** - 조리된 요리 쪽을
   찾아야 한다.
2. `SummonCharacterTrackNode` 의 정적 데이터(에셋 테이블)를 찾아 이름 →
   CharacterKey 대응을 읽는다.
3. 아이템 사용 경로(2676/2976)에 훅을 걸고 소환이 일어나는 순간의 노드를
   잡는다.

## 5. 곁가지로 고친 것

| 결함 | 증상 | 커밋 |

| 구동 게이트가 물리면 밖에서 못 봄 | 지급·소환이 전부 거부되는데 원인 불명. 게임 탓으로 오인했다 | `77ef58e` |
| 액터 매니저를 월드 진입 전에 잡음 | 근처 목록이 영영 빔(1703 → 1) | 이전 세션 |

`drive` 명령이 게이트 상태(대기·실행·쿨다운·잠긴 세션)를 낸다.
`drive reset` 은 30초 넘게 물린 것만 푼다.

## 6. 교훈

**하나. 문서를 먼저 읽을 것.**
금지 기록이 문서와 코드 주석 양쪽에 있었는데 읽지 않고 진행했다. 그 결과
게임이 세 번 멈추고 두 번 팅겼다. 세션 초반 5분이면 없었을 일이다.

**둘. 배포 전에 probe 로 확인할 것.**
주소·오프셋·사슬은 게임을 끄지 않고도 읽을 수 있다. 짐작으로 코드를 짜고
배포한 뒤 실패하고서야 probe 를 켠 적이 두 번이다. 재시작 20여 회 중
상당수가 그 탓이다.

**셋. "성공 코드"를 성공으로 단정하지 말 것.**
검사 함수가 0 을 돌려준 것을 등록 성공으로 읽고 커밋까지 했다. 화면에서
확인하기 전까지는 가설이다.

**넷. 로그 추출은 창을 고정할 것.**
플래그 스윕에서 옛 성공 줄을 세 번 다시 읽고 "성공 3건"으로 보고했다.
실제로는 구동이 전부 거부되고 있었다. `wc -l` 로 위치를 고정한 뒤에야
제대로 갈렸다.

**다섯. 한 경로에 매달리지 말 것.**
소환 치트가 막히자 그것만 파고 있었다. 등록 경로 둘의 호출 목록을
교집합하는 데 10분이 걸렸고, 그것이 검사 함수를 찾아 줬다.
