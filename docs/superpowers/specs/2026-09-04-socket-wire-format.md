# 어비스 소켓 와이어 형식 (2026-09-04, 실측 캡처로 완전 해독)

> ⛔ **이 기능은 제거됨(2026-09-05).** 아래는 조사·구현 기록이며, NPC 없는
> 완전자동이 왜 불가한지(핸들월드≠서버인벤토리)를 남긴다. 실제 코드는
> `develop`에서 제거되었고, 소켓 구동 코드는 원격 브랜치 `archive/socket-reimpl`
> (끝 커밋 `57494d3`, develop 에 없는 변경을 담은 커밋 11개)에 아카이브로 남아 있다. 처음 적었던
> 이름 `feat/socket-reimpl` 은 원격에 없다(2026-09-21 확인).
>
> ⚠️ **죽은 것은 이 "메시지 구동" 경로뿐이다 (2026-09-08 기준).** 소켓 기능
> 자체는 전부 된다 - 지급으로 열린 칸 주기, 이미 가진 장비의 **제자리 언락**,
> 부위별 소켓 수. **레코드에 직접 쓰는 방식**이라 컨테이너 핸들이 필요 없다.
> 락은 레코드 `+0x70`(열린 칸 수)과 칸 `[4]` 둘뿐이고 게임이 검증하지 않는다.
> 전문: `specs/2026-09-07-socket-grant-unlock-research.md`.
> **이 문서를 근거로 "소켓은 불가" 라고 결론내지 말 것.**


업데이트로 소켓이 아이템 생성 치트에서 빠지고 전용 게임플레이 메시지로
옮겨졌다. 소켓은 막힘/뚫림 상태가 있고(`SocketInfo._isBlocked`),
**막힌 소켓 → 뚫기 → 보석 장착** 흐름이다. 옛 방식(생성 치트에 소켓
바이트를 미리 채움)은 뚫기를 건너뛰어 새 게임이 거부했다.

## 캡처 방법

`socket_capture_install`(grant.cpp)이 소켓 메시지 6개(Add/Push/Pop ×
인벤/장비)의 역직렬화(vtable[2])를 후킹해, 게임이 실제로 소켓을 뚫고
장착할 때 들어오는 와이어 페이로드(패킷 +0x18 포인터, +0x10 u16 길이)를
로그한다. 사용자가 인벤토리 아이템 3개에 5슬롯 뚫기+5기어 장착을
실제로 해서 다음을 얻었다.

## 메시지·헤더

| 조작 | 메시지 | ID |
|---|---|---|
| 뚫기 | TrocTrAddSocketItemToInventoryReq | 2739 (0x0AB3) |
| 장착 | TrocTrPushSocketItemToInventoryReq | 2354 (0x0932) |
| (장비 경로) | ...ToEquipSlotReq | Add 2979 / Push 등 |

헤더 5바이트: `[메시지ID u16 LE][00][본문길이 u8][00]`. 본문길이 =
전체길이 - 5. 역직렬화가 `[패킷+0x10] - 5 == [payload+3](필드수)` 로
검사한다.

## 대상 아이템 참조 (본문 앞 9바이트) — 핵심

세 아이템의 [Add] 대상을 나란히 비교(딱 한 바이트만 다름):

```
혹한의 절망(키15901):   04 16 01 10 B0 02 00 5A 00
데메니스 전기톱:        04 16 01 10 B0 02 00 39 00
채석 손 드릴:           04 16 01 10 B0 02 00 05 00
```

구조: `[04 u8][컨테이너핸들 u32][(슬롯<<16)|0x0002 u32]`
- `04` : 참조 종류
- `0xB0100116` : **인벤토리 컨테이너 핸들, 세션 고정.** 메모리에서
  `16 01 10 B0 72 03 10 B0 84 03 10 B0 …` 핸들 배열의 첫 항목이다
  (0xB010 = 핸들 네임스페이스). 세션마다 바뀔 수 있어 동적으로
  읽어야 한다.
- 슬롯 = 아이템의 인벤토리 위치(90·57·5). `(슬롯<<16)|2` 로 인코딩.

## 조작 데이터 (대상 뒤)

**뚫기(Add) — 모든 아이템 공통·고정** (5슬롯 전부 개방):
```
02 00 05 00 00 00 01 00 00 02 00 00 03 00 00 04 00 00
```
(`05 00 00 00` = 슬롯 5개. 그대로 재사용 가능.)

**장착(Push) — {소켓슬롯 u8, 보석슬롯 u16} × 5**:
```
00 56 00  01 58 00  02 59 00  03 4A 00  04 49 00
```
소켓슬롯 0..4 에 보석슬롯 0x56·0x58·0x59·0x4A·0x49(인벤토리 위치).
즉 보석도 인벤토리에 있어야 하고 그 위치로 참조한다.

## 처리 방식 (역직렬화 인라인)

소켓 메시지는 처리기가 역직렬화 안에 인라인이다. 파싱 후
`call [rax+0xe8]`(세션에서 액터), `mov r9d,0x11`, `lea r8,[구조체]`,
`mov rcx,[전역 0x6C29C50]`, `call 0x26AFF70`(지급·소켓 공유 작업함수)로
라우팅한다. 즉 치트처럼 별도 처리기를 못 부르고, **와이어 페이로드를
만들어 역직렬화(vtable[2])를 서버 세션 패킷으로 구동**해야 한다.

## 구현 계획 (Phase 2)

1. **컨테이너 핸들 확보** — 0xB0100116(세션 고정)을 인벤토리 시스템에서
   읽는다. 핸들 배열의 첫 항목. (또는 캡처 훅으로 세션당 1회 학습.)
2. **아이템·보석 슬롯** — 모드의 인벤토리 리더가 위치를 안다.
3. **메시지 조립** — 헤더+대상+데이터로 Add(뚫기)·Push(장착) 와이어를
   만든다.
4. **전송** — 서버 세션 패킷을 만들어 역직렬화를 게임 스레드에서 구동
   (SEH 가드). 지급 치트의 실행 지점 인프라 재사용.
5. **흐름 배선** — 어비스기어 자동 지급 → 슬롯 찾기 → 뚫기 → 장착.
   이걸로 옛 "소켓 미리 채워 지급"을 결과적으로 대체한다.

## 컨테이너 핸들은 세션마다 바뀐다 (확정)

재시작 후 캡처하니 핸들이 0xB0100116 → 0xB0100102 로 바뀌었다.
둘 다 0xB010 네임스페이스의 런타임 핸들이고 세션마다 재할당된다.
세션 내에선 고정(같은 세션의 두 아이템이 같은 핸들). 즉 **하드코딩
불가, 동적으로 읽어야 한다.** 인벤토리 컨테이너 객체의 핸들 필드
(또는 핸들 배열 첫 항목)에서 읽는다.

실측:
```
지난 세션: 04 16 01 10 B0 02 00 [슬롯] 00   핸들 0xB0100116
이번 세션: 04 02 01 10 B0 02 00 [슬롯] 00   핸들 0xB0100102
```

## 미확정 (구현 중 확인)

- 컨테이너 핸들을 인벤토리 컴포넌트/컨테이너의 어느 오프셋에서 읽는지.
- 아이템/보석 슬롯 번호 = 컨테이너 아이템 배열의 인덱스인지(유력 -
  모드 인벤 리더가 순서대로 열거하므로 그 인덱스가 슬롯일 것).
- 장비 경로(EquipSlot)의 대상 형식(슬롯 번호 기반일 가능성).


## Phase 2 구현 (2026-09-05, 실험 - 라이브 실측 전)

와이어 형식이 완전 해독됐으므로 구현했다. **아직 실제로 소켓을 뚫어
보지는 않았다** - 실제 게임플레이 거래라 버릴 세이브에서 실측해야 한다.

### 핸들 확보 = 캡처 학습 (§3.3-1 해결)

컨테이너 핸들 0xB010xxxx 는 **객체에 저장돼 있지 않다.** 게임이 살아
있는 세션에서 `heapfind 020110B0` 을 돌렸더니 인벤토리 컴포넌트·컨테이너
영역(0x5B16xxxx)에 한 건도 없고 전역 핸들 테이블(0x5B0D21xxxx)에만
있었다. 컨테이너 객체(0x180바이트)를 통째로 떠도 핸들이 없다. 객체->핸들
역조회가 어려우므로, 이관 문서 §3.3-1 의 v1 대로 **캡처 훅이 게임의
실제 소켓 페이로드에서 학습**한다(`dump_socket_payload` -> 오프셋 6,
참조종류 0x04, 인벤/장비 나눠 저장). `socket_inv_handle()` 로 노출.
플레이어가 세션당 한 번 수동으로 소켓을 뚫거나 박으면 채워진다.

### 역직렬화 구동 검증 (읽기전용)

`probe socketmsg` 로 확인했다:

```
Add  2739  서술자 RVA 0x693CF20  deser RVA 0x293C560  +0x21=0 (구동 가능)
Push 2354  서술자 RVA 0x693CCE0  deser RVA 0x293B410  +0x21=0 (구동 가능)
```

deser RVA 가 캡처 훅 RVA 와 일치하고, deser 앞부분이 요구하는 서술자
`+0x21==0` 을 둘 다 만족한다. 즉 `deser(서술자, &결과, 패킷)` 로
구동할 수 있다. 패킷은 `[+0x10] u16 전체길이 · [+0x18] 페이로드 ptr ·
[+0x38] 플래그 0` 이면 된다(성공 경로는 packet+0 을 안 쓴다). deser
앞부분 실측: `[r8+0x10]-5 == word[payload+3]` 를 검사한다.

### 코드

- `build_socket_add_wire` / `build_socket_push_wire` (grant.cpp): 순수
  조립. 캡처(핸들 0xB0100102, 슬롯 0x56)와 바이트 일치 단위테스트 4개.
- `resolve_socket_message` (grant.cpp): 처리기 인라인이라
  resolve_cheat_message 가 실패하므로 서술자+deser+id 만 잡는 전용.
- `run_socket` + `Kind::Socket` + `request_socket_add/push`: 지급의
  게임 스레드 실행 인프라(pending·SEH·쿨다운) 재사용.
- grant 패널 "어비스 소켓 (실험)" 헤더: 슬롯·보석슬롯 입력 + Add/Push
  버튼. **자동 지급 흐름엔 안 걸었다.**

### 남은 것 (버릴 세이브 라이브 실측)

1. **슬롯 = 레코드 배열 인덱스 가정 확인.** 모드 인벤 리더의 `record.slot`
   (raw 배열 인덱스)이 와이어 슬롯과 같은지. 캡처의 슬롯값과 invlist 의
   해당 아이템 slot 을 대조하면 실측된다.
2. Add 로 5소켓이 실제로 뚫리는지 화면 확인.
3. Push 로 보석이 박히는지, 보석 슬롯 참조가 맞는지.
4. 인벤토리 오염이 없는지(다른 아이템에 작용하지 않는지).
5. 통과하면 어비스기어 자동 지급 흐름(지급->슬롯찾기->뚫기->장착)에 배선.


## 라이브 1차 실측 (2026-09-05) - 와이어 정확, 슬롯 타깃이 관건

배포 후 실험 UI 로 처음 구동해 봤다. 로그 실측:

- 사용자가 게임에서 아이템을 수동으로 소켓 -> 캡처가 핸들 0xB01000F4,
  슬롯 0x5F(95) 학습. 페이로드:
  `B3 0A 00 1B 00 04 F4 00 10 B0 02 00 5F 00 02 00 05 00 ...`
- 실험 UI 로 Add 구동(슬롯 5). 페이로드:
  `B3 0A 00 1B 00 04 F4 00 10 B0 02 00 05 00 02 00 05 00 ...`
- **슬롯 한 바이트(5F vs 05)만 빼고 게임의 실제 소켓과 바이트 단위로
  완전히 동일하다.** 구동 결과 0(성공), 즉시 크래시 없음.
- Add 를 슬롯5 로 3번 반복 -> 전부 결과 0 -> 이후 지급(성공) -> 약
  1.3초 뒤 게임 팅김.

결론: **와이어·핸들·역직렬화 구동 경로는 정확하다.** 크래시는 슬롯 5
(임의값, 소켓 가능 장비가 아닌 엉뚱한 아이템)에 소켓을 뚫어 그 아이템/
컨테이너를 오염시켰고, 이후 게임의 인벤토리 처리(지급 뒤)에서 터진
것으로 본다. 지급 자체는 정상 종료했다.

### 대응
- 캡처가 대상 슬롯도 학습(참조 뒤 u32 오프셋10 = (슬롯<<16)|2).
  `socket_inv_slot()` 노출. 실험 UI 가 학습된 슬롯(=게임이 실제로
  소켓한 소켓 가능 장비)을 기본 타깃으로 채운다.

### 남은 검증 (버릴 세이브)
1. **올바른 슬롯**(학습된 슬롯 = 소켓 가능 장비)에 Add 를 1회만 구동해
   실제로 5소켓이 뚫리고 크래시가 없는지. 슬롯5 크래시가 '잘못된
   타깃' 때문인지 '올바른 타깃이어도 터지는지'를 이걸로 가른다.
2. 통과하면 Push 로 보석 장착.
3. 미확정: 역직렬화를 메시지 펌프 밖(액터 조회 훅 자리)에서 직접
   불러도 안전한지 - 지급은 그렇게 해도 되지만 소켓은 표본이 1(슬롯5,
   크래시)뿐이라 올바른 슬롯 실측이 필요하다.


## 핸들 매니저 완전 리버스 (2026-09-05) - 완전 자동은 불가 확정

NPC 소켓 1회조차 없애려고(컨테이너->핸들 자동 조회) 핸들 시스템을 앵커
핸들로 통째로 리버스했다. 결론: **클린/퍼지 둘 다 불가.**

### 핸들 테이블 구조 (전역 경로는 세션 불변)
- managerA = [base+0x6C29AA8], registry = [managerA+0x10],
  store = [registry+8].
- 리졸버 = registry vtable[0x28] (RVA 0x836C20) -> 실제 룩업 0x3F4320:
  - bucketcount = [store+0x88], bucket = [store+0x98] + (handle%count)*0x100
  - bucket: [+0]=엔트리수, 엔트리[i] = {u32 handle @ +8+i*8, u32 slotidx @ +0xc+i*8}
  - 객체 = [store+0xa0][slotidx]
  - **object+4 == 자기 핸들** (백참조)
- 핸들 비트: (handle & 0x30000000) 로 타입 판별. 0xB010 = 컨테이너.

### 왜 불가한가
- 소켓 핸들이 가리키는 객체(핸들월드 컨테이너)는 **서버 인벤토리
  (ServerInventoryActorComponent)와 메모리 영역도 다르고 포인터 링크도
  전혀 없다.** heapptr 결과 그 객체를 가리키는 곳은 핸들 테이블 슬롯
  하나뿐(= 핸들로만 도달, 순환).
- RTTI 미식별(vtable 없는 평범 구조체).
- 퍼지 매칭 키도 없음: 핸들월드 컨테이너에 박힌 값(예 3041·907·261)이
  서버 컨테이너 아이템 순번과 하나도 안 맞음. 내용 대조 불가.

즉 모드(서버측)에서 핸들월드 컨테이너 핸들로 갈 결정적/근사 경로가
없다. **핸들은 실제 소켓 거래로만 노출**되므로 세션당 소켓 1회(NPC)는
불가피. 이건 추측이 아니라 리졸버·테이블·객체·대조까지 끝낸 확정.

### 그래서 최종 설계 (접지 않음 - 기능은 동작함)
- 세션당 NPC 소켓 1회 -> 캡처가 컨테이너 핸들 학습(scan_inv_item_ref).
- 인벤토리 행별 '소켓뚫기'(Add) + '보석'(Push, 같은 칸 강화보석 자동)
  원클릭. 학습된 칸의 소켓 가능 장비만 버튼 활성(오염 방지).
- 즉 소켓 1회 비용으로 그 세션 모든 장비를 무료·무제한 소켓+보석.
