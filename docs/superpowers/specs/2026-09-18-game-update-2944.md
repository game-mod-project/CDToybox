11:19 Steam 갱신. 직전 기준은 1.0.0.2850(2026-09-11). `specs/2026-09-01-patch-recheck.md`
절차대로 **게임을 켜지 않고 파일만** 보고 정적으로 대조했다. 런타임 확인은 아래 "남은 확인".

## 4. specguard — 넷만 다시 잡혔다

옛 exe 사본이 남아 있지 않아(Steam 이 덮어썼다) 바이트열을 **소스 주석의 피연산자와
patch_len 에서 복원**했다. 복원이 맞는지는 "div 길이 + 꼬리 길이 == patch_len" 이
스스로 증명한다.

| 사이트 | 2850 | 2944 | 폭 |
|---|---|---|---|
| `kDivMem[3]` `div [rdi+8]` + `mov edx,[rdi]` | 0x235021D | **0x240937D** | +0xB9160 |
| `kDivReg[0]` `div r8` + `cmp eax,[rdi+4]` | 0xF01981B | **0xF83F65B** | +0x825E40 |
| `kDivReg[1]` `div r14` + `mov ecx,edi` | 0x235003B | **0x240919B** | +0xB9160 |
| `kDivReg[2]` `div r9` + `mov ecx,r8d` | 0x2350454 | **0x24095B4** | +0xB9160 |
| `kDivMem[0]` `div [rbp+0xF0]` | 0xEB26B4 | **없음** | — |
| `kDivMem[1]` `div [rsp+0x38]` | 0xEA920F | **없음** | — |
| `kDivMem[2]` `div [rbp-0x38]` | 0x21DB8D8 | **없음** | — |

**셋은 그 형태가 새 exe 어디에도 없다.** 바이트열 검색이 0곳이라, 실행 섹션 전량을
디스어셈블해 `div r/m64`(메모리 피연산자) **244곳**을 전수로 봤다 — `.code` 안의
rbp/rsp 기반은 둘뿐이고 둘 다 무관하다. 가방 렌더 쪽 컴파일이 분모를 레지스터로
재할당한 것으로 보인다.

**못 찾은 셋은 배열에서 빼지 않고 옛 값으로 남긴다.** `install_*` 가 opcode 를
확인하고 어긋나면 패치하지 않으므로 안전하고, 배열에 남아 있어야 `kSiteTotal` 이 7 로
유지돼 `specguard_unsupported()` 가 참이 되어 지급 창이 경고를 낸다 — 실제로 가드가
셋 빠진 상태이므로 그것이 참이다. 배열에서 빼면 "7/7 설치" 라는 거짓 보고가 된다.

## 5. 재도출하지 못한 둘 — 안전 실패에 맡긴다

### `kCallSiteRva` (spawnguard) — 게임이 스스로 가드를 넣은 것으로 보인다

2850 의 지문 `mov rcx,rax ; call 조회 ; mov edi,0xC` 가 새 exe 에 **0곳**이다.
조회 함수를 부르는 272곳 중 142곳은 뒤에 `lea` 가 붙고, 그중 136곳이
`lea reg,[빈 레코드] ; test rax,rax ; cmovne` — **spawnguard 가 하던 일을 게임이
직접 한다.** 소환 작업 함수(0x2B9EB50) 안의 **유일한** 조회 호출(+0x1E7)도 그렇게
가드돼 있다.

옛 자리 0x2AD7238 은 지금 `je`(0x0F) 라 `spawnguard_install` 이
`소환 가드: 0x2AD7238 가 call 이 아니다 (0x0F) - 설치 안 함` 으로 거부한다.
**2944 에서 이 가드가 필요 없어졌을 수 있으나 정적으로는 단정 못 한다** — 크래시가
재현되면 그 자리를 라이브로 잡아 넣는다.

### `kGoodDriveSites` (grant) — 런타임으로만 잡힌다

옛 자리 0x2A03D7D 는 지금 `lea r13,[rip+..]` 다. 액터 조회(0x212A0F0)를 부르는
자리가 **681곳**이고, 그중 무엇이 "교착하지 않는 안전한 자리" 인지는 **코드 모양으로
안 갈린다** — 2850 때도 로그로 잡았다(성공 `+2A0263D`, 멈춤 `+27A95D5`).

역직렬화 이동 폭(+0xCCD00)을 적용한 예상치 0x2AD0A7D 근처에 후보가 여럿 있으나
(가장 가까운 것이 +0x5E0) **추측으로 넣으면 안 된다.** 멈춘 자리를 안전하다고
선언하면 게임 로직 스레드가 통째로 멈춰 저장도 정상 종료도 안 된다.

**증상:** 첫 실행에서 지급·획득이 전부 미뤄진다(2850 때와 똑같다).

**그래서 이번엔 다시 빌드하지 않아도 되게 만들었다** — `CDToybox.ini` 의
`drive_sites` 에 로그의 RVA 를 적으면 안전 목록에 더해진다(§7).

## 6. 매니저 전역 다섯 — 은행이 옮겨졌으나 칸은 정적으로 못 가린다

**둘은 잡았고 셋은 못 잡았다.**

| 상수 | 2850 | 2944 | 어떻게 |
|---|---|---|---|
| `kRegionMgrGlobalRva` (towngate) | 0x6C2E2F0 | **0x6D69AD0** | 표 이름 `regioninfo` → 그 문자열을 xref 하는 **함수 전체**를 훑어 지문 |
| `kCondMgrGlobalRva` (reserveslot) | 0x6C2F260 | **0x6D6AA38** | 표 이름 `conditioninfo` 로 같은 방법 |
| `kKnowMgrGlobalRva` | 0x6C2E2D8 | 미도출 | 표 이름이 `knowledge`(`...info` 아님)인데, 그 문자열을 **조회 함수가 아예 안 만진다** |
| `kSlotMgrGlobalRva` | 0x6C2E300 | 미도출 | `reserveslot` — 위와 같다 |
| `kGpvMgrGlobalRva` | 0x6C32880 | 미도출 | 표 이름을 못 특정했다 |
| `roster.h` 세션 전역 A/B | 0x6C2DC48/50 | 미도출 | 2850 에서도 미확정(주인공 표시만 영향) |

**되는 방법(표 이름 앵커)의 요점 둘.** 문자열은 갱신을 안 탄다. (1) `lea` 만
보지 말고 `xref_data.scan()` 의 여덟 형태를 다 본다. (2) **참조 자리 둘레가 아니라
`.pdata` 로 함수 경계를 구해 함수 전체를 훑는다** — regioninfo 는 문자열 참조가
오류 갈래(0x50D752)에 있고 전역 적재는 함수 머리(0x50D715)에 있어 0x3D 떨어져
있다. 둘레만 보면 절대 안 걸린다.

**못 잡은 셋은 추정을 넣지 않는다.** 폭으로 밀 수 없다 — regioninfo +0x13B7E0,
conditioninfo +0x13B7D8, `kEmptyRecordRva` +0x13AEB0, callgate 값 슬롯 +0x13AF58 로
같은 은행 안에서도 다 다르다. 그리고 **은행이 8바이트마다 빈틈없이 차 있어**
"예상 자리에 뭔가 있다" 가 확증이 못 된다 — 어느 칸을 찍어도 실재한다. 이웃을
잘못 집으면 정합성 검사가 통과해 버린다(지식 매니저가 구역 매니저 0x18 앞에 있다).

"전역 → `[+8]` 개수 · `[+0x58]` 배열" 지문으로 훑으면 전역 **157개**가 걸린다.
`reserveslot.h` 가 적어 둔 대로 "두 매니저는 배치가 같다" 이므로 지문만으로는 못
가린다. 은행 자체는 옮겨진 것이 보인다 — 후보가 0x6D69xxx~0x6D6Bxxx 대에 몰려 있고,
`kEmptyRecordRva` 의 폭(+0x13AEB0)·callgate 값 슬롯의 폭(+0x13AF58)과 맞는다.

RTTI 로도 끝까지 못 간다. `KnowledgeInfoManager` vtable 0x59BFAB0(생성자 lea @
0xF8D1F33) · `ReserveSlotInfoManager` vtable 0x57D89C0(lea @ 0xCDEB0A3) 까지는
나오지만, **생성자가 전역에 저장하지 않는다** — 2850 이 밝힌 대로 초기화 함수가
채우는 포인터 은행의 칸이고, 칸 어긋남은 정적으로 가릴 수 없다.

두 세션이 **각각 독립으로 네 갈래**를 시도해 전부 같은 벽에 닿았다: 지문 스캔 ·
표 이름 문자열 · RTTI 생성자 · `.pdata` 로 생성자 호출자 역추적(둘 다 **호출자
0곳** — 팩토리/vtable 간접 호출이다). 대조군으로 넣은 `RegionInfoManager` 조차
vtable 경로로는 안 나왔다. 2850 의 "런타임으로만 갈린다" 는 이제 관찰이 아니라
**재현된 사실**이다.

> **미도출 셋이 막는 범위는 생각보다 좁다.** 라이브 실측(12:42)에서
> `지식 3867 번을 레벨 1 로 - realm 2개` 가 정상 동작했다 — 지식 **쓰기**는
> 플레이어 사슬(`[액터+0x68]` → 컴포넌트)로 가므로 매니저 전역과 무관하다.
> 전역이 막는 것은 **표를 통째로 훑는 진단·목록**(원소 휠 진단, 예약 슬롯 표)
> 쪽이다. 우선순위를 그만큼 내려 잡을 것.

**2850 의 교훈이 그대로 재현됐다:** 데이터 전역은 단일 폭으로 옮기면 안 되고,
참조 수 근거는 포인터 은행에서 무력하며, 런타임(프로브 또는 로그)으로만 확정된다.

낡은 값을 읽으면 `know_mgr_sane` · `read_mgr` 의 정합성 검사에 걸려
"표를 아직 못 잡았습니다" 로 안전하게 실패한다.

## 7. 새로 넣은 것 — `drive_sites` (다시 빌드하지 않는 복구선)

`kGoodDriveSites` 는 두 번 연속(2850 · 2944) 게임 갱신에 죽었고, 두 번 다 증상이
"지급·획득이 조용히 안 된다" 였다. 두 번 다 **2차 빌드**가 필요했다.

`CDToybox.ini`:

```ini
; 지급을 구동해도 되는 자리(모듈 RVA).
drive_sites = 0x2AD0A7D
```

- 첫 실행 로그의 `구동 건너뜀: 확인되지 않은 자리 +<RVA>` 를 그대로 적는다.
- 판정(`drive_site_is_good`)은 **게임 디투어 안에서** 도므로 할당도 잠금도 없다 —
  고정 칸 여덟에 복사해 두고 원자 개수로만 읽는다(`set_extra_drive_sites`,
  시작할 때 `dllmain` 에서 한 번).
- `0` 은 `drive_site_rva()` 가 "모르는 자리" 에 쓰는 표식이라 **받지 않는다.**
  받으면 모든 자리가 안전해져 게임이 멈출 수 있다. 시험으로 못박았다.
- 16진(`0x`)과 10진을 둘 다 받고, 목록은 여덟에서 끊는다.

⚠️ **아무 자리나 적으면 안 된다.** 멈춘 자리를 적으면 게임이 멈춘다. 지급을 눌렀을
때 **반복해 찍히는** 자리만 적는다.

## 8. callgate · skillgate · dragondiag (피어 세션 도출분)

같은 브랜치의 c7bac29 · 2cb9447. 근거는 그쪽이 전한 것을 옮긴다.

**재도출 방법(공통).** 오류 이름·화면 문구는 갱신을 안 탄다. 등록 루프가 오류마다
`{값 전역 슬롯, 한국어 설명, eErrNo 이름}` 을 넘기므로 문자열 → 등록 자리 → 그 앞
`lea rcx`(값 슬롯) → 그 슬롯을 **읽는** 코드(= 내는 곳) → 앞의 분기 → 8바이트 창
순으로 내려간다. **AOB 가 필요 없다.**

### callgate — 넷 다 +0x7B1E0, 값 슬롯은 +0x13AF58

| 관문 | 값 슬롯 | 내는 곳 | 분기 RVA | 창 RVA(+off) | 창 8바이트 |
|---|---|---|---|---|---|
| 실내 | `+0x6CF7B18` | `0x9DE7DE` | `0x9DE7DC` je | `0x9DE7D8` (+4) | `03 03 84 C0 74 0E 8B 05` |
| 지붕 | `+0x6CF7B1C` | `0x9DE83B` | `0x9DE839` je | `0x9DE838` (+1) | `C0 74 0A 8B 05 DB 92 31` |
| 지역 | `+0x6CF7B20` | `0x9DD89B` | `0x9DD899` je | `0x9DD898` (+1) | `C0 74 75 8B 05 7F A2 31` |
| 위치 | `+0x6CF7AFC` | `0x9DD6C6` | `0x9DD6C4` **jne** | `0x9DD6C0` (+4) | `06 00 84 C0 75 0A 8B 05` |

⚠️ 2944 에서 **"호출할 수 없는 위치입니다" 문구를 쓰는 등록이 둘**이다(슬롯
`+0x6CF6F88` 과 `+0x6CF7AFC`). 우리 것은 뒤쪽이고, 창이 2850 과 바이트까지 같아서
구분된다. 앞쪽은 `0F 85`(near jne)를 쓰는 다른 코드다.

### skillgate — 폭이 서로 다르다

| 관문 | 2850 | 2944 | 폭 |
|---|---|---|---|
| 관문0 `CanLearnByFromType` | 0x0E0AB860 | **0x0E808870** | +0x75D010 |
| 관문1 `setge [rsp+0x40]` | 0x0208B639 | **0x02140CF9** | +0xB56C0 |

경로: `eErrNoCannotLearnKnowledgeByFromType`(0x5929B98) → 슬롯 `+0x6CF7BF0` →
내는 곳 `0x2140AEC`(= `CheckLearnOrLevelUp`, 0x2140730~0x2141885) → 직전
`call 썽크 0x2140640` → jmp 목적지가 관문0, 같은 함수의 `setge` 가 관문1.

**창 8바이트가 2850 과 글자 하나 안 틀린다** — 코드는 그대로고 자리만 밀렸다.

### towngate — 자기 치유한다, 고칠 것이 없었다

박아 둔 RVA 는 매니저 전역(`0x6C2E2F0`) 하나뿐이고 그것도 클래스 이름
(`Rtti::class_of_object`)으로 대조한 뒤 안 맞으면 `find_static_manager` RTTI
탐색으로 넘어간다. **`RegionInfo` 필드 오프셋이 2944 에서 그대로**다
(`_isTown +0x75` · `_limitVehicleRun +0x74` · `_stringKey +0x08`; 새 필드
`_regionInventoryInfo +0xA8` 이 생겼다). `RegionInfoManager` vtable 은
0x597BBF0 → 0x5A93CC0 으로 옮겼으나 towngate 는 그것을 안 박는다.

### dragondiag — 모르는 빌드에서는 안 건다

RVA 10개가 전부 **라이브 추적으로 얻은 것**이라 문자열·패턴 앵커가 없다. 재도출
대신 확인 둘을 넣었다.

1. `kDerivedForBuild = "1.0.0.2850"` 과 실행 중 exe 버전이 다르면 훅을 **하나도 안
   걸고** 로그 한 줄 남기고 돌아온다.
2. `.pdata` 함수 시작 대조 — 여덟 자리 전부. 예외 디렉터리를 이진 탐색해
   `BeginAddress` 와 같은지 본다. 2026-09-15 에 짐작으로 건 훅이 0x1450 빗나가
   함수 중간에 걸린 적이 있어 따로 필요하다.

결과적으로 2944 에서 dragondiag 는 전부 건너뛴다. `wheel_fill` 의 휠 칸 채우기가
안 되는데, 그 하나(`kFindRva`)를 라이브로 짚기 전까지는 어쩔 수 없다.

## 9. 안전망이 처음으로 실전에서 값을 했다

callgate 의 옛 창 넷이 새 exe 어디에도 없어 **설치가 거부됐다.** 쓰기 폭(1바이트
`74`)만 확인했다면 실행 섹션 수만 곳 중 아무 데나 통과했을 것이다. "원본 확인은
쓰기 폭이 아니라 **원자 창 8바이트 전체**로" 라는 규칙(`skill-gate-code-patch`)의
근거로 쓸 수 있다.

같은 이유로 `spawnguard` · `specguard` 도 옛 자리에서 조용히 거부됐고, 아무것도
망가뜨리지 않았다. **반대로 메시지 ID 에는 그런 그물이 없다** — 이번 갱신에서 가장
위험했던 것이 그것이다(§2).

## 남은 확인 (게임 실행 뒤 `bin64/CDToybox.log`)

### 먼저: `.prev` 와 같은 눈으로 세어 기준선을 잡는다

갱신 뒤 로그에 warn 이 보이면 **그것이 새 것인지부터 본다.** `.prev` 는 갱신
**전** 실행이라 그대로 기준선이다.

```bash
for f in CDToybox.log CDToybox.log.prev CDToybox.log.prev2; do
  echo "$f"; grep -oE 'WARN  [^0-9]{6,40}' "$f" | sort | uniq -c | sort -rn | head
done
```

이번에 기준선 없이 "새 구멍" 으로 오판할 뻔한 것 둘:

| 줄 | 실제 |
|---|---|
| `엔티티 조회 함수를 못 찾았다` | **2760 부터 있던 것.** `.prev`·`.prev2` 에도 각 1건이고 `specs/2026-09-11-game-update-2850.md` 가 이미 "무관" 으로 적어 뒀다. 소비자는 `camera.cpp:284` 하나 |
| `문: 세션 …에서 사슬이 끊겼다` | **오히려 줄었다.** 갱신 전 `.prev` 137건 → 지금 16건(`.prev3` 은 5건). 세션 수에 비례하는 값이라 구조가 밀렸다면 늘어야 한다 |



1. `고용 작업 추적 설치 (RVA 0x2BADB80)` · `소환 작업 추적 설치 (RVA 0x2B9EB50)`
   두 줄. 안 뜨면 §3 이 틀렸다.
2. `특수아이템 가드: 4/7개만 설치` — **4 가 정상이다**(§4). 4 보다 적으면 재도출이
   틀렸다는 뜻이다.
3. `소환 가드: 0x2AD7238 가 call 이 아니다` — **정상이다**(§5, 안전 거부).
4. `소환 진단: 이 빌드(1.0.0.2944)에서는 안 건다` — 정상이다(§8).
5. **`구동 건너뜀: 확인되지 않은 자리 +<RVA>` — 이 RVA 를 `drive_sites` 에 적는다**
   (§7). 지급·획득은 그때까지 안 된다.
6. 예약 슬롯·조건·지식 표가 "아직 못 잡았습니다" 로 나오는지(§6). 그러면
   `cdtb_probe` 로 매니저 인스턴스를 찾아 전역을 확정한다.
7. 아이템 표 개수·현지화·인벤 읽기·커서 가드·raw input — 2850 때와 같은 항목들.
8. 지급 한 건 실측(5 를 고친 뒤), 획득 한 건, 소환 한 건.

## 10. 수배(범죄수치) — 갱신이 드러낸 결함 하나와 남은 확인

이 기능을 만든 세션은 이미 끝났다. 인계를 문서로 남긴다.

### 해석해 놓고 안 쓰고 있었다 (2026-09-18 고침)

`wanted.cpp` 는 **이미 옳은 일을 하고 있었다** — 메시지 서술자를 클래스
이름(`TrocTrClearWantedReq` · `TrocTrChangeWantedStateReq`)으로 찾아 ID 를
`g_*_msg.id` 에 담고 로그로 찍는다. 이름은 갱신을 안 타므로 그 경로는 2944 를
그냥 넘겼다.

**그런데 와이어를 만드는 쪽은 박아 둔 상수를 쓰고 있었다.**

```cpp
const std::uint16_t id = kClearWantedId;   // 해석값을 무시했다
```

그래서 갱신 뒤 **로그는 맞는 값(2837)을 보여 주면서 전송은 틀린 값(2646)으로
나가는** 상태가 된다. 옛 번호가 다른 메시지에 재사용되는 상황(§2)에서는 그것이
"안 먹는다" 가 아니라 "엉뚱한 것이 돈다" 로 나타난다.

고쳤다 — 와이어는 `g_*_id`(해석값, 해석 전에는 상수)를 쓰고, 해석 시점에
상수와 갈리면 `message_id_drifted` 가 참을 돌려 **경고를 남긴다**:

```
WARN 메시지 ID 가 갈렸다: TrocTrClearWantedReq 은 코드에 2646 로 박혀 있는데
     게임은 2837 이다 - 전송에는 게임 값을 쓴다. 소스 상수를 고칠 것
```

**이것이 메시지 ID 에 없던 그물이다.** 다른 모듈로 넓힐 값이 있다 —
`companion.h` 의 ID 다섯은 아직 런타임 해석 자체가 없어 상수만 쓴다(후속).

### 남은 확인 (게임 안에서)

| 항목 | 왜 |
|---|---|
| `ClientSelfWantedActorComponent +0x30` → `WantedRegionData +0x30` | **정적으로 확인 불가.** 라이브로 얻은 오프셋이라 구조체에 필드가 하나 늘면 뒤가 전부 밀린다. 이번에 `RegionInfo` 에 `_regionInventoryInfo` 가 실제로 새로 생겼다 — 수배 쪽은 오프셋이 앞이라 안 밀렸지만 운이었다 |
| 컴포넌트 **재탐색** (b23737b) | 월드 진입 전 한 번만 찾고 포기하던 버그를 고쳤는데 **2850 에서도 인게임 확인이 안 된 채 끝났다.** 화면: 플레이어 창 → 범죄수치(수배) → "현재 벌금 N.NN". 그 줄이 보이면 로그에 `수배 컴포넌트: 0x… (지역 0x… .?AVWantedRegionData@pa@@)` 가 찍힌다 |
| 수배 해제·상태 변경이 실제로 먹는가 | ID 는 고쳤고 이제 해석값을 쓰지만, **먹히는지는 인게임 미확인**이다. 위 경고 줄이 안 뜨면 상수와 해석값이 같다는 뜻이다 |

> **미확인 전언 하나.** "수배 메시지가 결과 0 만 돌려줘서 거부인지 무동작인지
> 못 가린다" 는 이야기가 인계에 있었으나 **소스·문서에서 그 서술을 찾지
> 못했다**(`wanted.{h,cpp}` · STATUS · TROUBLESHOOTING 전부). 사실로 적지
> 않고 여기 그대로 남긴다. 만약 그 상황이 실제라면 §8 의 `eErrNo` 역추적
> (이름 문자열 → 한국어 설명 → 값 전역 슬롯 → 내는 코드 한 곳)이 정확히
> 그것을 가리는 도구다.

> **STATUS 에 이 기능의 절이 없다.** PR #27 이 기능을 넣으면서 `docs/STATUS.md`
> §1 에 항목을 안 만들었다. 인게임 확인이 끝나면 그때 절을 세우는 것이 맞다 —
> 지금 쓰면 "된다" 고 적을 근거가 없다.
