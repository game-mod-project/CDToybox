> **정리 (2026-09-21) — ✅ 해결.** `STATUS.md` §1.6. 여기의 전역 `0x1465BB288`("같은
> 계열")은 오기를 이어받은 것이다(`0x14625B288`, `2026-09-03-debug-console.md` §1).
> §7 주소 표는 옛 빌드 값이다 — 2944 값은 `2026-09-18-game-update-2944.md`.

**날짜:** 2026-09-01
**방법:** 구조는 EXE 정적 분석으로, 값은 실행 중인 게임에서 읽기로 확인.
**앞 문서:** `2026-09-01-cheat-system.md` 의 "다음에 이어갈 순서" 1·2번.
**상태:** **동작한다.** `cdtb_probe loc` 로 실측했다.

## 요약

아이템 이름을 푸는 경로를 확정하고 **살아 있는 게임에서 검증했다.**
게임 함수를 부를 필요가 없다 — 읽기만으로 걸을 수 있는 평평한
문자열 풀이다.

이름은 `풀기준 + 오프셋` 한 번의 덧셈이고, 오프셋은 64비트 키로
이분 탐색해 얻는다. 카메라 때와 달리 게임이 구조를 전부 드러내 준다.

실측 (Crimson Desert Enhanced 2.00.01, 게임 실행 중):

```
전역    0x146259478  (RVA 0x6259478)
시스템  0x3E384703280
풀      0x3E3F50B0000   크기 11,884,917 바이트
```

```
$ cdtb_probe loc item 2200
  필드 0x70  키 9448928051312 :  [카테고리 7] '편전'
  필드 0x71  키 9448928051313 :  [카테고리 7] '일반 화살보다 짧고 날렵한
      형태로 가공된 특수 화살. 일반 화살을 상회하는 막강한 관통력과
      파괴력을 보장한다.<br/>활을 장착하여 공격할 때 사용된다.'
```

이름과 설명이 서로 들어맞는다 — 편전은 짧고 관통력이 높은 화살이고,
설명이 정확히 그것을 말한다. 표본을 넓혀도 일관된다.

| 엔티티 | 0x70 |
|---|---|
| 2200 | 편전 |
| 50001 | 화살 |
| 50003 | 독 화살 |
| 1002045 | 봉인된 어비스 아티팩트 |
| 1 | 동화 |
| 100 / 2201 / 2202 | 없음 (키가 비어 있음 — 정직하게 실패한다) |

**아직 화면과 대조하지는 않았다.** 인게임 아이템 목록에서 '편전' 을
눈으로 확인하면 마지막 고리가 닫힌다.

## 1. 현지화 시스템 전역

전역 하나가 시스템 객체를 가리킨다. `.00cfg` 에 있고, 앞서 찾은 디버그
시스템 전역 `0x1465BB288` 과 같은 계열이다.

```
전역 VA 0x146259478   (RVA 0x6259478, 섹션 .00cfg)
```

**이 주소를 그대로 박으면 안 된다.** 게임이 갱신되면 깨진다. 아래
패턴으로 매번 찾는다 — 이미지 전체에서 **1곳**만 일치하는 것을 확인했다.

```
8B 41 18                mov  eax, [rcx+0x18]
48 8B 0D ?? ?? ?? ??    mov  rcx, [rip+disp]     <- disp 가 전역
3B 41 60                cmp  eax, [rcx+0x60]
72 08                   jb   +8
48 8D 05 ?? ?? ?? ??    lea  rax, [rip+disp]
C3                      ret
48 03 41 58             add  rax, [rcx+0x58]
C3                      ret
```

이것은 `LocalizationStringBase::str()` 의 본문 전체다 (`0x1410d6080`,
28바이트). 전역은 `일치주소 + 10 + disp32` 로 나온다.

## 2. 시스템 객체 레이아웃

```
+0x18  잠금 객체       vt[1]=lock, vt[2]=unlock
+0x48  카테고리 표     16바이트 항목, 인덱스 0..0x35 (54개)
         +0x00  포인터 배열 기준 (8바이트 항목, 키 오름차순 정렬)
         +0x08  u32 개수
+0x58  문자열 풀 기준
+0x60  u32 풀 크기
```

## 3. 항목 (`LocalizationStringBase`)

```
+0x00  vtable          0x144e83bc8 / 0x144e83bb0
+0x08  u16 종류        (=4)
+0x10  u64 키          <- 이분 탐색 대상
+0x18  u32 풀 오프셋   (0xFFFFFFFF = 아직 안 풀린 것)
+0x1c  u8  카테고리
```

RTTI: `.?AVLocalizationStringBase@pa@@`, TD `0x60c5558`, vtable `0x4e83bc8`.

## 4. 이름을 뽑는 절차 (전부 읽기)

```
sys      = *(void**)(모듈 + 0x6259478)          // 패턴으로 얻은 전역
pool     = *(char**)(sys + 0x58)
poolSize = *(u32*)  (sys + 0x60)

for cat in 0 .. 0x35:
    tbl = *(void**)(sys + 0x48 + cat*16)
    n   = *(u32*)  (sys + 0x48 + cat*16 + 8)
    // tbl 은 포인터 배열. tbl[i] 의 +0x10 이 키. 오름차순이라 이분 탐색 가능
    e   = 이분탐색(tbl, n, 키)
    off = *(u32*)(e + 0x18)
    if off != 0xFFFFFFFF && off < poolSize:
        이름 = pool + off
```

## 5. 조회 함수를 부르지 말 것

게임 자신의 조회는 `0x1410d7230` 이다.

```
resolve(시스템* rcx, u8 카테고리 dl, u64 키 r8) -> LocalizationStringBase*
```

호출부는 이렇게 생겼다 (`0x1410d60f6`):

```asm
movzx eax, byte [rbx+0x10]   ; 카테고리
cmp   al, 0x36               ; 54 미만인지
mov   r8,  [rbx+0x08]        ; 64비트 키
mov   rcx, [0x146259478]
movzx edx, al
call  0x1410d7230
```

본문은 깨끗한 이분 탐색이다.

```asm
r15 = 카테고리 * 16
rax = [sys+0x48]
r9d = [rax+r15+8]            ; 개수. 0 이면 즉시 실패
r11 = [rax+r15]              ; 포인터 배열
  rdi = [r11 + mid*8]
  cmp rbp, [rdi+0x10]        ; 키 비교
  je  찾음
```

**그런데 부르면 안 된다.** 두 가지 이유다.

1. 진입에서 `[sys+0x18]` 잠금을 잡고 나갈 때 푼다. 우리 스레드가
   게임 스레드와 경합한다.
2. **못 찾으면 항목을 새로 만들어 표에 끼워 넣는다** (`0x1410d9300`).
   읽기인 줄 알고 부른 것이 게임 상태를 바꾼다.

4번 절차는 이 둘 다 피한다.

## 6. 키의 정체 — 확인됨

앞 문서에서 아이템 레코드가 들고 있던 "숫자 현지화 키"를 64비트로
보면 깨끗하게 갈라진다.

| 십진 문자열 | 16진 | 상위 32 | 하위 32 |
|---|---|---|---|
| `9448928051312` | `0x0000089800000070` | `0x898` = **2200** | `0x70` |
| `214752659767408` | `0x0000c35100000070` | `0xC351` = **50001** | `0x70` |
| `214752659767409` | `0x0000c35100000071` | `0xC351` = **50001** | `0x71` |

```
키 = (엔티티키 << 32) | 필드번호
```

2200 과 50001 은 아이템 색인 표의 **첫 두 항목의 키와 정확히 같다.**
`0x70` 이 이름, `0x71` 이 그 다음 칸(설명으로 추정)이다.

처음에는 표본 3개짜리 가설이었다. EXE 안에서 통계로 검증하려 했으나
12~20자리 십진 문자열이 16개밖에 없고 전부 `4444444466666666` 같은
테스트 찌꺼기였다 — 현지화 ID 는 `.paz` 에서 런타임에 올라오므로
EXE 로는 검증할 수 없다.

**실행 중인 게임에서 확인했다.** 0x70 이 이름, 0x71 이 설명이다.
위 요약의 표를 볼 것.

아직 모르기 때문이다.

## 9. 도구

```
cdtb_probe loc                  시스템 + 카테고리별 개수
cdtb_probe loc <키>             키 하나 (10진 또는 0x16진)
cdtb_probe loc item <엔티티키>  이름(0x70)과 설명(0x71)
```

구현은 `src/game/localization.cpp` 다. 모드와 probe 가 같이 쓰도록
`src/game/` 에 두었다 (카메라와 같은 자리).

## 도구

이번에 쓴 오프라인 분석기는 스크래치패드에 있다 (저장소 밖).
PE 파싱은 문서에 기록된 섹션 표와 **정확히 일치**하는 것을 확인하고
썼다 — 실행 섹션은 `IMAGE_SCN_MEM_EXECUTE` 로 고르고 RVA→파일오프셋은
RawSize 로 자른다.

RTTI 타입 디스크립터는 **15,633개** 나왔다. 이름을 비탐욕 `@@` 로 끊으면
템플릿 인자가 잘려 서로 다른 클래스가 한 이름으로 뭉친다(그렇게 하면
14,267개로 줄었다). 이름은 NUL 종료 C 문자열로 읽어야 한다.
