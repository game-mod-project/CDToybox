# 게임 업데이트로 치트·지급·소환이 깨졌다 (2026-09-04)

게임이 업데이트되면서 실행 파일이 바뀌어, 바이트 패턴·주소로 찾는
기능이 전면적으로 깨졌다. RTTI(클래스 이름)로 찾는 것만 멀쩡하다.

|---|---|---|
| exe 크기 | 361,256,856 | 379,781,016 (+18MB) |
| exe 날짜 | 9/1 | 9/4 13:56 |
| 아이템 표 개수 | 6810 | 6813 |
| 캐릭터 개수 | 7251 | 7250 |
| 액터 조회 RVA | 0x1DF6940 | 0x2073710 |

## 되는 것 (RTTI 기반 - 이름은 안 바뀜)

- 로스터(탈것 34·캐릭터 7250), 아이템 표(6813), 카메라, 오버레이,
  현지화, 인벤토리 컴포넌트 탐색.

## 깨진 것 (패턴/구조 기반)

- **아이템 대응표**(키→순번). `변환 함수 패턴 0곳` - 그 함수의 스택
  오프셋·전역 로드 위치가 바뀌었다. `0F B7 00 66 89 03`(결과 u16
  읽어 저장)은 5곳 남았으나, 그중 인접 전역 로드가 있는 둘은 표
  개수가 15·37 로 아이템 맵(6813)이 아니다. 아이템 맵 변환 함수는
  전역 로드가 비인접해 더 넓은 탐색이 필요하다.
- **인벤토리 지급.** 메시지·생성자·표는 다 해석되는데 **지급이
  성공으로 뜨나 아이템이 안 들어온다.** 소환과 같은 유형 - 처리기가
  읽는 키가 어긋난다(아이템 데이터 변경 또는 TrItemValue 레이아웃
  변경 의심). 확인 필요: 새 지급 작업 함수를 디스어셈블해 TrItemValue
  가 읽히는 오프셋(옛 +0x08 키, +0x10 개수)이 그대로인지.
- **소환**(`SpawnCharacterCheatReq`), **바닥 스폰**, **내구도**,
  **능력치** - 전부 `처리기 호출을 못 찾았다`. 처리기를 찾는 본문
  패턴이 새 exe 에서 안 맞는다.

## 새로 뽑은 후보 (부분)

- 아이템 맵 변환 함수 후보(비인접 전역): 미확정. 6813 표를 가리키는
  전역을 runtime 개수로 가려야 한다.
- 다른 후보 전역 두 개: 0x6C46EB8(표 15개), 0x6C32E30(표 37개) - 둘 다
  아이템 맵 아님.

## 재도출 계획 (다음 세션 - 큰 작업)

`specs/2026-09-01-patch-recheck.md` 절차를 따른다. 순서:

1. **아이템 대응표.** `0F B7 00 66 89 03` 를 앵커로 그 함수의 전역을
   (비인접 포함) 뽑고, runtime 에서 [전역]+0x68 개수가 6813 인 것을
   고른다. `kConvertBodyPattern` 을 스택 오프셋 와일드카드로 더 튼튼히
   고친다.
2. **지급 실체화.** 새 작업 함수를 찾아 TrItemValue 읽기 오프셋을
   재확인한다. fill_item_value 의 오프셋이 그대로인지 대조.
3. **소환·바닥스폰·내구도·능력치.** 각 처리기를 찾는 본문 패턴
   (find_handler_call 등)을 새 exe 로 재도출.

패턴은 가능하면 스택 오프셋·인접성에 덜 의존하도록 튼튼하게 고쳐
다음 업데이트에도 견디게 한다.

## 해결 (2026-09-04 후속)

### ① 아이템 대응표 - 힙 스캔으로 재도출 (완료, probe 실측)

변환 함수 본문 패턴은 스택 오프셋·주소에 의존해 깨졌다. 대응표
객체는 힙에 그대로 있으므로 함수 인코딩에 기대지 않고 컨테이너
레이아웃(+0x04 개수, +0x08 용량, +0x10 슬롯, +0x18 레코드)으로 힙에서
직접 찾는다(`find_item_key_map_by_scan`). 개수가 expected 인 자리를
찾고 레코드 키가 실제 아이템 키에 전부 있는지로 확인한다.

probe 실측(게임 실행 중): 개수 6813/용량 8088, 채워진 칸 6813, 순번·
키 중복 0, 표에 없는 키 0, 아이템 표와 6813칸 전부 일치. 다음
업데이트에도 견딘다(exe 인코딩 무관). 커밋 e3e4407.

### ② 지급 실체화 - 처리기 탐지가 잘못된 경로를 집었다 (완료, 정적)

**TrItemValue 오프셋은 안 바뀌었다.** 근본 원인은 처리기 탐지다.
컴파일러가 역직렬화 함수의 성공코드 0 저장을 즉시값(`C7 /0 00000000`)
에서 미리 xor 로 0 을 만든 레지스터(`89 /r`, 예 `mov [rbx],esi`)로
바꿨다. 옛 `find_handler_call` 은 즉시값만 봐서:

- give: 즉시값 마커가 남은 자리는 스트림 경로 처리기(0x2B74030, 5인자)
  뿐이라 그걸 집었다. 우리가 채운 구조체를 안 쓰는 함수라 크래시
  없이 "성공"만 뜨고 아이템은 안 들어왔다.
- spawn/내구도/능력치: 즉시값 마커가 아예 없어 "못 찾았다".

정적 확인(cheat_report + disasm, 새 exe): give 역직렬화 0x2934F60 에
처리기 호출 둘 - 빠른 경로 0x2B73E50(3인자 self·packet·&struct,
게이트 [rax+0x140]+액터조회 0x2073710 을 부르는 진짜 처리기)과 스트림
경로 0x2B74030(`mov [rsp+0x20/0x28]` 스택인자 = 5인자).

수정: 두 저장 꼴을 다 인식하고, 후보가 여럿이면 스택인자(5+인자)
경로를 빼고 3인자 경로를 고른다. 단위 테스트 4개 추가. 커밋 b072fb7.
배포함 - 게임 켜서 지급 실체화 확인 대기. `probe cheat` 로 처리기
RVA 를 실측(give=0x2B73E50 이어야 함).

### ③ 나머지 (남음, 사용자 지시로 보류)

spawn·바닥스폰·내구도·능력치는 처리기가 이제 탐지되지만(단일 후보),
인자 수·구조가 give 와 달라(예: SpawnCharacter 는 pos·B·flag) 각각
호출 규약·오프셋 재검증이 필요하다. 함수끝 int3 미탐(인접 함수 겹침)도
정리 대상. 급하지 않음.

## 결론

게임 업데이트가 원인이었다. ① 대응표와 ② 지급은 exe 인코딩 변화
(C7 즉시값 → 89 레지스터)와 주소 시프트가 근본이었고, 둘 다 인코딩에
덜 의존하는 방식으로 고쳐 다음 업데이트에도 견디게 했다.

## ② 후속 - extras 가 팅김을 냈다 (2026-09-04, 실측 + 게이트)

처리기 수정을 배포하고 실측하니 **기본 지급(키+개수)은 정상**이었다 -
로그에 "인벤토리 지급 끝" 15건, 크래시 0. 그런데 담금질 10·소켓 1·
연마 40 짜리 한 건만 "끝" 3초 뒤 게임이 팅겼다(로그는 정상 반환).

정적 분석으로 생성 함수 `0x2A70000`(handler 0x2B73E50 이 부름,
r8=우리 TrItemValue)을 뜯어 확인:

```
mov   edx, [r8+0x08]          ; 키 - 그대로
cmp   [r8+0x10], r12          ; 개수 - 그대로
movzx ecx, [r14+0x0C]         ; 담금질 - 그대로 (r14=r8)
cmp   byte [r14+0x5E], dil    ; 소켓수
jbe   0x2A7028A               ; 0 이면 정상(아이템 추가 call 0x234F930)
mov   [r15], <오류코드>        ; >0 이면 오류 분기 - 옛 exe 는 여기서
                             ;   소켓을 복사했다. 업데이트로 바뀌었다.
```

즉 새 처리기는 **소켓수(+0x5E)>0 을 거부**한다. 소켓 1 을 넣으니 그
오류 경로를 타 상태가 오염됐고 나중에 죽었다. 내구도(+0x2A)·연마
(+0x1AE)도 전달 자리가 미검증이다.

**게이트**: `request_give` 가 소켓·내구도·연마를 0 으로 떨궈 보낸다.
키·개수·담금질만 확인됐다(생성 함수가 그대로 읽음). fill_item_value
자체는 안 건드려 오프셋 문서·테스트를 유지한다. 지급 패널·스태시
임포트 둘 다 request_give 를 거쳐 전부 커버. 커밋 49597dc.

**되살리려면(③ 일부)**: 소켓은 오프셋 문제가 아니라 전달 경로가
바뀌었다 - 새 처리기가 소켓을 어떻게 받는지(별도 인자? 다른 치트?)
`0x2A70000`/`0x234F930` 를 더 파야 한다. 내구도·연마는 새 struct 에서
읽는 자리를 `0x234F930` 계열에서 재확인하면 될 수 있다.

## ① 재정리 - 대응표는 ItemInfoManager+0x68 (2026-09-04, 실측)

힙 스캔은 확실하나 11GB 를 훑어 수십 초 걸렸다. 그동안 인벤토리·
지급 패널이 "대응표를 아직 못 읽었습니다" 로 막혀, 필터 UI 가 사라진
것처럼 보였다(실제로는 로드 지연).

`probe whatis <맵객체>` 로 밝혀냄: 맵 객체의 RTTI 가
`.?AVItemInfoManager@pa@@` 이고, 매니저 +0x30(아이템 개수)과 +0x6C
(맵 개수)가 둘 다 6813. 즉 **키->순번 대응표 테이블 = ItemInfoManager
+0x68**. 매니저는 이미 RTTI 로 찾으므로 `find_item_key_map_from_manager`
가 +0x68 을 즉시 읽는다. 스캔·패턴은 방어용 폴백으로만 남긴다.
RTTI 기반이라 업데이트에도 견딘다. 커밋 de7d592.

## ②-후속2 - 연마 복원, 소켓은 게임이 없앴다 (2026-09-04, 정적 확정)

지급 팅김의 원인은 오직 소켓이었다. 연마·내구도는 오프셋이 그대로다.

- **필드 복사 함수 0x234F930**(소켓수 0 정상 경로, r12=우리 TrItemValue):
  `movzx [r12+0x0C] 담금질 · movzx [r12+0x2A] 내구도 ·
   movsx [r12+0x1AE] 연마`(표 +0x2E8 상한으로 자름) - 옛 exe 와 동일.
  그래서 **연마·내구도를 되살렸다**(request_give 가 소켓수만 0 으로).
- ~~**소켓은 되살릴 수 없다.**~~ **이 판정은 틀렸다 - 아래 정정을 볼 것.**
  (당시 기록은 그대로 둔다.) 0x234F930 이 struct 에서 읽는 오프셋 전부를
  뽑아 보니(+0x0C·0x10·0x18·0x20·0x2A·0x30·0x38·0x5E·0x64·0x124~0x148·
  0x180·0x1AC~0x1AE) **소켓 바이트 배열(+0x40~0x5D)을 어디서도 안 읽는다.**
  +0x5E(소켓수)만 읽고, 생성 함수 0x2A70000 은 그게 >0 이면 무조건
  오류 분기(`mov [r15],err`). 즉 이 업데이트가 CreateItemFromTrItemValue
  의 소켓 전달을 없앴다. 우리 버그가 아니라 게임 변경이다.
  소켓을 주려면 별도 경로(다른 치트?)나 0x234F930 이 새로 읽는
  +0x124~0x148 필드의 뜻을 파야 하는데, 불확실하고 급하지 않다.

### ⚠️ 정정 (2026-09-07) — 소켓은 죽지 않았다

위 "소켓은 되살릴 수 없다" 는 **오독**이다. 두 군데를 잘못 읽었다.

1. **`0x234F930` 은 소켓 바이트를 지금도 읽는다.** `mov ecx,[r9+r12+0x40]`
   처럼 **레지스터 인덱스**(r9 = k*6)라서, 상수 변위만 훑는 방식으로는 안
   잡혔다. `tools/rtti/fields.py` 가 문서에 적어 둔 바로 그 실패 모드다.
2. **`0x2A70000` 은 갈래가 둘인데 하나만 봤다.** `je 0x2A70335` 를 안 따라
   가고 fall-through 만 읽었다. 그 fall-through 는 **겹치는 아이템 갈래**라
   소켓수>0 을 거부하는 게 당연하다. **장비 갈래**(0x2A70335)는
   `아이템표+0x238 >= 소켓수` 만 보고 통과시킨다. 판별자 0xF090BC0 의
   마지막 줄이 `_equipTypeInfo(+0x42) == 0xFFFF` 라, 장비는 언제나 그쪽이다.

지급 소켓은 **복원됐고 게임에서 검증까지 끝났다**(2026-09-08). 이어서 제자리
언락·부위별 소켓 상한까지 구현했다. 전문:
`specs/2026-09-07-socket-grant-unlock-research.md`.

**교훈:** "안 읽는다" 를 확인할 때 상수 변위만 훑으면 레지스터 인덱스를
놓친다. 분기는 양쪽을 다 따라간다.

## UI - 인벤토리 표 내부 스크롤 (2026-09-04)

BeginTable 에 outer_size 를 안 줘서 ScrollY 표가 남은 공간을 다 먹고
아래 안내문 두 줄이 창 밖으로 밀려 바깥 창 스크롤이 생겼다. 안내문
두 줄 높이를 남긴 outer_size 를 주어 표가 내부에서 스스로 스크롤하게
했다 - 필터·헤더·안내문이 늘 보인다.
