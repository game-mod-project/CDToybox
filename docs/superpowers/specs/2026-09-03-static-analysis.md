# 정적 분석: 지급 경로의 실제 구조 (2026-09-03)

> **정리 (2026-09-21) — ✅ 해결 (§8 반증).** 지급 경로 해독과 소켓·내구도 싣기는
> 실측으로 확인됐다(`STATUS.md` §6 "지급이 무엇을 싣는가"). 단 §8 "'수리 불가' 는
> 아이템 종류의 성질" 은 반증됐다 — 인스턴스 단위다(`STATUS.md` §6 "다음에 이어갈
> 지점" 1). 머리말의 내구도 자리(`+0x28`·`+0x2C`)는 같은 문서 뒤쪽이 `+0x40` 으로
> 바로잡았다.

## 요약

디스어셈블러를 대상에 겨눠 보니 **막고 있던 두 결론이 모두 틀렸다.**

1. "디스크 PE 는 Denuvo 로 싸여 있어 못 본다" — **아니다.** 우리가
   보려던 함수들이 디스크 파일에서 그대로 읽힌다.
2. "소켓은 지급 경로로 못 싣는다" — **아니다.** 실을 수 있다.
   개수 칸(`TrItemValue +0x5E`)을 안 채웠던 것이다. **고쳐서
   실측으로 확인했다** (4절).

내구도의 자리도 나왔다. 레코드 `+0x28` · `+0x2C` 는 `TrItemValue`
`+0x134` · `+0x130` 에서 온다.

## 1. 디스크 파일이 그대로 읽힌다

`tools/rtti/disasm.py` 는 전부터 있었다. 게임 실행 파일에 그대로
겨누면 된다.

```
$ python tools/rtti/disasm.py "...\bin64\CrimsonDesert.exe" 0x1D9CBB0 20
0x01D9CBB0  mov  qword ptr [rsp + 8], rbx
0x01D9CBB5  mov  qword ptr [rsp + 0x10], rsi
...
```

세 함수 모두 정상 코드다 — 내구도 조회(`0x1D9CBB0`), 소켓
생성자(`0x20CE900`), 카메라 좌표 갱신(`0xA58540`). 마지막 것은
프롤로그가 `48 8B C4`(`mov rax,rsp`)로, 후킹할 때 실측한 것과 같다.

`STATUS §2.1` 의 "Denuvo 로 뒤섞여 있음" 은 **섹션 배치**가
뒤섞였다는 뜻이었다(실행 코드가 `.text` 가 아니라 `.rdata`·`.sbss`
에 있다). 코드가 암호화돼 있다는 뜻이 아니었는데, 그렇게 읽고
넘어갔다. **막혔다고 적기 전에 한 번 겨눠 봤어야 했다.**

Ghidra·IDA 는 이 기계에 없다. capstone(5.0.7) + `disasm.py` 가
디스어셈블러다. 파이썬은 `C:\Users\deepe\AppData\Local\Python\bin\python.exe`
에 있다 — `PATH` 앞쪽의 `WindowsApps\python.exe` 는 스토어 스텁이라
아무것도 안 하고 종료 코드 49 를 낸다.

### 실측으로 확인했다 (2026-09-03, 게임 실행 중)

`probe dumpimage` 로 실행 중 이미지를 떠서 디스크 파일과 견줬다.

```
실행 섹션 311.2 MB 중 다른 바이트 5,211개 (0.0016%)
내구도 조회 · 내구도 처리기 · 소켓 생성자 · 변환 함수 ·
지급 작업 · 아이템표 조회 · 카메라 갱신 — 7개 함수 전부 같다
```

**디스크 파일이 곧 실행 코드다.** Denuvo 가 손대는 것은 5KB 남짓
(제 훅과 검사)뿐이다. 그러니 정적 분석은 디스크 파일로 해도 된다.

한 가지는 다르다 - **섹션 이름이 실행 중에 바뀐다.**

| 디스크 | 실행 중 | RVA |
|---|---|---|
| `.rdata` | `.debug` | 0x00001000 |
| `.text1` | `.sbss` | 0x0496C000 |
| `.00cfg` | `.xpdata` | 0x05E68000 |
| `.text` | `.bss` | 0x06959000 |
| `.sbss` | `.shared` | 0x06B32000 |

RVA 와 크기는 같으므로 주소는 그대로 쓸 수 있다. 실행 중 이미지는
섹션이 12개로 더 많고 전체 크기도 349.4 MB 로 크다(디스크 344.5 MB).
**섹션 이름으로 무엇을 판단하면 안 된다** - 뜬 이미지냐 디스크
파일이냐에 따라 답이 달라진다.

### 덤프 도구 (`probe dumpimage`)

디스크 파일로 안 되는 것이 남아 있다 — 런타임에만 채워지는 전역과
vtable, 그리고 혹시 Denuvo 가 변형한 함수가 있는 경우의 대조다.
`probe dumpimage` 가 실행 중 프로세스의 이미지를 뜬다. 자세한 것은
`src/mem/image_dump.h`.

## 2. `TrItemValue` -> 인벤토리 레코드 변환 (RVA `0x2094050`)

지급의 모든 것이 이 함수에 있다. `rdi` 가 레코드, `r14` 가
`TrItemValue` 다.

| 레코드 | <- | TrItemValue | 비고 |
|---|---|---|---|
| `+0x00` u64 | | `+0x00` | 인스턴스 ID |
| `+0x08` u16 | | `+0x08` u32 | **키 -> 순번** 대응표(`0x6331358+0x68`) |
| `+0x0A` u16 | | `+0x0C` u16 | 담금질 (이미 쓰고 있다) |
| `+0x10` i64 | | `+0x10` | 개수 |
| `+0x28` u32 | | `+0x134` u32 | **원본 1 / 지급분 0** |
| `+0x2C` u32 | | `+0x130` u32 | **원본 1 / 지급분 0** |
| `+0x30` u64 | | `+0x138` | |
| `+0x38` u64 | | `+0x140` | 원본 45844 / 지급분 0 |
| `+0x40` u16 | | `+0x2A` u16 | 원본 0xFFFF / 지급분 0 |
| `+0x58` u16 | | `+0x1AE` i16 | **상한 있음** — 표 `+0x2E8` 로 자른다 |
| `+0x60` 배열 | | `+0x40`..`+0x5D` | **소켓 6바이트 x 5** |
| `+0x70` u8 | | `+0x5E` u8 | **소켓 개수** |
| `+0x78` 목록 | | `+0x64` 부터 0x10 간격 12개 | `+6` 이 음수면 멈춤 |
| `+0x88` u32 | | `+0x128` | |
| `+0x8C` u32 | | `+0x12C` | |
| `+0x98` u64 | | `+0x148` | 만든 시각 |
| `+0xA0`/`+0xA1` u8 | | `+0x1AC`/`+0x1AD` | |
| `+0xA8` 배열 | | `+0x180` 부터 0xC 간격 3개 | 6바이트 항목 |

`+0x28`·`+0x30`·`+0x38` 은 함수 앞부분에서 0·-1·0 으로 **초기화된
뒤 나중에 덮어쓴다.** 앞부분만 보고 "지급 경로가 0 으로 박는다" 고
읽으면 안 된다.

### 소켓 (RVA `0x2094324`)

```
movzx ebx, byte [r14+0x5E]        소켓 개수
mov   dword [rdi+0x68], 0
lea   edx, [r13+5]                5칸
lea   rcx, [rdi+0x60]
call  0x209A990                   레코드 소켓 배열 확보
mov   byte [rdi+0x70], bl         레코드 +0x70 = 개수

r8b = 0..4, r9 = 0,6,12,18,24:
    r8b >= [rdi+0x70]  -> 건너뜀 (오류 0x62C0B4C)
    [rdi+0x68] <= r8b  -> 건너뜀 (오류 0x62C0B48)
    ecx = dword [r14+0x40+r9]     TrItemValue 소켓 i 의 앞 4바이트
    dx  = word  [r14+0x44+r9]     뒤 2바이트
    rax = [rdi+0x60]
    dword [rax+r9]   = ecx
    word  [rax+r9+4] = dx
    byte  [rax+r9+4] = r8b        ★ 5번째 바이트는 슬롯 번호로 덮어쓴다
```

**6바이트를 그대로 옮긴다.** 다섯 번째 바이트만 슬롯 번호로
덮어쓴다 — export 한 원본이 `...00FF` · `...01FF` · `...02FF` 로
슬롯 번호를 들고 있던 이유가 이것이다.

`+0x40` 의 값은 **순번이지 아이템 키가 아니다.** 이 루프는 키->순번
변환을 하지 않는다.

작업 함수(`0x26A2600`)가 부르기 전에 거른다.

```
겹치는 아이템:  [r14+0x5E] 가 0 이어야 한다        (아니면 오류 0x62A5E14)
장비:           표 +0x238 >= [r14+0x5E]            (아니면 오류 0x62C0B48)
```

`표 +0x238` 은 우리가 이미 아는 소켓 개수다.

**그래서 "소켓은 지급 경로로 못 싣는다" 는 틀렸다.** 지급분에 소켓
줄이 없었던 것은 `+0x5E` 가 0 이라 루프가 한 칸도 안 돈 것이다.

## 3. `VaryEnduranceItemByCheatReq` (ID 2736)

처리기 `0x2792E70` 이 부르는 `0x1D9CBB0` 이 실제 작업이다.

```
f(rcx = [[세션액터+0x68]+0x38],   인벤토리/장비 컴포넌트
  rdx = &결과코드,
  r8w = 대상 핸들,
  r9w = 개수)
```

처리기는 결과 코드를 받아 알림 메시지(`0x3F5`)를 만들어 보낸다.
인자 두 개는 **값이 아니라 (대상, 개수)** 다.

### 0xD0 간격 표의 정체

```
mov  rax, [r12+0x80]
mov  rbx, [rax+8]         배열
mov  eax, [rax+0x10]      개수
imul rcx, rax, 0xD0
add  rcx, rbx             끝
loop:
  cmp si, word [rbx+0xC8]   ★ 검색 키
  je  찾음
  add rbx, 0xD0
```

원소 안쪽이 **인벤토리 레코드와 같다** — `+0x08` u16 순번(0xFFFF 면
빈 칸), `+0x10` i64 개수, `lea rcx,[rbx+8]; call 0x317900` 로 아이템
표를 찾는다. 레코드는 0xC8 이고 여기는 0xD0 이므로,
**`{레코드(0xC8), u16 핸들}` 의 배열**이다. 검색 키는 그 핸들이다.

**그래서 내구도 치트에 순번(6438)을 넣었을 때 아무 일도 없었다.**
그 자리는 순번이 아니라 `+0xC8` 의 핸들이다.

### 아이템 표의 새 필드

| 오프셋 | 크기 | 쓰임 |
|---|---|---|
| `+0x1FC` | u8 | 0 이 아니면 소진 시 거부 |
| `+0x2E8` | i16 | 레코드 `+0x58` 의 상한 |
| `+0x3F0` | u8 | 지급 작업 함수의 분기 |
| `+0x400` | u16 | 0xFFFF 면 이 검사를 건너뛴다 |

`0x1D9CBB0` 의 거부 조건은 셋이 모두 참일 때다.

```
표 +0x400 != 0xFFFF  &&  레코드 +0x40 <= 0  &&  표 +0x1FC != 0
  -> 오류 0x36
```

`0x317900` 은 순번 -> 아이템 표 레코드다. 전역 `0x6331358` 의
`+0x58` 배열을 순번으로 색인하고 `[rbx+8]` 로 범위를 검사한다.

## 4. 소켓 지급 - 실측 확인 (2026-09-03)

정적으로 읽은 대로 됐다. 보관함에서 꺼낸 지급분의 소켓이 원본과
**바이트 단위로 같다**.

```
[ 54] 담금질 1  ID 1000085  군주의 검      <- 원본
      소켓[0] 3364 바람 가르기 (24 0D FF FF 00 FF)
      소켓[1] 3214 파괴 I      (8E 0C FF FF 01 FF)
      소켓[2] 3216 질풍 I      (90 0C FF FF 02 FF)
[ 87] 담금질 1  ID 1000248  군주의 검      <- 지급분
      소켓[0] 3364 바람 가르기 (24 0D FF FF 00 FF)
      소켓[1] 3214 파괴 I      (8E 0C FF FF 01 FF)
      소켓[2] 3216 질풍 I      (90 0C FF FF 02 FF)
```

학살의 기사 판금 장갑(소켓 2개)도 같다. **화면에서도 보석 3개가
툴팁에 뜬다.** 모드 로그도 맞는다.

```
인벤토리 지급: 키 200914 개수 1 담금질 1 소켓 3
인벤토리 지급: 키 121054 개수 1 담금질 2 소켓 2
```

**"소켓은 지급 경로로 못 싣는다" 가 뒤집혔다.** 개수 칸(`+0x5E`)을
안 채워 복사 루프가 한 칸도 안 돌았던 것뿐이다.

몇 분 뒤 다시 읽어도 그대로다 - **게임이 되쓰지 않는다.** 앞
세션에 `poke` 로 레코드에 직접 쓴 소켓은 되돌아왔는데, 게임의
생성 경로로 넣은 것은 남는다. 담금질 때와 같은 갈림이다.

## 5. 아이템 표 `_maxEndurance` - 실측

**군주의 검은 내구도가 없다** (`_maxEndurance` = 0xFFFF). 6,810개
중 내구도를 가진 것은 **122개**뿐이고 전부 "폭주하는 ~" 류(내구도
100)다. 무기 · 방어구는 내구도 시스템 밖이다.

그러니 지급분의 "수리 불가" 는 내구도 때문이 아니다.

## 6. 원본과 지급분의 남은 차이

레코드를 바이트로 견줬다. 앞 세션 기록과 다르다.

| 칸 | 원본 | 지급분 | 비고 |
|---|---|---|---|
| `+0x0A` 담금질 | 1 | 1 | 실린다 |
| `+0x70` 소켓 수 | 3 | 3 | 실린다 (이번에) |
| `+0x28` | 1 | 0 | **아직 안 실린다** |
| `+0x2C` | 1 | 0 | 게임이 나중에 채운다 |
| `+0x38` | 176718 | 0 | 게임이 나중에 채운다 |
| `+0x40` | 0xFFFF | 0 | **현재 내구도** (10절) |

`+0x2C` · `+0x38` · `+0x40` 은 **저장 · 재시작을 거치면 채워진다.**
지난 세션에 지급한 것들(칸 80 · 81 · 82 · 84)은 이번에 켜니 전부
`+0x2C` 1, `+0x38` 176718, `+0x40` 0xFFFF 로 원본과 같아졌고, 방금
지급한 것(칸 87 · 91)만 0 이다. 시간이 지나서가 아니라 세이브를
한 바퀴 돌아야 채워진다.

앞 세션이 "지급분은 0 이라 안 실린다" 고 적은 것은 갓 지급한 것을
본 탓이다. **지급 직후의 레코드로 판단하면 안 된다.**

`+0x38` 은 아이템별 값이 아니다 - 게임을 다시 켜니 모든 아이템이
65069 에서 176718 로 함께 바뀌었다. 전역 카운터 · 시각으로 보인다.

`+0x28` 만 지급분이 0 으로 남는다. 다만 **정상 아이템 507개 중
200개도 0** 이다(화살 · 열쇠 · 늑대의 한손검). "지급분 표식" 이
아니므로 무엇인지 더 봐야 한다.

## 7. `0xD0` 배열의 정체 - 장비 슬롯 (실측)

세션에서 따라가 확인했다. `[[세션+0x68]+0x38]` 이
**`pa::ServerEquipSlotActorComponent`** 이고, 그 `+0x80` 이 가리키는
곳이 `{+0x08 배열, +0x10 개수}` 다. 실측 **18칸**.

```
칸  인스턴스ID  순번   담금질  핸들+0xC8  이름
 0   1000193   6424    0       0      검은 운명
 1   1000194   6384    0       1      데메니스 친위대 방패
 4   1000183   5568    3       4      차가운 어둠의 판금 갑옷
17   2198      5829    0      20      섭리의 팔찌
```

**`+0xC8` 핸들은 장비 슬롯 번호다** (0..16, 20). 순번도 인스턴스
ID 도 아니다. 그러니 `VaryEnduranceItemByCheatReq` 의 첫 u16 은
**장비 슬롯 번호**이고, 이 치트는 **장착 중인 것에만** 듣는다.

### 그런데 장착한 것에 내구도가 없다

장착 중인 17개를 아이템 표와 대조했다. **`_maxEndurance` 가
0xFFFF 아닌 것이 하나도 없다.**

```
검은 운명 · 데메니스 친위대 방패 · 에세리온 활 · 차가운 어둠의
판금 갑옷 · 타리브 천 장갑 · 곡괭이 ... 전부 소켓 · 담금질만 있다
```

**내구도 치트가 아무 일도 안 한 이유가 이것이다.** 슬롯 번호를
바르게 넣어도 대상에 내구도가 없다. 순번 6438 을 넣은 것이 틀린
것도 맞지만, 바로 넣었어도 결과는 같았을 것이다.

내구도를 가진 122개는 전부 "폭주하는 ~" 류(내구도 100)다. 그것을
장착할 수 있는 자리가 있는지부터 봐야 이 치트를 시험할 수 있다.

## 8. "수리 불가" 는 아이템 종류의 성질이다 (실측)

지급분에 "수리 불가" 가 붙는 것이 지급 탓인 줄 알았다. 아이템 표를
직접 읽어 보니 아니다.

```
                _maxEndurance(+0x400)   _repairDataList(+0x408)
군주의 검         0xFFFF                  ptr 0, 개수 0
늑대의 한손검      0xFFFF                  ptr 0, 개수 0
검은 운명         0xFFFF                  ptr 0, 개수 0
```

**셋 다 내구도가 없고 수리 데이터도 비어 있다.** 여기까지는 사실이다.

여기서 "늑대의 한손검과 검은 운명은 원본이니 원본에도 뱃지가 붙는
것" 이라고 적었는데 **틀렸다.** 사용자가 바로잡았다 - 그 둘도 지급으로
넣은 것이다. 대조군이 아니었다. 결론을 물린다.

지금 확실한 것은 이것뿐이다.

- 군주의 검은 **종류 자체가** 내구도도 수리 데이터도 없다
- 그러므로 지급이 무엇을 빠뜨려서 "수리 불가" 가 붙는 것은
  **아닐 가능성이 크다** - 지급으로 채울 수 있는 인스턴스 칸에
  수리 관련이 없다
- 다만 **한 번도 지급한 적 없는 장비로 대조하지 못했다**

**판매가는 지급 탓이 아니었다** - 소켓과 담금질이 값을 올리는데
그때 지급분은 둘 다 없었다. 소켓 3개 + 담금질 1 을 실은 지금은
**11.06** 이 나온다(화면 확인).

### 수리 데이터는 아무 아이템에도 없다 (실측)

```
probe items 7000
  수리 데이터를 가진 종류   0 / 6810
  내구도를 가진 종류      122 / 6810
```

오프셋이 맞는지 따로 확인했다. 폭주하는 파괴(내구도 100)의 표
`+0x400` 이 `64 00` = 100 이고, 같은 레코드의 `+0x408`(ptr) ·
`+0x410`(개수)은 0 이다. **내구도가 있는 아이템조차 수리 데이터가
없다.**

그러니 `_repairDataList` 가 뱃지를 가르는 것은 아니다 - 그것이라면
6,810개 전부에 붙어야 한다.

### 내구도 122개의 정체

"폭주하는 ~" 류만이 아니었다. 도구 · 장치 · 깃발 계열이다.

```
내구도 100  유황 방독면 · 강궁 장갑 · 화염 걸음 신발 · 농업용 분무기
내구도  50  벼락 양손망치 · 전기 창 · 풍력 방패 · 공기 손대포
내구도  30  미로숲의 한손검 · 벌집 몽둥이 · 불꽃 창
내구도  20  각종 깃발 77개
내구도  15  마법 낫 · 전자극 화염방사기 · 수면침봉
내구도   1  종말의 도끼
```

**일반 장비(군주의 검 등)만 내구도가 없다.** 이 게임의 내구도는
장치성 무기와 소모형 도구에만 걸려 있다.

### 남은 가설과 그것을 가릴 시험

뱃지가 `_maxEndurance == 0xFFFF` 로 갈린다면(= 내구도가 없으니
수리할 것도 없다) 일반 장비에는 전부 붙고 원본이든 지급분이든
같다.

**시험은 하나면 된다.** 내구도가 있는 장비를 **지급으로** 넣어
보는 것이다. `미로숲의 한손검`(키 1002261, 내구도 30) 을 지급해
툴팁에 "수리 불가" 가 **안 붙으면**, 뱃지는 종류가 가르는 것이고
지급과 무관하다는 것이 한 번에 증명된다. 원본 대조군을 구할
필요가 없다.

### 남은 `+0x28` 은 무엇인가

원본과 지급분에서 유일하게 갈리는 칸이다. 다만 정상 아이템 507개
중 **200개도 0** 이다.

```
학살의 기사 판금 장갑  담금질 2 소켓 2
  ID 1000001  +28 1   <- 원본
  ID 1000249  +28 0   <- 지급분 (나머지 칸은 전부 같다)

늑대의 한손검 ID 2183  +28 0   <- 원본인데 0
회색늑대 한손검 ID 1000051  +28 1
```

원본인데 0 인 것도, 같은 아이템의 원본이 1 인 것도 있다. 지급
여부와 무관한 무엇이다. 화면에 드러나는 차이가 없으므로 급하지 않다.

## 9. `+0x40` 은 현재 내구도다 (실측으로 확정)

가설이 틀렸다. "뱃지는 `_maxEndurance == 0xFFFF` 로 갈린다" 고
적었는데, 내구도가 있는 장비(미로숲의 한손검, 최대 30)를 지급해
보니 **뱃지가 그대로 붙었다.** 대신 진짜 원인이 화면에 나왔다.

```
미로숲의 한손검
  내구도   0/30      (빨간색)
  공격력   -11
  판매가   18
```

레코드를 보니 `+0x40` 이 **0** 이다.

```
[55] 순번 6575  키 1002261  ID 1000261  미로숲의 한손검
     +40 0
```

**`레코드 +0x40` (u16) = 현재 내구도**이고 화면의 `0/30` 과 정확히
맞는다. 변환 함수가 `TrItemValue +0x2A` 에서 옮기는 그 칸이다.

```
movzx eax, word [r14+0x2A]
mov   word [rdi+0x40], ax
```

지급이 이 칸을 안 채우니 **부서진 채로 나온다.** 이 게임은 아무
아이템도 수리 데이터가 없으므로(0 / 6,810) 되돌릴 방법도 없다.

내구도가 없는 아이템(군주의 검 등)은 0 으로 두면 게임이 저장 ·
재시작을 거치며 0xFFFF 로 채운다. 그래서 앞에서 "게임이 나중에
채운다" 로 보였던 것이다 - 그쪽만 보고 칸의 뜻을 놓쳤다.

### 고쳤다 - 실측 확인

`GiveExtras::endurance` -> `TrItemValue +0x2A`. 두 지급 경로가
아이템 표의 `_maxEndurance` 를 보고 가득 채워 보낸다(내구도가
없는 아이템은 0).

같은 아이템을 다시 지급해 세 곳이 다 맞는 것을 봤다.

```
로그    인벤토리 지급: 키 1002261 ... 내구도 30
메모리  [55] ID 1000261 미로숲의 한손검   +40 30
화면    내구도 30/30 · 공격력 22 +10   (전에는 0/30 · -11)
```

판매가는 18 -> 1.88 로 바뀌었다. 단위가 바뀐 것으로 보인다
(동화 -> 은화). 확인하지 않았다.

"수리 불가" 뱃지는 그대로다. 표에 수리 데이터가 아예 없으니
(0 / 6,810) 이 빌드에서는 무엇도 수리할 수 없고, 지급과 무관하다.

## 10. 다음에 할 것

1. **`+0x28`** 이 무엇인지. `TrItemValue +0x134` 에서 온다.
2. **`[컴포넌트+0x80]` 배열.** 0xD0 간격으로 훑어 `+0xC8` 핸들이
   무엇인지 본다. 그 핸들을 내구도 치트에 넣으면 반응이 있어야 한다.
3. ~~소켓의 첫 u16 을 아이템 키로 되돌리는 것~~ **했다.** 모드가
   배경에서 키 -> 순번 대응표를 읽어 두고(`discover_item_ids`), 지급할
   때 보관함이 든 보석 키로 순번을 다시 찾아 6바이트의 앞 두 칸을
   덮어쓴다. 못 찾으면 원본 바이트를 그대로 둔다.

   이 빌드에서는 결과가 같다 - 표에서 찾은 순번(3364 · 3214 · 3216)이
   원본 바이트(`24 0D` · `8E 0C` · `90 0C`)와 정확히 맞는다. 게임이
   갱신되면 그때부터 값이 갈린다.
