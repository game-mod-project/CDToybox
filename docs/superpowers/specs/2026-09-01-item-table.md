# 아이템 표 구조

**날짜:** 2026-09-01
**방법:** 실행 중인 게임을 읽기만 해서 확인.
**앞 문서:** `2026-09-01-localization-lookup.md`
**상태:** **동작한다.** `cdtb_probe items` 로 6,810개를 이름까지 뽑았다.

## 요약

아이템 표를 통째로 걷는다. 6,810개 중 **6,738개(98.9%)의 이름이
풀린다.**

```
$ cdtb_probe items 20
매니저   0x3E37DD45A00
아이템   6810개

키        이름키            이름
2200       9448928051312        편전
50001      214752659767408      화살
1002557    4305949527375984     지속 보급 화살
50003      214761249702000      독 화살
1000070    4295267943710832     수면 화살
50011      214795609440368      효시
1001321    4300640947798128     폭발 화살
1001316    4300619472961648     불화살
1001315    4300615177994352     전격 화살
1001314    4300610883027056     냉기 화살
```

이름이 의미 단위로 이어진다 — 화살 계열, 묶음, 포탄 순이다. 표의
순서가 곧 개발자가 넣은 순서로 보인다.

## 1. 매니저 (`pa::ItemInfoManager`)

RTTI 로 찾는다. 실측에서 살아 있는 인스턴스는 하나였다.

```
+0x00  vtable        0x14511D768
+0x28  색인 표       (u32 키, u32 용도미상) 쌍의 배열
+0x30  u32 개수      6810
+0x34  u32 용량      6810
+0x58  레코드 포인터 배열 (8바이트 항목)
```

`+0x38`·`+0x40`·`+0x68`·`+0x70` 에도 (u32, 6810) 꼴의 쌍이 더 있고
`+0x48`·`+0x50`·`+0x60`·`+0x78`·`+0x80`·`+0x88` 이 다른 배열을
가리킨다. 이번 목적에는 필요 없어 파지 않았다.

## 2. 레코드 (0x500 바이트)

`+0x58` 은 **포인터 배열**이다. 가리키는 레코드들이 0x500 간격으로
이어져 있다 — 배열 자체가 0x500 간격인 것이 아니다.

```
recs[0] -> 0x3E3C8C92300
recs[1] -> 0x3E3C8C92800   (+0x500)
recs[2] -> 0x3E3C8C92D00   (+0x500)
```

레코드에서 이번에 쓰는 칸은 둘이다.

```
+0x00  u32 키
+0x28  u64 이름 현지화 키
```

**이름 키를 조립하지 않는다.** 앞 문서에서 `(키 << 32) | 0x70` 임을
확인했지만, 레코드가 게임 자신의 값을 `+0x28` 에 그대로 들고 있다.

```
레코드[0] +0x28  70 00 00 00 98 08 00 00  ->  0x0000089800000070
레코드[1] +0x28  70 00 00 00 51 C3 00 00  ->  0x0000C35100000070
```

조립식은 맞지만, 게임이 준 값을 쓰는 편이 필드 번호가 다른 항목이
섞여 있어도 견딘다.

## 3. 후보 검증

RTTI 후보를 그대로 믿지 않는다. 카메라에서 vtable 값을 우연히 담은
메모리를 집어 11회 어긋난 적이 있다.

**색인 표의 첫 키와 첫 레코드의 키가 같은지 본다.** 두 배열이 서로를
확인해 주므로 우연히 맞기 어렵다. 여기에 개수 검사(0 이 아니고
2^20 이하)를 더한다 — 후보를 잘못 집으면 개수가 쓰레기값이 되고,
그대로 믿고 할당하면 메모리를 통째로 먹는다.

## 4. 이름이 안 풀리는 72개

키가 이렇게 생겼다.

```
200997  200998  200999  210998  250999  13800
620911  620912  1000019  1000267  1000675  1001071 ...
```

`200997`~`200999` 처럼 연속이고 `250999`·`620911`~`620912` 같이
묶여 있다. 개발용·미사용 항목으로 보이지만 **확인한 것은 아니다.**
표에는 있고 현지화 표에는 없다는 사실만 확인했다.

## 5. 색인 표의 두 번째 u32 (미해결)

```
(2200, 0)  (50001, 690)  (1002557, 1374)  (50003, 2061)  (1000070, 2756)
...
(끝) (0x07D088B6, 3940573)
```

0 에서 시작해 항목마다 640~700 씩 단조 증가하고 끝에서 3,940,573 이
된다. 레코드 간격(0x500 = 1280)과 맞지 않으므로 레코드 오프셋은
아니다. 누적 바이트 오프셋으로 보이나 **무엇의 오프셋인지 모른다.**

레코드 포인터 배열을 직접 걸으면 필요 없으므로 더 파지 않았다.

키가 정렬돼 있지 않다는 것도 확인했다(2200, 50001, 1002557, 50003…).
이분 탐색용 표가 아니라 레코드 배열과 나란한 표다. 키가 u32 범위를
쓰는 것도 확인했다 — 끝쪽에 `0x07D088B6` 이 있다. 클래스 이름의
`StaticInfoManager2<..., G>` 에서 `G`(unsigned short)는 이 표의 키
폭이 아니다.

## 6. argv 인코딩 함정

`items find 화살` 이 0건으로 나왔다. 게임 문자열 풀은 UTF-8 인데
`argv` 는 시스템 ANSI 코드페이지로 온다 — 이 기계의 ACP 는 **949** 다.
한글은 절대 맞지 않는다.

비교 전에 `MultiByteToWideChar(CP_ACP)` → `WideCharToMultiByte(CP_UTF8)`
로 옮긴다. 옮긴 뒤 `화살` 검색이 정상 동작한다.

찾다가 알게 된 것: 이 게임의 회복 아이템은 **`비약`** 이다. `물약` 은
0건이다.

## 7. 도구

```
cdtb_probe items [최대]         키 + 이름 나열 (기본 40개)
cdtb_probe items find <문자열>  이름에 그 문자열이 든 것만
```

구현은 `src/game/items.cpp`. 모드와 probe 가 같이 쓰도록 `src/game/`
에 두었다.
