# 소환 가드 `kCallSiteRva` 재도출 — 2944

**날짜:** 2026-09-20
**대상:** Crimson Desert Enhanced, exe **1.0.0.2944**
**앞 편:** `2026-09-18-game-update-2944.md` §5 (이 편이 그 절을 **닫는다**)

---

## 0. 무엇이 안 됐나

2944 갱신 뒤 소환 널 가드가 안 걸린다.

```
WARN  소환 가드: 0x2AD7238 가 call 이 아니다 (0x0F) - 설치 안 함
```

이 가드는 **종을 바꾼 동반자를 소환할 때 죽는 것**을 막는다. 명부 레코드의
종(`+0x20`)을 제자리에서 바꾸면 게임의 종류별 색인이 안 따라와 "번호 → 레코드"
조회가 널을 내는데, 게임이 그 널을 **한 자리에서만** 안 막는다
(`TROUBLESHOOTING.md` §1.3 · `STATUS.md` §1.10).

앞 편은 이렇게 닫았다:

> 2850 의 지문 `mov rcx,rax ; call 조회 ; mov edi,0xC` 가 새 exe 에 **0곳**이다.
> … 소환 작업 함수(0x2B9EB50) 안의 **유일한** 조회 호출(+0x1E7)도 그렇게
> 가드돼 있다. **2944 에서 이 가드가 필요 없어졌을 수 있으나 정적으로는 단정
> 못 한다** — 크래시가 재현되면 그 자리를 라이브로 잡아 넣는다.

---

## 1. 앞 조사가 빗나간 이유

**지문을 명령 배열(`mov rcx,rax ; call ; mov edi,0xC`)로 잡았다.** 그건
컴파일러가 언제든 바꾼다 — 실제로 2944 에서 0곳이 됐다.

그리고 **엉뚱한 함수를 봤다.** 앞 조사는 "소환 작업 함수 `0x2B9EB50`" 안의
조회 호출을 보고 "가드돼 있다" 고 했는데, 죽는 자리는 그 함수가 아니다.

---

## 2. 바꾼 지문 — 명령 배열이 아니라 **결함 그 자체**

우리가 찾는 것은 *"조회를 부르고 그 반환값을 널 검사 없이 역참조하는 자리"* 다.
그 결함의 실물이 이미 문서에 있었다(`spawnguard.h`, 2760 실측):

```
0x2AD520F  cmp qword ptr [rax+0x28], -1     <- 여기서 죽었다
```

`cmp qword ptr [rax+0x28], -1` 의 바이트는 **`48 83 78 28 FF`** 다. 이건
컴파일러가 바꿀 수 없다 — 구조체 오프셋과 비교값이 코드의 의미이기 때문이다.

### 조회 호출자를 전수로 분류했다

`call rel32` 로 `kLookupRva`(0x2146110)를 부르는 자리를 실행 섹션 전량에서
모아(**273곳**) 뒤 12명령을 보고 갈랐다.

| 분류 | 개수 |
|---|---|
| 막힘 — `test rax,rax` / `cmov` 가 먼저 온다 | **266** |
| **널 검사 없이 `[rax+…]` 역참조** | **6** |
| 그 밖(흐름이 갈림) | 1 |

여섯 중 **`[rax+0x28]` 을 만지는 것은 하나**다.

```
0x02149135  mov r13, rax ; mov [rax+0xb0], esi ; movzx ecx, word [rax+0x20] …
0x0214DA26  mov byte [rax+0xe5], 0 …
0x0214DA80  mov byte [rax+0xe5], 1 …
0x0214DB09  mov byte [rax+0xe5], 0 …
0x02B8DD36  cmp qword [rax+0x28], -1 ; je … ; cmp word [rax+0x20], 0xffff   <<<
0x02BC10BB  mov rbx, rax ; … vmovsd [rax+0xc8], xmm0
```

`0x02B8DD36` 은 `spawnguard.cpp` 가 확인하는 **표식 둘**(`+0x28 == -1` ·
`+0x20 == 0xFFFF`)을 연달아 검사한다. 다른 다섯은 그 모양이 아니다.

---

## 3. 자리 확정 — `0x02B8DD36`

```
0x02B8DD2E  lea  rcx, [r12 + 0x18]
0x02B8DD33  mov  rdx, rbx
0x02B8DD36  call 0x2146110                   E8 D5 83 5B FF
0x02B8DD3B  cmp  qword ptr [rax + 0x28], -1  48 83 78 28 FF
0x02B8DD40  je   0x2B8DE32
0x02B8DD46  mov  ecx, 0xffff
0x02B8DD4B  cmp  word ptr [rax + 0x20], cx
0x02B8DD4F  je   0x2B8DE32
```

| 확인 | 결과 |
|---|---|
| 첫 바이트 | `E8` (call) ✓ |
| call 대상 | `0x2146110` = `kLookupRva` ✓ |
| 바로 뒤 | 2760 크래시 명령 그대로 ✓ |
| 그 뒤 | 빈 레코드 표식 둘째(`+0x20 == 0xFFFF`)까지 ✓ |
| 패치 폭 | `E8 rel32` 의 rel32 만 바꾼다 — 길이·opcode 불변이라 창 문제가 없다 |

### 형제 자리가 같은 이웃에 있다 (결정적 확증)

`spawnguard.h` 는 2760 에서 **게임이 스스로 막는 형제 자리**를 적어 두었다.
그것이 2944 에도 **레지스터까지 같은 모양**으로 있다.

| | 2760 (문서) | 2944 (실측) |
|---|---|---|
| 조회 호출 | `0x2ABD8EB` | `0x02B89E36` |
| 빈 레코드 | `lea rbx,[0x6BB3F70]` | `lea rbx,[rip+…]` → `0x6CF2F70` ✓ |
| 가드 | `test rax,rax ; cmovne rbx,rax` | 동일 ✓ |
| 뒤따르는 검사 | — | `cmp qword [rbx+0x28], -1` ← 우리 자리의 가드판 |

### 사슬

```
0x2B89CF0 (호출자 함수, 12,753 B — 형제 자리 보유)
   -> 0x2B8C823
      -> 0x2B8D2F0 (4,289 B — 부르는 곳이 **한 곳뿐**)
         -> 0x2B8DD36  우리 자리
```

2760 에서는 호출자 `0x2ABD850` 이 곧장 `0x2AD4F70` 을 불렀다. 2944 는 중간에
한 단계가 더 있을 뿐 **구조가 같다.**

### 빌드별 이동

```
0x2AD51F8 (2760)  ->  0x2AD7238 (2850)  ->  0x2B8DD36 (2944)
                          +0x2040              +0xB6AFE
```

`+0xB6AFE` 는 같은 갱신의 다른 폭들(`+0x7B1E0` · `+0xB9160` · `+0x825E40`)과
비슷하지만 **같지 않다** — 폭을 빌려 쓰면 안 된다는 기록 그대로다
(`TROUBLESHOOTING.md` §5.1).

## 4. 설치 판정을 **꼬리까지** 넓혔다

전에는 `E8` 인지와 call 대상만 봤다. 그러면 **게임이 이미 막아 둔 266곳도 전부
통과한다** — 자리가 낡아 그중 하나에 떨어지면 멀쩡한 자리를 우리 썽크로 돌리게
된다. 얻는 것 없이 위험만 보탠다.

그래서 뒤 5바이트(`48 83 78 28 FF`)를 함께 본다. 실측:

| 지문 | 곳 |
|---|---|
| `call <조회>` | 273 |
| `call <조회>` + 뒤가 `cmp qword [rax+0x28],-1` | **1** |
| 파일 397MB 전량(섹션 무관)에서 같은 10바이트 지문 | **1** |

`TROUBLESHOOTING.md` §1.5 의 *"확인 폭 ≠ 쓰기 폭"* 을 이 가드에도 적용한 것이다.

판정은 순수 함수 `spawnguard_check_site()` 로 뺐고 거부 사유를 넷으로 나눈다
(`kNotCall` · `kWrongTarget` · `kGuarded` · `kShort`). `kGuarded` 는 새 사유다 —
**"조회는 맞는데 이미 막힌 자리"** 를 조용히 통과시키지 않고 로그에 낸다.

  시험이 봐야 하는데 `spawnguard.cpp` 를 `cdtb_tests` 에 더하면 **링크 배치가
  바뀌어** 워치포인트 자체 시험이 죽은 전례가 있어서다(`TROUBLESHOOTING.md` §1.5).
  배포 빌드에서 그 시험이 여전히 통과하는 것을 확인했다.
- `kCallSiteRva` `0x2AD7238` → **`0x2B8DD36`**.
- 설치 판정에 꼬리 검사를 더했다.
- 시험 6개(전부 RED 확인 후 GREEN — 자리를 옛 값으로 되돌리면 3건이 실제로

## 6. 게임 확인 — **됐다 (2026-09-20)**

배포해 실제로 돌렸다(exe 1.0.0.2944, 18:36~18:50).

```
18:36:43  소환 가드 설치 - 0x2B8DD36 의 조회가 널이면 빈 레코드로 대신한다 (썽크 0x13FF80000)
18:46:11  쓰기 동반자 종 번호 1001225: 행 6591(Animal_Crow_Wild_30029) -> 행 7034(Riding_Bear_1000)
18:46:25  동반자 캡처 [스폰선택] ID 3069
18:49:42  고용 작업: 핸들 0xB0100B6F 플래그 0 -> 코드 0 (성공)
18:49:42  획득 응답: 새 동반자 번호 1001540
```

| 확인 | 결과 |
|---|---|
| 설치 | 뜬다. `소환 가드: … 설치 안 함` 경고가 **사라졌다** |
| 종 교체 → 소환 | **크래시 없음** |
| 그 뒤 획득(2959)까지 | 코드 0 성공 |
| 새 크래시 파일 | 없음(마지막 기록이 이번 실행보다 앞) |
| ERROR | 0 |

설치가 떴다는 것은 판정 넷이 **라이브 메모리에서** 통과했다는 뜻이다 - `E8` ·
대상 == 조회 · 꼬리 == `cmp [rax+0x28],-1` · 빈 레코드 표식(`+0x28 == -1`,
`+0x20 == 0xFFFF`).

> **한계.** 가드는 호출마다 로그를 남기지 않아 **이번 판에 널 갈래가 실제로
> 탔는지는 못 쟀다.** 말할 수 있는 선은 *"가드가 걸렸고 죽던 절차가 안 죽었다"*
> 까지다 - 2760·2850 때와 같은 기준이다. 더 굳히려면 썽크에 1회성 로그를
> 넣어야 한다.

죽었으면 볼 곳: `bin64/CDToybox.crash.txt` 의 RVA. `0x2B8DD3B` 면 썽크가 안
걸린 것이고, 다른 자리면 §2 의 나머지 다섯 중 하나일 수 있다.

> **덧붙여** — 앞 편은 *"2944 에서는 이 가드가 필요 없어졌을 수 있다"* 고 적었다.
> 이번 조사로 **그건 아니다**: 죽는 자리는 그대로 있고 널 검사도 여전히 없다.
> 앞 조사가 본 `0x2B9EB50` 은 다른 함수였다.
