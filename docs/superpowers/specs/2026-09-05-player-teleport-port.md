# 플레이어 치트(B-1) · 텔레포트(B-5) 이식 설계

사용자 선택 기능 중 B-9(Max Refine)·B-7(가방)은 구현 완료. 이 문서는 남은
**B-1 플레이어 치트**와 **B-5 텔레포트**의 리버스 근거와 계획.

출처: XeTrinityz(=ReXooGen)/Trinity (MIT). CT(Nexus 3209) Lua 실측 참고.

---

## B-1 플레이어 치트 (Godmode · 무한 자원 · 스탯)

### 스탯 블록 구조 (CT 실측, 확정)

한 "status block" 이 체력·스태미나·정신력의 현재/최대 쌍을 담는다. 값은 전부
**x1000** (시트 1650 → 메모리 1650000). 쌍은 0x10 간격, 항목은 0x90 그리드.

```
블록 r 기준:
  체력    cur r+0x08   max r+0x18     (CDR.hpOff = 0x08 로 확정. 0x518 은 그들이 정정한 오답)
  스태미나 cur r+0x6C8  max r+0x6D8
  정신력  cur r+0x758  max r+0x768
```

### 블록 판별 (_looks) — 적/NPC 배제의 핵심

```
_pair(r,cur,max): mx=i32(r+max); 0<mx<=50,000,000; cu=i32(r+cur); 0<=cu<=mx.
_looks(r): _pair(r,0x6C8,0x6D8) AND _pair(r,0x758,0x768)
           (스태미나 + 정신력 쌍을 둘 다 요구 → 적은 정신력 풀이 없어 걸러진다)
```
- 캐릭터 전환 시 블록이 바뀐다(참고 모드 버그: 이전 몸에 계속 쓰던 것). 매 틱
  캐시 블록에 _looks 재확인, 실패면 재해석.
- ⚠ Max Combat Stats/속도류는 "아무 액터"에서 닿는 스탯 컨테이너를 건드려
  **주변 NPC까지 강화**된 전례. 반드시 cplayer 로 좁힐 것.

### cplayer → 스탯 블록 도달 (우리 방식)

CT 는 asm 훅("Player base hook")으로 런타임에 캡처하지만, 우리는 구조 검색으로
간다(훅 불필요, 패치 내성):
1. cplayer = 우리 `equip_player_actor()` (G 체인, 이미 있음).
2. cplayer 및 그 서브(+0x68 등)에서 **8바이트 포인터를 0..0x800 범위로 훑어**,
   가리키는 대상 p 가 `_looks(p)` 를 만족하는 첫 포인터를 스탯 블록으로 채택.
   (equip 컴포넌트를 백참조로 찾던 것과 같은 결.)
3. 채택 후 캐시. 매 틱 _looks 재확인.

### 토글 (freeze 루프 — 분석 스레드)

- **Godmode**: 매 틱 `i32(r+0x08) = i32(r+0x18)` (체력 현재=최대).
- **무한 스태미나**: `r+0x6C8 = r+0x6D8`.
- **무한 정신력**: `r+0x758 = r+0x768`.
- **스탯 에디터**(선택): 블록 덤프를 x1000 로 표시·편집. (나중에)
- 쓰기는 SEH. 게임에서 검증 전에는 기본 OFF.

### 검증 순서 (게임 켠 채, 쓰기 전 필수)

1. cplayer 유효, 구조 검색이 _looks 블록을 유일하게 찾는지(probe 로 덤프).
2. 세 쌍의 값이 시트 x1000 과 맞는지.
3. 캐릭터 전환 시 블록이 따라 바뀌는지.
4. **버릴 세이브**에서 Godmode 만 켜 체력 고정 확인 → 스태미나/정신력.

## B-5 텔레포트 (맵 마커) — 참고자료 빈약, 깊은 리버스 필요

**문제:** CT Lua 에는 위치 쓰기/월드 원점 오프셋이 **없다**. 텔레포트·라이브
염색 연구는 ASI 바이너리(`CrimsonInvEditor.asi`)에만 들어 있고 출처는
ReXooGen/Trinity MIT. 즉 CT 를 실측 참고하던 방식이 안 통한다.

ASI changelog 에서 건진 사실(구현 근거는 아님):
- 월드 원점을 **라이브로 읽는다**(고정 주소 금지 - 1.17 에서 이동). 마커 좌표↔
  월드 좌표 변환이 지역마다 달라, 단일 측정 캘리브레이션은 그 지점에서만 맞음.
  → 원점 상대로 캘리브레이션을 들고 점프 후 스트리밍 대기 → 새 shift 읽어 자기보정.
- 우리가 이미 읽는 것: PlayerCameraComponent+0x360 = 카메라 초점 좌표
  (`read_world_position`, grant_panel 의 camera_position). 이건 카메라지 플레이어
  발밑이 아니다.

**필요 리버스(다음 세션 규모):**
1. 플레이어 액터의 **위치 필드**(월드 좌표 write 지점). 카메라 초점과 별개.
2. 맵 마커(빨간 핀) 좌표 읽는 곳.
3. 월드 원점(라이브) + map↔world 변환.
4. 텔레포트 = 플레이어 위치에 (마커→월드) 좌표 write. 스트리밍 안정 대기.

접근: (a) ASI 를 정적 디스어셈블해 오프셋/AOB 추출(우리 pythoncore rtti 도구),
또는 (b) 게임에서 직접 위치 필드 탐색(값 변화 스캔). ASI 정적 분석이 빠를 것.

**결론:** B-5 는 별도 리버스 세션으로. B-1 을 먼저 완성한다.

## B-1 라이브 실측 (2026-09-05, 게임 2.00.01 / build 2658, 캐릭터 Kliff)

probe 로 라이브 게임을 직접 조사한 결과, **CT 오프셋은 이 빌드에서 무효**였고
값 스캔도 막혔다. 확정 사실:

- **스탯 클래스**: `Server/Client/CommonStatusActorComponent@pa@@` (RTTI 로 열거됨,
  Server 만 438개+). equip 과 같은 Server/Client/Common 3분할.
- **용기(courage)**: Server status `+0x2CC`(현재)/`+0x2D4`(최대), **int32**, 8바이트
  간격(CT 의 0x10 과 다름). 시트 106/110 과 일치. 단 그 컴포넌트는 **HP·스태미나를
  담지 않음**(용기·저항 전용으로 보임). 게다가 같은 값 컴포넌트가 여럿이라
  플레이어 것 특정이 애매.
- **HP·스태미나는 status 컴포넌트에 없음**. HP 는 int/x1000/float 어느 표현으로도
  status 에서 안 잡힘.
- **값 변화 스캔 실패**: HP 를 2040→1153→218 로 바꿔 교집합했으나 매번 0개.
  원인: (a) **HP 가 빠르게 재생성**돼 스크린샷↔스캔 사이에 값이 이미 바뀜,
  (b) **표시값이 반올림**돼 시트 정수 ≠ 저장 실수. int·x1000·float 다중 표현으로
  잡아도 0 → 정확한-값 스캔은 이 게임 HP 에 신뢰 불가.

**결론:** 정확한-값 스캔은 HP 재생성+반올림으로 막힌다. 참고 모드가 값 스캔이
아니라 **코드 훅**("Player base hook")을 쓰는 이유다. B-1 의 신뢰 경로는 둘:
1. **코드 훅** (권장, 참고 모드 방식): HP 를 읽/쓰는 명령을 AOB 로 찾아 트램펄린을
   걸어 그 자리에서 정확한 주소·구조를 캡처. 재생성·반올림·표현 무관.
2. **상대 변화(diff) 스캔 도구**: 미지값 스냅샷 → 증가/감소 필터(재생성·반올림
   무관). probe 에 스냅샷-diff 스캔을 추가해야 함(현재 없음). 여러 왕복 필요.

만든 도구(WIP): `probe player`(status 열거·액터 앵커·값 스캔·dump),
`probe hpscan`(다중표현 값 변화 스캔, hp_candidates.txt 교집합). player.h/cpp 는
스캐폴딩(오프셋 미확정 - CT 값이라 이 빌드엔 안 맞음, 재작성 필요).

**차선책**: 용기(+0x2CC/+0x2D4)는 잡혔으니, 플레이어 컴포넌트만 특정하면 무한
용기/기력은 가능할 수 있다. 단 HP(godmode)가 핵심이라 훅 경로가 맞다.

## 순서

1. **B-1 플레이어 치트** — 코드 훅으로 HP 를 캡처(권장) 또는 diff 스캔 도구 추가.
   값 스캔은 재생성 때문에 포기. 훅 대상 명령을 AOB 로 탐색하는 것이 다음 작업.
2. **B-5 텔레포트** — ASI 정적 분석으로 오프셋 확보 후 착수.
